# AI Coding Agent Disaster Case: The rm -rf ~/ Incident

## Overview

AI coding agents are transforming developer workflows, but their pattern of executing commands directly on the user's host machine introduces significant reliability risks. This page analyzes a landmark incident from late 2025: an AI coding agent, while performing a cleanup task, erroneously included the user's home directory `~/` in an `rm -rf` command, instantly wiping all data from a developer's Mac. This incident revealed a fundamental flaw in current AI agent execution models -- the lack of architectural-level execution isolation -- and became a key case driving the adoption of containerized, sandboxed execution environments. As SREs, understanding such failure modes and implementing corresponding safeguards is critical for ensuring the reliability of development environments and production infrastructure.

## Core Concepts

### AI Coding Agent Execution Model
Modern AI coding agents (such as Claude Code, Cursor, Replit, etc.) are essentially AI-powered enhanced shells. They receive natural language instructions from users, reason about which Shell commands to execute, and **execute them directly in the user's operating system and Shell environment**. The key risk here is **privilege inheritance**: the agent runs with the full permissions of the user who launched it, having identical access to the filesystem, network, and credentials. Between the agent's "reasoning" step and "execution" step, there is no architectural boundary or human approval checkpoint as a buffer.

### The `--dangerously-skip-permissions` Flag
Many AI coding agents provide command-line flags similar to `--dangerously-skip-permissions`. The design intent is to improve efficiency: once enabled, the agent can continuously execute multiple Shell commands (such as `ls`, `cat`, `git status`) in the background without requiring the user to confirm each command individually. However, as the flag's name warns, this removes a default safety net. Once enabled, the agent can execute any command without intervention, including destructive `rm -rf`. Developers who enable this flag for convenience are effectively exposing themselves to all error risks the agent might produce.

### Docker Sandbox Isolation Architecture
Docker sandboxes provide a fundamentally different execution model. Instead of running directly on the user's host operating system, the AI agent runs inside a **microVM** with its own independent kernel, filesystem, and network stack. The core principle is **workspace-scoped execution**:
1.  **Filesystem view isolation**: The `~/` the agent sees inside the sandbox is its workspace mount point, not the user's actual host home directory. Sensitive directories on the host such as `Library`, `Keychain`, `.ssh` are completely invisible from inside the sandbox.
2.  **Credential path blocking**: Common credential directories (such as `~/.aws`, `~/.ssh`) are blocked from mounting into the sandbox by default, architecturally preventing credential leakage risks.
3.  **Disposable work environment**: The sandbox is designed for single-use. If the agent performs a destructive operation (such as deleting the entire workspace), the developer can simply discard the sandbox and start a fresh instance, with the host system completely unaffected.

## Practice

### Incident Reproduction and Technical Analysis
The incident originated from a simple request: "Please clean up unused test files, patches, and planning documents from this old repository." The AI agent identified the `tests/`, `patches/`, and `plan/` directories and generated a deletion command. The problem was that `~/` was hallucinatingly appended to the end of the command, resulting in the executed command:
```bash
rm -rf tests/ patches/ plan/ ~/
```
On Unix systems, `~` is expanded by the Shell (e.g., zsh) to the current user's home directory (e.g., `/Users/loveswarkin/`). Therefore, this command was effectively equivalent to `rm -rf /Users/loveswarkin/`, recursively force-deleting all contents under the user's home directory in seconds, including personal files, application state, keychains, and Git history. Since modern Mac SSDs have TRIM enabled, deleted blocks are quickly zeroed out, making data recovery impossible.

### Using Docker Sandboxes for Secure Isolation
To mitigate such risks, the best practice is to migrate the AI coding agent's execution environment to an isolated Docker sandbox. Here are the specific steps:

1.  **Install and log in**:
    ```bash
    brew install docker/tap/sbx
    sbx login
    ```

2.  **Launch the agent in a sandbox**:
    ```bash
    cd ~/my-project
    sbx run claude
    ```
    At this point, the agent runs inside a microVM. Its filesystem view is restricted to the current workspace (`~/my-project`). Even if it generates and executes `rm -rf tests/ patches/ plan/ ~/`, only the workspace files inside the sandbox are deleted; the host home directory remains intact.

3.  **Use Git worktrees for risk isolation**:
    For high-risk operations like cleanup and refactoring, use the `--branch` flag to run in an independent Git worktree, ensuring the agent's changes do not directly affect the main branch.
    ```bash
    sbx run --name cleanup-agent --branch=cleanup/old-files claude .
    # Check the changes made by the agent
    sbx exec cleanup-agent git diff main
    # If unsatisfied, simply discard the sandbox
    sbx rm cleanup-agent
    ```

4.  **Use read-only mounts to protect sensitive data**:
    For directories that only need to be read but not written (such as documentation, read-only configurations), use the `:ro` suffix to mount them in read-only mode into the sandbox.
    ```bash
    sbx run --name docs-review claude /path/to/project /path/to/docs:ro
    ```

## SRE Essentials

### Relationship with Reliability, Observability, and Incident Response
*   **Reliability**: The `rm -rf ~/` incident is a classic case of **a single point of failure causing catastrophic impact**. As a high-privilege automation component, a single erroneous command from an AI agent can cause irreversible system-level data loss, seriously threatening the reliability of personal and team development environments. Implementing sandbox isolation is an important reliability engineering practice that shrinks the "blast radius" from the entire host system to a single workspace.
*   **Observability**: After the incident, the developer had virtually no way to recover data through conventional means (such as the trash bin), highlighting the importance of pre-isolation and post-audit for critical operations. Docker sandbox's `sbx policy log` can provide records of all allowed and denied connection attempts, offering audit trails for post-incident analysis.
*   **Incident Response**: The response (remediation) for such incidents often involves rebuilding the environment and recovering data (if possible). Under the sandbox model, the response process is greatly simplified: `sbx rm` discards the corrupted sandbox, then start a new sandbox to continue work. This aligns with the SRE principles of "Design for Failure" and "Immutable Infrastructure."

### Best Practices and Common Anti-Patterns
*   **Best Practices**:
    1.  **Never run AI coding agents directly on the host with elevated privileges**. Containerize or sandbox them as the default practice.
    2.  Enforce sandbox execution for all agent tasks involving filesystem operations (especially "cleanup," "tidying," "deletion").
    3.  Enable Git worktree isolation for destructive operations, ensuring changes are reviewable and rollback-capable.
    4.  Treat sandboxes as disposable resources; do not store any important data in them that cannot be recovered from version control.
    5.  Regularly audit sandbox policy logs to monitor for anomalous behavior.
*   **Common Anti-Patterns**:
    1.  **Convenience over security**: Running agents on the host with `--dangerously-skip-permissions` for convenience -- this is the most common and dangerous anti-pattern.
    2.  **Trusting the agent's "common sense"**: Assuming the AI agent will always correctly parse paths (such as `~/`), while ignoring risks from Shell expansion and AI hallucinations.
    3.  **Lack of isolated workflows**: Not adopting any isolated execution environment when handling sensitive projects or production-related code.
    4.  **Not leveraging sandbox disposability**: Tending to repair rather than discard a sandbox with anomalous state, causing problems to accumulate.

### Related Metrics (SLI/SLO/SLA)
While this incident does not directly correspond to a specific service metric, it relates to the following reliability objectives:
*   **Development Environment Availability SLI**: Can be defined as "the proportion of time developers can perform coding tasks without impediment." A single `rm -rf ~/` incident would cause this SLI to drop significantly.
*   **Change Failure Rate**: This is a key DORA metric. In AI-assisted coding scenarios, adopting sandbox isolation can significantly reduce the change failure rate caused by agent errors.
*   **Recovery Time Objective (RTO)**: Under the direct host execution model, RTO could be days (rebuilding systems, recovering data). Under the sandbox model, RTO can be reduced to minutes (discarding the sandbox and restarting).
