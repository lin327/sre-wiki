# Automate safety monitoring with computer vision and generative AI

## Overview

Workplace safety monitoring is evolving from reliance on manual spot checks to **continuous, automated real-time monitoring**. The system described in this article utilizes computer vision (CV) and generative AI to perform near-real-time analysis of images captured from a distributed camera network deployed on AWS, using a serverless, event-driven architecture to detect personal protective equipment (PPE) violations and area safety risks (such as improper item placement). For SRE teams, this system itself is a critical safety infrastructure that requires high availability, scalability, and observability. Understanding its architecture, scaling patterns, and reliability design is essential for operating and supporting such AI-based monitoring systems.

## Core Concepts

### System Architecture Overview
The solution uses a layered, event-driven serverless architecture with the following core components:
1.  **Image Collection and Anonymization**: Periodically collect images from authorized cameras, use Amazon Rekognition to detect faces and apply blurring to protect privacy. Original images are cleared after a retention period of several days according to policy.
2.  **Training Pipeline**: Use Amazon SageMaker Ground Truth for data annotation, and build automated model training, evaluation, and registration workflows through Amazon SageMaker AI Pipelines. Model updates are decoupled from application infrastructure code through CI/CD pipelines.
3.  **Inference Pipeline**: Each use case (such as PPE detection, 5S site management) has its own inference flow. After an image is triggered, it is routed via SQS queues to dedicated SageMaker inference endpoints for risk detection.
4.  **Risk Management and Alerting**: Aggregate risks through Lambda functions to avoid alert fatigue. The system checks whether risks persist on demand, tracks resolution SLAs, and performs tiered notifications through multiple channels (Slack, email, etc.).
5.  **Web Application and Data Analysis**: A React-based frontend application for safety managers to view and respond to risks. Risk data is periodically exported to Amazon Redshift for BI teams to perform trend analysis through Amazon QuickSight.

The system achieves **security isolation and separation of responsibilities** by deploying different components (training, inference, application, analysis) across multiple AWS accounts, which is an important practice in cloud-native security architecture.

### Intelligent Alert Detection: Four-Stage Process
To ensure alert accuracy and reduce false positives, the system performs four-stage verification on each image:
1.  **Object Detection**: The model identifies equipment, materials, and worker safety gear in the image, distinguishing between the visual outline of objects and their actual ground projection.
2.  **Region-Based "Digital Tape" Analysis**: Calculate the overlap percentage between the detected object's ground projection and preset safety zones ("tape" definitions). Exceeding the threshold (such as 50%) is judged as a violation. For PPE detection, the system has context awareness, able to determine the required PPE type based on different zones.
3.  **"Dwell Time" Algorithm**: Through cross-time-interval analysis and mask similarity algorithms, track the duration of the same violating object, avoiding false positives triggered by brief passage. High-risk zones have shorter dwell time thresholds.
4.  **Multi-layer Verification and Alert Generation**: After applying confidence thresholds, RLE mask consistency checks, and zone context verification, structured alerts are generated containing object type, location, violation duration, confidence, and visually annotated images.

### Serverless Driver-Worker Pattern
This is the core architectural pattern for handling large-scale camera processing. The **driver** is responsible for task orchestration, and **workers** concurrently process images. This pattern achieves component decoupling and fault isolation, allows independent scaling, and leverages the ML inference layer as an "intelligent filter," passing only images with detected risks to downstream processing, preventing databases (such as Amazon Aurora) from being overwhelmed by massive raw image data.

## Practice

### Key Technical Decisions from PoC to Production Scaling
1.  **Inference Infrastructure Upgrade**: Migrated from SageMaker Serverless inference (memory and GPU limitations) to SageMaker stateful inference endpoints (using `ml.g6` instance families), and configured auto-scaling policies to support large-scale concurrent processing.
2.  **Lambda and SQS Limit Optimization**: To support thousands of concurrent Lambda executions, service limit increases were requested. Memory allocation was optimized, multi-threaded processing was adopted, error handling logic was refactored to minimize failed containers, and SQS batch sizes were adjusted to maximize throughput within memory constraints.
3.  **Data-Driven Ground Truth Management**: Abandoned the unsustainable "daily per-site" full annotation approach. Instead, **Amazon Athena** was used to analyze inference results and user feedback data at scale, identifying camera types or deployment conditions with poor model performance, prioritizing re-annotation and re-training for high-error-rate image sources. Additionally, **Claude multimodal LLM on Amazon Bedrock** was used to analyze misclassified samples, discovering underrepresented categories in training data to guide data collection strategies.

### Using Generative AI (GLIGEN) to Solve Data Scarcity
For scenarios with rare safety violations (such as floor liquid spills) or insufficient data diversity (such as monotonous PPE colors), traditional manual annotation is inefficient. The solution is to build a synthetic data generation pipeline:
- Use **GLIGEN** (a diffusion-based generative model) deployed as a SageMaker batch job.
- Input bounding box coordinates specifying object positions to generate synthetic images (512x512) with realistic backgrounds and automatically embedded ground truth annotations.
- The raw image output is streamed to S3, decoded and converted to YOLO annotation format, forming a training-ready dataset.
- This method successfully generated a PPE dataset of 75,000 images (3 categories) and a housekeeping dataset (7 categories), training high-accuracy models without using any manually annotated real images.

## SRE Key Points

### Connection to Reliability, Observability, and Incident Response
- **Reliability**: The system's architecture design fully considers reliability. **Multi-account isolation** ensures environment independence; the **driver-worker pattern** and **SQS queues** provide fault isolation and buffering; **intelligent filtering** reduces downstream database pressure; **DLQ (Dead Letter Queue)** is used to capture and handle failed messages. SLOs (such as time from image capture to alert delivery) need to be clearly defined and monitored.
- **Observability**: The system has built-in multi-layer observability. At the business level, risk records are stored in DynamoDB for fast queries; the BI layer provides trend analysis dashboards through Redshift and QuickSight. At the technical level, core metrics such as ML inference endpoint latency, error rates, SQS queue backlog, and Lambda execution failure rates need monitoring — these are typical [[slo-sli-error-budgets]] application scenarios.
- **Incident Response**: The system itself is an automated incident response system, capable of detecting risks, aggregating alerts, tracking resolution status, and escalating notifications. For SRE teams, incident response plans need to be established for **the monitoring system itself**, such as: response procedures when inference pipeline latency spikes, model accuracy drops, or large-scale camera data streams are interrupted.

### Best Practices and Common Anti-patterns
**Best Practices:**
- **Focus on Data Quality, Not Just Models**: Investing in high-quality, accurately annotated ground truth data (supplemented by synthetic data) is the foundation of model success.
- **Decouple Science and Engineering**: Decouple model training/approval from endpoint update deployment through event-driven pipelines, allowing data scientists and software engineers to work collaboratively.
- **Implement Layered Role-Based Access Control**: Define clear user roles (super user, site administrator, region owner, etc.) and permissions to ensure operational safety.
- **Design for Scale**: Adopt serverless and event-driven patterns from the start, with specific designs for handling large-scale concurrency (Lambda limits, SQS batch optimization).

**Common Anti-patterns:**
- **Ignoring Privacy Protection**: Not effectively anonymizing personally identifiable information (PII) in images.
- **Over-reliance on Manual Annotation**: Continuing unsustainable annotation strategies as data scales, not utilizing data-driven or synthetic data methods for optimization.
- **Underestimating Operational Complexity**: Treating ML systems as "black boxes" without establishing comprehensive observability, alerting, and incident response processes.
- **Monolithic Architecture**: Coupling inference and data processing for all use cases together, leading to scaling difficulties and large blast radius of failures.

### Related Metrics (SLI/SLO/SLA)
- **SLI (Service Level Indicator)**:
    - **Processing Latency**: Time from image arrival at the anonymous S3 bucket to alert delivery to the relevant area responsible person (tested value in the article is within 37 seconds).
    - **System Throughput**: Number of images successfully processed per second.
    - **Detection Accuracy**: Model's mean average precision (mAP@50), precision, recall.
    - **Alert Effectiveness**: Proportion of alerts confirmed as true violations by manual review (i.e., low false positive rate).
    - **Pipeline Health**: Critical queue (SQS) backlog message count, Lambda function error rate, number of messages in DLQ.
- **SLO (Service Level Objective)**: Set target values for the above SLIs, for example: "99% of image processing latency is less than 60 seconds," "system continuous processing capability supports 10,000+ cameras at one frame per minute per camera."
- **SLA (Service Level Agreement)**: The risk resolution SLA the system needs to meet (for example, high-risk alerts must be responded to within 30 minutes) is a business metric that the **risk detection application** layer needs to monitor and escalate.
