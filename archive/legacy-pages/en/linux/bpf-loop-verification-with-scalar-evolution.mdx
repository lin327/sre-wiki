# [$] BPF loop verification with scalar evolution

## Overview

BPF (Berkeley Packet Filter), as one of the most core programmable infrastructures in the modern Linux kernel, is widely used in network monitoring, security policies (such as [[linux-seccomp]]), performance analysis (such as [[bpf-tracing]]), and system observability. Before BPF programs are loaded and executed by the kernel, they must undergo a rigorous **static verifier (BPF Verifier)** for safety checks to ensure they do not cause kernel crashes, infinite loops, or illegal memory access. Among these, **loop verification** is one of the most complex challenges the verifier faces. The verifier must prove at compile time (load time) that loops necessarily terminate and do not exceed bounds, which is a classic static analysis problem. This article explores the traditional methods and limitations of how the BPF verifier handles loops, as well as the key improvements brought by introducing **Scalar Evolution** analysis techniques.

## Core Concepts

### BPF Verifier and the Challenge of Loop Analysis

The BPF verifier's core task is to prove program safety before execution by simulating all possible execution paths. For `while` or `for` loops, the verifier needs to prove two things: 1) the loop body necessarily executes the exit condition within a finite number of iterations; 2) all memory accesses and register operations within the loop are within legal bounds. The traditional approach is **iteration-by-iteration simulation**: the verifier actually unrolls the loop, processing one iteration at a time, until it encounters an exit branch or reaches some internal limit (such as maximum instruction count or maximum verification steps). This method works for simple loops, but when facing **nested loops**, loops whose bounds depend on external input, or complex conditions, it may cause the verifier to prematurely reach instruction limits and reject a program that is actually safe, because it "unrolled" too many iterations during verification.

### Scalar Evolution Analysis

**Scalar Evolution (SCoP)** is a static analysis technique originating from the compiler optimization field, used to analyze how a scalar variable (such as a loop counter) in a loop changes with iteration count. For example, for a simple loop `for (int i = 0; i < n; i++)`, SCoP analysis can identify that variable `i` increases by 1 after each iteration, and its value range can be expressed as `[0, n-1]`.

Applying this technique to the BPF verifier means the verifier no longer needs to clumsily simulate loops iteration by iteration. Instead, it can analyze the evolution patterns of key variables in the loop (particularly those controlling loop bounds and internal memory accesses) to **derive their value ranges across all iterations in one pass**. This enables the verifier to verify loop safety more efficiently and precisely, especially when handling complex nested loops.

## Practice

Eduard Zingerman's presentation at the 2026 Linux Storage, Filesystem, Memory Management, and BPF Summit showcased his ongoing improvement work. The core idea is to integrate scalar evolution analysis into the BPF verifier's loop handling logic.

**Technical implementation directions include:**

1.  **Loop modeling**: When the verifier encounters a loop structure, it first identifies its basic components, such as the initialization section, condition evaluation, and increment section.
2.  **Variable tracking and modeling**: For scalar registers modified in the loop, analyze how they are computed based on the previous iteration's value. For example, `r1 = r2 + 4` is modeled as `r1_i = r1_{i-1} + 4`.
3.  **Range derivation**: Combining loop conditions and variable evolution models, use abstract interpretation or constraint solving techniques to infer the upper and lower bounds of the variable's possible values throughout the loop's lifetime.
4.  **Verification integration**: When verifying operations inside the loop body (such as memory access `*(u32*)(r10 + r2)`), the verifier no longer relies solely on the current state but uses variable ranges obtained from scalar evolution analysis (e.g., `r2` always satisfies `0 at most r2 < 16` in the loop) to prove memory access safety.

Through this "analysis for iteration" approach, the verifier can avoid unnecessary loop unrolling, thereby handling more complex loop structures with limited verification resources while maintaining or even improving the strength of safety guarantees.

## SRE Key Points

### Relationship with Reliability and Observability

BPF programs are the building blocks for constructing cloud-native observability stacks (such as Prometheus's eBPF Exporter, Cilium's Hubble, Pixie, etc.). The BPF verifier's capabilities directly determine what complexity of monitoring and analysis logic these tools can write. If the verifier is too conservative and rejects reasonable and efficient loops (especially nested loops), SRE engineers and platform developers are forced to adopt clumsier, less efficient alternatives, impacting **monitoring data collection precision and system performance**. Therefore, improving the verifier's loop analysis capability directly enhances the ability to build complex, high-performance kernel-level observability tools.

### Best Practices and Common Anti-Patterns

- **Best practices**:
    - **Understand verifier limitations**: When writing complex BPF programs (especially those involving deeply nested loops or large loops), be aware of the verifier's resource limits. Sometimes simplifying loop logic or loop bounds through mathematical transformations can improve verification pass rates.
    - **Leverage kernel version benefits**: Follow kernel version release notes. Verifier enhancements like scalar evolution are released with mainline kernels, and upgrading the kernel may automatically allow previously rejected BPF programs to pass.
    - **Utilize verifier feedback**: Modern BPF verifiers provide detailed error logs and "verification state graphs." When debugging BPF load failures, SREs should carefully analyze these logs to determine whether it's a genuine safety issue or a false rejection due to verifier limitations.

- **Common anti-patterns**:
    - **"Brute force" loop unrolling**: Manually unrolling loops into large amounts of repeated code to avoid verification errors. This not only makes code hard to maintain but may also increase actual runtime overhead, without solving the fundamental problem.
    - **Over-relying on single large BPF programs**: Trying to implement all complex logic in one BPF program, causing loops and branches to be too deep, challenging verifier limits. A better pattern is to use **BPF program chains** or **Tail Calls** to decompose complex logic.

### Related Metrics (SLI/SLO/SLA)

While BPF verification itself does not directly correspond to user-facing SLIs/SLOs, its efficiency and capability are key indicators of underlying platform capability:

- **Verification latency**: The time required to load a BPF program. Optimizations like scalar evolution can reduce verification time, improving response speed in system configuration or dynamic tracing scenarios.
- **Verification pass rate**: For a set of representative BPF program templates (covering various loop patterns), the proportion of successful verifier loads. The improvement goal is to increase the pass rate of complex loop programs.
- **Runtime overhead**: More precise verifier analysis may allow the kernel to generate more optimized BPF native code, indirectly reducing CPU overhead during program execution, thereby affecting the performance SLO of the application or node hosting the BPF program.
