# 

## Overview

AppArmor is an important Linux kernel security module used to restrict program resource access. In containerized environments, container runtimes such as containerd often load specific AppArmor profiles for container processes to enhance security. However, under specific kernel configurations (such as enabling configuration file stacking) and operations (such as entering the container through `kubectl exec`), the original security rules may not correctly match the identity (peer) of the process, causing legitimate operations to be rejected by the kernel, generating security audit events, and even affecting the normal operation of the process. This document explains the cause, impact, and corresponding fixes of this problem, which is crucial to maintaining the security and reliability of the container environment.

## Core concepts

* **AppArmor Profile Stacking**: This is an advanced feature of AppArmor (controlled by `/sys/kernel/security/apparmor/features/domain/stack`). It allows multiple security profiles to be applied simultaneously to a process, with a main profile (e.g. `cri-containerd.apparmor.d`) stacked with an additional profile declared via special syntax (e.g. `//&unconfined`). This provides more flexible and fine-grained security policies.
* **CRI ExecSync**: An operation in the Container Runtime Interface (CRI), corresponding to `kubectl exec` or exec-based survival probe/readiness probe. It creates a new process inside the running container.
* **Peer name matching**: In AppArmor's `signal` and `ptrace` rules, you can use the `peer=` keyword to specify the profile name of the target process that is allowed to interact. Whether the rule takes effect depends on whether the configuration file of the initiating process matches the value specified by `peer=`.
* **Source of the problem**: When a process created by `exec` (such as the Go runtime sending `SIGURG` for goroutine preemption) runs under the stack configuration file (`cri-containerd.apparmor.d//&unconfined`), the original `peer={{.Name}}` (expanded to `cri-containerd.apparmor.d`) rules cannot be matched. `cri-containerd.apparmor.d//&unconfined` This peer causes the kernel to reject the operation.

## Practice

This fix addresses the matching issue by adding wildcard rules to the container's AppArmor profile template.

**Fix:**
In the `signal` and `ptrace` rules of the container's AppArmor configuration file template (generated by containerd), modify the original `peer={{.Name}}` rule to a version that includes wildcard characters so that it can match both the base configuration file name and the stacked configuration file name.

Modified rule example:
```
signal (send) peer={{.Name}},
signal (send) peer={{.Name}}//&*,

ptrace (trace, read, traceby, readby) peer={{.Name}},
ptrace (trace, read, traceby, readby) peer={{.Name}}//&*,
```

where `//&*` is a wildcard pattern that matches any stacked configuration file suffix (e.g. `//&unconfined`).

**Application steps:**
1. **Update containerd**: Deploy the containerd version that includes this fix (after PR #12887).
2. **Load configuration file**: Use the `apparmor_parser --replace <profile_file>` command to load the updated configuration file into the kernel. This step ensures that the new rules take effect.
3. **VERIFICATION FIX**: On a kernel with AppArmor profile stacking enabled (like 6.17 used in testing), execute a command like `kubectl exec <pod> -- cat /proc/self/attr/apparmor/current` to confirm that the new process is running under the stacked profile. Then monitor the system audit log (such as `audit.log`) to confirm that the previous `apparmor="DENIED" operation="signal"` event no longer occurs within a period of time (for example, after performing multiple exec operations).

**Test environment reference:**
* Operating system: Ubuntu 25.10 (questing) aarch64
* Kernel version: 6.17.0-1007-raspi
* AppArmor parser: 5.0.0~alpha1
* containerd version: v2.1.5-k3s1

## SRE Key Points

* **Reliability**: This fix directly removes the risk of process signals being rejected due to false positives from security rules. Signals (such as `SIGURG`) are a key mechanism for inter-process cooperation (such as Go's goroutine scheduling). Rejection may lead to process hang, performance degradation or even failure. After repair, the operational reliability of applications in the container is significantly improved.
* **Relevance to Observability**: Prior to the fix, a large number of `DENIED` events generated by AppArmor appeared in the system audit log. These "noises" can interfere with SRE's monitoring and alerting of real security threats or system anomalies. After the fix, the audit logs became cleaner, helping to improve the quality of observability data.
* **Best Practices and Anti-Patterns**:
    * **Best Practice**: When designing and testing AppArmor policies, you must consider various process identity modes, including profile stacking. Using wildcards (such as `//&*`) to enhance the robustness of rules is an effective means to deal with dynamic process environments.
    * **Common anti-patterns**: Hardcoding or assuming fixed process identities in security policies (such as only using `peer={{.Name}}`) can easily fail in complex container and orchestration environments. This is a fragile static configuration anti-pattern.
* **Related indicators**:
    * **SLI**: The "Number of process signaling failures due to AppArmor rejections" can be considered a reliability SLI. This fix aims to reduce this metric to zero.
    * **SLO**: You can set an SLO such as "In 99% of `exec` operations, underlying process communication should not fail due to AppArmor policy issues".
