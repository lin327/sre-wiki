# Dashboards: Data links double URL encode strings

## Overview

In the daily practice of SREs, the Grafana dashboard is the core interface for system observability and troubleshooting. The Data Links feature allows users to create clickable links in the panel to external systems or internal detail pages, which is critical for quickly jumping from aggregated views to raw logs, traces, or specific resource details. This document describes a double URL encoding issue in such link generation that causes links containing special characters (such as the Base64 filler `=`) to break, disrupting workflow and potentially delaying failure response.

## Core concepts

**URL encoding**: Also known as percent encoding, it is an encoding method that converts characters into `%` followed by two hexadecimal digits. For example, `=` would be encoded as `%3D`. Its purpose is to ensure that only safe characters are included in the URL, especially when passing data containing reserved characters such as `&`, `?`, `#`, etc.

**Data Link**: In Grafana, this is a way to create dynamic hyperlinks. The link's target URL can contain variables for panel data fields (such as `${__value.raw}`). When the user clicks on the link, Grafana replaces the variable with the value of the current data point and generates the final URL.

**Field Overrides and Data Links**: Users can uniformly add data links to specific data fields through the Field Overrides function. This is a common method to implement batch link configuration.

**Essence of the problem**: The core of this problem is that Grafana performs **secondary encoding** on the URL-encoded string when generating the final URL of the data link. For example, after a raw string `key=%3D` (where `%3D` is the encoding of `=`) is referenced in a link variable, the `%` character will be encoded again and become `%25`, resulting in `key=%253D` in the final URL, which is obviously wrong.

## Practice

### Problem reproduction and diagnosis

1. **Steps to Reproduce**:
    * Create a table panel in the Grafana dashboard and configure its data source (such as BigQuery).
    * Add a data link to a field through "Field Override".
    * Use a variable in the link URL to reference a field whose value ** itself contains encoded characters ** (such as `%3D`).
    * Try clicking or copying the link to check the resulting URL.

2. **Diagnostic Phenomenon**:
    * In the browser's link inspector or in the URL string obtained through the "copy link" function, it was observed that the portion that should be `%3D` became `%253D`.
    * Such links point to pages that return 404 due to incorrect parameters or fail to parse the data correctly.

### Solutions and avoidance methods

According to the related Grafana GitHub discussion ([PR #98494](https://github.com/grafana/grafana/pull/98494)), the issue was identified as a defect that needed to be fixed. Until an official fix is released, consider the following workarounds:

1. **Use raw value variables**: If Grafana provides a variable like `${__value.rawURL}` (as the original question suggests), this variable should return the raw URL string without additional encoding. Please consult the documentation for your current Grafana version to confirm available data link variables.

2. **Preprocessing** in the data source: At the query level, try to return the **unencoded** raw string. Let Grafana do the first (and only) encoding after being referenced by a data link variable (such as `${__value.raw}`). This requires ensuring that the original string does not contain reserved characters that need to be encoded, otherwise it will cause other problems.

3. **Dynamic Link Building (Advanced)**: For extremely complex scenarios, it may be necessary to manually splice URLs and control encoding behavior through custom JavaScript plug-ins or more complex variable expressions, but this will significantly increase maintenance costs.

### Best Practice Precautions

* **Test Data Links**: After configuring a data link containing dynamic values for a production dashboard, be sure to test link functionality on multiple data samples, especially when field values contain special characters (e.g. `+`, `=`, `&`, spaces).
* **Monitor Grafana version updates**: Pay close attention to Grafana's release notes, as such flaws are often fixed in subsequent patches or minor versions.

## SRE Key Points

### Association with reliability

* **Troubleshooting efficiency**: Data link is the "bridge" connecting monitoring views and root cause analysis. Link failure will directly interrupt the SRE troubleshooting process and increase the mean time to recovery (MTTR).
* **Observability Closed Loop**: A fully functional dashboard is a key component of observability. Ensuring that all of its interactive elements, such as links, work properly is a fundamental requirement for maintaining the reliability of the monitoring system itself.

### Best Practices and Anti-Patterns

* **Best Practice**:
    * Manage data links as functional codes and incorporate them into version control and change review.
    * Write simple documentation or test cases for key data links to illustrate their expected behavior and usage scenarios.
    * Perform smoke testing of dashboards involving data links after upgrading Grafana version.
* **Common anti-patterns**:
    * **Assume links will always work**: Deploy data links to complex URLs to production without testing.
    * **Passing sensitive data in the URL**: Data links are usually visible to all users who have access to the dashboard. Passing sensitive information such as passwords and tokens directly in the URL should be avoided.

### Related indicators (SLI/SLO)

* **Dashboard Availability SLI**: It is possible to define an SLI that measures the "rate of successful clicks on key dashboard data links". If a large number of links fail due to double encoding, etc., the value of this SLI will decrease.
* **Internal service dependency SLI**: If the data link points to other internal monitoring systems (such as link tracking UI, log platform), its availability is also a sub-item of the overall monitoring system reliability.

For this specific issue, the release of the fix should be tracked as an observability platform maintenance task. Before the repair goes online, you should consider recording this known issue and its avoidance methods in the corresponding operation and maintenance manual or fault runbook to prevent SRE personnel from being hindered by link failure in an emergency.
