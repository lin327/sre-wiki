# etcd issue #18667: Specifying a revision for a range request in a transaction

## Overview

In the distributed key-value store etcd, ensuring data consistency across all members is the cornerstone of reliability. This issue reveals a data split-brain risk caused by improper transaction processing optimization: when a client specifies a particular revision for a range request (such as `get k1 --rev=10`) within a transaction (TXN), it may cause different cluster members to ultimately hold different data states. For systems relying on etcd as the Single Source of Truth, especially Kubernetes which bears service discovery and configuration center responsibilities, this is a reliability concern that needs to be taken seriously. As an SRE, understanding its root cause and mitigation methods is critical for ensuring cluster health and rapid fault recovery.

## Core Concepts

- **TXN (Transaction)**: The atomic operation unit provided by etcd, allowing multiple operations (comparisons, gets, writes) to be bundled together for execution. Transactions guarantee atomicity of their internal operations, meaning either all succeed or all fail.
- **Range Request**: An operation that retrieves a range of key-value pairs. For example, `get k1 --rev=10` retrieves the value of key `k1` at revision 10. This relies on etcd's Multi-Version Concurrency Control (MVCC) capability.
- **Revision**: etcd's logical clock, monotonically increasing with each committed transaction. It provides the system with a globally consistent view of state snapshots.
- **Compact**: etcd periodically cleans up old version history data to free space. The `compact` operation deletes all history before a specified revision, after which access to those historical versions will return errors.
- **MVCC and Consistency**: etcd maintains multiple historical versions for each key through MVCC. All members must agree on the data state corresponding to the same revision number, which is the basis for ensuring linearizable reads and distributed transaction correctness.

## Practice

### Issue Reproduction Steps

The issue can be reliably reproduced with the following steps, simulating a typical transaction scenario:
1.  Create a brand new three-node etcd cluster.
2.  Insert keys `k1` through `k20` sequentially, forming 20 revision history entries.
3.  Execute a compact operation to clean up history before revision 21 (`etcdctl compact 21`).
4.  Execute an interactive transaction (`etcdctl txn --interactive`). The transaction's comparison condition depends on possibly already-compacted old version data (`value("k1") = "v1"`), and in the success branch includes a range request specifying a compacted revision (`get k1 --rev=10`).
5.  Since revision 10 has been compacted, the member the client is connected to will fail the entire transaction due to `checkRange` failure.
6.  However, the critical point is that other members not connected to the client may have already **removed this problematic range request** from the transaction, thereby successfully applying the write operation (`put k2 foo`) in the transaction.
7.  The final result is data split between cluster members: on the member the client is connected to, `k2`'s value is the original `v2`, while on other members the value is `foo`.

### Temporary Workaround

Before an official fix is released, SREs can use the following methods to restore consistency:
- **Single member failure**: If only one member is inconsistent, follow etcd's [replace a failed machine](https://etcd.io/docs/v3.5/op-guide/runtime-reconfiguration/#replace-a-failed-machine) guide to replace that member and clear its data directory, letting it sync correct data from other healthy members.
- **Multiple member failure**: If all members' data is inconsistent, you need to manually designate a "source of truth." The operation steps are: stop the entire cluster, use only one member's data directory to force create a new single-member cluster (`--force-new-cluster`), then add other members one by one (making sure to clear their original data directories before adding). **This is a high-risk operation requiring full backup and testing.**

### Root Fix and Mitigation

The root fix is: **no longer remove range requests from transactions on members not connected by the client**. Specifically:
- Retain all range requests, but on other members, do not execute their data queries, only perform validation to ensure all members apply consistent legitimacy checks for the same transaction.
- This makes the correct trade-off between performance and consistency -- consistency takes priority.

As SREs, proactive mitigation strategies are more important than post-incident fixes:
- **Audit transaction usage**: Check application code to ensure **not using range requests with old revision specifications in transaction comparisons (compare) or subsequent operations (put/del)**. Kubernetes core components have been confirmed to be unaffected, but custom Operators or clients need to be thoroughly examined.
- **Monitor data consistency**: Regularly perform cross-endpoint consistency checks on critical key-values (being careful to avoid repeated reads of historical versions), which can be integrated as monitoring items in health checks.

## SRE Key Points

### Relationship with Reliability

This issue directly impacts the core property of distributed systems -- consistency (Consistency). Data inconsistency can cause clients to read stale or incorrect states, potentially triggering cascading failures (such as Kubernetes making incorrect scheduling based on wrong configurations). It undermines trust in etcd as a reliable coordination service and severely impacts SLO commitments regarding data accuracy.

### Incident Response and Best Practices

- **Incident response**: Once suspected data inconsistency is discovered (such as different nodes reading different values for the same key), investigation should begin immediately. First confirm whether this known issue was triggered (check transaction usage patterns), then proceed with recovery according to the above **Workaround**. After recovery, be sure to review the root cause and apply the official patch.
- **Best practices**:
    1.  **Use transactions cautiously**: Only use transactions when necessary, and avoid embedding complex queries that may depend on historical snapshots within transactions.
    2.  **Keep revision numbers fresh**: Try to avoid referencing very old revisions in transaction operations to reduce the probability of conflict with compaction.
    3.  **Monitor Compaction metrics**: Closely monitor metrics like `etcd_mvcc_db_compaction_keys_total` to understand historical data cleanup status.
    4.  **Version upgrades and patches**: For affected versions (including 3.4.x, 3.5.x, and main), actively follow and apply official fix patches.
- **Common anti-patterns**:
    - Using `--rev` parameter in transactions to query old version data that may have been compacted.
    - Assuming that transactions handle range requests identically on all members, ignoring their possibly optimized internal mechanisms.

### Related Metrics (SLI/SLO)

- **SLI (Service Level Indicator)**: Can define SLIs related to data consistency, such as "number of inconsistencies when reading values for the same key from different endpoints within a 5-minute window."
- **SLO (Service Level Objective)**: Set a strict target for the above SLI, such as "monthly data inconsistency incidents < 1," and make it a key guarantee for etcd cluster reliability.
- This issue reminds us that SLOs should not only focus on availability (such as uptime) but must also include quality attributes like data consistency.
