# Grafana Alert Rule Export Contains Stale Data Source UID Issue

## Overview

In SRE practice, the portability and version control of alert rules are critical. Whether used for Configuration as Code, cross-environment migration, or disaster recovery backups, exporting alert rules to structured files (such as YAML or JSON) is a core operation. This page describes a known defect in Grafana's alerting module: when a user duplicates an alert rule and manually modifies its target data source, the configuration file generated by the "Export" function does not reflect this update, instead incorrectly retaining the original rule's data source reference (UID). This issue undermines the accuracy of configuration exports and may pose risks to SRE automation workflows and environment consistency.

## Core Concepts

### Alert Rules and Data Sources
In Grafana, an alert rule defines the conditions that trigger an alert. The condition is typically based on query results from a **data source** (such as Prometheus, Loki, TestData). Data sources are referenced by their type and unique identifier (**UID**). This UID is key to ensuring Grafana can correctly connect to the data source for queries.

### Export Function
Grafana's alert rule management interface provides an "Export" function that allows users to export the current rule configuration as YAML or JSON format. Ideally, the exported configuration file should precisely reflect the rule's **current state** as saved in the UI, so it can be reliably re-imported in other environments or through GitOps workflows.

### Root Cause: Stale UID Reference
The core of this defect (Bug) is that the export logic fails to fully synchronize the updated state of the rule's data source UID. When a new rule (Rule B) is created by duplicating an existing rule (Rule A), even if the user changes Rule B's data source from Rule A's data source (e.g., `prometheus`) to another data source (e.g., `test-data`) in the UI, the data source-related fields in the exported configuration file (`datasourceUid` and `model.datasource.uid`) still point to Rule A's old UID (`prometheus`). This is a state synchronization failure.

## Practice

### Defect Reproduction Steps
1. **Create source rule**: Create and save an alert rule (Rule A) using a Prometheus data source.
2. **Duplicate rule**: In the rule list, duplicate Rule A as a new rule (Rule B). At this point, Rule B's data source is the same as Rule A's.
3. **Modify data source**: Edit Rule B, change its data source to another data source (such as TestData) in the UI, and save the changes.
4. **Trigger export**: In the alert rule list, perform the "Export -> With modifications" operation on Rule B.
5. **Verify output**: Check the generated YAML or JSON file. Even though the UI has been updated, the `datasourceUid` and `model.datasource.uid` field values in the file still reflect the original Rule A's data source UID (e.g., `prometheus`).

**Example: Exported YAML file (incorrect)**
```yaml
# ... other fields
          data:
            - refId: A
              # ...
              datasourceUid: prometheus  # <-- Error: should be testData
              model:
                datasource:
                  type: prometheus      # <-- Error: type also not updated
                  uid: prometheus       # <-- Error: UID incorrect
                # ...
```

### Impact and Workarounds
This defect primarily affects scenarios that rely on exported configuration files for automated deployment or environment synchronization. For example, a script designed to migrate rules from a test environment (using TestData) to a production environment (using Prometheus) may fail or produce incorrect queries because it imported a configuration containing the TestData UID.

**Possible Workarounds**:
- **Manual Correction**: After exporting, manually edit the YAML/JSON file to replace `datasourceUid` and `model.datasource.uid` with the correct values for the target environment. However, this defeats the purpose of automation and is error-prone.
- **Create New Rules Directly**: Avoid using the "Duplicate" function; instead, create new rules directly from templates or from scratch, specifying the correct data source. This ensures the UID is correctly set at creation time.
- **Monitor Upstream Fix**: Track the official fix for this issue (such as [Grafana Issue #122469](https://github.com/grafana/grafana/issues/122469)) and re-verify the export functionality after upgrading to the fixed version.

## SRE Key Points

- **Relationship to Reliability**: Configuration Drift is a common source of system unreliability. This defect directly causes inconsistency between configurations maintained through the UI and those managed through export files. If SRE teams rely on exported configurations as the Single Source of Truth, erroneous export content will introduce production risks.
- **Observability Considerations**: Incorrect `datasourceUid` causes imported alert rules to fail to correctly query their intended data sources, leading to alert condition evaluation failures or evaluations based on incorrect data. This directly impacts the effectiveness of the monitoring system and alert accuracy, weakening system observability.
- **Incident Response and Automation**: During incident response, quickly restoring alert rules from backups is a critical capability. If backup export files have this defect, restoration operations will fail. For teams using GitOps, automated synchronization processes will push incorrect configurations to production.
- **Best Practices and Anti-Patterns**:
    - **Best Practice**: Always validate critical fields (such as data source UIDs) using `gdev` or scripts before and after export or import. Establish configuration validation steps in CI/CD pipelines to check whether rules point to the allowed data source list.
    - **Common Anti-Pattern**: Blindly trusting the output of the toolchain without validating critical steps in automation workflows. Assuming that "duplicate and modify" operations are seamless across all subsequent stages (including export).
- **Related Metrics (SLI/SLO)**: While this defect itself doesn't directly produce SLI metrics, it affects SLOs related to alert system reliability. For example, an SLO could be "all active alert rules achieve a query success rate > 99.9% on their intended data sources." Export errors could undermine this SLO.
