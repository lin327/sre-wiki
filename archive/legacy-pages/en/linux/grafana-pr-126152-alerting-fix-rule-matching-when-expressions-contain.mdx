# 

## Overview

In complex monitoring systems, alert rule name conflicts are a scenario that requires careful handling. When multiple **identically named** alert rules exist within the same rule group, the monitoring system (such as Grafana Mimir) needs a reliable mechanism to distinguish them. The Grafana alerting UI uses a "query fingerprint" (based on the `hashQuery` function) as the key identifier for differentiation. However, the presence and handling of comments in PromQL expressions directly affects fingerprint calculation, leading to rule synchronization anomalies — the appearance of "ghost" rule entries. This fix completely resolves the fingerprint mismatch caused by **inline comments** (`#` appearing within a code line) not being correctly stripped, ensuring the correctness of alert rule lifecycle states (such as "creating," "deleting"), which is critical for maintaining the stability and trustworthiness of the alerting system.

## Core Concepts

1.  **Identically Named Rules and Fingerprint Comparison**: Within the same rule group, if two rules have identical `name` fields, the system falls back to using the hash value of the query expression (i.e., the fingerprint) to distinguish them. This requires that the expression used for fingerprint calculation must be standardized.
2.  **PromQL Comment Handling and Standardization**: Prometheus configuration management systems (such as Mimir) perform **standardization** on PromQL expressions before storing rules, with a key step being the removal of all comments. This ensures that regardless of how comments are written in the source expression, the stored expression is semantically unified.
3.  **Full-Line Comments and Inline Comments**:
    *   **Full-Line Comments**: `#` is the first non-whitespace character at the beginning of the line, such as `# This is a full-line comment`.
    *   **Inline Comments**: `#` appears after code on the same line, such as `metric > 0.5 or # fallback condition metric < 0.1`.
4.  **Root Cause**: Before the fix, Grafana could only strip **full-line comments**. When expressions contained **inline comments**, Grafana Ruler returned the original expression with comments, while Mimir stored the expression with comments stripped. The fingerprints calculated from these two were different, causing the system to incorrectly treat them as two different rules, marking one as "creating" and the other as "deleting," forming "ghost" entries that never disappear.

## Practice

This fix standardizes PromQL expressions by introducing a more robust comment-stripping utility function to ensure fingerprint calculation consistency.

1.  **Extract Common Utility Function**: A new utility function called `stripPromQLComments` was added (exported from `rule-id.ts`). It uses the regular expression `/#[^\n]*/g` to precisely match and remove **all** PromQL comments, whether they are at the beginning of a line (full-line comments) or inline (inline comments).
2.  **Unify Fingerprint Calculation Path**: The core `hashQuery` function was refactored. Before calculating the hash, it no longer handles comments itself but uniformly delegates to the `stripPromQLComments` function. This ensures that all code paths calling `hashQuery` use the same standardization logic.
3.  **Scope of Application**: The fix was applied simultaneously to the new rule list view (`ruleMatching.ts`) and the traditional rule view (`useCombinedRuleNamespaces` path), since both ultimately rely on `hashQuery` to distinguish identically named rules.
4.  **Verification and Testing**: To ensure the robustness of the fix, multi-layer tests were added:
    *   **Unit Tests**: For the `stripPromQLComments` function, covering full-line comments, inline comments, mixed comments, comment-only lines, no comments, and various edge cases such as empty line folding caused by comments.
    *   **`hashQuery` Function Tests**: Specifically testing fingerprint generation in scenarios with inline comments and mixed comments.
    *   **Integration Tests**: In the `matchRulesGroup` scenario, two recording rules with the same name were simulated, where one Ruler expression contained inline comments, verifying that both could correctly match the corresponding rules stored in Mimir (Prometheus) and **would not produce ghost entries**.

## SRE Key Points

### Connection to Reliability
*   **Incident Response**: This issue directly causes **incorrect and persistent status indicators** ("creating," "deleting") in the alerting UI. This can seriously mislead the SRE team's judgment of the system's true state, potentially leading to incorrect actions (such as manually deleting a rule that actually exists) or ignoring real configuration drift, thereby affecting the accuracy and efficiency of incident response.
*   **Observability**: Alert rules themselves are the foundation of observability. This issue undermines the credibility of the alert management interface, a critical observability tool. The uncertainty of rule status makes it impossible to reliably answer the fundamental question of "whether the configuration is effective."

### Best Practices and Common Anti-patterns
*   **Best Practice**: When developing systems involving configuration parsing and comparison, **normalize input early and thoroughly**. This case demonstrates that only handling some cases (such as full-line comments) while ignoring others (inline comments) introduces hidden and difficult-to-debug defects.
*   **Best Practice**: Write comprehensive unit tests for critical functions (such as `stripPromQLComments`, `hashQuery`) covering all possible input variants (comment positions, mixed content, empty values, etc.) as the cornerstone of preventing regressions and ensuring logical correctness.
*   **Common Anti-pattern**: **Using inconsistent data representations across different components (such as Ruler and Mimir)**. Ruler returns "commented" original expressions while Mimir stores "comment-free" standardized expressions — this is the fundamental architectural cause of the problem. Standardization should be completed early on one end of the data flow.
*   **Common Anti-pattern**: **Ignoring the impact of edge cases on state machines**. This issue may appear to be a minor string processing flaw, but its ultimate effect is to trap the rule matching state machine in an invalid state.

### Related Metrics (SLI/SLO/SLA)
*   **Alert Rule Validity SLI**: Can measure the proportion of rules where the UI-displayed rule state (such as "healthy") matches the actual state in identically named rule scenarios. This metric was low before the fix.
*   **Rule Synchronization Delay SLO**: The time from configuration modification of alert rules to achieving a consistent and correct state across all components (such as UI, evaluator). This issue could theoretically cause the delay to approach infinity (never consistent).
*   **Alerting System Availability SLA**: An internal SLO ensuring that the alert management interface provides accurate and reliable status information to avoid misleading operations.
