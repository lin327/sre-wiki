# grafana/grafana#114102 - Custom Grafana Query headers are not URL encoded

## Overview

When building an observability platform, Grafana serves as the front-end display and query portal, and its interaction with back-end data sources (such as Prometheus, PostgreSQL) is crucial. A common architecture is to deploy a web application firewall (WAF) in front of Grafana for enhanced security. When Grafana's custom query header contains non-ASCII characters (such as the German character `öÖäÄüÜß`) and is not encoded correctly, it will directly violate many WAF security rules and HTTP protocol specifications (RFC 9110), causing legitimate data query requests to be incorrectly intercepted, seriously affecting system observability and operation and maintenance efficiency. This problem reveals that in distributed systems, seemingly small coding details can have a significant impact on end-to-end reliability.

## Core concepts

- **Custom query headers**: Grafana allows users to attach custom HTTP headers to data source queries, such as `x-dashboard-title` and `x-panel-title`, which are used to pass contextual information (such as the title of the dashboard or panel) to facilitate logging or auditing on the backend.
- **Non-ASCII characters and URL encoding**: The HTTP header standard (RFC 9110) requires that its value must consist of visible ASCII characters. Non-ASCII characters (such as UTF-8 encoded characters) must be converted by **URL encoding (Percent-encoding)**, for example `ö` is encoded as `%C3%B6` to ensure that they will not be misunderstood or filtered when transmitted between different systems.
- **WAF rules**: Web application firewalls are usually configured with strict rule sets to defend against attacks. One common rule is to **deny any HTTP header containing high ASCII values ​​(&gt;127)** because malicious payloads (such as SQL injection, command injection) often use non-ASCII characters for obfuscation. Unencoded non-ASCII headers directly trigger such a rule.

## Practice

When encountering a Grafana query that fails due to WAF interception, you can follow the following steps to diagnose and resolve:

### 1. Confirm the problem
- **Check browser developer tools**: When executing a query on a Grafana page, open your browser's developer tools (F12) and find the failed request in the Network tab. Check the `x-dashboard-title` and `x-panel-title` request headers to see if their values ​​contain raw non-ASCII characters (such as `ö`) rather than their encoded form.
- **Check WAF logs**: Check the logs of WAF (such as ModSecurity, cloud vendor WAF) to confirm whether the reason for interception is "violated HTTP header value" or "non-ASCII character".
- **Version Backtrace**: This issue does not exist in Grafana 11.2.0, but appears in later versions (as reported in 12.2.1), indicating that it may be a regression introduced by a version upgrade.

### 2. Temporary solution
While waiting for an official fix, you can take the following steps to restore service:
- **Modify dashboard and panel titles**: Change all dashboard and panel titles that contain non-ASCII characters to pure ASCII characters (e.g., change "`Überwachung`" to "`Ueberwachung`"). This is the most direct method, but it affects readability.
- **Adjust WAF rules (do this with caution)**: Set exception rules on the WAF side for traffic from the Grafana server that contains specific headers (`x-dashboard-title`, `x-panel-title`) and **only** allow those specific headers to contain non-ASCII characters. **This requires careful assessment of security risks** and ensuring only targeting trusted sources (such as the Grafana server IP).

### 3. Permanent solution
- **Upgrading Grafana**: Pay close attention to the official Grafana release, a fix for this issue (GitHub Issue #114102) (usually `encodeURIComponent()` encoding these header values in the code) may be included in a future version update. Upgrading to a repaired version is the ultimate solution.
- **Contribution fix**: If you use the open source version, you can refer to the discussion in the Issue, apply the fix patch yourself and rebuild Grafana.

## SRE Key Points

- **Reliability Correlation**: This issue directly harms the reliability of the system's **observability pipeline**. When queries are intercepted by the WAF, the SRE loses access to critical system metrics and logs and is unable to perform effective monitoring, alerting, and troubleshooting, which violates the core goals of **Reliability Engineering**.
- **Incident Response**: When an incident occurs, it is critical to quickly identify the issue as an "observability infrastructure self-failure**". Two threads need to be started at the same time: one is to apply the above temporary solution to restore the data flow, and the other is to report the problem to the Grafana community or vendor and track the fix.
- **Best Practices and Anti-Patterns**:
    - **Best Practice**: When passing data containing user-generated content or localized text between systems (especially across boundaries such as web, API), you should always **URL encode or Base64 encode**. Compatibility testing for WAF should be added to the development and testing environments.
    - **Common anti-patterns**: Using "raw" strings directly in protocol-strict locations such as HTTP headers; configuring WAF rules to be too broad without making necessary exceptions for internal trusted services, or conversely, overly relaxing security rules for a quick fix.
- **Related indicators (SLI/SLO/SLA)**:
    - **SLI (Service Level Indicator)**: Can monitor "Grafana data source query success rate by request", specifically distinguishing failures due to `4xx` (e.g. intercepted by WAF).
    - **SLO (Service Level Objective)**: Set a goal for "observability data query availability", such as 99.9% of query requests successfully returning data. This WAF issue directly impacts this SLO.
    - In the service SLA (service level agreement), external dependency failures caused by security policies (such as WAF) should be clearly listed as matters that need to be jointly diagnosed and resolved.
