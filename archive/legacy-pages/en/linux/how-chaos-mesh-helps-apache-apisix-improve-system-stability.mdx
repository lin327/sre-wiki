# How Chaos Mesh Helps Apache APISIX Improve System Stability

## Overview

Apache APISIX, as a cloud-native, high-performance microservice API gateway, handles billions of requests per second from customers across industries including finance, internet, and manufacturing. As its functionality and interaction with external components (such as etcd) become increasingly complex, the likelihood of potential system failures also increases. To proactively identify failure scenarios that are difficult to cover in regular CI/CD processes (such as network jitter, node outages), the Apache APISIX team introduced Chaos Engineering practices. They use the cloud-native chaos engineering platform [Chaos Mesh] to simulate faults in production environments, verify system resilience, and based on the results fix defects and build confidence in the system's ability to operate under abnormal conditions. This is a typical SRE practice case of using chaos engineering to improve the reliability of critical business systems.

## Core Concepts

This case involves several core concepts in SRE and reliability engineering:

*   **Chaos Engineering**: A practice of proactively injecting faults to discover potential weaknesses in distributed systems. Its core is to establish a **steady-state hypothesis** for the system (such as "the system should maintain a certain throughput"), then introduce controllable faults, observe whether the system can maintain or return to steady state, thereby exposing problems and fixing them.
*   **Steady-State Hypothesis**: A quantifiable description of the system's normal operating behavior before a chaos experiment begins. For example, in the Apache APISIX case, steady state is characterized by "route creation and access succeed, etcd connection is maintained, and requests per second (RPS) is stable."
*   **Fault Injection**: Using tools like Chaos Mesh to simulate real-world faults, such as network latency, Pod kills, file system errors, etc. This is the key execution step in chaos engineering.
*   **Chaos Mesh**: An open-source, cloud-native chaos engineering platform that runs on Kubernetes, providing comprehensive fault injection capabilities (including Pod, network, file system, kernel, etc.) to help users discover system weaknesses.

## Practice

The Apache APISIX team designed and executed chaos experiments using Chaos Mesh for two specific scenarios reported by users, successfully locating and resolving the issues.

**Experiment Scenario 1: High Network Latency Between etcd and APISIX**
1.  **Define Steady State and Metrics**: The team determined the normal steady state as: `create route` and `access route` operations succeed, etcd connection is maintained, and RPS is stable. They collected metrics through Prometheus and used Grafana for visual monitoring, while also analyzing Nginx error logs.
2.  **Establish Control Group**: Without injecting faults, a baseline test was conducted to confirm all operations were normal and record the RPS.
3.  **Inject Faults**: Using Chaos Mesh's **NetworkChaos** experiment, a **5-second delay** was injected into the network between etcd and APISIX.
4.  **Observe and Verify**: After fault injection, testing revealed that the `set route` operation failed (as expected, due to operation timeout), but `access route` succeeded, etcd remained connectable, and the core RPS metric did not change significantly. This verified that under brief network latency, APISIX's data plane (traffic forwarding) continues to work normally, and the system behavior meets expectations.

**Experiment Scenario 2: etcd Cluster Node Failure**
1.  **Establish Control Group**: Same as scenario 1, a fault-free baseline test was conducted first.
2.  **Inject Faults**: Using Chaos Mesh's **PodChaos** experiment, randomly killing nodes in the etcd cluster was simulated.
3.  **Problem Discovery**: The experiment reproduced the production environment issue. The team found that when killing the second node in the `etcd endpoint` list, the `set route` operation would continuously return `connection refused` errors, while deleting other nodes might succeed. A large number of connection refused errors appeared in the logs.
4.  **Root Cause Analysis and Fix**: Investigation revealed that the etcd Lua API used by Apache APISIX **sequentially binds to the first endpoint in the list rather than randomly selecting or having failover capability** when creating clients. This causes the client connection to continuously fail when that specific node goes down. The team subsequently added a **health check mechanism** to this API to avoid sending large numbers of requests to unavailable nodes; they also added a **fallback mechanism** to provide fallback handling when the etcd cluster is completely unavailable, preventing logs from being flooded with errors.

## SRE Key Points

This case provides valuable insights for SRE practice from multiple perspectives:

*   **Improving Reliability and Resilience**: Chaos engineering is a powerful means of proactively finding system weaknesses and improving reliability. It complements unit testing, integration testing, and end-to-end testing, especially in scenarios that **verify complex external dependency interactions**. By fixing the discovered issues (such as the etcd client's failover defect), the system's overall fault tolerance is substantially improved.
*   **Strengthening Observability-Driven Approach**: Successful chaos experiments heavily depend on comprehensive observability. The Apache APISIX team defined and verified "steady state" through Prometheus, Grafana, and log analysis, directly demonstrating that **observability** is the foundation for implementing chaos engineering and quantifying system health.
*   **Improving Incident Response and Recovery**: The faults simulated by chaos experiments (such as node outages) are exactly the incidents that may occur in production environments. By fixing issues discovered in experiments, the team improves the system's **automatic recovery capability** in real incidents (such as etcd connection failover), thereby reducing MTTR (Mean Time To Recovery).
*   **Best Practices**:
    *   **Start from Specific Scenarios**: Design experiments from real user pain points or potential risk scenarios (such as etcd network latency) to ensure chaos engineering's value directly serves business needs.
    *   **Small Scale, Incremental**: Start implementing in CI/CD or test environments, verify methods and build confidence, then consider expanding to production environment canary or limited-scope experiments.
    *   **Define Clear "Blast Radius"**: Tools like Chaos Mesh allow fine-grained control over the scope and intensity of fault injection, which is key to safely conducting chaos experiments.
*   **Related Metrics**: The experiment used **SLIs** (such as RPS, etcd connection status) to measure steady state. The experiment results directly impact **SLO** setting and **error budget** consumption — a system not validated by chaos engineering may have overly optimistic SLOs, while chaos test results can help teams more accurately assess the system's true reliability, thereby establishing more reasonable SLOs.

Through this practice, Apache APISIX not only fixed specific defects but also established a mechanism to integrate chaos engineering into the development process, with plans to expand it to E2E testing scenarios and more related projects, continuously driving system stability improvement.
