# Introducing the UX Research Working Group - Prometheus Blog

## Overview

Prometheus has long focused on solving complex technical challenges to build a reliable, high-performance open-source monitoring system. However, as the user base grows and the ecosystem expands, a range of user experience (UX) pain points have gradually emerged, spanning areas from onboarding configuration and documentation quality to mental model construction and system interoperability. To systematically address these issues, the Prometheus community established the **UX Research Working Group**. The core goal of this working group is to integrate structured user research, deep user insights, and usability perspectives into the community's development workflow and decision-making processes, thereby comprehensively improving the Prometheus user experience. For SREs, a monitoring tool that is easy to understand, configure, and troubleshoot directly reduces operational burden, minimizes the risk of misconfiguration, and improves incident response efficiency.

## Core Concepts

The UX Research Working Group is a cross-functional community group focused on "users" and "experience." Its core work is to build a bridge between **User-Centered Design** and Prometheus technical development.

- **User Research**: The working group systematically collects the behaviors, needs, and frustrations of target users (including new users, experienced users, and administrators) when using Prometheus through methods such as interviews, surveys, and usability testing. This goes beyond simple feature feedback, aiming to deeply understand users' **mental models** and workflows.
- **UX Deliverables**: Based on research, the working group produces a series of guiding documents, such as **Personas**, **User Journeys**, **Wireframes**, and **Prototypes**. These tools transform abstract user pain points into concrete, actionable design recommendations.
- **Prioritization**: Faced with numerous user experience issues, the working group helps the community **prioritize** pain points. This ensures that limited development resources are first invested in improvements that have the greatest impact on users, such as optimizing the new user onboarding process or improving the clarity of documentation for critical operations.
- **Collaboration and Enablement**: The working group does not operate in isolation but works closely with Prometheus sub-project maintainers and contributors as an **enabler**, providing research support, user feedback, and usability assessments to help them consider the user experience dimension in technical decisions.

## Practice

The working group provides clear collaboration and participation paths for two core participants in the Prometheus ecosystem:

### How to Assist Prometheus Maintainers

If you are a maintainer of a Prometheus component or feature and face the following situations, you can collaborate with the working group:
1.  **Unclear Requirements**: When developing features, the real needs and usage scenarios of target users are unclear.
2.  **Trade-off Decisions**: Hesitating between two or more technical approaches, wanting to evaluate the **trade-offs** from a user perspective.
3.  **Pre-release Evaluation**: Wanting to obtain usability feedback from real users before feature release.

**Collaboration Process**: Simply communicate your goals to the working group (for example, "I want to optimize the Alertmanager configuration workflow"). They will work with you to determine the most appropriate research type (such as user interviews, card sorting tests) and scope, execute the research, analyze the data, and ultimately provide a complete report containing user personas, improvement recommendations, and a prioritized list.

### How to Participate (as an End User)

Prometheus end users are a valuable source of improvement. You can contribute in the following ways:
- **Participate in Research**: Express your willingness to participate in user research on the Slack channel or GitHub. When a research project matching your background starts, the working group will proactively contact you.
- **Report Issues**: When encountering a poor experience (such as complex configuration or confusing documentation), you can reach out to the working group for help. They can help you clearly express the problem as a community issue and guide you to the relevant maintainers or discussion channels.

## SRE Key Points

### Connection to Reliability Engineering
Improving the user experience of monitoring tools directly serves the core goal of SRE — **reliability**.
- **Reducing Human Error**: Clear documentation, intuitive configuration interfaces, and designs that align with mental models can significantly reduce configuration errors caused by misunderstanding or misoperation, thereby avoiding monitoring blind spots or false alerts, which are common causes of or contributors to prolonged incidents.
- **Accelerating Incident Response**: In high-pressure troubleshooting scenarios, an easy-to-navigate UI, meaningful alert descriptions, and efficient dashboard creation workflows help SREs locate problems faster, reducing **MTTR (Mean Time To Repair)**.
- **Increasing Observability Adoption**: If Prometheus has too high a learning and usage barrier, teams may choose to bypass it or only use the most basic features. Good UX reduces friction in adopting new features, enabling teams to fully leverage the capabilities of the Prometheus ecosystem (such as OTel integration) for more comprehensive system observability.

### Best Practices and Common Anti-patterns
- **Best Practice**: Treat user experience as an **integral part of system reliability**. When designing new alert rules, SLO monitoring dashboards, or deployment workflows, proactively consider the operational paths of users (such as on-call engineers). Actively leverage the UX Working Group's resources and incorporate user feedback loops into the development cycle.
- **Common Anti-pattern**: Designing features purely from a technical implementation perspective, ignoring "how humans interact with it." For example, generating a technically correct but information-overloaded default dashboard, or designing a configuration syntax that requires deep background knowledge to use correctly. These all translate into **Operational Toil** during long-term operations.

### Related Metrics
Traditional SRE metrics (such as latency, error rate, traffic, saturation) measure the reliability of **the monitored system**. The UX Working Group focuses on the health of **the monitoring system itself**, and its related metrics can include:
- **User Task Completion Rate**: The time and number of steps required for a new user to successfully deploy Prometheus and receive their first alert.
- **User Satisfaction (CSAT) or Net Promoter Score (NPS)**: Periodic surveys targeting specific features or the overall experience.
- **Support Request Volume**: The number of community support questions or GitHub issues related to specific features (such as configuration syntax, remote write). The working group's work aims to reduce these issues at the source.
