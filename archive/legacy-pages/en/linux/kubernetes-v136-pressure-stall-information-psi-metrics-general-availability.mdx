# Kubernetes v1.36: Pressure Stall Information (PSI) Metrics General Availability

## Overview

Pressure Stall Information (PSI) is a mechanism originating from the Linux kernel that provides high-fidelity signals for system pressure by reporting the proportion of time tasks are stalled due to resource saturation. In Kubernetes v1.36, PSI metrics are officially declared Generally Available (GA), marking the Kubernetes ecosystem's acquisition of a reliable, standardized interface for observing resource contention at the node, Pod, and container levels. For SRE teams, this goes beyond traditional resource utilization monitoring and serves as an important tool for proactive capacity planning, precise incident root cause analysis, and setting reliable Service Level Objectives (SLOs).

## Core Concepts

Traditional monitoring typically focuses on CPU or memory utilization percentages, but this can be misleading. A node may report 80% CPU utilization, yet some tasks may be experiencing severe performance degradation due to scheduling delays. PSI is designed to fill this gap.

**Core metrics provided by PSI include:**

*   **Cumulative Total**: The absolute time spent in a stalled state.
*   **Moving Averages**: Provides averages over 10-second, 60-second, and 300-second windows, enabling operations personnel to distinguish between transient peaks and sustained resource pressure.

PSI monitoring covers three major resource categories: **CPU**, **Memory**, and **I/O**. Each category provides metrics for different time windows, such as `cpu_psi_10s_avg` or `io_psi_300s_total`, collectively painting a complete picture of resource pressure.

## Practice

### Prerequisites and Enablement

To use PSI metrics in a Kubernetes cluster, nodes must meet the following requirements:

1.  **Linux Kernel Version**: 4.20 or higher.
2.  **cgroup Version**: Must use cgroup v2.
3.  **OS-Level Enablement**: The kernel must be compiled with `CONFIG_PSI=y`, and the boot parameter must not set `psi=0`.

Starting with Kubernetes v1.36, Kubelet PSI metrics are enabled by default, requiring no Feature Gate configuration. As long as nodes meet the above OS requirements, metrics are automatically collected and exposed.

### Data Collection and Access

PSI metrics are primarily exposed through two methods:

*   **Metrics Endpoint**: PSI data can be obtained by scraping the Kubelet's `/metrics/cadvisor` endpoint using a Prometheus-compatible monitoring system. This is the primary method for continuous monitoring and alerting in production environments.
*   **Summary API**: For real-time diagnostics, privileged node administrators can access the Kubelet's Summary API through the API Server proxy. For example, use the following command to get real-time pressure data for a specific container:
    ```bash
    CONTAINER_NAME="example-container"
    kubectl get --raw "/api/v1/nodes/$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')/proxy/stats/summary" | jq '.pods[].containers[] | select(.name=="'"$CONTAINER_NAME"'") | {name, cpu: .cpu.psi, memory: .memory.psi, io: .io.psi}'
    ```
    **Note**: Proxying to the Kubelet is a privileged operation with security risks. Ensure the operator has appropriate administrator permissions.

### Caveats

*   PSI is a Linux kernel feature, so **Windows nodes do not provide these metrics**. In mixed clusters, the Kubelet automatically ignores PSI metric collection on Windows nodes.
*   In v1.36, even if the OS has not enabled PSI (`psi=0`), the Kubelet will no longer report misleading zero-value metrics. Instead, it correctly detects and omits these metrics, avoiding false positive alerts.

## SRE Essentials

### Connection to Reliability

PSI is a core pillar for improving system observability and achieving reliability goals.

*   **Capacity Planning**: Consistently high PSI values (e.g., `io_psi_300s_avg` sustained above threshold) are a direct signal of excessive node resource contention, providing warnings much earlier than simply observing utilization, supporting more precise capacity planning.
*   **Incident Response and Root Cause Analysis**: When services experience latency or errors, checking the PSI metrics of related containers or nodes can quickly locate bottlenecks (CPU scheduling delays, memory reclaim pressure, or I/O blocking), greatly reducing troubleshooting time (MTTR).
*   **SLO Definition and Error Budget**: PSI metrics for key resources (such as CPU stall time proportion) can serve as Service Level Indicators (SLIs) or supplements. For example, defining an SLO that requires the 99th percentile of `cpu_psi_60s_avg` to be below a certain threshold, directly linking resource pressure to business reliability goals.

### Best Practices and Common Anti-Patterns

*   **Best Practices**:
    *   Integrate PSI metrics into monitoring dashboards and alert rules, particularly focusing on **moving averages** to identify trends.
    *   Combine PSI with traditional utilization metrics for comprehensive judgment. PSI provides "impact" (task stalling), while utilization provides "state" (resource occupation).
    *   Use PSI to guide vertical or horizontal Pod autoscaling decisions, making responses more closely aligned with actual performance impact.
*   **Common Anti-Patterns**:
    *   **Ignoring Alerts**: Dismissing PSI alerts as "false alarms," thereby missing early signals of resource saturation.
    *   **Viewing Metrics in Isolation**: Only viewing PSI at the node level without correlating to specific Pods or containers may prevent locating the responsible workload.
    *   **Relying on Snapshot Values**: Over-focusing on instantaneous PSI peaks while ignoring their duration (judged through moving average windows) may lead to unnecessary corrective actions.

### Related Metrics (SLI/SLO/SLA)

PSI metrics themselves can serve as powerful SLI candidates. For example:

*   `node_cpu_psi_10s_avg`: Node CPU pressure 10-second average.
*   `pod_memory_psi_60s_avg`: Pod memory pressure 60-second average.
*   `container_io_psi_300s_total`: Container I/O pressure 5-minute cumulative stall time percentage.

SLOs can be set based on these metrics, for example: "At 99% of sampling points, the CPU 10-second pressure average for production Pods should not exceed 5%."
