# [UI: auto-complete handles escape character incorrectly](https://github.com/prometheus/prometheus/issues/11629)

## Overview

In the daily operation and maintenance of Prometheus, ensuring the accuracy and consistency of query statements (PromQL) is the basis for ensuring the reliability of the monitoring system. A recently discovered UI behavior discrepancy indicates a parsing inconsistency between Prometheus' Web UI table presentation, autocompletion, and manually written PromQL queries when metric label values ​​contain UTF-8 escape sequences (e.g. `\x2d`). This will not only cause user confusion, but may also affect the accuracy of troubleshooting and alerting rules due to copied "invalid" queries, which is a potential hazard that affects the reliability of the observability tool chain. This article will analyze the rationale for this problem, steps to reproduce it, and its implications for SRE practice.

## Core concepts

1. **PromQL string literals and escaping**: The PromQL parser supports the use of backslash `\` for escaping in string literals, including the `\xHH` form representing UTF-8 byte sequences. In the Prometheus configuration file, the label value `faulty_label: \x2d` will be stored unchanged. However, when the value is used as a string in a PromQL query, the parser actively interprets `\x2d` as a hyphen `-`.
2. **Query Builder and Parser**: Prometheus UI includes a visual query builder that provides auto-completion and the ability to copy tag matchers from a table. The strings generated by these functions may deviate from the strict syntax required by the PromQL parser, especially when the tag value contains special characters.
3. **Source of inconsistency**: The core of the problem is that the UI fails to process the stored original string (`\x2d`) consistently with its logical value (`-`) after it is interpreted by PromQL when displaying and building queries. This causes the UI table to display escaped characters, but the copied query statement may be the original unescaped string, and vice versa.

## Practice

### Problem reproduction and verification

1. **Configure a label containing special characters**: Define a label containing a UTF-8 escape sequence in the Prometheus configuration file.
    ```yaml
    scrape_configs:
      - job_name: "prometheus"
        static_configs:
          - targets: ["localhost:9090"]
            labels:
              faulty_label: \x2d
    ```
2. **Observe inconsistencies in the UI**:
    * When querying metrics in the UI (such as `prometheus_build_info`), the table will show `faulty_label="-"` (the interpreted value).
    * Click the matcher in the table to copy, and then paste it into the query box for execution. The result is empty. Because the query statement generated at this time may be `{faulty_label="\x2d"}`, but the PromQL parser will also interpret it as `-` when querying, and the actual stored original string may be double-interpreted due to the way of collecting configuration, resulting in matching failure.
3. **Correct way to query**: To match the original string `\x2d` exactly, you must explicitly escape the backslash in the PromQL query, that is, use `{faulty_label="\\x2d"}`.

### SRE response and best practices

* **Tag naming convention**: To avoid such ambiguities, it should be explicitly required in the naming convention of the monitoring infrastructure: Avoid using special characters in tag values ​​that can be interpreted by PromQL or UI (such as backslash `\`, double quotes `"`). Use pure letters, numbers, underscores, and hyphens whenever possible.
* **Configuration Consistency Check**: Integrate static analysis of Prometheus configuration files into the CI/CD process to check for potentially problematic characters. You can use `promtool check config` to perform basic verification and customize rules to scan for suspicious tag values.
* **Query debugging and verification**: When it is found that the query results copied by the UI are abnormal, the SRE engineer should first suspect that there is an escaping problem. You can try manually adding extra backslashes to the query statement for escaping, or query directly using the API to bypass potential pitfalls in the UI.
* **Follow related updates**: Pay close attention to the Prometheus version update log, especially the entries about UI improvements and PromQL parser changes. The resolution of this issue ([Issue #11629](https://github.com/prometheus/prometheus/issues/11629)) will directly improve the reliability of the query experience.

## SRE Key Points

* **Relevance to Reliability**: Such UI/query inconsistencies directly impact the **consumability** of observability data. If engineers cannot reliably copy the correct query statement from the interface, it will increase the troubleshooting time (MTTR) and may lead to misjudgment of the system status, which goes against the original intention of SRE to pursue system reliability.
* **Best Practice**:
    * **Defensive configuration**: Follow the simple tag value principle to avoid complexity from the source.
    * **Queries as Code**: Store key PromQL queries and alert rules as code in the repository and verify them with `promtool check rules`, reducing reliance on interactive UI builds.
    * **Toolchain Validation**: Regularly verify the consistency of behavior of the monitoring toolchain (e.g. UI, API, Alert Manager) when handling edge cases.
* **Common anti-patterns**:
    * **Over-reliance on the UI**: Using queries automatically generated by the UI directly for production alert rules or long-term analysis without validation.
    * **Ignore character encoding**: When passing tags across systems (such as configuration management, application embedding, Prometheus), do not pay attention to character encoding and escaping rules.
* **Related indicators (SLI/SLO/SLA)**:
    * **SLI (Service Level Indicator)**: "Prometheus UI query replication success rate" or "Alert rule query first match accuracy rate" can be defined as an internal quality indicator.
    * **SLO (Service Level Objective)**: For internally used monitoring platforms, an SLI can be set to ensure that the accuracy of key queries generated by the UI does not fall below a certain threshold (for example, 99%) in specific scenarios. This needs to be monitored through automated testing or user feedback mechanisms.
