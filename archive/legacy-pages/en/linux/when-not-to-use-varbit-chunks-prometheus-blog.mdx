# When (not) to use varbit chunks - Prometheus Blog

## Overview

In Prometheus' time series database (TSDB), raw sampled data is stored in fixed-size chunks. To optimize storage efficiency, Prometheus introduces a variety of encoding schemes. Among them, the **varbit encoding** (encoding version 2) introduced since version 0.18.0 has achieved a significant breakthrough in compression rate compared with the previous default **double-delta encoding** (encoding version 1), but it also brought about changes in data access patterns. The choice of encoding scheme is directly related to disk and memory usage, write throughput, and response speed to specific types of queries. Therefore, it is one of the key decisions that SREs need to make when planning Prometheus storage and performance tuning.

## Core concepts

Each chunk of Prometheus TSDB contains metadata, allowing independent selection of encoding versions. There are currently three main versions:

- **Version 0**: Original delta encoding, now largely deprecated.
- **Version 1 (Double-Delta)**: Improved Double-Delta encoding, long term the default option. It allows **random access** to sampled data within a chunk via an index.
- **Version 2 (Varbit)**: A new variant of double differential encoding, named for its use of **Varbit width** to store sample values. Its design is partly inspired by Facebook's Gorilla in-memory timing database.

The core difference between the two is:

- **Compression efficiency**: The compression rate of Varbit encoding is much higher than that of double-delta encoding. Typical production data shows that double-delta encoding requires approximately 3.3 bytes/sample, while varbit encoding can be reduced to approximately 1.28 bytes/sample, achieving approximately **3x** compression improvement.
- **Access Mode**: Double-delta encoded chunks support **random reading** by index. Varbit-encoded chunks can only be accessed sequentially.
- **Computational overhead**: Varbit encoding has a slightly higher computational cost than double-delta encoding when encoding and decoding, but this increase is usually a small fraction of the total operation cost.

## Practice

### Enable Varbit encoding

Enabling the new varbit encoding is very simple. When starting the Prometheus server, specify the encoding version via a command line flag:

```bash
prometheus -storage.local.chunk-encoding-version=2
```

**IMPORTANT NOTE**:
- This setting only takes effect for newly created chunks. Existing chunks will retain the encoded version when they were created until they are phased out and replaced according to the data retention policy.
- You can switch between different encoding versions at any time with no side effects. This makes it easy to A/B test or adjust your strategy as load changes.

### Verification and Monitoring

After switching encodings, you need to monitor key metrics to evaluate the effect:
1. **Storage Usage**: Observe the disk usage of the data directory and the size of the in-memory block cache, varbit encoding should significantly reduce both.
2. **Write performance**: Monitor indicators such as `prometheus_tsdb_head_samples_appended_total`. Varbit encoding may improve write throughput by reducing disk I/O.
3. **Query Performance**: Focus on monitoring the `query_duration_seconds` of affected queries (especially those that require random sampling from historical data) to ensure that their latency is within an acceptable range.

## SRE Key Points

### Links to reliability and performance

- **Storage Efficiency**: Varbit encoding is a powerful tool to deal with disk space pressure and extend the data retention period (Retention Time). Higher compression ratio directly means lower hardware cost and smaller failure surface (less data volume).
- **Write throughput**: Disk I/O is one of the main bottlenecks affecting Prometheus write speed. Varbit encoding significantly reduces the number of disk operations through approximately 3x data compression, thereby significantly increasing the data ingestion rate. This is crucial for high-cardinality, high-sampling-frequency scenarios.
- **Query performance trade-off**: This is the most important consideration for using varbit encoding. For most queries (such as getting all data within a time interval, getting the latest value), the performance impact is minimal. But for queries that require randomly sampling a small number of non-adjacent sampling points from a very long series of historical data (for example, displaying one data point per month for the past month on a dashboard), performance will drop significantly. This is because varbit encoding requires sequential scanning of chunks, while double-delta can be located directly.

### Best practices and common anti-patterns

**Best Practices:**
1. **Bottleneck-based decision**: If the main bottleneck is **disk I/O or storage space**, it is strongly recommended to try varbit encoding. If the main bottleneck is latency for a specific type of query, you should evaluate carefully or keep the default double-delta encoding.
2. **Optimize slow queries with Recording Rules**: Regardless of encoding, for complex aggregation queries or queries that are frequently used on dashboards, [[prometheus-recording-rules]] should be used to precompute results. This not only greatly alleviates the performance problems of random queries under varbit encoding, but also fundamentally optimizes the overall query performance.
3. **Progressive Verification**: Do not switch all data at once in the production environment. You can enable the new environment first, run it long enough to generate a large number of new chunks, and then perform performance comparison tests on key queries.

**Common anti-patterns:**
- **Ignore the query mode and enable it directly**: Without understanding your own query mode (especially the frequency and scale of random queries on historical data), blindly enabling varbit encoding may lead to unacceptable delays in key dashboards or alarm rules.
- **Rely on old complex queries without using Recording Rules**: Expect varbit encoding to bring benefits in storage and writing without changing any query habits.

### Related indicators

- **SLI/SLO association**:
  - **Availability**: Encoding choices do not directly affect service availability, but can indirectly enhance stability by optimizing resource usage.
  - **Latency**: Different query latency SLOs need to be developed for different encoding schemes. For users relying on historical random queries, the latency SLO under varbit encoding may be relaxed.
  - **Error Budget**: If the SLI of some queries exceeds the standard due to enabling varbit encoding, its consumption needs to be included in the error budget and compensated by optimizing the query (such as introducing Recording Rules).
- **Key Indicators**:
  - `prometheus_tsdb_storage_blocks_bytes`: Monitor changes in disk storage usage.
  - `prometheus_engine_query_duration_seconds`: Monitor query delay changes and analyze by query type.
  - `prometheus_tsdb_head_chunks`: Monitor the number of chunks in memory and estimate memory usage combined with encoding.
