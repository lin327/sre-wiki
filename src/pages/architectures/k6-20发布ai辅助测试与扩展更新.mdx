## 概述

k6 是一款广受欢迎的开源负载测试工具，旨在帮助团队主动进行性能测试，以便尽早发现并解决性能问题，从而交付更可靠的用户体验。随着软件交付周期不断加速，尤其是 AI 辅助开发工作流的兴起，对测试工具提出了更高的自动化、可解释性和规模化要求。k6 2.0 版本的发布正是为了应对这些挑战，它不仅延续了 1.0 版本的稳定性和 TypeScript 支持，更通过一系列新特性，极大地增强了测试脚本的创建、验证、自动化与规模化能力，使得 k6 成为 AI 驱动的现代软件开发生命周期中不可或缺的性能验证工具。

## 核心概念

**k6 核心架构**：k6 基于 Go 语言构建，使用 JavaScript 编写测试脚本，其核心优势在于高性能、轻量级以及清晰的测试指标（如响应时间、吞吐量、错误率）。它通过 **脚本（scripts）**、**检查（checks）**、**阈值（thresholds）** 和 **场景（scenarios）** 来定义和执行测试。

**扩展系统 (Extensions)**：这是 k6 的核心扩展机制，允许开发者为 k6 添加新的协议支持、客户端、输出格式或 CLI 功能。扩展分为由 Grafana Labs 维护的 **官方扩展** 和由社区贡献维护的 **社区扩展**。k6 2.0 引入了统一的扩展目录，明确区分两者，并提供了更规范的提交流程。

**AI 集成与可编程性**：k6 2.0 通过一系列 `k6 x` 子命令，将 k6 从一个单纯的测试执行器转变为一个可编程的测试平台。它支持 **模型上下文协议（MCP）**，允许 AI 编码助手（如 Claude Code, Cursor 等）直接调用 k6 的功能来生成、验证和运行测试，实现了测试与 AI 开发工作流的深度集成。

**断言 API (Assertions API)**：与现有的 **检查（checks）** 不同，断言 API 提供了更细粒度的测试条件判断。**非重试断言** 用于检查即时状态（如 HTTP 状态码），而 **自动重试断言** 则会等待条件满足或超时（尤其适用于浏览器测试中的元素出现）。当断言失败时，通常意味着测试场景已失效，应终止测试，这与检查（记录指标但继续执行）的设计哲学有所区别。

## 实践

**1. 设置 AI 辅助测试工作流**
使用新增的命令快速启动与 AI 代理的集成：
- `k6 x agent`: 在支持的 AI 编码助手中初始化一个能够编写正确、现代 k6 测试的代理环境。
- `k6 x mcp`: 启动一个内置的 MCP 服务器，允许 AI 代理通过标准协议与 k6 交互，获取资源、运行脚本并查看结果。
- `k6 x docs`: 在命令行中直接查询 k6 文档、API 参考和示例。
- `k6 x explore`: 浏览和过滤官方及社区扩展目录，自动发现并集成所需扩展。

**2. 利用扩展目录与开发工具**
- **浏览扩展**：通过 `k6 x explore` 命令或 [在线目录](https://grafana.com/docs/k6/latest/extensions/explore/) 查找支持特定协议（如 MQTT, SQL, Kafka, DNS）的扩展。对于支持自动解析的扩展，只需在脚本中引用，k6 会自动处理依赖。
- **开发与贡献扩展**：使用增强版的 `xk6` 工具箱进行扩展开发。
  ```bash
  # 从模板创建新扩展项目
  xk6 new --template=my-extension
  
  # 构建并测试扩展
  xk6 build --with my-extension=./my-extension
  xk6 test ./tests/
  
  # 检查扩展是否符合注册表规范
  xk6 lint
  ```

**3. 迁移与编写浏览器测试**
k6 2.0 大幅提升了其浏览器模块与 [Playwright](https://playwright.dev/) API 的兼容性。现有 Playwright 测试脚本可以更容易地迁移到 k6 中，从而利用 k6 的负载测试能力。团队可以平滑地从“功能是否正确”的验证过渡到“在高负载下功能表现如何”的性能验证。

**4. 编写断言测试**
根据场景选择使用 **检查** 或 **断言**。
- 对于负载测试中的静态断言（如状态码），使用非重试断言：
  ```javascript
  import { expect } from 'https://jslib.k6.io/k6-testing/0.6.1/index.js';
  // ... 在默认函数中
  expect(response.status).toBe(200);
  ```
- 对于需要等待元素的浏览器测试，使用自动重试断言：
  ```javascript
  import { expect } from 'https://jslib.k6.io/k6-testing/0.6.1/index.js';
  // ... 在浏览器测试函数中
  await expect(page.locator("#login-button")).toBeVisible();
  ```

**5. 集成与规模化部署**
- **CI/CD 集成**：k6 2.0 新增了结构化的 JSON 摘要输出，便于 CI/CD 系统和 AI 代理解析测试结果，做出自动化决策。
- **实时可观测性**：通过原生的 [OpenTelemetry 输出](https://grafana.com/docs/k6/latest/results-output/real-time/opentelemetry/)，可以将 k6 的性能指标与应用本身的 APM 遥测数据关联分析。
- **生产环境规模化**：使用稳定版的 [k6 Operator](https://grafana.com/blog/2025/09/16/distributed-performance-testing-for-kubernetes-environments-grafana-k6-operator-1-0-is-here/) 在 Kubernetes 集群中运行分布式测试，生成真实且可扩展的负载。

## SRE 要点

- **与可靠性、可观测性的关联**：k6 2.0 的更新直接服务于 SRE 的核心目标——提升系统可靠性。通过 AI 加速测试用例生成，可以更早地发现性能瓶颈。与 OpenTelemetry 的集成实现了“左移”的性能观测，使得在开发和测试阶段获得的性能数据能与生产监控数据无缝衔接，形成完整的可观测性闭环。扩展能力让 SRE 可以针对消息队列、数据库等关键基础设施组件进行专门的性能测试。

- **最佳实践与常见反模式**：
    - **最佳实践**：将 `k6 x agent` 生成的测试作为基础，由工程师审核和完善。利用扩展目录避免重复造轮子，优先使用官方或经过社区验证的扩展。在负载测试中，合理区分使用 **检查**（记录指标）和 **断言**（终止无效场景）。结合 k6 Operator 实现贴近生产的分布式测试。
    - **常见反模式**：过度依赖 AI 生成的测试而不进行人工评审。为简单场景引入不必要的扩展，增加复杂度。在需要持续收集错误率指标的负载测试中错误地使用断言而非检查。

- **相关指标（SLI/SLO/SLA）**：k6 是定义和测量性能 **SLI（服务水平指标）** 的理想工具。它可以轻松测量：
    - 响应时间（如 P95、P99 延迟）
    - 吞吐量（每秒请求数）
    - 错误率（基于 HTTP 状态码、`checks` 或 `assertions`）
    这些指标直接用于设定性能 **SLO（服务水平目标）**，例如“95%的订单 API 响应时间应小于 200ms”。k6 的 `thresholds` 功能可以在测试中直接校验这些 SLO 是否达成，是自动化性能门禁（作为 **SLA** 的一部分）的关键组件。
