## 概述

混沌工程是一种通过主动注入故障来验证系统容错能力和提升服务韧性的实践，对于保障现代分布式系统的可靠性至关重要。Chaos Mesh 作为一个开源的 Kubernetes 原生混沌工程平台，旨在简化这一过程。其 2.0 版本是一次重要的里程碑发布，通过在易用性、实验编排和故障类型三个核心维度的大幅改进，正朝着构建一个更完整的“混沌工程生态”目标迈进。这使得 SRE 团队能够更高效、更全面地在生产环境或测试环境中模拟真实故障，从而验证和提升系统的 SLI（服务水平指标）表现与 SLO（服务水平目标）的达成率。

## 核心概念

Chaos Mesh 2.0 引入了几个关键的新概念和组件，以支持更复杂的混沌实验场景。

*   **Chaos Dashboard**：一个用于编排和管理混沌实验的 Web 界面。2.0 版本扩展了其功能，使其能够统一管理 Kubernetes 内资源（如 Pod）以及云环境资源（如 AWS EC2、GCP VM）的故障注入，提供了跨环境的一致性体验。
*   **Workflow（原生工作流引擎）**：用于定义和编排多个混沌实验的执行逻辑。它取代了早期与 Argo 的集成方案，原生支持实验的串行、并行执行，并可以嵌入通知和健康检查步骤，从而模拟复杂的故障场景。
*   **Schedule（调度器）**：一个自定义的 Kubernetes 对象，用于更精确地控制周期性混沌实验的执行。它借鉴了 CronJob 的思想，但增加了更明确的语义属性（例如，是否允许多个实验实例同时运行），使得对期望行为的描述更加清晰。
*   **应用层故障注入**：除了传统的系统级故障（如网络、磁盘），2.0 版本正式引入了针对应用层的故障类型，包括 **JVMChaos**（用于 Java/Kotlin 应用）和 **HTTPChaos**（用于 HTTP 协议）。
*   **Chaosd**：一个从 Chaos Mesh 的核心组件 `chaos-daemon` 演变而来的独立命令行工具，专门用于对物理机（非 Kubernetes 环境）进行故障注入。

## 实践

以下内容基于 Chaos Mesh 2.0 的主要功能更新，展示了如何利用新特性进行混沌实验。

### 1. 使用 Chaos Dashboard 管理实验
2.0 版本的 Dashboard 为实验提供了更全面的可视化。用户现在可以在同一个界面中完成以下操作：
*   **创建与管理云环境故障**：直接定义并管理 `AWSChaos`（如模拟 EC2 实例停止）和 `GCPChaos`（如模拟 GCE 实例停止）实验，无需手动编写 YAML。
*   **实验状态可视化**：查看每个实验更详细的执行记录和状态，提升了实验过程的可观测性。

### 2. 使用 Workflow 编排复杂实验
`Workflow` 允许您将多个实验组织成一个自动化流程，以模拟更真实的级联故障。例如，可以创建一个工作流，首先执行网络延迟注入，然后并行执行数据库连接池耗尽和 CPU 压力测试，最后发送通知报告结果。这可以通过定义 `Workflow` 自定义资源来实现。

### 3. 使用 Schedule 定义周期性实验
替代原先简单的 `cron` 和 `duration` 字段，`Schedule` 对象提供了更丰富的配置项来定期运行混沌实验。您可以设置 cron 表达式，并定义并发策略（如 `Forbid` 或 `Replace`），以控制实验的调度行为，避免意外的实验重叠。

### 4. 注入应用层故障
*   **JVMChaos**：通过 Java Agent 技术，无需修改应用代码即可注入故障。支持的故障类型包括方法调用延迟、指定返回值、模拟 OOM 以及抛出自定义异常。
*   **HTTPChaos**：可以劫持目标服务的 HTTP 请求和响应，支持故障注入（如延迟）、中断连接以及修改 Header 或 Body。适用于所有基于 HTTP 协议的微服务。

## SRE 要点

混沌工程是 SRE 实践中主动验证系统可靠性的关键手段。Chaos Mesh 2.0 的改进直接服务于这一目标。

*   **与可靠性的关联**：通过更丰富的故障类型和更强大的编排能力，SRE 团队可以更真实地模拟生产环境中的各类故障（从基础设施到应用协议层），从而更准确地评估系统在真实故障下的表现，驱动可靠性改进。这与管理 [[error-budget]] 直接相关，通过实验消耗 Error Budget 来主动发现问题。
*   **最佳实践**：
    *   **循序渐进**：从非生产环境开始，使用 `Schedule` 建立定期的、可控的“健康检查”式混沌实验。
    *   **场景化设计**：利用 `Workflow` 模拟具体、有业务含义的故障场景（如“某个可用区网络分区时，核心下单流程的表现”），而非孤立地注入故障。
    *   **可观测性先行**：在注入故障前，确保有充足的监控指标（[[SLI]]）和告警，以便准确度量故障的影响范围和持续时间。
*   **常见反模式**：
    *   **无监控的混沌**：在缺乏度量的情况下盲目注入故障，无法确定系统是否按预期处理了故障。
    *   **“爆炸半径”失控**：未在实验中设置充分的实验范围和停止条件，导致故障影响超出预期范围。
    *   **仅关注系统层故障**：忽略应用层（如 JVM、HTTP）的故障注入，导致对系统韧性的评估不完整。
*   **相关指标**：混沌实验是验证 [[SLI]] 和 [[SLO]] 有效性的终极测试。例如，通过注入网络延迟来验证“请求延迟”这一 SLI 在故障下是否仍能满足 SLO。实验的执行和结果应成为可靠性评审的一部分。
