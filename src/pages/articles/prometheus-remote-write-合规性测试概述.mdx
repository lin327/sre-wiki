## 概述

Prometheus 是云原生监控领域的事实标准，其 [Remote Write](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write) 协议是连接 Prometheus 生态系统与外部存储或分析系统的关键桥梁。该协议允许 Prometheus 服务器将收集到的指标数据实时推送至远程存储系统，为数据长期保存、跨集群聚合分析以及构建统一可观测性平台提供了基础。为确保不同工具（如发送端）能够正确、可靠地实现该协议，Prometheus 社区发起了合规性计划（Conformance Program），其中一项核心内容就是 **Remote Write 合规性测试套件**。本文将对该测试套件、测试方法以及当前主要生态工具的合规性测试结果进行概述，帮助 SRE 工程师评估和选择符合标准的组件，以保障监控数据管道的可靠性。

## 核心概念

### Remote Write 协议

Remote Write 是一个基于 HTTP 的推送协议，用于将 Prometheus 格式的时间序列数据发送到远程接收端。它定义了数据的编码格式（通常是 Protocol Buffers 或 Snappy 压缩格式）、必需的元数据标签（如 `__name__`、`job`）以及数据排序、过时处理等行为规范。一个正确实现的发送端必须能够处理计数器（Counter）、直方图（Histogram）、摘要（Summary）等所有指标类型，并在遇到重复标签、空标签或乱序数据等边缘情况时，遵循协议指定的行为。

### 合规性测试套件

合规性测试套件是一组自动化的测试用例，旨在验证某个 Remote Write 发送端实现是否完全符合官方协议规范。测试套件通过模拟各种场景来检查发送端的行为，这些场景包括但不限于：
1.  **基础指标类型**：验证是否正确发送和编码 Counter、Gauge、Histogram、Summary 等类型的数据。
2.  **标签处理**：测试对空标签、重复标签、标签排序、`instance` 和 `job` 标签的自动添加/覆盖（`honor_labels`）等处理逻辑。
3.  **数据完整性**：验证时间戳处理、数据点排序、过时（staleness）标记以及特殊时间序列（如 `up` 指标）的发送。
4.  **协议特性**：测试自定义 HTTP 头（Headers）的发送等。

该测试套件的代码和规范在 Prometheus 的 GitHub 合规性仓库中维护，为生态系统中的所有参与者提供了一个清晰、可验证的质量基准。

## 实践

### 测试框架与运行

合规性测试套件是一个基于 Go 的测试程序，它会启动一个模拟的接收端（接收 Remote Write 数据），然后分别运行针对各个待测发送端（如 Prometheus、Grafana Agent 等）的测试。测试通过比较发送端实际推送的数据与预期数据来判定用例是否通过。

### 当前测试结果示例

根据 Prometheus 官方博客在 2021 年 5 月发布的测试结果，主要工具的合规性得分如下表所示。得分是根据通过的测试用例比例计算的。

| 发送端 (Sender) | 版本 (Version) | 合规性得分 (Score) |
| :--- | :--- | :--- |
| Grafana Agent | 0.13.1 | **100%** |
| Prometheus | 2.26.0 | **100%** |
| VictoriaMetrics Agent | 1.59.0 | 76% |
| Telegraf | 1.18.2 | 65% |
| OpenTelemetry Collector | 0.26.0 | 41% |
| Timber Vector | 0.13.1 | 35% |

**测试用例详解**：每个工具都会运行一系列相同的测试用例。例如，一个完整的测试通过（PASS）列表可能包括：`Counter`, `EmptyLabels`, `Gauge`, `Headers`, `Histogram`, `HonorLabels`, `InstanceLabel`, `Invalid`, `JobLabel`, `NameLabel`, `Ordering`, `RepeatedLabels`, `SortedLabels`, `Staleness`, `Summary`, `Timestamp`, `Up` 等。具体测试输出示例如下：
```
--- PASS: TestRemoteWrite/grafana (0.01s)
    --- PASS: TestRemoteWrite/grafana/Counter (10.02s)
    --- PASS: TestRemoteWrite/grafana/EmptyLabels (10.02s)
    ... (所有用例通过)
```
反之，失败（FAIL）的用例则清晰指出了具体问题领域。例如，一个在 `Ordering` 和 `Staleness` 上失败的工具，可能在处理乱序数据点或标记过时指标方面不符合协议要求。

## SRE 要点

### 与可靠性的关联

使用完全符合 Remote Write 协议的发送端是构建可靠监控数据管道的基础。合规性直接关系到数据完整性和一致性。例如，`Ordering`（排序）测试失败可能导致存储端接收到乱序数据，引发数据覆盖或查询错误；`Staleness`（过时）处理不当可能导致监控系统持续展示已失效的指标，误导故障排查。

### 最佳实践与常见反模式

-   **最佳实践**：
    1.  **优先选择高合规性工具**：在架构选型时，优先考虑通过全部或大部分合规性测试的工具（如 Grafana Agent、Prometheus 自身）。
    2.  **定期验证**：对于自研或定制化的 Remote Write 发送端，应集成此合规性测试套件到 CI/CD 流程中，确保持续符合标准。
    3.  **关注测试细节**：不仅要看总分，更要分析具体失败用例，评估其对自身业务场景的影响。例如，如果业务场景对 `Histogram` 数据精度要求极高，则需特别关注相关测试项。
-   **常见反模式**：
    1.  **忽视合规性**：仅基于功能需求或性能指标选择工具，而忽略其对核心协议的实现质量，导致生产环境出现难以排查的数据问题。
    2.  **使用过时版本**：测试结果与版本紧密相关（如上表）。使用旧版本可能已知存在问题，应及时升级到通过测试的版本。

### 相关指标

虽然合规性测试本身不是 SLI，但它直接保障了监控数据管道中 **数据质量** 这一关键 SLO 的实现。高质量、符合协议的数据是计算有意义 SLI（如延迟、错误率、吞吐量）的前提。合规性差的工具可能导致 SLI 计算错误或数据缺失，进而影响 Error Budget 的评估和可靠性决策。
