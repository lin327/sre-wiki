# AWS上的网络弹性恢复：针对勒索软件和破坏性事件的参考方案

## 概述

网络弹性（Cyber Resilience）是当攻击者已影响环境后，将工作负载恢复到已知可信状态的能力。传统的预防和检测机制固然重要，但网络弹性聚焦于**恢复**：当备份、凭证或部分基础设施本身可能不再可信时，如何恢复出一个可信的环境。对于在 AWS 上运行关键工作负载的组织而言，勒索软件、数据勒索等破坏性事件已成为恢复规划的核心。本页面概述了 AWS 官方提出的一个参考架构，它通过隔离恢复环境、提供防删除的备份存储以及建立验证流水线，确保恢复过程本身是安全可靠的。这是现代 SRE 和平台工程团队在构建全面 [[disaster-recovery]] 策略时必须深入理解的实践。

## 核心概念

该方案的核心思想是**将恢复所依赖的环境、身份和控制平面与被恢复的生产环境进行彻底隔离**。如果生产身份已被攻陷，恢复过程绝不能依赖它。该架构通过 AWS Organizations 中的专用账户来实现这一目标。

### 关键角色与信任边界
1.  **生产账户 (Production Account)**：运行实际工作负载的账户。一旦确认发生网络事件，这些账户将被隔离以供调查，所有恢复工作都不会在此进行。
2.  **恢复账户 (Recovery Account)**：拥有**AWS Backup 逻辑隔离恢复点库 (Logically Air-gapped Vault)** 的专用账户。此账户的核心职责是保护备份的安全性和控制权。它负责配置谁可以共享恢复点库、谁可以发起恢复操作，以及通过**多方批准 (Multi-party Approval, MPA)** 机制审批恢复操作。通过服务控制策略 (SCPs) 将控制权限限制在恢复账户内，可以防止生产账户中被攻陷的身份修改备份策略或删除恢复点。
3.  **隔离恢复环境 (Isolated Recovery Environment, IRE)**：在此账户中执行恢复点的恢复、验证，并在切换前重建新的生产环境。IRE 与生产账户没有信任关系，没有 VPC 对等连接，也没有面向互联网的资源。其目的是形成一个“沙盒”，即使恢复的备份仍然包含威胁，也能将其控制在 IRE 内部，而不会传播回生产环境或互联网。IRE 中的基础设施部署通过 VPC 端点 (AWS PrivateLink) 访问 AWS 服务 API，无需互联网或与生产网络的连接。

这种账户级隔离是确保恢复控制面（如恢复审批）在生产身份被攻陷后仍然有效的基础架构保障。

## 实践

### 1. 利用 AWS Backup 逻辑隔离恢复点库进行防删除保护
逻辑隔离恢复点库是 AWS 提供的原生选项，用于保护备份存储免受删除。它始终锁定在**合规模式**下，由 AWS 服务本身强制执行保留期，在此期间任何主体（包括账户根用户或被攻陷的管理员）都无法删除恢复点。这提供了关键的**防篡改**保障。恢复点实际上存储在 AWS 服务拥有的账户中，而恢复账户中的库对象是治理和访问边界。通过 **AWS Resource Access Manager (AWS RAM)** 可以在账户间共享恢复点，从而让 IRE 能够访问和恢复数据。

### 2. 构建多层验证流水线
仅仅成功恢复备份是不够的，还需要确认恢复的数据是**安全可用的**。一个健壮的验证流水线应在 IRE 内运行，并结合多个层次：
-   **AWS 原生验证**：如 **AWS Backup 恢复测试**，可自动验证备份的可恢复性。
-   **恶意软件扫描**：例如使用 **Amazon GuardDuty 恶意软件保护**对恢复的卷进行扫描。
-   **工作负载特定检查**：例如数据库一致性检查、应用程序不变量验证、与已知良好基线的配置差异对比。这是发现攻击者长期潜伏并修改合法代码或配置的关键。
-   **日志与审计审查**：使用 AWS CloudTrail 和工作负载日志，识别备份时间窗口内意外的身份或配置变更。

只有当 AWS 原生验证和工作负载特定验证都通过后，恢复点才会被批准用于恢复。

### 3. 选择安全的恢复点
对于网络事件，最新的备份往往不是最佳选择，因为攻击者可能在事件被检测到之前就已存在。安全的恢复点选择流程是：
-   基于 CloudTrail、VPC Flow Logs、GuardDuty 等构建事件调查时间线，确定**事件边界**。
-   按照时间倒序，从事件边界之前最近的备份开始评估。
-   对每个候选恢复点运行验证流水线。如果验证失败，则回退到下一个更早的候选点。
-   记录最终选定恢复点的批准者、调查发现和决策依据。

### 4. 执行并行化恢复工作流
恢复工作流包含五个阶段，其中三个阶段可以并行运行以最小化业务中断时间：
-   **阶段1：建立时间线** (与阶段2、4并行)
-   **阶段2：验证候选恢复点** (与阶段1、4并行)
-   **阶段3：批准** (关键闸门点)
-   **阶段4：重建与恢复** (与阶段1、2并行)
-   **阶段5：切换**
其中，阶段3（批准）是数据恢复前的关键控制点，必须确保在批准前完成验证。在阶段4的恢复过程中，应遵循 **Rebuild-Restore-Rotate 框架**。

### 5. 应用 Rebuild-Restore-Rotate 框架
这个框架指导恢复操作中不同组件的处理方式：
-   **基础设施从代码重建 (Rebuild from Code)**：如 IAM 策略、安全组、VPC、Lambda 等。它们来自经过审查、版本控制的基础设施即代码 (IaC) 模板，而非可能已被污染的备份。
-   **数据从备份恢复 (Restore from Backup)**：如 RDS 数据库、EFS 文件系统、EBS 卷等。这些是业务核心数据，必须从经过验证的、不可变的备份中恢复。
-   **凭证轮换或重新签发 (Rotate or Re-issue)**：如访问密钥、数据库密码、API 密钥、证书等。任何可能在事件窗口内暴露的机密都必须更换，不能从备份中沿用。**AWS Secrets Manager** 等工具为此提供了自动化框架。

该框架假设 IaC 仓库本身未被攻击。否则，恢复需从上游可信源开始。

## SRE 要点

### 与可靠性、可观测性及事件响应的关联
-   **增强系统可靠性**：此方案通过架构隔离和防删除保护，显著提升了系统从破坏性事件中恢复的可靠性，降低了恢复过程本身二次失败的风险。
-   **深度依赖可观测性**：方案的成功高度依赖强大的可观测性能力。**AWS CloudTrail**、**Amazon VPC Flow Logs**、**Amazon GuardDuty** 和 **AWS Security Hub** 提供了构建事件时间线、识别事件边界所需的日志、指标和安全事件数据。
-   **标准化事件响应流程**：该方案为应对高级持续性威胁 (APT) 和勒索软件提供了一个结构化的 [[incident-response]] 流程，将恢复操作分解为明确的、可并行的阶段，减少了混乱和决策延迟。

### 最佳实践与常见反模式
-   **最佳实践**：
    -   **永远不要假设生产环境是干净的**：恢复必须在完全隔离的环境中进行。
    -   **实施多方批准 (MPA)**：为恢复操作增加人为审查层，防止单一身份被攻陷后滥用恢复能力。
    -   **定期演练恢复工作流**：不仅要测试备份的可恢复性，还要完整演练从调查、验证、重建到切换的整个流程。
    -   **维护已知良好的配置源**：确保 IaC 仓库、流水线定义和源代码存储在一个独立的、受保护的可信源中。
-   **常见反模式**：
    -   **在原地恢复**：在遭受攻击的同一生产环境中进行修复，无法保证完全清除威胁。
    -   **依赖最新的备份**：对于网络事件，这可能恢复了攻击者的操作。
    -   **忽略凭证轮换**：仅恢复数据和基础设施，但沿用可能已泄露的凭证，导致攻击者能立即重新进入系统。
    -   **将 IRE 与生产环境网络连通**：破坏了隔离原则，使恢复环境可能受到污染或成为攻击跳板。

### 相关指标 (SLI/SLO/SLA)
虽然该方案未直接定义 SLI/SLO，但它是保障更高层级可靠性目标的关键使能器。可以定义和监控以下与恢复能力相关的指标：
-   **恢复时间目标 (Recovery Time Objective, RTO) 的达成能力**：演练中完成并行化恢复工作流各阶段所需的时间。
-   **恢复点目标 (Recovery Point Objective, RPO) 的验证通过率**：定期验证恢复点可恢复性与安全性的成功率。
-   **备份防删除策略有效性**：定期测试无人能（包括根用户）在保留期内删除恢复点。
-   **恢复演练的平均故障修复时间 (MTTR)**：从事件确认到生产切换完成的时间。

这些指标可用于衡量组织 **[[error-budget]]** 在面对安全事件时的韧性，并驱动对恢复能力的持续投资。
