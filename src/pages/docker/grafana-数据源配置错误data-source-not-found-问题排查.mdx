## 概述
在 Grafana 监控系统的运维实践中，通过 [Provisioning（配置即代码）](https://grafana.com/docs/grafana/latest/administration/provisioning/) 功能声明式地管理数据源（Datasource）和仪表板是确保环境一致性和可重复性的关键实践。然而，在启动过程中，有时会遇到 `Datasource provisioning error: data source not found` 这一错误，表明 Grafana 在初始化时无法找到或加载配置文件中指定的数据源定义。这个问题会直接导致数据源配置失败，影响后续的监控数据可视化和告警。

## 核心概念
- **Provisioning (配置即代码)**：Grafana 支持通过 YAML 文件在启动时自动配置数据源、仪表板等资源。这避免了手动在 UI 上操作，使配置可版本化、可审计。
- **Datasource (数据源)**：定义 Grafana 如何连接到外部系统（如 Prometheus, Loki, InfluxDB）以获取数据的实体。
- **`data source not found` 错误**：该错误通常发生在 Grafana 的 Provisioning 服务运行期间。它表示配置文件中引用的某个数据源定义无法被加载或解析，导致整个配置流程中断。需要明确的是，此错误与插件安装失败或签名错误（如日志中出现的 `grafana-lokiexplore-app` 插件签名无效）通常是两个独立的问题，但同时出现时可能增加排查复杂度。

## 实践
根据提供的错误案例，以下是解决此问题的具体排查步骤和实践：

1.  **验证配置文件路径与格式**：
    -   确保在 `docker-compose.yml` 或 Grafana 配置中正确设置了 `GF_PATHS_PROVISIONING` 环境变量，指向包含数据源 YAML 文件的目录。例如：`- GF_PATHS_PROVISIONING=/etc/grafana/provisioning/datasources`。
    -   检查该目录下是否存在至少一个 `.yaml` 或 `.yml` 文件。确认文件内容语法正确，可以使用 YAML 校验工具进行检查。
    -   一个最简单的数据源配置示例如下：
        ```yaml
        apiVersion: 1
        datasources:
          - name: Prometheus
            type: prometheus
            access: proxy
            url: http://prometheus:9090
            isDefault: true
        ```

2.  **检查数据源定义的具体内容**：
    -   **`uid` 匹配问题**：如果仪表板（Dashboard）的 JSON 模型中硬编码了某个数据源的 `uid`，而 Provisioning 文件中创建的数据源 `uid` 与之不匹配，或者在 Provisioning 文件中根本没有指定 `uid`，Grafana 可能会尝试查找一个不存在的 `uid`，从而引发错误。建议在 Provisioning 文件中显式声明 `uid`。
    -   **`name` 与 `type` 字段**：确认 `name` 和 `type` 字段填写正确且拼写无误。`type` 必须与 Grafana 支持的数据源插件标识符一致。
    -   **依赖的插件**：如果数据源类型依赖于一个未安装或安装失败的插件（如案例中的 `grafana-lokiexplore-app`），即使数据源配置文件本身正确，也可能因插件缺失而导致加载失败。需要先解决插件安装问题（例如，解决签名验证或网络连接问题）。

3.  **文件位置与权限**：
    -   确保数据源的 YAML 文件位于 `GF_PATHS_PROVISIONING` 指定的子目录（通常是 `datasources`）下，而不是根目录或其他位置。
    -   检查 Grafana 进程（在容器中通常是 `grafana` 用户）对配置文件和目录是否有读取权限。

4.  **重启与日志分析**：
    -   在修正配置文件后，重启 Grafana 容器。
    -   仔细查看启动日志。成功的配置会在日志中输出类似 `logger=datasource.provisioning t=... level=info msg="Provisioned datasource" name=...` 的信息。如果仍然失败，根据更详细的错误日志进一步定位是哪个具体的 YAML 文件或数据源定义出了问题。

## SRE 要点
- **可靠性与可观测性**：数据源配置失败是影响监控系统可靠性的直接原因。它会导致“监控盲区”，使团队无法获取关键系统的性能指标、日志或链路追踪数据，在故障发生时严重影响事件响应和根因分析的能力。确保 Provisioning 流程的稳定性是保障可观测性基础的重要环节。
- **最佳实践**：
    -   **版本控制**：将所有 Provisioning 的 YAML 文件纳入 Git 等版本控制系统，实现配置变更的可追溯和可回滚。
    -   **健康检查**：在部署流水线中加入配置文件语法校验（如 `yamllint`），避免因低级语法错误导致服务启动失败。
    -   **渐进式部署**：修改配置后，先在非生产环境验证，再通过 CI/CD 管道部署到生产环境。
- **常见反模式**：
    -   **手动修改后不同步**：在 Grafana UI 上修改了数据源配置，但未将变更同步回代码仓库中的 YAML 文件，导致下次部署时被覆盖。
    -   **忽略启动日志**：忽略 Grafana 启动时的 Provisioning 警告或错误，认为服务“能用就行”，这可能隐藏着潜在的配置不一致问题。
- **相关指标 (SLI/SLO)**：
    -   虽然 `data source not found` 错误本身不是一个直接的 SLI，但它的发生频率和持续时间会影响“监控数据可用性”这一更上层的 SLI。SRE 团队可以监控类似 `grafana_config_provisioning_errors_total`（如果存在）或 Grafana 日志中出现该错误的频率，作为配置健康状况的衡量指标。
