# Build a Multi-Tenant Configuration System with Tagged Storage Patterns

## Overview

In modern microservice architectures, configuration management is a core operational challenge. As organizations scale, two major gaps become particularly prominent: handling tenant metadata that changes faster than cache TTLs, and the metadata service itself becoming a performance bottleneck when scaling. Traditional caching strategies force architects to choose between stale tenant contexts (potentially causing incorrect data isolation or feature flags) and aggressive cache invalidation that sacrifices performance and increases load on the metadata service. The **Tagged Storage Pattern** introduced in this article provides a solution. It automatically routes configuration requests to the most appropriate AWS storage service using key prefixes (such as `tenant_config_` or `param_config_`), building a scalable, real-time zero-downtime update multi-tenant configuration service. This pattern is critical in SRE practice because it directly addresses core reliability concerns including configuration drift, cache consistency, and service availability.

## Core Concepts

### Tagged Storage Pattern

The core idea of this pattern is to determine the storage backend based on the configuration item's key prefix. This is a convention-based routing mechanism that enables the configuration service to intelligently select optimal storage. For example:

- **`tenant_config_*`**: Routes to Amazon DynamoDB. Suitable for high-frequency reads with low latency requirements for tenant-specific configurations (such as feature flags, payment gateway settings).
- **`param_config_*`**: Routes to AWS Systems Manager Parameter Store. Suitable for hierarchically managed, lower change-frequency shared parameters (such as API endpoints, database connection strings).

### Strategy Pattern

To enable flexible switching between storage backends, the system employs the Strategy Pattern. This design pattern encapsulates algorithms (storage operations in this case) in independent classes (strategies) that can be interchanged. A `ConfigStrategyFactory` selects the corresponding storage strategy (such as `DynamoDBConfigStrategy` or `SSMConfigStrategy`) from a mapping table based on the request's configuration key prefix. This decoupled design makes adding new storage backends (such as Amazon S3 or Secrets Manager) simple, without modifying core service logic.

### JWT-Based Tenant Isolation

Secure multi-tenant systems require strict tenant data isolation. This solution uses Amazon Cognito for authentication and embeds an immutable `custom:tenantId` claim in the JSON Web Token (JWT). **The key security principle** is that the configuration service **never** trusts the `tenantId` from request parameters, but always extracts the tenant context from the verified JWT token. This fundamentally prevents cross-tenant access attacks.

### Event-Driven Refresh Mechanism

To solve cache staleness and avoid service restarts, the system employs a reactive architecture. Amazon EventBridge monitors Parameter Store changes and triggers AWS Lambda functions. Lambda locates healthy service instances through service discovery (AWS Cloud Map) and notifies them to refresh their local in-memory caches via gRPC calls. This achieves second-level real-time configuration updates that are completely imperceptible to users (zero downtime).

## Practice

### Architecture Components

The entire system is deployed on AWS, with core components including:

1. **Authentication and ingress layer**: Amazon Cognito handles user authentication, AWS WAF provides protection, and traffic enters the internal load balancer through API Gateway and VPC Link.
2. **Service layer**: Two core microservices running on Amazon ECS Fargate:
    - **Order Service**: Processes REST requests and calls the configuration service via gRPC.
    - **Configuration Service**: Exposes a gRPC API, using the strategy factory to dynamically select the storage backend based on key prefixes.
3. **Storage layer**:
    - **Amazon DynamoDB**: Stores tenant-specific configurations using composite keys (`TENANT#{tenantId}` as partition key, `CONFIG#{configType}` as sort key) for efficient querying and logical isolation.
    - **AWS Systems Manager Parameter Store**: Stores shared parameters organized by hierarchical paths (e.g., `/config-service/{tenantId}/{service}/{parameter}`), supporting batch retrieval.
4. **Event and refresh layer**: Amazon EventBridge and AWS Lambda work together to enable push-based configuration update propagation.
5. **Observability**: Amazon CloudWatch centrally collects logs and metrics, AWS Cloud Map manages service discovery.

### Multi-Tenant Data Model

**DynamoDB Schema Example**:

```json
{
  "pk": "TENANT#acme-corp",
  "sk": "CONFIG#payment-gateway",
  "config": { ... },
  "isActive": true,
  "version": 2,
  "createdAt": "2024-01-15T10:30:00Z",
  "updatedAt": "2024-02-20T14:45:00Z"
}
```

- **Composite key design**: The partition key `TENANT#{tenantId}` ensures tenant data co-location, while the sort key `CONFIG#{configType}` allows querying specific configuration types within a tenant.
- **Soft delete and versioning**: The `isActive` field supports soft deletes, and the `version` field supports change tracking and rollback.

**Parameter Store hierarchy**:

```
/config-service/
├── acme-corp/
│   ├── api/
│   │   └── endpoint
│   └── database/
│       └── connection-string
└── globex-inc/
    └── ...
```

This structure supports bulk retrieval via the `GetParametersByPath` API and facilitates access control through IAM policies.

### Strategy Pattern Implementation

Implemented through a `ConfigStrategyFactory` class. It internally maintains a `keyStrategyMap` that maps configuration key prefixes to concrete strategy implementations. Adding a new backend only requires: creating a new strategy class implementing the `ConfigStrategy` interface, and adding a prefix-strategy mapping row in the factory's mapping table.

### Authentication and Tenant Isolation Implementation

The service layer extracts `tenantId` from the verified request context (not the raw request body) and passes it to the storage strategies. This ensures that even if an attacker attempts to tamper with the request payload, they cannot access other tenants' data. For compliance scenarios requiring stronger isolation (such as HIPAA), temporary tenant-scoped credentials implemented via AWS STS (Token Vending Machine pattern) can be considered.

### Event-Driven Refresh Mechanism

**Flow**: Parameter Store change -> EventBridge rule match -> Lambda function triggered (extracts tenantId from path) -> Lambda discovers all healthy configuration service instances via Cloud Map -> Calls each instance's gRPC refresh interface -> Instance updates in-memory cache. This mechanism avoids polling overhead and restart-induced downtime.

### When to Use This Pattern?

This pattern is particularly suitable for:

- Multi-tenant SaaS applications requiring strict tenant isolation and compliance.
- Microservice architectures with complex configuration requirements spanning multiple services and environments.
- Systems where different configuration types have significantly different access patterns (high-frequency reads vs. hierarchical sharing).
- Applications pursuing high throughput (1000+ requests/second) with sub-millisecond response times.

## SRE Takeaways

### Reliability, Observability, and Incident Response Connection

- **Reliability**: This pattern directly improves service availability and data integrity through zero-downtime event-driven updates and strong tenant isolation, avoiding planned downtime or data breach events caused by configuration updates.
- **Observability**: The entire architecture natively integrates with Amazon CloudWatch, enabling centralized monitoring of configuration service latency, error rates, and throughput. EventBridge provides complete audit logs of configuration changes, facilitating post-incident analysis and compliance auditing.
- **Incident response**: Clear configuration data models and event-driven paths simplify fault investigation. If a configuration-related incident occurs, EventBridge event history can quickly identify which tenant's parameter was modified when, accelerating root cause analysis.

### Best Practices and Common Anti-Patterns

- **Best practices**:
    1. **Never trust the client tenant ID**: Always extract the tenant context from a verified identity token (such as a JWT).
    2. **Choose the right storage for the configuration type**: Leverage DynamoDB's high performance for hot data, and Parameter Store's hierarchical structure and change tracking for shared parameters.
    3. **Implement multi-layer caching**: Combine application memory caching and event-driven invalidation to balance performance with freshness.
    4. **Use clear key prefix conventions**: This is the core of tagged storage mode routing and must be clear and consistent.
    5. **Choose secure storage for sensitive data**: Do not store sensitive information in cache; use Parameter Store's SecureString encrypted storage.

- **Common anti-patterns**:
    1. **Single storage backend for all scenarios**: May lead to performance bottlenecks (such as using Parameter Store for high-frequency reads) or cost surges (such as using DynamoDB for rarely accessed configurations).
    2. **Polling configuration checks**: Generates unnecessary API calls and costs, and introduces update delays.
    3. **Restart-based configuration updates**: Unacceptable in production environments, causing connection interruptions and degraded user experience.
    4. **Hardcoded conditional branches in storage logic**: Leads to high code coupling and difficulty in extension and testing.

### Relevant Metrics (SLI/SLO/SLA)

While the article does not directly define SLIs/SLOs, based on its design, the following key reliability metrics can be defined:

- **SLI (Service Level Indicator)**: End-to-end latency (P99) of configuration service gRPC requests, error rate (5xx errors), configuration update propagation time (from Parameter Store change to service in-memory cache taking effect).
- **SLO (Service Level Objective)**: For example, "99.9% of configuration read requests per month have latency below 50ms," or "Configuration updates should propagate to all service instances within 10 seconds of change detection."
- **SLA (Service Level Agreement)**: Usually a commitment to SLOs with breach penalties. The reliability and zero-downtime update features of this architecture help achieve tighter SLAs.
