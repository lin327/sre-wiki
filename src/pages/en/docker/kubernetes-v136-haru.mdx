# Kubernetes v1.36: ハル (Haru)

## Overview

Kubernetes v1.36 (codename "Haru") was released in April 2026, continuing the project's stable quarterly release cadence with 70 enhancements included. For Site Reliability Engineering (SRE) teams, several updates in this release directly impact cluster security posture, observability depth, resource scheduling efficiency, and the long-term reliability foundation of operations. This guide aims to highlight the key changes in v1.36 from an SRE practice perspective, particularly those features that have reached stable status, helping teams plan upgrades, strengthen security configurations, and optimize operational workflows.

## Core Concepts

Kubernetes releases follow a feature maturity model where new features progress through Alpha (experimental), Beta (disabled by default but feature-complete), and Stable (generally available with backward compatibility guarantees) stages. The release theme "Haru" evokes spring, clear skies, and distant horizons, symbolizing the project's continuous evolution toward broader prospects. Understanding the features in this release requires attention to the following core concepts:

*   **Dynamic Resource Allocation (DRA)**: A framework designed to provide more flexible, declarative allocation of hardware resources (such as GPUs, network devices). In v1.36, several DRA-related features have reached Beta or Stable status, signaling that Kubernetes support for heterogeneous compute resource management is maturing, which is critical for SRE teams running AI/HPC workloads.
*   **Workload Aware Scheduling (WAS)**: Uses the `PodGroup` API to treat a group of related Pods as a single logical entity for atomic scheduling, solving the problem of Pod scheduling fragmentation in distributed jobs. This Alpha-stage feature signals that the reliability of complex batch workload scheduling will improve in the future.
*   **Declarative Policies**: For example, the now-Stable `MutatingAdmissionPolicies` allows defining resource mutation logic using Common Expression Language (CEL) within the API server, reducing dependency on external Webhooks and thereby lowering network latency, operational complexity, and attack surface.

## Practices

In response to the v1.36 updates, SRE teams should take a series of proactive measures to convert new features into reliable operational capabilities.

### Upgrade Planning and Security Hardening
The v1.36 release is an excellent opportunity to audit and harden cluster security. First, evaluate and plan migration to **fine-grained Kubelet API authorization** (`KubeletFineGrainedAuthz`, now stable) to replace the broad `nodes/proxy` permissions, following the principle of least privilege. Second, note that the **`Service.spec.externalIPs` field has been deprecated** (scheduled for removal in v1.43) due to man-in-the-middle attack risks (CVE-2020-8554); migrate to LoadBalancer, NodePort, or Gateway API instead. Meanwhile, the **`gitRepo` volume driver has been permanently removed**; ensure workloads do not depend on this feature and use Init containers or tools like `git-sync` instead.

### Observability Enhancement
Improving internal visibility into nodes and components is key to troubleshooting. The now-stable **Node Log Query** (`NodeLogQuery`) feature in v1.36 allows viewing kubelet/kube-proxy logs directly on nodes via `kubectl` without SSH login, simplifying initial node problem diagnosis. Additionally, the now-Beta **component status zpage** (`/statusz`) and **flag zpage** (`/flagz`) endpoints provide real-time build version, startup parameters, and other low-overhead visibility information for core components, which can be integrated into monitoring and audit workflows.

### Resource and Storage Management Optimization
For workloads relying on persistent storage, the now-stable **Volume Group Snapshot** feature allows consistent snapshots across multiple PVCs, providing more reliable backup and recovery points for critical applications. Meanwhile, **Mutable CSINode Allocatable** is now stable, allowing CSI drivers to dynamically update node volume capacity limits, preventing scheduling failures due to stale information. For hardware resources, the **Resource Health Status** (Beta) Pod status reporting can quickly identify whether Pod crashes are caused by device failures (`Unhealthy`/`Unknown` status), accelerating hardware problem identification.

### Preparing for Scheduling and Automation
Although **Workload Aware Scheduling (WAS)** and **HPA scaling to zero based on custom metrics** are still in Alpha, SRE teams should begin evaluating their integration potential with existing batch jobs, queue systems, or cost optimization strategies. These features promise to improve resource utilization efficiency and system resilience in the future.

## SRE Key Points

The Kubernetes v1.36 release profoundly embodies the core principles of SRE culture: "automation, observability, and incremental change."

*   **Connection to Reliability, Observability, and Incident Response**: Stable PSI metrics support (based on cgroupv2) provides SREs with a more granular view of resource pressure than traditional utilization metrics, helping distinguish between system busy states and resource exhaustion, enabling more accurate SLO setting and vertical autoscaling. Component-level zpage endpoints (`/statusz`, `/flagz`) provide fast, standardized component health snapshots during incident response, reducing troubleshooting paths. The Node Log Query feature directly simplifies on-site information collection for node-level failures.

*   **Best Practices and Common Anti-Patterns**:
    *   **Best Practices**: After upgrading to v1.36, actively enable and utilize `KubeletFineGrainedAuthz` and `NodeLogQuery` to improve security and operational efficiency. When planning storage operations, evaluate adopting `VolumeGroupSnapshot` to protect stateful applications. Track the progress of DRA and WAS to prepare for future management of special hardware resources like GPUs.
    *   **Common Anti-Patterns**: Ignoring deprecation warnings for `Service.externalIPs` and continuing to use that field exposes security risks. Failing to clean up or migrate workloads that depend on the removed `gitRepo` volume driver after upgrading will cause Pods to fail scheduling. When running high-density containers on nodes, not utilizing PSI metrics or DRA resource status feedback may prevent timely detection of resource contention or hardware failures.

*   **Related Metrics (SLI/SLO/SLA)**: v1.36 provides new tools for defining more precise SLIs. For example, the new **native histogram** (Alpha) support enables more efficient and accurate collection of kube-apiserver latency distributions, providing high-fidelity data for API response time SLOs. The `ComponentStatusz` endpoint can serve as an SLI data source for component version consistency. Meanwhile, `allocatedResourcesStatus` provides a direct metric for Pod restart frequency due to hardware failures, which can be used to define hardware reliability SLOs.

## Other Important Updates and Deprecations

In addition to the highlights above, v1.36 includes other updates significant for SRE:
*   **Ingress NGINX Retirement**: This controller was retired in March 2026 and has stopped receiving security updates. SREs should plan migration to other Ingress solutions, such as Gateway API implementations or cloud-native load balancers.
*   **SELinux Volume Labeling Acceleration (Stable)**: This feature applies SELinux labels via `mount -o context=XYZ`, improving mount performance, but may introduce breaking changes in the future (such as when sharing volumes on the same node). Audit SELinux policy usage in your cluster.
*   **Constrained Impersonation (Beta)**: Tightens the user impersonation mechanism by requiring impersonators to have both impersonation permissions and operation permissions, preventing privilege escalation and enhancing security in multi-tenant environments.
