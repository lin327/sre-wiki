# 5 Software Supply Chain Security Best Practices for Development Teams

## Overview

Software supply chain security is a critical practice for ensuring the integrity of software components, dependencies, and build environments throughout the entire process from development to deployment. As malicious software attacks against open-source package managers (such as npm) become increasingly automated and sophisticated, and third-party data breaches account for a growing proportion year over year, converting supply chain security awareness into repeatable engineering practices has become essential. For teams building and deploying container-based workloads, a structured supply chain security program is no longer optional — it is a cornerstone for ensuring system reliability.

## Core Concepts

Understanding the following core concepts is the foundation for practicing supply chain security:

*   **Software Bill of Materials (SBOM)**: A machine-readable document that details all components, libraries, and their version information contained in a software product. It is the foundation for vulnerability management and compliance auditing.
*   **Build Provenance**: Answers "where was this artifact built, by which system, and from what source code?" It provides complete context about the artifact's build process and is key to verifying artifact trustworthiness.
*   **SLSA Framework**: Stands for "Supply-chain Levels for Software Artifacts." It defines a progressive build integrity maturity model (from Level 1 to Level 4), providing teams with a clear path to improve the security and transparency of their build platforms.
*   **Vulnerability Exploitability eXchange (VEX)**: Used in conjunction with SBOMs to declare whether a specific vulnerability is actually exploitable in the current artifact context, thereby significantly reducing vulnerability alert noise and focusing on risks that truly need to be remediated.

## Practice

This section describes five key practices organized around the natural flow of software delivery.

### 1. Start from Trusted Content

**Choose verified, minimal base images**: Every container image inherits the security posture of its base image. Production environments should build from base images that are continuously maintained, provide complete SBOMs, have SLSA Level 3 or higher build provenance, and cryptographic signatures. Minimal images (such as those with unnecessary shells and tools removed) effectively reduce the attack surface.

**Pin dependencies and verify integrity**: Dependency pinning is a simple and effective practice for preventing upstream accidental or malicious changes from flowing into builds. Use SHA256 digests to pin container images rather than mutable tags (such as `python:3.12`). Also, use lock files to precisely pin language-level dependencies (such as npm, pip), and verify lock file hashes in CI. If the dependency hash pulled by the build system does not match the submitted hash, the build should fail.

### 2. Harden the Build Pipeline

**Enforce build provenance and attestation**: Configure the CI/CD system to generate signed provenance conforming to the SLSA framework (typically using in-toto attestation format) for every image build. These attestations cryptographically link the artifact to its source code commit, build configuration, and builder identity, serving as the basis for deployment policy verification.

**Harden CI/CD infrastructure**: The build pipeline itself is a high-value attack target. Hardening measures include: providing isolated, temporary environments for each build job; limiting the secrets available to build jobs; pinning CI plugins such as GitHub Actions to full commit SHAs; enforcing code review and status checks before merging to release branches.

### 3. Verify Before Deployment

**Continuously generate and consume SBOMs**: Generate SBOMs at every build, attach them as attestations to images, and consume them downstream in admission controllers, vulnerability scanners, and license compliance checks. When new CVEs are disclosed, teams with current SBOMs can identify affected workloads within minutes. Combining VEX information can further improve remediation targeting.

**Integrate vulnerability analysis into developer workflows**: Vulnerability scanning is most effective when results and remediation guidance are presented directly in developers' existing workflows (such as PRs, local builds, CI), rather than relying on separate security department dashboards. This achieves "shift-left" security, allowing issues to be discovered and resolved before they enter the registry.

### 4. Control Access and Enforce Policies

**Manage registry access and image policies**: Implement registry access controls, restrict allowed image sources (such as only allowing verified publishers or internal builds), and require signature verification before images enter production. This ensures production only consumes reviewed, policy-compliant images.

**Implement least privilege throughout the pipeline**: Assign each credential, token, and API key in the pipeline only the minimum permissions needed to complete its specific task. For example, a build service account should not have permission to push to the production registry, and a deployment token should not be able to modify build configuration. Additionally, enable phishing-resistant multi-factor authentication on all developer and CI/CD accounts.

### 5. Monitor, Respond, and Improve

**Implement runtime monitoring**: Static analysis and build-time scanning cannot capture all threats. Runtime monitoring identifies attacks that have bypassed pre-deployment controls by detecting unexpected container behavior (such as outbound network connections that should not exist, file system modifications on immutable images). It requires anomaly detection based on behavioral baselines, not just matching known malicious signatures.

**Build incident response into the supply chain program**: When supply chain incidents occur, response speed depends on prior preparation. Plans should include: identifying all artifacts produced by the compromised component (provenance and SBOMs are critical here), revoking and rotating potentially exposed credentials, rebuilding affected images from verified sources, and communicating with downstream consumers of the software.

## SRE Key Points

*   **Connection to Reliability, Observability, and Incident Response**: Supply chain security is directly related to system reliability. A compromised dependency can cause production outages or data breaches. Observability is not only for performance monitoring but should also be applied to [[observability]] supply chain security, such as monitoring runtime anomalous behavior. Clear provenance and SBOMs can greatly accelerate "blast radius" analysis during incident response, identifying the scope of impact, and are core data support for incident response plans.
*   **Best Practices and Common Anti-patterns**:
    *   **Best Practice**: Adopt a "security as engineering" philosophy, treating the above practices as repeatable, automated engineering tasks rather than one-time compliance checks.
    *   **Common Anti-pattern**: Allowing arbitrary pulling of unverified public images in development environments; generating SBOMs only once at release time and archiving them; CI/CD pipelines having excessively high persistent permissions; ignoring runtime anomalous behavior monitoring.
*   **Related Metrics (SLI/SLO/SLA)**:
    *   **SLI**: Consider "proportion of images with valid build provenance," "active component coverage with generated SBOMs," "mean time to remediation for critical vulnerabilities."
    *   **SLO**: Set targets such as "100% of production container images come from policy-approved sources," "identification time for affected services after new critical CVE disclosure is within 1 hour."
    *   These metrics ensure that supply chain security practices are not just on paper, but have measurable, reliability-oriented goals.
