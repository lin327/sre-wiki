## Overview

Seth Larson, security developer-in-residence at the Python Software Foundation, has identified an increasingly common security ambiguity in modern integrated development environments (IDEs): When built-in AI code completion tools suggest and potentially autocomplete code with serious security vulnerabilities, how should we define and address the risk? This incident not only challenges the classification framework of traditional vulnerability disclosures (such as CVE), but also places new requirements on SRE teams that rely on the security of development tool chains. Under the trend of "everything can be programmed and everything can be automated", ensuring that security is injected from the source of code writing has become a key part of ensuring system reliability and observability.

## Core concepts

### AI-driven code completion
Modern IDEs such as PyCharm are increasingly integrating code completion capabilities based on deep learning models. These tools predict and suggest next lines or blocks of code by analyzing local code context or vast open source code bases. Its core benefit is to improve development efficiency, but it also introduces a key risk: the model's training data or learning model may contain bad practices or known vulnerable code patterns.

### Security vulnerabilities and vulnerability classification
Security vulnerabilities generally refer to flaws that can be exploited to violate system security policies (such as confidentiality, integrity, availability). Systems such as Common Vulnerability Exposures (CVE) are used to standardize the classification of widely recognized and confirmed vulnerabilities. The core of Larson's case is: How should the responsible party be defined for unsafe code "suggested" by AI tools that can be accepted by developers? Does it constitute a reportable and trackable "vulnerability"? This involves the scope of software supply chain security.

### Coordinated Disclosure Policy
This is a practice in security research that aims to work with software vendors to give vulnerabilities a reasonable window of time to fix them before they are widely exploited. Larson said that after he reported the issue to JetBrains, they cited the Coordinated Disclosure Policy, suggesting that it might be considered a security issue, but at the same time informed that it was not a "direct security vulnerability." This contradictory response highlights the lack of industry consensus on this emerging issue.

## Practice

Faced with the security risks that AI code completion tools may introduce, SRE and security teams should adopt proactive practices and incorporate them into existing security development and operation and maintenance processes.

1. **Establish a security assessment process for AI-generated code**:
    * In the CI/CD pipeline, integrate the Static Application Security Testing (SAST) tool, which not only scans handwritten code, but also performs equally strong security analysis on code generated by AI suggestions (especially newly submitted code blocks).
    * Add a check on "Code Source" to the Code Review checklist to clearly identify which parts use AI completion and encourage reviewers to conduct a more careful security review of these parts.

2. **Update security policy and developer guide**:
    * Clearly formulate a security policy regarding the use of AI code generation tools, stipulate its allowed usage scenarios, prohibited operations (such as modules directly used to process authentication, encryption or sensitive data), and emphasize that developers are fully responsible for the final submitted code.
    * Educate development teams on the limitations of AI tools, particularly their potential to replicate unsafe patterns in historical code, and on how to verify and harden AI-generated code.

3. **Implement deep monitoring and observability**:
    * Monitor newly introduced code patterns. If multiple services or repositories are found to have similar suspicious code generated by AI tools in similar locations, it may indicate a widespread tool chain risk that requires urgent evaluation.
    * Incorporate the version and model fingerprint of the code generation tool into the software bill of materials (SBOM) so that when systemic security issues are found in a specific model, affected services can be quickly located.

## SRE Key Points

* **Association with reliability and observability**: A seemingly small SQL injection or dependency package vulnerability suggested by AI may lead to large-scale data leakage or service interruption, directly affecting the reliability and SLA of the system. SREs need to consider development toolchain vulnerabilities as potential sources of system failure modes and integrate their monitoring into the overall observability strategy.
* **Best Practices and Common Anti-Patterns**:
    * **Best Practice**: Treat AI coding tools as "junior developers" and subject them to rigorous "code reviews". Establish automated gatekeeping to prevent the incorporation of code containing known high-risk AI generation patterns. Actively communicate with tool manufacturers, submit cases of bad behavior you find, and promote industry improvements.
    * **Common anti-patterns**: Blindly trusting AI recommendations and accepting code completion without review; Underestimating the risk by thinking "this is generated by a local tool, not a network attack"; Giving up on reporting and tracking such issues due to difficulty in classifying vulnerabilities.
* **Relevant Metrics (SLI/SLO/SLA)**: While it is currently difficult to directly develop an SLO for "AI code completion security", SREs can promote the definition of relevant **SLI**, such as:
    * `AI-Generated-Code-Critical-Vulnerability-Detection-Rate`: The number/proportion of critical vulnerabilities discovered by AI-generated code sections during code review or SAST.
    * Such SLIs can be tied into broader security reliability goals, such as "the number of emergencies caused by exploitable vulnerabilities introduced by the development tool chain should approach zero."
