# Identity and Access Management Whitepaper - CNCF Blog

## Overview

Under cloud-native architecture, as systems become increasingly distributed, dynamic, and automated, identity has become the new security boundary. Traditional network perimeter-based authentication and authorization methods are difficult to cope with short-lifecycle workloads, frequent inter-service communications, and zero-trust security requirements. Identity and Access Management (IAM) is no longer an optional security component but a cornerstone of building secure, reliable, scalable cloud-native systems. For the SRE team, a robust IAM system is a key prerequisite to ensure trust between services, achieve fine-grained access control, automate operation and maintenance operations, and minimize the explosion radius.

## Core concepts

### From perimeter security to zero trust security
Traditional network security models rely on clear internal and external boundaries (such as firewalls) and assume that the internal network is trusted. However, in a dynamic cloud-native environment, where the IP addresses and locations of workloads (containers, pods, virtual machines) are constantly changing, the boundaries of network boundaries become blurred. **Zero Trust** architecture abandons the assumption of "trusting the internal network" and its core principle is "never trust, always verify." It requires strict authentication and authorization for every access request, whether the request comes from internal or external sources.

### Workload identity: SPIFFE
**SPIFFE (Secure Production Identity Framework For Everyone)** is a standard framework for implementing workload identity in a cloud-native environment. It provides a globally unique, verifiable identity (SPIFFE ID) for each workload, usually presented in URI format (such as `spiffe://trust-domain/team-a/service-b`). SPIFFE securely implements mutual authentication (mTLS) between services by issuing a short-term, automatically rotating SVID (SPIFFE Verifiable Identity Document, usually an X.509 certificate or JWT token) to prove its identity.

### Authorization architecture: PEP/PDP
Modern authorization decisions often follow the Policy Enforcement Point/Policy Decision Point (PEP/PDP) architectural pattern to achieve separation of concerns and centralized management of policies.
- **Policy Decision Point (PDP)**: Acts as the central brain responsible for evaluating access requests and making "allow" or "deny" decisions based on policy.
- **Policy Enforcement Point (PEP)**: As a gatekeeper, deployed at the entrance of protected resources (such as API gateway, Sidecar proxy), it intercepts requests, forwards them to PDP query decisions, and executes the policy (release or block) based on the returned results.
- **Policy Information Point (PIP)**: PDP usually needs to obtain the context attributes of the request (such as user role, resource label) from PIP to assist decision-making.

## Practice

### Verify workload identity
In a Kubernetes environment, SPIFFE ecosystems such as Istio or Linkerd can be leveraged to automatically assign and manage workload identities to Pods.
1. **Install and configure the service mesh**: Deploy Istio or Linkerd with SPIFFE enabled as the data plane.
2. **Declare service identity**: In Kubernetes `Service` or custom resource, define the SPIFFE ID of the workload through annotations or labels. For example, set `spiffe://cluster.local/ns/bookinfo/sa/reviews` for the `reviews` service.
3. **Automatic certificate issuance**: The control plane of the service mesh (such as Istiod) will automatically issue a short-term SVID to the matching Pod and use it in mTLS through the Envoy Sidecar proxy without application code modification.

### Implement fine-grained authorization control
Combined with PDP, attribute-based access control (ABAC) or role-based access control (RBAC) can be implemented.
1. **Define policy**: Use a common policy language (such as Rego of Open Policy Agent) to write authorization rules. For example: "Allow only requests from `spiffe://cluster.local/ns/default/sa/frontend` to read the `products` database".
2. **Deploy PDP**: Deploy OPA as a PDP as a Sidecar or centralized service.
3. **Integrated PEP**: Configure proxies such as Envoy to send access requests for specific paths as context to OPA for evaluation, and execute the allow/deny decision it returns.

## SRE Key Points

### Association with reliability, observability, incident response
- **Reliability**: Correct IAM settings can prevent unauthorized operation and maintenance operations (such as accidental deletion of Pods, incorrect configuration changes) and avoid human-caused failures. Identity audit logs allow you to trace back who performed the actions that caused the failure and when.
- **Observability**: Injecting contextual information such as SPIFFE ID and user identity into logs, indicators and distributed tracing can greatly improve the efficiency of troubleshooting. You can quickly correlate an erroneous request to a specific service instance or user.
- **Incident Response**: In security incident response, accurate identity information is critical. IAM logs and policies can help SRE teams quickly locate compromised lateral movement paths, revoke compromised credentials, and block attacks based on identity rather than temporary IP.

### Best practices and common anti-patterns
- **Best Practices**:
    - **Default Deny**: All policies should deny access by default and then explicitly grant the necessary permissions.
    - **Principle of Least Privilege**: Grant workloads and users only the minimum set of permissions required to complete their tasks.
    - **Short-term Credentials**: Extensively use short-term, automatically rotating credentials (such as SPIFFE SVID, temporary API keys) to reduce the risk of leakage.
    - **Centralized Policy Management**: Use PDP to centrally manage policies instead of hardcoding permission logic in application code.
- **Common anti-patterns**:
    - **Equating network location with identity**: A request should not be trusted just because it comes from an "internal" network.
    - **Static, long-term valid credentials**: Difficult to manage and highly risky if compromised.
    - **Overbroad Permissions**: Granting `*` or `admin` permissions for convenience violates the principle of least privilege.

### Related Indicators (SLI/SLO)
- **SLI (Service Level Indicator)**:
    - **Authorization Decision Delay**: P99 delay in PDP processing of authorization requests.
    - **Authorization Success Rate**: The proportion of legitimate requests that are rejected due to policy configuration errors.
    - **Voucher Issuance Success Rate**: The success rate of the workload obtaining a new SVID.
- **SLO (Service Level Objective)**:
    - P99 delay of PDP should be less than 50ms.
    - The availability of authentication/authorization services should be 99.99%.
    - The incidence of unauthorized access events should be 0.
