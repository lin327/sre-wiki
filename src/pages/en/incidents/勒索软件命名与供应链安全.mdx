# On Ransomware Naming - Prometheus Blog

## Overview

In the open source and cloud native ecosystems, well-known tool and project names are often highly recognizable. However, this reputation can also be exploited by malicious actors; for example, a ransomware group recently started using "Prometheus" and "Thanos" as the names of its malware families. Although such behavior does not directly affect existing software, it reminds us that **software supply chain security** is the cornerstone of Site Reliability Engineering (SRE) to ensure system reliability and security. This page is intended to summarize SRE best practices distilled from this incident.

## Core concepts

### Supply Chain Attack
Supply chain attacks are a security threat that targets software development, distribution, and deployment processes. The attacker does not attack the target system directly, but penetrates into upstream dependency libraries, build tools, software warehouses or distribution channels, implanting malicious code or tampering with software packages. When users download and deploy this software from tainted sources, they unintentionally introduce risks.

### Software supply chain security
This is a core practice in the SRE and DevSecOps world that aims to ensure the integrity and authenticity of the software delivery pipeline from code writing, building, storage to final deployment. It includes verifying software sources, verifying software integrity, and maintaining a trustworthy software dependency relationship. [[software-supply-chain-security]]

## Practice

In order to deal with brand misappropriation and potential supply chain risks, the SRE team must establish and implement strict software acquisition and verification processes. Here are the practical paths to follow, in order of priority, when deploying third-party software such as Prometheus and Thanos:

1. **Obtain and verify from official sources**: Always download binaries from the project's official release page and strictly verify the provided checksum (such as SHA256). This is the most basic and critical step.
    * Prometheus official release page: https://github.com/prometheus/prometheus/releases
    * Thanos official release page: https://github.com/thanos-io/thanos/releases

2. **Use official container image**: Pull the image from the official container image repository controlled by the project party.
    * Prometheus: `quay.io/repository/prometheus/prometheus` or `docker.io/prom/prometheus`
    * Thanos: `quay.io/repository/thanos/thanos` or `docker.io/thanosio/thanos`

3. **Through trusted distribution channels**: Use the official software source of the operating system distribution (such as installation through `apt`, `yum`) or the company's internal security-audited mirror warehouse.

4. **Reliance on internal build and verification**: Within the enterprise, a dedicated build and verification team (such as through a GitOps pipeline) uniformly builds, scans, signs, and distributes software artifacts. The SRE team should consume these internal trusted artifacts.

5. **Build from source code yourself**: For environments with extremely high security requirements, you can obtain the code from the official source code repository and build it according to the official documentation to fully control the build environment.

The core principle is: **You should not use software unless you can reasonably trust its specific source and the entire supply chain. **

## SRE Key Points

### Association with reliability, observability, incident response
* **Reliability**: Supply chain security is directly related to the stability of the production environment. Introducing tampered or malicious software components can lead to data leakage, service disruption, or extortion.
* **Observability**: Monitoring the pipeline itself (such as using [[Prometheus]] to monitor the build system) and runtime software behavior (such as abnormal network connections, high resource usage) are important means of detecting potential supply chain attacks.
* **Incident response**: When a security incident occurs (such as the use of software components marked as malicious), a clear software bill of materials (SBOM) and deployment records can greatly speed up the [[incident-response]] process and help quickly locate the affected scope and components.

### Best practices and common anti-patterns
* **Best Practice**:
    * **Automated verification**: Integrate software package checksum verification and image signature (such as Cosign) into the automated deployment pipeline.
    * **Enforce least privilege**: Only install and run necessary components to reduce the attack surface.
    * **Regular audit dependencies**: Use tools to regularly scan software dependencies in the production environment to identify known vulnerabilities or suspicious sources.
    * **Build an internal knowledge base**: Record verified software sources and versions as the team's standard configuration reference.
* **Common anti-patterns**:
    * **Trust Unknown Sources**: Download software from unofficial sources (such as personal blogs, third-party sites recommended by search engines).
    * **Ignore updates**: Not updating software versions with known vulnerabilities for a long time due to concerns about compatibility.
    * **Lack of Verification**: Package integrity or signature is not verified before deployment.

### Related indicators (SLI/SLO/SLA)
Although supply chain security itself does not directly define SLI, it can be integrated into the reliability system in the following ways:
* **SLI**: The "proportion of software deployed in the production environment and verified by official signatures" can be used as a security SLI. For example: 100% of core monitoring components like Prometheus are built and signed via an internal controlled pipeline.
* **SLO**: Set goals based on the above SLI, such as "100% signature verification of core observability components for all production environments at deployment time."
* **SLA**: This is usually a constraint on internal teams to ensure that operation and maintenance practices comply with security specifications, thereby indirectly guaranteeing the commitment to data integrity and service continuity in the SLA for external user services.
