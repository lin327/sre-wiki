# What is Software Supply Chain Security? | Docker Blog

## Overview

Software supply chain security is a core element in SRE practice for ensuring system reliability and security. It goes beyond traditional application security, focusing on the security of all components and processes throughout the entire software delivery lifecycle — from source code, third-party dependencies, build systems, container image registries, to production environment deployment. In modern microservice and container-based architectures, software is often assembled from a vast number of open-source components. A compromise at any point can trigger a large-scale security incident, directly affecting service availability and data integrity. Therefore, treating it as a critical infrastructure practice rather than a compliance check is essential for building resilient delivery pipelines.

## Core Concepts

The core of software supply chain security lies in the explicit management and verification of the **chain of trust**. Unlike application security, which primarily focuses on vulnerabilities in team-developed code, supply chain security concerns **all dependencies** of the code and **all systems** it comes into contact with on its path to production. This is particularly prominent in containerized environments, where a container image contains application code, operating system dependencies, runtime environment, and configuration — vulnerabilities in any layer of the image can be brought into production.

**Expanded Attack Surface**: Since modern software is assembled rather than written from scratch, when developers introduce a package, they are essentially making a series of **implicit trust decisions** — trusting the package's functionality, the maintainer's identity, the registry's integrity, and its ability to provide continuous security updates. Attackers exploit these implicit trust relationships through methods such as dependency confusion, typosquatting, and maintainer account takeover. Additionally, CI/CD pipelines have become high-value targets due to their possession of deployment credentials and production environment access.

**Transparency is Key**: Achieving supply chain security relies on transparency tools. The **Software Bill of Materials (SBOM)** is a key component — it is a machine-readable inventory listing all components, versions, licenses, and their relationships within a software artifact. Automatically generated SBOMs enable organizations to quickly answer the question "Are we affected? Where?" when new vulnerabilities are disclosed, which is the foundation for rapid incident response. Related to this is **Provenance**, which provides verifiable information about how, by whom, and from where an artifact was built.

## Practice

Building software supply chain security is a layered, incremental process that requires implementing specific controls at every stage of the software delivery pipeline.

### 1. Source Code and Dependency Security
Begin establishing the security foundation at the code commit stage. Implement strict repository access controls, commit signing (such as GPG or SSH signatures), and branch protection rules to ensure only authorized changes can be merged into the codebase. For dependency management, it goes far beyond just keeping things updated:
- Use lock files and hash verification to pin dependency versions.
- Verify that package sources are trustworthy, and use private registries or curated package sources to control what enters the dependency tree.
- Perform trust assessments on transitive dependencies (dependencies of dependencies).

### 2. Build Process Security
The build system is where source code is transformed into deployable artifacts — its compromise would result in all outputs being tainted.
- **Build Environment Isolation**: Run builds in clean, temporary, isolated environments for each build.
- **Generate Transparency Artifacts**: Automatically record the build process (provenance) and generate SBOMs.
- **Adopt the SLSA Framework**: Follow the **Supply-chain Levels for Software Artifacts (SLSA)** framework, targeting **SLSA Build Level 3**, which means builds run on hardened platforms, provenance is non-falsifiable, and build environments are isolated to prevent cross-build tampering.

### 3. Container Image and Registry Security
Container images are the primary delivery artifact in modern supply chains.
- **Use Trusted Base Images**: Use minimal base images that are regularly rebuilt based on upstream security fixes and come with SBOMs, vulnerability scan results, and cryptographic signatures. Transparency is key — truly trustworthy images will display all vulnerabilities, including unpatched ones, so teams can make informed decisions.
- **Registry Governance**: Implement image signing and verification policies (for example, using Notation or Cosign), control who can push/pull images, and enable audit logs for registry interactions. Treat the registry as a "trusted source of truth," not just an artifact dumping ground.
- **Pipeline-Integrated Scanning**: Perform continuous vulnerability scanning after image build, at push time, and before production deployment to discover and fix issues early.

### 4. Deployment and Runtime Security
This is the last line of defense in the supply chain.
- **Deployment Policy Enforcement**: Use admission controllers (such as Kubernetes Admission Webhooks) or deployment policies to only allow pulling images from trusted registries that are signed and pass policy checks (such as vulnerability thresholds).
- **Runtime Protection**: Deploy runtime security monitoring to detect anomalous behavior (such as unusual network connections, file access) to discover compromised components that may have bypassed pre-deployment defenses. Use sandboxed execution environments to limit the blast radius.

## SRE Key Points

Software supply chain security is closely linked to the core SRE responsibility — ensuring system reliability. A secure supply chain is a prerequisite for a reliable delivery pipeline.

- **Connection to Reliability**: Supply chain attacks (such as malicious dependency injection, base image backdoors) can lead to service outages, data breaches, or performance anomalies, directly impacting SLOs. Establishing verification mechanisms (such as image signature verification, SBOM checks) is **proactive defense** against such failures. When new vulnerabilities (CVEs) are disclosed, having accurate SBOMs and deployment inventories can greatly reduce **Mean Time To Recovery (MTTR)**, as teams can quickly locate affected services and environments.
- **Observability**: Supply chain security activities themselves need to be observed. Events such as SBOM generation, image signature verification failures, high-severity vulnerabilities discovered by scanning, and pull attempts blocked by deployment policies should be integrated into existing monitoring and alerting systems, making them part of **observability** data.
- **Incident Response Integration**: Supply chain security incidents should be incorporated into standard **incident response** processes. Plans need to include: how to isolate affected services when trusted dependencies or base images are compromised, how to quickly verify remediated artifacts, and how to roll back to a known clean state.
- **Best Practices and Anti-patterns**:
    - **Practice**: Enforce supply chain security policies as part of **Infrastructure as Code (IaC)**, rather than relying on process documentation. Assume some components will eventually be compromised, and design systems with **minimal blast radius** through the **principle of least privilege**, build environment isolation, and runtime sandboxes.
    - **Anti-pattern**: Treating supply chain security as a **one-time compliance check** before going live. Ignoring automation and relying on manual reviews. Hiding vulnerability scan results to make reports "look better." Allowing base images to be pulled from arbitrary public sources.
- **Related Metrics (SLI/SLO/SLA)**:
    - **SLI**: Trackable metrics include: proportion of signed image deployments, SBOM coverage rate, vulnerability scan execution rate in pipelines, average time from discovery to remediation of high-severity vulnerabilities.
    - **SLO**: Internal targets can be set, such as "100% of production containers use signed and verified base images," "100% SBOM coverage for critical service base images."
    - **SLA**: While supply chain security itself is typically not directly defined in external SLAs, its failure (such as service disruption due to supply chain attacks) will affect **availability** SLA achievement. Maintaining supply chain security is a foundational capability for fulfilling availability commitments.
