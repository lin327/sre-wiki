# Isolation Requirements for Autonomous AI Agents: From Containers to MicroVMs

## Overview

With the rise of AI coding agents (Claude Code, Copilot, etc.), developers are granting these autonomous agents real access and execution privileges to their codebases. This fundamentally changes the security threat model: workloads are no longer known code from "trusted" sources but unknown commands autonomously generated, dependency-installed, and executed by a "tenant." Traditional container isolation (shared-kernel Docker containers) was designed for known, audited code and struggles with this high-privilege, autonomous, unpredictable new tenant. This forces isolation technology evolution toward stronger boundaries like microVMs, providing robust isolation while maintaining lightweight developer experience.

## Core Concepts

### Trust Spectrum and Isolation Matching

An effective security model matches isolation strength to workload **trust profile**:

1.  **Left (High Trust)**: Self-written, team-reviewed code. Standard containers suffice.
2.  **Middle**: CI/CD pipelines, supervised AI agents. Hardened container policies (seccomp, capability stripping, strict network policies).
3.  **Right (Low Trust/Autonomous)**: **Autonomous AI agents**. Nobody reviews every command. Trust model: "I need something operating unsupervised; I want failure mode to be 'confined in a disposable VM' not 'on my laptop.'" This is microVM territory.

### MicroVM Isolation

Docker Sandboxes run each AI agent session in an independent **microVM**:

*   **Kernel isolation**: Each microVM runs its own Linux kernel and complete Docker Engine. Agent commands only affect microVM internals.
*   **Credentials never cross borders**: API keys stored in host OS keychain. Agent network requests go through host-side proxy that transparently injects credentials; **credential values never stored in microVM**.
*   **Isolation, not limitation**: Within boundaries, agents can run as root with full Docker Engine control (legitimately needing package installation and image building). Isolation ensures these operations' effects don't overflow.

### Network Policies and Transparent Proxy

All outbound traffic must pass through host-side proxy:
*   **Proxy policies**: `Open`, `Balanced`, `Locked Down` presets based on domain names.
*   **TLS inspection**: Proxy terminates TLS, performs domain checking, re-encrypts with own certificate.
*   **Inherent limitations**: **Proxy filtering is domain-based, not content-based**. Allowing `github.com` means allowing anything on that domain (including public Gist creation). **Domain fronting** is also difficult to defend against.

### Shared Workspace: Necessary Attack Surface

For working with real codebases, **host and sandbox share workspace directory at the same absolute path**.

*   **Bidirectional sync**: Files modified by agent in sandbox sync to host; host new commits sync to sandbox.
*   **Stealth attack surface**: Shared area includes **implicitly executed files** like Git hooks (`.git/hooks/`), CI configs, `package.json` scripts, Makefiles. These are often unreviewed by developers.
*   **Mitigation**: Isolation cannot solve this; it requires developer discipline: review agent output like untrusted contributor code. Use `git diff` on `.git/hooks/` directory, or use `--branch` flag for isolated Git worktrees.

## Practice

### Architecture

Client-first architecture running on developer's machine:
1.  **MicroVM**: Hypervisor.framework (macOS), Windows Hypervisor Platform, or KVM (Linux).
2.  **Internal Docker Engine**: Complete, independent Docker daemon and image cache per microVM. Multiple sandboxes don't share layers.
3.  **CLI Management**: `sandbox` CLI (or `sbx`) manages sandboxes.
4.  **Workspace Mounting**: Volume mounts map specified host directories to same path inside sandbox.

### Workflow

```bash
sandbox create --name my-ai-session --workspace .
sandbox attach my-ai-session --agent claude
# All operations in isolated environment
sandbox destroy my-ai-session
```

## SRE Essentials

### Reliability Trade-offs

*   **New failure domains**: MicroVM manager, proxy network layer are new components requiring availability and performance monitoring.
*   **Immutable infrastructure pattern**: A "contaminated" sandbox can be discarded and rebuilt rather than repaired, improving predictability and recovery speed.

### Best Practices and Anti-Patterns

**Best Practices:**
1.  **Least privilege**: Start network policies with `Locked Down`, explicitly add allowlists.
2.  **Treat untrusted input**: Agent output is **untrusted code**. Must be human-reviewed before merging/execution.
3.  **Dedicated branch development**: Use `--branch` or Git worktrees for agent work.
4.  **Logging and observability**: Record agent network requests and file modifications for audit.

**Anti-Patterns:**
1.  **Over-trusting isolation boundaries**: Ignoring shared workspace risks.
2.  **Relaxing network policies for convenience**: Setting `Open` or overly broad domain allowlists.
3.  **Reviewing results not process**: Only caring if generated code runs, not reviewing specific modifications and installed dependencies.

### Related Metrics (SLI/SLO/SLA)
*   **SLI**: Sandbox creation success rate and latency; workspace file sync latency; agent network request success rate.
*   **SLO**: 99% sandboxes created and interactive within specified time (under 5 seconds).
*   **Key incident metrics**: "Unreviewed agent commits merged count"; "agent behaviors triggering network policy denials."

## Summary

AI coding agents as new autonomous, high-privilege workloads expose traditional container models' **trust boundary** deficiencies. Docker Sandboxes provide stronger isolation baselines through microVMs, but this isn't a silver bullet. Core insight: **isolation strength should match workload trust profile**. For fully autonomous agents, hardware-level isolation (microVMs) is necessary, but **the necessary shared workspace design makes developer security discipline the final defense line**. SREs and developers must adopt "zero trust" thinking, leveraging strong isolation boundaries while strictly reviewing outflow artifacts (file changes). This marks runtime security's paradigm shift from "trusting image sources" to "not trusting any autonomous executor."
