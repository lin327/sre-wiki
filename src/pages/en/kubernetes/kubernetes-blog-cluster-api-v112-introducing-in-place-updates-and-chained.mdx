# 

## Overview

Cluster API supports the complete lifecycle of Kubernetes clusters through declarative management, allowing platform teams to define the desired state of clusters and relying on controllers to continuously reconcile, ensuring the actual state matches the desired state. Similar to using `Deployment` or `StatefulSet` to manage Pods in Kubernetes, Cluster API uses `KubeadmControlPlane` to manage control plane nodes and `MachineDeployment` to manage worker nodes. In SRE practice, safely and controllably managing the lifecycle of large numbers of clusters (such as creation, updates, upgrades) is a core challenge for ensuring service [[reliability]] and [[operational-efficiency]].

The release of Cluster API v1.12.0 introduces two major features — **In-place Updates** and **Chained Upgrades** — aimed at reducing friction in common lifecycle operations, making it easier and safer for users and SRE teams to manage Kubernetes clusters. These improvements reflect the project's evolutionary direction of continuously reducing workload disruption while maintaining the advantages of the [[immutable-infrastructure|immutable infrastructure]] principle.

## Core Concepts

### In-Place Updates

Traditionally, Cluster API (and Kubernetes `Deployment`) uses an immutable rolling update strategy: when a machine's Spec changes, a new machine is created and the old one is destroyed, achieving a rolling release. This approach has the advantages of being simple, predictable, and not dependent on the machine's specific configuration (such as operating system or boot mechanism).

The **In-place Updates** feature introduced in v1.12.0 extends this model. It allows users to apply certain changes to existing machines **without deleting and recreating them**. Cluster API controllers now have a decision point: when detecting a spec change, they automatically choose between using the traditional rolling update (creating a new machine) or calling the new **Update Extension** to execute changes in-place on the existing machine.

The choice of which approach to use depends on the nature of the change. Cluster API maintainers recommend that for changes that do not result in node eviction or Pod restarts (such as modifying machine user credentials), in-place updates are more appropriate; for changes that will inevitably cause workload disruption, continue using rolling updates.

### Chained Upgrades

In Kubernetes' release cycle, users typically need to upgrade one minor version at a time (for example, 1.32 -> 1.33 -> 1.34). The `ClusterClass` and managed topology features provide powerful abstractions for Kubernetes-as-a-Service platforms.

The **Chained Upgrades** feature introduced in v1.12.0 allows users to declare a target version spanning multiple minor versions in a single operation (for example, upgrading directly from 1.32 to 1.35). Cluster API will handle safely orchestrating the required **intermediate upgrade steps**, automatically calculating the upgrade plan and executing it in the correct order (control plane first, then worker nodes). It will also optimize the worker node upgrade path based on the Kubernetes version skew policy, potentially skipping certain intermediate versions.

## Practice

For cluster operators and SRE teams, these new features are directly reflected in updating Kubernetes resource definitions.

1.  **In-place Update Practice**:
    *   Ensure your Cluster API version is v1.12.0 or higher.
    *   For specific types of changes requiring in-place updates (such as machine credential updates), you need to implement or use an existing **Update Extension**.
    *   When you modify the `.spec` of a `Machine` or `KubeadmControlPlane`, Cluster API will automatically determine based on the change content. If the change is suitable for in-place update and a corresponding extension exists, it will perform an in-place update rather than a rolling creation.
    *   This feature supports use on both `KubeadmControlPlane` and `MachineDeployment`.

2.  **Chained Upgrade Practice**:
    *   This feature is based on `ClusterClass` and managed topologies.
    *   In the YAML file declaring the cluster resource, set the `.spec.topology.version` field directly to your desired **final Kubernetes version** (for example, `v1.35.0`), without worrying about intermediate versions.
    *   The Cluster API controller will automatically:
        a.  Calculate the optimal upgrade plan from the current version to the target version (including the order for control plane and worker nodes).
        b.  Execute control plane upgrades (potentially multiple rolling updates).
        c.  Upgrade worker nodes according to the plan.
    *   You can customize the upgrade plan calculation logic through **Upgrade Plan Runtime Extensions**, or use **Lifecycle Hooks** to execute custom tasks at specific stages of the upgrade (such as after control plane upgrade completes), such as upgrading cluster add-ons.

## SRE Key Points

*   **Connection to Reliability**:
    *   **In-place Updates** reduce unnecessary Pod rescheduling and node eviction caused by rolling updates, thereby lowering the [[pod-disruption-budget|Pod disruption]] risk during upgrades and improving service availability.
    *   **Chained Upgrades** automate the complex multi-version upgrade process, reducing manual operational steps and potential configuration errors, making version evolution of large-scale clusters safer and more predictable.
    *   Both together reduce the "operational friction" of cluster lifecycle management, allowing SRE teams to focus more on architectural optimization and root cause resolution.

*   **Best Practices and Anti-patterns**:
    *   **Best Practice**: For machine configuration changes that do not involve container runtime or kernel upgrades and will not affect workloads, prioritize using in-place updates. Treat in-place updates as a tool for "lightweight" changes and rolling updates as a tool for "heavyweight" changes.
    *   **Best Practice**: Even though chained upgrades provide convenience, you **must** follow Kubernetes' release lifecycle policy and apply patch versions in a timely manner. Do not completely defer all minor version upgrades just because chained upgrade capability exists.
    *   **Anti-pattern**: Using in-place updates for underlying changes that may cause kernel or container runtime incompatibilities, which may exceed the extension's handling capability and lead to node failures.
    *   **Anti-pattern**: Ignoring compatibility checks and [[chaos-engineering|chaos engineering]] verification before [[kubernetes-upgrades|version upgrades]], completely relying on Cluster API's automation process.

*   **Related Metrics (SLI/SLO/SLA)**:
    *   Monitor **cluster upgrade duration** (from start to target version fully ready).
    *   Monitor **node NotReady duration** and **Pod rescheduling count** during upgrades.
    *   Define **"Service error rate during major version upgrades"** as an SLI with a corresponding SLO to ensure the upgrade process does not significantly impact user experience.

*   **Observability and Incident Response**:
    *   Closely monitor Cluster API controller logs and metrics to understand the upgrade plan's formulation and execution status.
    *   Set up alerts for key events during the upgrade process (such as control plane upgrade start/completion, worker node batch upgrade start) to facilitate incident response and process auditing.
