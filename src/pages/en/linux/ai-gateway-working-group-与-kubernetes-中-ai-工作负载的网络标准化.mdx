# Announcing the AI Gateway Working Group

## Overview

As Artificial Intelligence (AI) increasingly takes a central role in modern cloud-native applications, ensuring these AI workloads run efficiently, securely, and reliably in Kubernetes clusters has become a key challenge for Site Reliability Engineering (SRE). AI inference requests often have unique traffic patterns and resource consumption characteristics. To address this, the Kubernetes community announced the formation of the **AI Gateway Working Group (WG)**, aimed at establishing standards and best practices for network infrastructure (such as proxy servers, load balancers) to better support AI workloads. The working group focuses on extending Kubernetes' [Gateway API](https://gateway-api.sigs.k8s.io/) to provide dedicated policy enforcement, security protection, and optimization capabilities for AI traffic, which is critical for ensuring AI application SLOs and overall reliability.

## Core Concepts

### What is an AI Gateway?

In the Kubernetes context, an **AI Gateway** is not an entirely new product category but rather refers to network gateway infrastructure enhanced with AI workload support capabilities. It typically implements the [Gateway API](https://gateway-api.sigs.k8s.io/) specification and adds AI traffic-specific features on top of it. Its core objective is to implement fine-grained policy control over AI-related traffic, with primary functions including:

*   **Token-Based Rate Limiting**: Fine-grained quota management for AI API calls, preventing a single application or user from exhausting global resources or budgets.
*   **Fine-Grained Access Control**: Implementing strict permission policies for Inference APIs.
*   **Payload Inspection**: Intelligent inspection of complete HTTP request and response payloads, enabling smart routing, caching, and security guardrails.
*   **Support for AI-Specific Protocols and Routing Patterns**: Understanding and handling communication patterns commonly found in AI inference services.

### Working Group Mission and Charter

The AI Gateway WG's primary goal is to provide proposals for Kubernetes SIG Network and other sub-projects, with core tasks including:

1.  **Standards Development**: Establishing declarative APIs, standards, and guidelines for AI workload networking in Kubernetes.
2.  **Community Collaboration**: Facilitating discussion and building consensus around AI infrastructure best practices.
3.  **Extensible Architecture**: Ensuring AI-specific gateway extensions have good composability, plugin support, and ordered processing capabilities.
4.  **Standards-Based Approach**: Building AI-specific capabilities in layers on top of established networking foundations (such as Gateway API).

## Practice

The AI Gateway WG is currently addressing key challenges in AI workload networking through a series of active proposals. These proposals define declarative configuration standards and processing pipelines, forming the practical foundation for deploying AI gateways in future production environments.

### Key Proposal 1: Payload Processing

This proposal addresses the critical need for AI workloads to inspect and transform complete HTTP payloads. It defines declarative payload processor configurations, ordered processing pipelines, and configurable failure modes.

*   **AI Inference Security Enhancement**:
    *   Defending against malicious prompts and prompt injection attacks.
    *   Filtering AI-generated response content.
    *   Signature-based detection and anomalous traffic detection.
*   **AI Inference Optimization**:
    *   Semantic routing based on request content.
    *   Intelligent caching to reduce inference costs and improve response times.
    *   Integration with RAG (Retrieval-Augmented Generation) systems to enhance context.

### Key Proposal 2: Egress Gateways

Modern AI applications frequently rely on external inference services (such as OpenAI, Vertex AI, Bedrock, etc.). This proposal aims to establish standards for securely routing traffic outside the cluster.

*   **External AI Service Integration**:
    *   Secure access to cloud-based AI services.
    *   Managing authentication and token injection, simplifying access to third-party AI APIs.
    *   Supporting geographic compliance and failover.
*   **Advanced Traffic Management**:
    *   Defining backend resources for external Fully Qualified Domain Names (FQDNs) and services.
    *   Managing TLS policies and Certificate Authorities (CAs).
    *   Supporting cross-cluster routing for centralized AI infrastructure management.

**Participation**: The AI Gateway WG follows an open contribution model. SRE and platform engineers can participate and influence the development of these standards through:
*   Reviewing and contributing proposals in the [GitHub repository](https://github.com/kubernetes-sigs/wg-ai-gateway).
*   Joining the weekly Thursday 2 PM (EST) meetings.
*   Discussing in the `#wg-ai-gateway` channel on Kubernetes Slack.

## SRE Key Points

### Reliability and Observability Association
AI Gateway directly serves to enhance AI application **reliability** and **observability**. Through payload inspection, semantic-based monitoring and alerting can be achieved—for example, detecting anomalies in model response quality or detecting prompt injection attacks. Intelligent caching and routing can significantly reduce inference latency and improve availability, contributing to achieving **AI application SLOs**. Egress gateways enhance resilience against external AI service dependencies through standardized failover and retry mechanisms.

### Best Practices and Common Anti-Patterns
*   **Best Practices**:
    *   **Policy as Code**: Leverage AI Gateway's declarative API to version and automate management of rate limiting, access control, content filtering, and other policies.
    *   **Defense in Depth**: Implement initial security protections (such as input/output filtering, rate limiting) at the gateway layer, forming defense in depth with backend application-layer security measures.
    *   **Intelligent Caching Strategy**: Implement caching for repeated or similar inference requests—not only improving performance but also effectively controlling **Error Budget** consumption.
    *   **Comprehensive Observability**: Ensure AI Gateway exposes detailed metrics (such as token usage, cache hit rates, latency percentiles, security events) and integrates with the centralized observability platform.
*   **Common Anti-Patterns**:
    *   Allowing applications to directly access external AI services without unified gateway control, causing security, cost, and compliance risks to spiral out of control.
    *   Treating all AI traffic as ordinary HTTP traffic, ignoring its special resource consumption and security characteristics, potentially causing "noisy neighbor" problems or security vulnerabilities.
    *   Neglecting monitoring and review of AI-generated content, potentially causing compliance issues or propagating harmful information.

### Related Metrics (SLI/SLO)
To monitor the health of AI Gateway and the AI applications it supports, the following SLIs should be tracked:
*   **AI Request Success Rate**: Percentage of inference requests successfully completed.
*   **AI Inference Latency (P99, P999)**: End-to-end inference request latency percentiles.
*   **Cache Hit Rate**: Proportion of inference requests served by cache.
*   **Token Consumption Rate and Error Rate**: Token quota consumption and proportion of requests triggering rate limiting.
*   **Security Event Count**: Number of malicious prompts or anomalous responses detected and blocked.
*   **Egress Traffic Error Rate**: Request failure rate when connecting to external AI services.
