# Alerting: Recording rules do not write stale markers

## Overview
In an observability system based on Prometheus, data freshness and accuracy are the cornerstones of system reliability. Recording Rules are used to precompute commonly used or complex query results to improve query performance and provide stable indicators for alarms. When the source metric on which a recording rule is based disappears, the ideal behavior is that the time series generated by the rule should also be marked as expired and eventually stopped. This article describes a flaw in Grafana-managed recording rules in this scenario: it does not write expiration markers to the target data source, causing expired data to be incorrectly persisted.

## Core concepts

### Time series expiration (Staleness)
In the Prometheus data model, the Prometheus engine considers a time series to be "expired" when it no longer produces new sample points. This is an important mechanism for data lifecycle management, ensuring that queries do not return stale or terminated metric values ​​indefinitely.

### Stale Marker
The expiration flag is a special `NaN` value (specifically represented by the `__name__="..."` tag being removed), which is sent to the receiving data source (such as Thanos, Cortex, or another Prometheus instance) through the Remote Write protocol. Its core function is to explicitly notify downstream systems: "This time series has ended." Systems that receive an expired flag will update the sequence's status to expired so that it is handled correctly when queried.

### Default behavior of Prometheus
Native Prometheus will actively generate and write an expiration mark when the recording rule stops outputting a time series. This ensures that the indicator's continuity correctly reflects its life cycle. For example, for a metric that generates data every two minutes, if the source data disappears between generations, Prometheus will send an expiration mark when evaluating, causing the time series to appear disconnected or ended on the chart, rather than always showing the last value.

## Practice

According to the issue report, the difference in expired mark behavior between Grafana and native Prometheus can be reproduced by following these steps:

1. **Prepare the same source metrics**: Make sure there is a source metric (such as via remote write or application exposure) that produces data intermittently, such as "every two minutes."
2. **Create a recording rule in Grafana**: In the alarm/recording rule interface of Grafana, create a recording rule using the same query expression as Prometheus.
3. **Create the same recording rule in Prometheus**: In the native Prometheus instance, configure and create an identical recording rule.
4. **Observations**:
    * **Prometheus Recording Rules**: When the source metric disappears between two expected generations, the time series generated by the corresponding recording rule will correctly write the expiration mark, and there will be obvious gaps between its data points.
    * **Grafana Recording Rules**: Time series generated by Grafana-hosted recording rules persist even if the source metrics disappear and do not receive an expiration mark. This means that the time series will always retain the last value and may appear as a continuous, never-ending straight line on the chart, creating the illusion that the data persists.

**Impact of the problem**: This behavior difference will cause downstream consumers (such as dashboards and alert rules) that use Grafana recording rules to make decisions based on incorrect data. For example, an alarm that relies on the rate of change of a metric may never trigger because the metric value appears to be "stable" when in fact the source data has long since stopped.

## SRE Key Points

### Association with reliability, observability, incident response
* **Data Integrity**: This problem directly destroys the integrity of the monitoring data. SRE relies on accurate, timely data to assess system status (SLO) and make operational decisions. Wrong data may result in false positives (False Positive) or false negatives (False Negative).
* **Incident Response**: During troubleshooting, the SRE may review historical data of recorded rules to trace the issue. If the time series is not ended correctly, it can mislead engineers into thinking that a service or metric was still functioning "normally" during the failure.
* **Alert Accuracy**: Many alert rules are based on the output of recorded rules. The absence of the expiration mark will prevent the alarm rules from detecting the termination of the indicator, which may cause the alarm logic to fail.

### Best practices and common anti-patterns
* **Best Practice**: Understand and verify the ability of each link in your monitoring pipeline to handle time series expiration. For key recording rules, it is recommended to simulate the scenario where the indicator disappears in the test environment to verify whether its behavior is as expected.
* **Common anti-pattern**: Blindly trusting the "freshness" of data in all monitoring pipelines without end-to-end verification. It is believed that "data has always existed" equals "the system has always been healthy", ignoring possible faults in the data flow itself (such as the missing expiration mark this time).
* **Workaround**: Before Grafana fixes this issue, the SRE team may need to consider using native Prometheus recording rules as the source of core monitoring data, or adding additional "heartbeat" or "survival" detection logic on top of the Grafana recording rule output to indirectly determine whether the time series is active.

### Related indicators (SLI/SLO/SLA)
* **SLI (Service Level Indicator)**: A relevant SLI could be "expiration mark timely write rate for key time series".
* **SLO (Service Level Objective)**: You can set "In the Grafana recording rule scenario, within [X] minutes after the indicator disappears, the downstream data source must be able to observe the corresponding expiration mark."
* **The health of the monitoring system itself**: This issue highlights the importance of monitoring the reliability of the monitoring system pipeline itself. Monitoring pipelines (such as Grafana's alerting engine, Prometheus' remote writing) also need to have their own health indicators and SLOs.
