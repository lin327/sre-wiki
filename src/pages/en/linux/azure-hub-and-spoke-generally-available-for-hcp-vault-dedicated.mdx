# Azure hub-and-spoke generally available for HCP Vault Dedicated

## Overview

The Azure Hub-and-Spoke network model is a foundational architecture for enterprises building secure, scalable cloud networks. It centralizes core shared services (such as firewalls, DNS) in a central "Hub" virtual network, while individual business systems are deployed in isolated "Spoke" virtual networks, connected and access-controlled through the Hub. HashiCorp recently announced that its managed HCP Vault Dedicated service now officially supports integration into this Hub-and-Spoke architecture. This means Vault can serve as a core, managed Tier 0 security service, seamlessly integrating into an enterprise's existing Azure network governance model without requiring special routing design or exception configurations, thereby significantly enhancing deployment security, compliance, and operational efficiency.

## Core Concepts

### Hub-and-Spoke Network Model
This is a common cloud network architecture pattern. The **Hub** virtual network serves as the control point for network traffic and the location of shared services (such as firewalls, VPN gateways, DNS). The **Spoke** virtual networks host applications and workloads, accessing shared services and the internet through VNet peering with the Hub. This model enables centralized management, unified security policy enforcement, and traffic inspection.

### HashiCorp Virtual Network (HVN)
HVN is a managed network component provided by HashiCorp Cloud Platform (HCP), serving as the network environment where Vault Dedicated runs. HVN can establish private peering with Azure native virtual networks (VNets), ensuring communication between workloads always traverses Azure's backbone private link rather than being exposed to the public internet.

### Tier 0 Services
In security classification, Tier 0 services refer to core systems that are critical to the entire enterprise, carrying the most sensitive data and privileges. **Vault, as a secret management service, is a typical Tier 0 security service.** Deploying it in a Hub-level trusted zone means its access is controlled by the strictest network policies and is subject to centralized log review and monitoring.

## Practice

### Integration Configuration
For Azure users already using HCP Vault Dedicated, the Hub-and-Spoke connection mode can now be enabled directly in the console. This is an important architectural decision, and the configuration process typically includes:
1.  **Enabling Hub Mode**: In HCP Vault Dedicated's network settings, choose to include Vault's HVN as part of the central Hub virtual network.
2.  **Establishing Peering**: Establish a peering relationship between HVN and the Hub VNet in the enterprise's Azure environment. This creates a private connection path between Vault and the enterprise's core network (such as firewalls, DNS).
3.  **Configuring Routing and Firewall Policies**: Define standard traffic routing and firewall rules in the enterprise Azure Hub VNet. Since Vault now follows the unified Hub inbound/outbound pattern, its network policies can share the same rule sets as other Tier 0 services, without needing to maintain special exception policies for Vault.
4.  **Traffic Path**: After configuration, traffic from applications in Spoke VNets accessing Vault will pass through the enterprise's central firewall for inspection, then reach Vault through the peering link between Hub and HVN, ensuring traffic always remains within a controlled private network.

### Architectural Advantages
This integration approach means Vault is no longer an "exception" in the network architecture. It follows the established architectural blueprint like other core enterprise services. When enterprises need to expand applications (adding new Spokes) or cover new regions, they only need to follow standard processes—typically no additional configuration changes to Vault's network connectivity are required, unless adjustments to the centralized network policy itself are involved.

## SRE Key Points

### Reliability, Observability, and Incident Response Association
- **Reliability**: By integrating into the enterprise's mature, proven Hub-and-Spoke architecture, Vault's network connectivity depends on existing, highly available network infrastructure (such as the central Hub's redundant design), reducing the risk of single points of failure that customized network solutions might introduce.
- **Observability**: All of Vault's network traffic passes through the enterprise's centralized network checkpoints (such as firewalls, network virtual appliances). This enables security teams and platform teams to use unified monitoring, logging, and auditing tools (such as Azure Monitor, enterprise SIEM) to collect and analyze Vault's network activity, greatly enhancing overall observability.
- **Incident Response**: When security incidents occur, the clear, standardized network topology and centralized log points simplify troubleshooting and root cause analysis. Due to centralized policy management, response measures against network-layer attacks (such as lateral movement), such as updating firewall rules, can take effect quickly and globally, reducing Mean Time to Resolve (MTTR).

### Best Practices and Common Anti-Patterns
- **Best Practices**:
    1.  **Policy as Code**: Include Vault network access rules (firewall policies, route tables) defined on the Hub VNet in version control and CI/CD processes, ensuring their changes are auditable and rollback-capable.
    2.  **Least Privilege Access**: Leverage the clear isolation boundaries of the Hub-Spoke architecture to only configure Vault access for necessary application Spokes, strictly limiting direct cross-Spoke communication.
    3.  **Unified Monitoring and Alerting**: Correlate Vault's connection logs with central network device log streams, establishing unified alert rules for anomalous access patterns.
- **Common Anti-Patterns**:
    1.  **Bypassing Hub with Direct Peering**: For convenience, directly peering Vault HVN with a business Spoke VNet, violating the centralized control and traffic inspection architectural principles.
    2.  **Ignoring Central Policy Updates**: After completing integration on the Vault side, forgetting to add or update necessary allow rules in the enterprise central Hub's firewall or network groups, causing connectivity failures.
    3.  **Overly Broad Rules**: Configuring overly permissive inbound/outbound rules for Vault in the Hub, weakening the security the architecture should provide.

### Related Metrics (SLI/SLO/SLA)
While this topic focuses on network architecture, it has a direct impact on Vault service SRE metrics:
- **SLI (Service Level Indicator)**: `Vault_API_Success_Rate` (Vault API call success rate), `Vault_Secret_Retrieval_Latency` (secret retrieval latency). Stable networking is the foundation for ensuring these metrics.
- **SLO (Service Level Objective)**: SLOs can be set for Vault API availability and latency. The Hub-and-Spoke architecture, by using reliable Azure private links, helps achieve more stable performance.
- **SLA (Service Level Agreement)**: HCP Vault Dedicated itself provides an SLA guaranteeing the availability of its managed service. Enterprises need to ensure their own Azure network (Hub and its interconnections) reliability to achieve end-to-end service assurance, which can be achieved through Azure's SLA and the enterprise's own redundancy design.
