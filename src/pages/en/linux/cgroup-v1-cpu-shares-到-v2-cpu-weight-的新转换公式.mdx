## Overview

The allocation and limitation of CPU resources is a key link to ensure system stability and performance, and is also one of the core issues of SRE work. As Linux control groups (cgroups) migrate from v1 to v2, Kubernetes needs to map CPU request values ​​to new resource control parameters accordingly. This article details an important improvement in the Kubernetes ecosystem: **The new conversion formula from cgroup v1 `cpu.shares` to cgroup v2 `cpu.weight`**. This change resolves two serious issues with the old linear mapping formula: reduced priority of Kubernetes workloads relative to non-Kubernetes processes, and insufficient granularity for fine-grained resource allocation within containers. This improvement has direct implications for reliability, performance prediction, and capacity planning of all Kubernetes clusters running on cgroup v2 systems.

## Core concepts

To understand this change, you first need to clarify a few key concepts and their differences.

1. **cgroup v1 `cpu.shares`**: In cgroup v1, a parameter used to represent the CPU shares of the container. Its default value is `1024`, which defines the relative weight of CPU time allocated between different cgroups when there is contention for CPU resources. For example, a request for 1 CPU (1000m) would be calculated as `cpu.shares = 1000 * 1024 / 1000 = 1024`.
2. **cgroup v2 `cpu.weight`**: Alternative parameter in cgroup v2, ranging from `1` to `10000` (10⁰ to 10⁴), and the default value is `100`. It represents relative weight more directly.
3. **Old linear conversion formula**: The mapping method adopted by early Kubernetes: `cpu.weight = (1 + ((cpu.shares - 2) * 9999) / 262142)`. This formula linearly maps v1's `cpu.shares` range `[2, 262144]` to v2's `cpu.weight` range `[1, 10000]`.
4. **New quadratic conversion formula**: The formula introduced in this improvement is designed to map key value points more accurately:
    `cpu.weight = ⌈ 10^(L²/612 + 125L/612 - 7/34) ⌉`, where `L = log₂(cpu.shares)`.
    This formula has been carefully designed to ensure accurate mapping of three key points:
    - `(cpu.shares=2, cpu.weight=1)`: minimum value.
    - `(cpu.shares=1024, cpu.weight=100)`: Default value.
    - `(cpu.shares=262144, cpu.weight=10000)`: maximum value.

## Practice

### Application and integration of new formulas

The new conversion formula is implemented in the OCI (Open Container Initiative) runtime layer instead of the Kubernetes core code. This means that its adoption is entirely dependent on updates to the underlying container runtime. Currently, OCI runtime versions that support this formula include:
- **runc**: version `1.3.2` and above.
- **crun**: version `1.23` and above.

When a cluster node is upgraded or replaced to use a new version of the OCI runtime, the newly created Pod will automatically apply this new formula to calculate `cpu.weight`.

### Impact on existing deployments and migration considerations

For Kubernetes clusters already running in a cgroup v2 environment, upgrading the OCI runtime to adopt the new formula requires careful evaluation. **Key impacts include**:

1. **Expected Behavior Change**: The workload's CPU scheduling priority and weight values will change. For example, a container requesting 1000m CPU would have its `cpu.weight` raised from `≈39` calculated by the old formula to `102` calculated by the new formula, closer to the default value of `100`.
2. **Toolchain Compatibility**: Any tools that directly rely on or assume the old linear formula for calculating expected `cpu.weight` values ​​(such as some custom resource managers, monitoring systems, or validation scripts) may need to be updated. It is important to note that since the formula is a many-to-one mapping (e.g. a CPU request from 90m to 109m may be mapped to `cpu.weight=17`), it is unreliable to reversely derive the exact original `cpu.request` value from `cpu.weight`.
3. **Migration path**: **Strongly recommended** to test the impact of the new formula on existing workloads and tool chains in a non-production environment, and then upgrade the OCI runtime in the production environment after confirming compatibility. The exact CPU request value should always be read from the Pod's spec, rather than deduced from the cgroup parameters.

## SRE Key Points

- **Link to Reliability**: One of the main problems with the old formula was the reduced CPU priority of Kubernetes workloads relative to system daemons. When resources are tight, this may cause critical business containers to be unnecessarily preempted for CPU resources, affecting service availability and latency. The new formula restores fair prioritization, which directly improves resource guarantees and predictability for production workloads in contention scenarios.
- **Link to Observability/Monitoring**: This change requires the SRE team to update their understanding of CPU resource allocation and related monitoring alert rules. The baseline threshold and expected value comparison logic for `cpu.weight` in the monitoring system may need to be recalibrated to avoid false positives or false negatives due to formula changes.
- **Relevance to Incident Response**: When investigating CPU performance issues (such as throttling) in a cgroup v2 environment, the SRE needs to know the version of the node OCI runtime and which transformation formula it is applying, as this directly affects the analysis of whether the `cpu.weight` value is reasonable. The root cause of the problem may be related to such underlying configuration changes.
- **Best Practices**:
    1. **Explicit dependencies**: When managing resource quotas and SLOs, the underlying cgroup version and CPU weight conversion logic should be clearly recorded.
    2. **Incremental Upgrade**: Before upgrading the OCI runtime, be sure to conduct sufficient non-production environment testing.
    3. **Avoid reverse dependencies**: Avoid hardcoding the specific value of `cpu.weight` in monitoring or automation tools or relying on it to reversely deduce the original request value.
- **Common anti-patterns**:
    - Directly upgrade OCI runtime in production environment without compatibility testing.
    - Set a fixed `cpu.weight` threshold alarm in monitoring based on the old formula, resulting in a large number of false alarms.
    - Mistakenly believe that the CPU resources declared by the Pod can be restored with high accuracy through `cpu.weight`.
- **Related Metrics (SLI/SLO)**: This change directly affects the value of `cpu.weight`, the underlying **SLI (Service Level Indicator)**. Although it does not directly constitute an independent SLI, it is a key underlying parameter to achieve CPU scheduling fairness and resource guarantee capabilities. Relevant SLOs (such as "P99 latency below X" or "CPU throttling time below Y%") may be indirectly dependent on the correctness and fairness of the CPU weight mapping. The SRE should track the OCI runtime version as one of the metadata used to calculate the health of the infrastructure.
