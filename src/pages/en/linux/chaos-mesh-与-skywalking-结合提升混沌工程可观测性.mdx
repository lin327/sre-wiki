# Chaos Mesh + SkyWalking: Enhancing Chaos Engineering Observability

## Overview

The core value of chaos engineering lies in validating system resilience through proactive fault injection. However, merely knowing that a fault has been injected is not enough -- SREs and developers need to precisely observe when and to what extent these faults affect application service performance (such as throughput and latency). The integration of Chaos Mesh and Apache SkyWalking is designed to address this observability gap. Chaos Mesh is responsible for simulating real-world faults in Kubernetes environments, while Apache SkyWalking, as a distributed tracing and performance monitoring tool, can clearly correlate fault events with application performance metrics, providing a critical feedback loop for chaos experiments and thereby strengthening confidence in system reliability.

## Core Concepts

### Chaos Mesh
[[chaos-mesh]] is a cloud-native chaos engineering platform running on Kubernetes. It allows users to conveniently inject multiple types of faults (such as Pod Kill, Network Delay, CPU Stress) into targets like Pods, nodes, or networks through a declarative API, simulating various anomalies that may occur in production environments. Its built-in Chaos Dashboard provides an experiment management interface, but does not itself provide fine-grained application performance monitoring.

### Apache SkyWalking
[[observability]] is one of the pillars of reliability engineering, and Apache SkyWalking is a powerful open-source Application Performance Monitoring (APM) and observability analysis platform. It is particularly adept at monitoring and diagnosing cloud-native, containerized distributed systems, providing a panoramic view of system health by collecting Metrics, Traces, and Logs. In chaos engineering scenarios, SkyWalking's key role is to correlate and visualize Kubernetes events generated by chaos experiments with system performance metrics.

### SkyWalking Kubernetes Event Exporter
This is a component that forwards events generated in the Kubernetes cluster (particularly events from fault injection by Chaos Mesh) to the SkyWalking backend. It listens, filters, and sends events, enabling SkyWalking to directly annotate the fault injection time points on the performance monitoring panel, allowing observers to visually compare service performance changes before and after fault injection.

## Practice

The following steps demonstrate how to set up an observation environment combining Chaos Mesh and SkyWalking, and observe the impact of stress-type faults on service performance.

### 1. Prepare the Environment
Before starting, you need to complete the following preparations:
- **Deploy SkyWalking Cluster**: Deploy SkyWalking in your Kubernetes cluster following the official SkyWalking documentation.
- **Deploy Chaos Mesh**: Install [[chaos-mesh]] in the same Kubernetes cluster using Helm.
- **Prepare Load Generation Tools**: Install JMeter or other load testing tools to generate stable request loads for the target application.
- **(Optional) Deploy a Demo Application**: A simple microservice such as Spring Boot can be used as the target for monitoring and fault injection. Note that port configuration should avoid conflicts with SkyWalking's default port (8080).

### 2. Deploy SkyWalking Kubernetes Event Exporter
This is the key step to connecting chaos experiments with performance monitoring. After deploying the exporter, it will begin listening for events in the cluster.
- Configure and apply the `exporter-deployment.yaml` file according to the official guide.
- Customize the `filters` and `exporters` sections in the configuration file to ensure that events generated by Chaos Mesh are correctly captured and sent to the SkyWalking backend.

### 3. Generate Baseline Load
Before injecting faults, you need to establish a stable performance baseline for the target application (e.g., the Spring Boot Demo).
- Use JMeter to apply a continuous load to the target application endpoint (e.g., `localhost:8079`), such as setting up 5 concurrent threads.
- Observe and record the service performance metrics in the SkyWalking UI, such as Calls Per Minute (CPM) and success rate. The example shows a baseline CPM of approximately 5300.

### 4. Inject Faults and Observe Performance Changes
Use Chaos Mesh's Chaos Dashboard to create a stress-type fault experiment, such as simulating CPU load.
- Configure a `StressChaos` in the Chaos Dashboard targeting the Pod running Spring Boot, and set specific CPU pressure values.
- Start the experiment. On the SkyWalking monitoring panel, you will see the fault injection time points annotated by the event exporter.
- **Observation Results**:
    - **Low Load (10% CPU)**: Service CPM may slightly decrease (e.g., to 4929) and recover after the experiment ends.
    - **Medium Load (50% CPU)**: Service CPM decreases more noticeably (e.g., to 4307).
    - **High Load (100% CPU)**: Due to OS scheduling mechanisms, the service may still handle some requests (e.g., 40% of baseline), but performance severely degrades.
    By comparing the SkyWalking metric charts during fault injection with the baseline period, you can intuitively quantify the specific impact of each fault on service performance.

## SRE Takeaways

### Reliability, Observability, and Incident Response Connections
- **Validating SLOs**: By quantifying the impact of faults on performance, you can more accurately assess the potential impact of failures on Service Level Objectives (SLOs) and help set more reasonable Error Budgets.
- **Strengthening the Observability Loop**: Chaos Mesh provides "perturbation," SkyWalking provides "observation." Together they form a complete "experiment-observe-learn" cycle, representing an advanced application of [[observability]] in chaos engineering.
- **Assisting Incident Response Training**: Observing fault impacts in a controlled environment helps teams rehearse real failures and optimize incident response processes and escalation strategies.

### Best Practices and Common Anti-patterns
- **Best Practices**:
    1.  **Start with Baselines**: Observe under stable loads to ensure a clear comparison baseline.
    2.  **Control Variables**: Inject only one fault type per experiment to accurately correlate the cause of performance changes.
    3.  **Full Monitoring Coverage**: Ensure that key service metrics (such as Latency, Error Rate, Saturation, Traffic) are all connected to SkyWalking.
    4.  **Automate**: Script the startup and shutdown processes of Chaos experiments and performance monitoring for fast, repeatable experiments.
- **Common Anti-patterns**:
    1.  **Only Watching Experiment Status**: Focusing only on whether Chaos Mesh successfully injected faults while ignoring deep analysis of application performance metrics.
    2.  **Starting in Complex Environments**: Progressing through experiments in unverified simple environments rather than "blind testing" directly in production.
    3.  **Ignoring Recovery Phase**: Performance returning to normal after fault recovery is equally important to observe, as it indicates the system's self-healing capability.

### Related Metrics (SLI/SLO/SLA)
This integration directly serves performance-related SLI (Service Level Indicator) observation, such as:
- **Throughput (Traffic)**: Requests per unit time (e.g., CPM/RPS); changes in this metric after fault injection are the primary observation target.
- **Error Rate (Errors)**: Whether fault injection causes an increase in request failure rate.
- **Latency (Latency)**: Whether fault injection causes request response times to increase.
By quantifying these SLIs under failure conditions, you can more scientifically define and validate the related [[slo]] and [[sla]].
