# Chaos Mesh and the Evolution Toward Chaos as a Service (CaaS)

## Overview

Chaos Mesh is a cloud-native chaos engineering platform focused on orchestrating chaos experiments in Kubernetes environments. As a CNCF sandbox project, it can inject various types of faults into Pods, networks, file systems, and even the kernel to test system resilience and robustness. However, to achieve broader adoption and a better user experience, Chaos Mesh needs to evolve toward a "Chaos as a Service" (CaaS) model. Based on the official blog, this document details the CaaS concept and how Chaos Mesh takes a key step toward CaaS by restructuring its Dashboard, enhancing chaosd capabilities, and improving observability. This has important reference value for SRE teams looking to build or adopt automated, platform-based chaos engineering capabilities.

## Core Concepts

### Chaos as a Service (CaaS)
Chaos as a Service (CaaS) is not just a tool, but a delivery model. It aims to provide a commercial-service-like experience, including an intuitive graphical user interface (GUI), customer support, out-of-the-box integrations, and convenient experiment management. An ideal CaaS platform should have:
- **Unified Console**: For centralized management, configuration, and creation of chaos experiments.
- **Visualized Metrics**: Real-time display of experiment status and impact on systems.
- **Lifecycle Management**: Support for pausing, archiving, or terminating experiments.
- **Simple Interaction**: Such as drag-and-drop operations to orchestrate experiment objects.

### Architecture Decoupling and Unified Management
Traditional chaos tools are often tied to specific infrastructure (such as a single Kubernetes cluster). A key step toward CaaS is achieving architecture decoupling, enabling a single control plane to manage and coordinate multiple heterogeneous fault injection points, whether they are Kubernetes clusters or physical servers.

## Practice

To move toward the CaaS model, Chaos Mesh underwent a key architectural refactoring during a hackathon, primarily in the following areas:

### Restructuring Chaos Dashboard
The original Dashboard was tightly coupled to a single Kubernetes cluster. After restructuring, **the Dashboard was decoupled from the core architecture**, enabling it to be deployed outside the cluster. Through the Web UI, users can add multiple Kubernetes clusters to the Dashboard for unified management. The `chaos-controller-manager` inside each cluster reports status to the Dashboard, and the two interact through Custom Resource Definitions (CRDs). The Dashboard manages chaos experiments in each cluster indirectly by operating on these CRDs, thereby achieving multi-cluster management capabilities.

### Enhancing chaosd Capabilities
`chaosd` is a tool for running chaos experiments on physical machines. The refactoring brought a qualitative leap in its capabilities:
- **RESTful API Support**: Transformed from a pure command-line tool into a programmable service.
- **CRD Format Compatibility**: Can parse CRD-format JSON or YAML files to configure experiments.
- **Node Registration and Heartbeat**: `chaosd` nodes can actively register with the Dashboard and report status through heartbeat signals, enabling the Dashboard to uniformly manage chaos nodes on both physical machines and containers.
- **Experiment Scheduling and Lifecycle Management**: Supports executing experiments at specified times and can manage the full experiment lifecycle, bringing the user experience on physical machines closer to that on Kubernetes.

### Improving Observability
Observability is the key to verifying whether chaos experiments are successfully injected and observing their impact. After restructuring, `chaos-daemon` (Kubernetes environment) and `chaosd` (physical machine environment) integrated `node_exporter` to collect node-level metrics. In Kubernetes clusters, `kube-state-metrics` and cAdvisor are also deployed to collect container and cluster state metrics. These metrics are stored and visualized through Prometheus and Grafana, providing users with an intuitive view of experiment status.

The optimized architecture after restructuring is as follows: A central Chaos Dashboard manages multiple Kubernetes clusters (via `chaos-controller-manager`) and a set of physical machine nodes (via `chaosd`), with all experiments defined and coordinated through standard CRDs.

## SRE Takeaways

### Reliability, Observability, and Incident Response Connections
Chaos engineering is an important practice for improving system reliability. By proactively injecting faults, SRE teams can:
- **Discover Unknown Defects**: Chaos engineering helps reveal "unknown unknowns" -- unexpected system weak points -- thereby hardening the system before real failures occur.
- **Validate SLO/SLI**: Observing Service Level Indicators (SLIs) under controlled chaos experiments helps validate whether Service Level Objectives (SLOs) still hold under various pressures, as well as the state of [[error-budget]] consumption.
- **Improve Incident Response Capability**: By rehearsing failure scenarios, teams can practice and optimize fault detection, localization, and recovery processes, making incident response smoother.

### Best Practices and Common Anti-patterns
- **Best Practices**:
  - **Incremental Implementation**: Start with experiments that have a small blast radius and gradually expand the scope.
  - **Integrate with CI/CD**: Include chaos experiments in the deployment pipeline as a checkpoint for system readiness.
  - **Prioritize Observability**: Ensure comprehensive monitoring (e.g., Prometheus) and log collection to fully assess experiment impact.
- **Common Anti-patterns**:
  - **Blind Experiments in Production**: Performing large-scale fault injection without adequate preparation or contingency plans.
  - **Inject Without Observing**: Lacking supporting monitoring and metric analysis, making experiment results unquantifiable.
  - **Not Feeding Results Back Into Improvements**: Failing to form an "explore-discover-analyze-improve" feedback loop, making chaos engineering a mere formality.

### Related Metrics (SLI/SLO/SLA)
Chaos experiments themselves can produce specific experimental data metrics (such as injected network latency values, CPU pressure values), which are direct evidence of experiment success. More importantly, experiments will trigger changes in the system's **regular SLIs**, such as:
- **Availability**: Whether request success rate decreases due to fault injection.
- **Latency**: Whether P99/P95 response times on critical paths exceed SLO.
- **Error Rate**: Whether application error logs or HTTP 5xx error rates spike.

SRE teams need to define acceptable fluctuation ranges for SLIs during chaos experiments and use this to determine whether an experiment "passes safely" or exposes SLO violation risks that need to be addressed.

### Future Outlook and Community Proposals
The article also discusses Chaos Mesh's future evolution directions, which are critical for building a more complete chaos engineering platform:
1.  **Orchestration and Closed Loops**: Achieving chaos engineering closed loops by using orchestration capabilities to combine experiments with monitoring feedback (such as PromQL queries) and automated remediation (such as rollback).
2.  **Plugin-Based Extension**: Exploring the use of WebAssembly, HTTP callbacks, and other methods to implement a secure plugin system, eliminating language restrictions and reducing security risks.
3.  **Tool Integration**: Integrating with other chaos tools (such as Litmus, PowerfulSeal) and cloud platforms (such as AWS) to manage a broader range of fault types through a unified model (such as Chaos Hub).

## Community Practice Case
A leading Chinese cybersecurity company extended Chaos Mesh based on its own needs, with practices covering:
- **Physical Nodes**: Executing custom scripts to simulate restarts, shutdowns, NIC shutdowns, and CPU context switches.
- **Containers**: Randomly adjusting Deployment replica counts, or embedding Ingress and Cilium network policy objects to simulate rate limiting and network fluctuations.
- **Applications**: Running custom Jobs to execute chaos logic, or using the Newman tool to inject random parameters into HTTP interfaces.

These cases demonstrate the flexibility and extensibility of Chaos Mesh's architecture, providing valuable practical experience for the community.
