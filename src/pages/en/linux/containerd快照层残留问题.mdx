## Overview

In modern containerized environments, the Docker engine is gradually migrating its underlying storage management to containerd. When the `containerd-snapshotter` feature is enabled, the storage of the image layer is managed by containerd's snapshot component. However, there is a known issue: Interrupted image pull operations permanently occupy disk space and cannot be cleared through standard commands such as `docker system prune`. This brings additional challenges to the daily operation and maintenance of SRE (such as disk space monitoring and reclamation), which may cause production accidents due to disk space exhaustion. Understanding the root cause and solution to this problem is critical to ensuring host reliability and storage health.

## Core concepts

- **Containerd Snapshotter**: A plug-in in containerd that manages the file system snapshots required for containers to run. When Docker is configured to use this feature, the layer extraction operation of `docker pull` is handled by the snapper and the data is stored in containerd's directory structure.
- **Overlayfs snapshot (`io.containerd.snapshotter.v1.overlayfs`)**: This is a specific implementation of the snapper, used to store the decompressed image layer. Interrupted pull operations can leave incomplete or orphaned snapshot data.
- **Content-addressed storage (`io.containerd.content.v1.content`)**: Stores the original image layer package (usually a compressed tar file) downloaded from the repository. Even if the snapshot is cleaned up, these contents may remain due to reference relationships.
- **Garbage Collection (GC)**: The mechanism used by containerd to clean up unreferenced objects. It is usually run periodically by the Docker daemon or containerd itself, but there may be policy restrictions that prevent it from cleaning residual data in a specific state.
- **Lease**: containerd's mechanism for tracking the life cycle of a set of related objects (such as all content and snapshots involved in a pull operation). The interrupted operation may create a lease that is not properly released, preventing the GC from reclaiming its associated data.

## Practice

### 1. Diagnose the problem
First confirm whether the problem exists. After interrupting a pull, check the disk usage using the following command:
```bash
# View the disk usage reported by Docker, pay attention to the Images section
docker system df -v

# Directly view the disk usage of the containerd storage directory
du -sh /var/lib/docker/io.containerd.snapshotter.v1.overlayfs
du -sh /var/lib/docker/io.containerd.content.v1.content
```
If these directories continue to grow and `docker system prune -a` cannot free up their space, a problem exists.

### 2. Check and clean up orphan leases
Use containerd's command line tool `ctr` to check for outstanding leases. This is the key to unlocking linked data.
```bash
# List all leases
sudo ctr -n moby leases ls

# Look for leases in an abnormal state that may have been created by interrupted pulls (usually no tags or associated references)
# Delete suspicious leases (please operate with caution to confirm that they are not operating normally)
sudo ctr -n moby leases rm <lease-id>
```
After a lease is deleted, containerd's garbage collection may reclaim the associated data the next time it is run.

### 3. Forced cleaning and manual intervention
If the above method does not work, you may need to stop the Docker service and clean up manually, but this will cause all containers to stop and should be done during the maintenance window:
```bash
# Stop the Docker service
sudo systemctl stop docker

# Carefully delete remaining snapshots and content directories (the path needs to be confirmed based on the actual environment)
sudo rm -rf /var/lib/docker/io.containerd.snapshotter.v1.overlayfs/???
sudo rm -rf /var/lib/docker/io.containerd.content.v1.content/blobs/sha256/???

# Restart the Docker service
sudo systemctl start docker
```
**Note:** Manual deletion is a last resort, be sure not to accidentally delete a snapshot that is in use. Best practice is to make a backup or double-check the directory contents before deleting.

## SRE Key Points

- **Correlation with Reliability**: This issue directly threatens the storage reliability of the host. Unreleased disk space may cause critical services (such as databases and application containers) to crash due to write failures, which is a potential single point of failure. SREs need to incorporate such storage leaks into capacity planning and alarm monitoring.
- **Observability Gap**: The standard Docker monitoring tool (`docker system df`) cannot accurately reflect the real disk usage managed by the containerd snapper, resulting in an observability blind spot. SRE needs to establish monitoring of specific directories under `/var/lib/docker/` and set disk space usage alarms.
- **Incident Response and Best Practices**:
    - **Best Practice**: In a production environment, for nodes with `containerd-snapshotter` enabled, an operation and maintenance script should be established to check leases regularly (such as daily) and clean up abnormal leases. Incorporate it into automated operations and maintenance processes.
    - **Anti-Pattern**: Ignoring persistent differences between `docker system df` and the actual `du` value; executing `rm -rf` directly without confirming safety.
    - **Operation process**: When receiving a disk space alarm, you should give priority to using `du` combined with `ctr leases` for diagnosis, and try to make GC take effect by clearing leases first, rather than directly manually deleting files.
- **Relevant Indicators (SLI/SLO)**:
    - **SLI (Service Level Indicator)**: You can define "container host available disk space percentage" as the SLI for storage reliability.
    - **SLO (Service Level Objective)**: Set a goal for this SLI, such as "99.9% of the time, the Docker root directory (`/var/lib/docker`) will have more than 15% free space."
    - By monitoring this SLI, capacity issues caused by storage leaks can be detected in advance and corresponding operation and maintenance operations (such as performing the above cleanup process) can be triggered to avoid SLO violations.
