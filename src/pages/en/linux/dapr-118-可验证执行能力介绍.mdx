## 概述

在云原生生态系统的演进中，从保障系统韧性到建立系统可信性是一个关键的范式转变。传统的可观测性工具（日志、指标、追踪）告诉我们发生了什么，但它们依赖于对系统的信任，且无法防篡改。Dapr 1.18 引入的**可验证执行**是一组基础性能力，它通过密码学手段为工作流执行历史提供**防篡改证明、来源可追溯和可信度认证**。对于 SRE 而言，这不仅是增强系统可靠性的技术升级，更是构建**零信任架构**、满足严格合规要求、以及保障关键业务流程和 AI 智能体可信赖性的核心治理基石。

## 核心概念

### 可观测性的局限性与可验证执行的需求

可观测性提供了系统运行时的**视图**，而可验证执行提供了运行历史的**证明**。前者依赖于系统自身的诚信，后者则提供密码学保证。在分布式系统和自主 AI 智能体日益普及的场景下，仅仅知道“发生了什么”已不足够，我们需要能够**证明**它确实发生了、证明它的执行路径是完整的、且证明它没有被事后篡改。

### Dapr 1.18 的三大核心能力

1.  **工作流历史签名 (Workflow History Signing)**：
    *   **是什么**：在工作流执行过程中，Dapr 会对工作流历史记录生成密码学签名。
    *   **解决什么**：创建**防篡改的执行历史**。任何对历史记录的修改都会破坏签名，使得篡改行为变得显而易见。这为审计和合规提供了比单纯日志或数据库记录更坚实的基础。

2.  **工作流历史传播 (Workflow History Propagation)**：
    *   **是什么**：允许执行谱系（execution lineage）跟随请求在服务、工作流、活动（Activity）和智能体之间流动。
    *   **解决什么**：解决了分布式上下文碎片化的问题。下游组件不再需要从多个日志和追踪中拼凑信息，而是可以直接获得关于“这个工作来自哪里”、“经过了哪些工作流”、“执行顺序是什么”的完整谱系。它将执行上下文从本地信息提升为分布式执行的一等公民。

3.  **工作流认证 (Workflow Attestation)**：
    *   **是什么**：允许工作流和活动接收并验证**密码学可验证的执行上下文**。
    *   **解决什么**：将执行谱系从“信息性元数据”转变为“可信信号”。下游系统可以基于经过验证的谱系做出决策，例如：一个银行系统只接受来自特定审批工作流的转账请求，从而强制执行安全策略。

### 基于 SPIFFE 的身份基础

可验证执行建立在 Dapr 已有的 **SPIFFE 工作负载身份** 基础之上。SPIFFE 解决了“你是谁？”（工作负载身份认证）的问题，而可验证执行则进一步回答了“你是如何到达这里的？”（执行谱系验证）。两者结合，构建了一条跨越编排器、活动、服务、智能体的**可信链条**，将密码学信任从通信层面延伸至执行层面。

## 实践

### 架构与流程描述

在启用 Dapr 1.18 这些能力后，一个典型的工作流执行流程将增加以下维度：

1.  **签名阶段**：当工作流状态发生转换或活动执行完毕时，Sidecar 会使用与工作负载身份关联的密钥对相关历史记录进行签名，并将签名附加到历史中。
2.  **传播阶段**：当工作流调用活动、活动调用其他服务，或智能体触发新的工作流时，Dapr 会自动将已签名的执行谱系信息（如父工作流ID、调用链、签名历史片段）注入到请求上下文（如 gRPC metadata 或 CloudEvents）中进行传播。
3.  **验证阶段**：接收请求的下游服务或工作流，可以使用 Dapr SDK 或内置 API 验证收到的执行谱系签名。它可以通过与初始签名者的 SPIFFE 身份对应的公钥进行校验，确保谱系未被篡改，并确认工作流的来源和路径符合预期。

### 操作示例（概念性）

```python
# 概念性代码，展示验证逻辑
from dapr.clients import DaprClient

def handle_incoming_request(request):
    with DaprClient() as d:
        # 验证请求中附带的工作流谱系和签名
        attestation = d.verify_workflow_attestation(request.context)
        
        if not attestation.is_valid:
            # 签名无效或谱系不满足策略要求，拒绝请求
            raise SecurityError("Invalid workflow attestation")
        
        # 检查谱系是否来自允许的父工作流
        if "approved-payment-workflow" not in attestation.provenance:
            raise SecurityError("Unapproved execution provenance")
        
        # 基于可信的上下文处理业务逻辑
        process_verified_payment(attestation.data)
```

## SRE 要点

### 与可靠性、可观测性、事件响应的关联

*   **可靠性**：可验证执行增强了**状态一致性**的保障。通过密码学签名，SRE 可以确信工作流的历史状态是准确且未被破坏的，这在故障恢复和幂等性验证中至关重要。
*   **可观测性**：它为现有的可观测性三支柱（日志、指标、追踪）增加了**可信维度**。一个带有有效签名的追踪链，其可信度远高于没有签名的追踪链。它使得异常检测可以基于“执行路径是否违背预期”而不仅仅是“指标是否异常”。
*   **事件响应**：在安全事件或故障排查中，**防篡改的执行历史**是宝贵的取证工具。SRE 团队可以精确地重建事件的完整、可信的因果链，确定是哪个工作负载、按照什么路径触发了问题，极大地提升事件分析的准确性和速度。

### 最佳实践与常见反模式

*   **最佳实践**：
    1.  **分层信任**：将 Dapr 的工作流认证作为关键业务决策（如支付、合规检查）的**强制门禁**，而非可选项。
    2.  **密钥管理**：确保用于签名的密钥（通常由 SPIFFE/SPIRE 等基础设施管理）有严格的访问控制和轮换策略。
    3.  **结合策略引擎**：将验证逻辑与 OPA (Open Policy Agent) 等策略引擎结合，实现基于执行谱系的动态、细粒度访问控制。
    4.  **作为 SLI 的一部分**：将“工作流签名验证成功率”或“谱系传播完整率”作为新的 SRE 指标，纳入 SLO 考核。
*   **常见反模式**：
    1.  **仅用于审计**：将可验证执行仅视为事后审计工具，而未在运行时作为关键决策依据，未能发挥其实时防护价值。
    2.  **信任所有签名**：未对签名验证结果进行基于策略的细化处理，仅仅检查“签名有效”就放行，忽略了对谱系内容（如来源工作流、调用路径）的检查。
    3.  **性能考量不足**：在超高吞吐量路径上未评估签名验证带来的延迟开销，应通过异步验证或策略优化来平衡安全与性能。

### 相关指标 (SLI/SLO/SLA)

*   **新 SLI 候选**：
    *   `workflow_attestation_verification_success_rate`: 工作流认证验证的成功率（即签名有效且符合策略）。
    *   `workflow_history_propagation_completeness`: 工作流历史传播的完整性比例（关键工作流是否携带了完整的谱系信息）。
*   **对 SLO 的影响**：可为“关键业务流程的数据完整性和不可否认性”这类 SLO 提供更强大的技术支撑和可量化的验证手段。SLA 中关于审计追溯和责任认定的条款可以基于此能力得到更可靠的技术履行。
*   **事件预算消耗**：由密码学签名验证失败或谱系缺失导致的请求拒绝，应被分类为**安全事件**，并单独计算其对事件预算（Error Budget）的消耗，以区分其与传统基础设施故障的影响。
