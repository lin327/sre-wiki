## Overview

During the development of Grafana's `dashboardNewLayouts` feature, an architectural change caused multiple scrolling-related behavioral exceptions. This feature moves the page's scroll container from the root `body` element to an inner child element. In SRE practice, the availability of monitoring panels, the reliability of automated screenshots, and the consistency of access across platforms (desktop and mobile) are key to ensuring observability and incident response efficiency. Although this change may serve new layout requirements, its side effects directly affect the core user operation process and require analysis and repair from the perspectives of reliability and user experience.

## Core concepts

* **Scroll Container**: refers to the HTML element that hosts scrollable content in a page or application. In traditional web pages, the `body` or `html` element is usually the default scroll container.
* **Keyboard Navigation**: The way users use the keyboard (such as arrow keys and Tab keys) to move focus and scroll content on the page. This is an important part of Web Accessibility (WCAG).
* **Full Page Screenshot**: A technology that captures the complete visible area of ​​a web page (or the entire document) as an image at one time. It is often used for automated testing, fault report archiving, and document generation.
* **Mobile Viewport**: The display area allocated by mobile device browsers for web content. Its behavior is often related to the display/hide dynamics of the address bar (URL Bar).

## Practice

The rolling container changes introduced by `dashboardNewLayouts` have led to the following three specific issues, which SREs need to pay attention to when using the monitoring panel and automated operation and maintenance:

### 1. Keyboard scrolling function interrupted

* **Issue Description**: When a user uses the keyboard's up/down arrow keys on a Grafana dashboard page, it is expected that the entire page should scroll smoothly. However, since scroll events are now captured by internal elements, the keyboard's scroll instructions may not be delivered correctly, causing the page to fail to scroll or scrolling to behave unexpectedly.
* **SRE Impact**: In large monitoring centers or operation and maintenance centers, operators may rely on the keyboard for quick navigation and viewing. This issue reduces operational efficiency and can be disruptive in incident response scenarios where long dashboards need to be quickly scanned to locate critical information.

### 2. Full page screenshot is invalid

* **Problem description**: Many snipping tools and browser built-in features rely on the scroll height of `document.documentElement` (i.e. the `<html>` element) or `body` to determine the total height of the page in order to capture the full page content. When the scroll container is an inner element, these tools may not get the correct total height of the page, causing the screenshot to only capture the currently viewable area rather than the complete scroll content.
* **SRE Impact**: Full-page screenshots are an important means for SREs to document fault snapshots, create reports, and archive incident status. The screenshots generated by automated scripts may be incomplete, affecting the completeness of post-analysis and report quality. [[observability]]

### 3. The hiding mechanism of the address bar in mobile browsers is blocked

* **Problem description**: In mobile browsers, when the user scrolls down the page, the address bar is usually automatically hidden to maximize the content visible area. This mechanism usually relies on scroll events from the page's root scroll container. The change of the scroll container may have interrupted this event chain, causing the address bar to not be hidden properly, making the visible area smaller when viewing the dashboard on the mobile terminal.
* **SRE Impact**: With the increase in mobile operation and maintenance scenarios, SREs may need to quickly view dashboard status on mobile phones or tablets. Continuous display of the address bar will compress valuable screen space and affect diagnostic efficiency on the mobile terminal. [[Mobile Observability]]

## SRE Key Points

* **Association with reliability, observability, incident response**:
    * This issue is a typical **front-end reliability** flaw that weakens the usability and consistency of the monitoring tool (Grafana) itself.
    * During incident response, SREs need fast, unhindered access to monitoring data. Interrupted keyboard navigation and mobile display issues can increase operational friction and impact **incident response MTTR (Mean Time to Repair)**.
    * The failure of automated screenshots may affect the archiving integrity of **observability** data, making it difficult for subsequent review and root cause analysis.

* **Best Practices and Common Anti-Patterns**:
    * **Best Practice**: When making major changes to the underlying DOM structure of a web application (such as changing the scroll container), **regression testing** must be performed. The scope of testing should cover accessibility (keyboard navigation), automation tool compatibility (such as screenshots, crawlers), and cross-device/browser consistency (especially mobile).
    * **Anti-Pattern**: Optimize only for visual layout, while ignoring the knock-on impact of this change on page interaction behavior and existing automated workflows. This reflects the mentality of "coding for testing" rather than "designing for reliability".

* **Related indicators (SLI/SLO/SLA)**:
    * **SLI (Service Level Indicator)**: Consider defining "operability of key monitoring panels on major browsers and devices" as an SLI. Specific indicators can include "keyboard navigation success rate", "mobile terminal full view reachability rate" or "automated screenshot script success rate".
    * **SLO (Service Level Objective)**: SLOs can be set for "core functionality availability" of internal tools like Grafana, such as "99% of common operations (e.g. scrolling, screenshots) work as expected in specified browser and device configurations".
    * If this defect is not fixed, it will directly threaten the achievement of relevant SLOs and affect the reliability commitment of internal tool services.
