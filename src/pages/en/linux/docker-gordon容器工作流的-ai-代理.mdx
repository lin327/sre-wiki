## Overview

Gordon is the AI Agent officially launched by Docker and is deeply integrated into Docker Desktop and Command Line Interface (CLI). Its core value lies in extending AI capabilities from simple code writing assistance to the specific "friction points" faced by developers when building, debugging, and running containerized applications. For SRE and operation and maintenance teams, Gordon represents a new paradigm that brings intelligent operation and maintenance (AIOps) capabilities to the development process. By understanding the real container environment context, it can significantly shorten the time of fault diagnosis and environment configuration, thereby improving overall system reliability and delivery efficiency.

## Core concepts

- **Container context-aware AI agent**: Unlike general-purpose AI programming assistants, Gordon is designed to be an "agent". It has access to the local development environment and can read the running container logs, image list, Compose files, and the contents of the working directory. This means it understands the state of your system before you even ask a question, providing precise, context-based recommendations and solutions.
- **Approval-First Principle**: This is the cornerstone of Gordon's security. Any action proposed by Gordon (such as executing a shell command, modifying a file, running a Docker command) will be clearly shown to the user before execution, and will require the user's explicit approval. This transparent, controlled interaction model ensures developers have the final decision-making power and prevents accidental operations.
- **Session-scoped permissions**: Gordon's permissions (such as shell access, file system operations) are limited to the current session. Once the session is closed, these temporary permissions are reset, ensuring security and avoiding the risk of persistent backdoors.

## Practice

**Access and Use**
Gordon is currently available via Docker Desktop version 4.74+ and the Docker CLI.
1. **Through Docker Desktop**: There is a dedicated Gordon tab in the sidebar of the Docker Desktop interface, which can be separated and used floatingly. In addition, when problems occur in management interfaces such as images, containers, and volumes (such as container startup failure), Gordon can be started directly from the list for diagnosis and repair.
2. **Via the command line**: Run the `docker ai` command in any directory to start a terminal-based Gordon session, which has the same capabilities and context as the desktop version.

**Typical application scenarios and operations**
- **Troubleshooting**: When the container exits or the build fails, describe the problem directly to Gordon (such as "My container keeps exiting"). It reads the logs, traces back to the root cause of the failure (e.g. missing environment variables, wrong base image, wrong volume mount) and proposes a fix, waiting for your approval before automatically applying it.
- **Quick environment setup**: Faced with a new service without a Dockerfile, you can ask Gordon to "Containerize this app and set up a dev environment with Postgres." It analyzes the code, generates a Dockerfile, writes docker-compose.yml, runs and displays the results.
- **Task Automation and Optimization**: Can perform daily operation and maintenance tasks, such as "Clean up unused images". It's also possible to optimize an existing configuration, for example by asking "Optimize this Dockerfile" and Gordon might suggest using a multi-stage build, adjusting the layer order to take advantage of caching, switching to a lighter base image and adding health checks.
- **Instant query and learning**: No need to memorize complex CLI parameters, just ask "Show me running containers" or "How much disk space is Docker using?" to get information. You can also ask about Docker concepts such as “Explain bind mounts vs named volumes in the context of my setup.” to get an explanation based on your actual environment.

## SRE Key Points

**Association with reliability, observability, incident response**
Gordon partially extends observability from traditional centralized logging/monitoring systems to developers' local debugging. By analyzing real-time data such as container logs and running status, it acts as the "first responder" in the development phase and can quickly locate the root cause of environment configuration errors or application crashes and prevent such problems from flowing into the production environment. This directly helps to improve system reliability (Reliability) and shorten the mean time from problem discovery to repair (MTTR).

**Best Practices and Common Anti-Patterns**
- **Best Practices**:
    - **As a context extender**: Use Gordon as a complement to existing SRE and monitoring tools to solve "it works on my machine" problems encountered in local development environments.
    - **Teaching with its approval mechanism**: For a junior member of the team, observing and approving the actions Gordon performs is a process in itself of learning Docker best practices and troubleshooting logic.
    - **Integrated into CI/CD failure debugging**: Although Gordon is mainly used locally, its ability to analyze logs and propose fix ideas can inspire teams to write smarter CI/CD failure alerts and automatic diagnostic scripts.
- **Common anti-patterns**:
    - **Complete Blind Trust**: Although there is an approval mechanism, developers still need to understand every suggestion Gordon makes, rather than mechanically "approving" it. AI may produce imperfect or suboptimal solutions.
    - **Ignore session security**: Forgetting to close a session will reset permissions, so be sure to close the session promptly after use in sensitive environments.
    - **Replaces learning of fundamental principles**: Gordon is an efficient tool, but it cannot replace a developer's understanding of core concepts such as Docker, container networking, and storage.

**Related Indicators (SLI/SLO/SLA)**
Although Gordon itself is a development aid, its effective use can indirectly affect the following SRE focused metrics:
- **SLI (Service Level Indicator)**: For example, reducing the number of development process interruptions caused by environment configuration errors.
- **SLO (Service Level Objective)**: Teams can use "Successfully resolve X% of local container issues using Gordon" as an internal performance SLO.
- **SLA (Service Level Agreement)**: For teams that provide an internal developer platform, integrating such AI tools can improve the "internal SLA" to developers, promising faster environment preparation and issue resolution time.
