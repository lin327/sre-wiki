## Overview

This document provides a detailed analysis of an important client behavior change introduced in etcd v3.7: when a non-zero `DialTimeout` is set, the `clientv3.dial` function becomes a blocking call. This change is different from the behavior of etcd v3.5 and v3.6. It may cause client tools (such as `etcdctl`) to be unable to query healthy nodes normally when some cluster nodes are down, thus affecting the efficiency of operation and maintenance operations and troubleshooting. Understanding the cause, impact, and resolution of this change is critical to maintaining the reliability of your etcd cluster and the robustness of your clients.

## Core concepts

### `clientv3.dial` and DialTimeout

`clientv3.dial` is a key function used within the etcd client library to establish a gRPC connection with the etcd server. The `DialTimeout` parameter controls the timeout for establishing this connection.

### Behavior change analysis

In **etcd v3.5 and v3.6**, the blocking behavior of `clientv3.dial` is strictly controlled by the `grpc.WithBlock()` option. Only when this option is set, `dial` will block until the connection is established or times out. By default (`WithBlock()` is not set), `dial` is non-blocking, returning immediately and the connection is established in the background.

Starting with **etcd v3.7** (introduced by [PR #21282](https://github.com/etcd-io/etcd/pull/21282)), `clientv3.dial` becomes a blocking call whenever `DialTimeout` is set to a non-zero value, regardless of whether `grpc.WithBlock()` is specified. This means that when the client starts, it will be blocked until the connection is established or times out.

This change stems from a fix for a gRPC anti-pattern. According to the recommendations of [gRPC-Go official documentation](https://github.com/grpc/grpc-go/blob/master/Documentation/anti-patterns.md), the client should not actively check whether the connection is "Ready" before initiating an RPC call, but should rely on the error returned by the RPC call itself to handle connection problems. The new behavior is intended to follow this pattern more closely, but unexpectedly changes the semantics of calling the `clientv3.dial` function.

### Impact scenario: Some nodes in the cluster fail

The most direct impact of this behavior change is reflected in the client behavior when some nodes in the cluster fail:
- **v3.6 Behavior**: When connecting to a failed node fails (`connection refused`), the client library will report an error immediately, but the load balancer will redirect it to other healthy nodes, and commands (such as `etcdctl endpoint status`) can still be successfully executed and return the status of the healthy node.
- **v3.7 Behavior**: Since `dial` is blocking, it will continue to try to connect to all endpoints until one of the connections succeeds or `DialTimeout` times out. If the first endpoint trying to connect is the failed node, and the connection timeout is set to a long time, the client will block until timeout, and eventually the entire command will fail, even if other nodes are healthy.

## Practice

### Solutions and configuration examples

#### Solution 1: Set DialTimeout to 0 (recommended)

This is the most direct and compatible solution. Set `DialTimeout` to `0` to revert to the non-blocking behavior of v3.6 and earlier.

```go
import (
    "go.etcd.io/etcd/clientv3"
    "time"
)

// Use DialTimeout: 0 to restore non-blocking behavior
cli, err := clientv3.New(clientv3.Config{
    Endpoints: []string{"etcd1:2379", "etcd2:2379", "etcd3:2379"},
    DialTimeout: 0, // Key settings
})
```

For `etcdctl`, this can be set via environment variables or command line parameters:
```bash
ETCDCTL_DIAL_TIMEOUT=0 etcdctl endpoint status -w table --cluster
```

#### Option 2: Combined with `grpc.WithBlock()` for precise control

If a blocking connection is indeed required for pre-start checking, the `grpc.WithBlock()` option should be used explicitly, along with a reasonable timeout. This scenario is more consistent with gRPC's recommended usage.

```go
import (
    "go.etcd.io/etcd/clientv3"
    "google.golang.org/grpc"
    "time"
)

// Use WithBlock explicitly and set a timeout
cli, err := clientv3.New(clientv3.Config{
    Endpoints: []string{"etcd1:2379", "etcd2:2379", "etcd3:2379"},
    DialTimeout: 5 * time.Second,
    DialOptions: []grpc.DialOption{grpc.WithBlock()},
})
```

#### Container and orchestration environment considerations

In environments such as Kubernetes, the connection parameters of etcd clients (such as kube-apiserver) are usually controlled by startup parameters. It is necessary to check and possibly adjust related configuration items such as `--etcd-servers` and `--etcd-dial-timeout`. For etcd clusters managed using etcd-operator or a custom operator, ensuring compatibility of the client library version with the etcd server version is key.

## SRE Key Points

### Impact on reliability

- **Troubleshooting window narrows**: When some nodes fail, the behavior of operation and maintenance personnel using tools such as `etcdctl` to check the cluster status changes from "partial success" to "complete failure", which may delay the judgment of the overall cluster health.
- **Increased risk of client startup**: In a distributed system, the list of nodes on which a client connection depends may not all be available. Blocking connections mean that the client startup (or reconnection) process may be prolonged due to a single unreachable node, increasing the vulnerability and uncertainty of service startup.
- **Timeout Configuration Sensitivity**: Improper `DialTimeout` settings can amplify this problem. Too short may cause the client to be unable to connect to a healthy slow node; too long may cause the client to block for a long time in front of the failed node.

### Best Practices and Anti-Patterns

- **Pre-upgrade compatibility testing**: Before upgrading the etcd cluster or client library version, be sure to test the behavior of the client under various failure scenarios (such as node downtime, network partitions) in a pre-release environment.
- **Clear client connection intent**: When writing custom etcd client programs, you should explicitly select "non-blocking" (`DialTimeout=0`) or "blocking and explicitly set timeout" (`DialTimeout>0` + `WithBlock()`) mode to avoid ambiguous default behavior.
- **Monitor Connection and Latency**: Monitor the client's connection establishment time and failure rate. This behavior change may result in a significant increase in P99 latency for clients to establish connections, especially if the cluster is unhealthy.

### Related Indicators (SLI/SLO/SLA)

- **SLI (Service Level Indicator)**:
    - `etcd_client_connection_duration_seconds`: Histogram of the time it takes for the client to establish a connection.
    - `etcd_client_requests_failed_total`: The total number of failed client requests due to connection problems or timeouts.
- **SLO (Service Level Objective)**: SLO can be set, such as "99% of the time, the client's delay in connecting to an available etcd node is < 500ms". Behavioral changes in v3.7 may affect achievement of this SLO, requiring the `DialTimeout` parameter to be re-evaluated and adjusted.
- **Error Budget**: Additional client connection failures or timeouts caused by this behavior change will consume the "error budget" of the service and may trigger alarms about etcd client stability, requiring the SRE team to intervene in investigation and adjustment.
