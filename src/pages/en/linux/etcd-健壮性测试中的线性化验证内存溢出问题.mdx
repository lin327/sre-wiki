## Overview

In etcd's continuous integration (CI) process, robustness testing (Robustness Test) is a key link to ensure data consistency and system stability. Among them, Linearization Validation is a resource-intensive step that analyzes event history to confirm that the operation sequence conforms to the linear consistency model. According to etcd project issue #21928 records, this verification process can consume up to 40GB of peak memory in certain high-traffic test scenarios, causing the process running the test to be forcibly terminated by the operating system due to out-of-memory (OOM). This problem directly affects the reliability and test coverage of etcd CI, and is an important improvement point to improve the flexibility and reliability of etcd.

## Core concepts

### Linearization

Linearization is a strong consistency model in distributed systems. It requires that all operations appear to take effect atomically in some global order at a single point in time. For key-value stores like etcd, linearized reads and writes ensure that the data view seen by all clients is consistent and predictable. In robustness testing, verifying linearization is a key means of proving that etcd can maintain its core consistency promises despite disturbances such as network partitions, node failures, etc.

### OOM (Out-Of-Memory)

OOM refers to a process in which the memory requested by a process exceeds the limit allocated by the system or container cgroup and is terminated by the OOM Killer of the operating system kernel. In test and production environments, the occurrence of an OOM is often considered a serious reliability event because it can lead to service interruptions, task failures, and the risk of data loss. In a CI environment, OOM means a test task failed, possibly masking the real problem to be detected.

### Space Exploration

In linearization verification, to confirm the validity of a sequence of events, the algorithm may need to explore all possible orderings of operations and overlapping relationships (i.e., the "space"). For very long or complex histories (such as logs generated by high-traffic scenarios), this exploration can lead to exponential memory growth, which is the root technical cause of OOM.

## Practice

### Problem reproduction and analysis

This problem was discovered in etcd's nightly robustness test (Robustness test nightly run jobs), which manifested itself as CI jobs (such as `ci-etcd-robustness-main-arm64`) being killed by the system. With improvements introduced in etcd PR #21807, tests can now save reports before validating them, allowing issues to be reproduced locally.

A typical reproducible case comes from the test case `TestRobustnessExploratory_KubernetesHighTraffic_ClusterOfSize1_raftAfterSave=sleep`. In the Kubernetes high-traffic scenario simulated by this use case, when linearizing the generated event history, the memory usage peaked at about 40GB, which is far beyond the memory limit of a regular CI node or container.

### Initial solution ideas

The community proposed some initial ideas in issue #21864, but due to the inherent space exploration nature of the linearized verification algorithm, it is extremely difficult to completely eliminate the risk of OOM in all cases. The current phase focuses on establishing locally reproducible test benchmarks (such as saved historical reports) and tracking subsequent optimization efforts. Possible optimization directions include:

1. **Algorithm Optimization**: Improve the linearization verification algorithm, adopt more memory-saving heuristic methods or pruning strategies, and reduce unnecessary space exploration.
2. **Memory limits and monitoring**: Set more precise memory limits for verification tools or CI jobs, and add memory usage monitoring to gracefully degrade or save intermediate states before reaching thresholds.
3. **Test case stratification**: Classify test cases based on historical complexity and expected memory consumption, and use ultra-high resource consumption cases to be scheduled separately or run on higher-configured nodes.

## Key points of SRE regulations

* **Relationship with reliability and event response**: Although this problem occurs in the test environment, it is directly related to the reliability verification capabilities of etcd itself. Instability of the test infrastructure (such as failure due to OOM) hinders our confidence assessment of the reliability of production components. Treat this as an internal SRE event that needs to be tracked until resolved to ensure the robustness of the verification pipeline.
* **Best Practices and Common Anti-Patterns**:
    * **Anti-Pattern**: Ignore the resource constraints of the test infrastructure and hard-code resource-intensive tasks into the standard pipeline, leading to instability.
    * **Best Practice**: Implement **resource budget** and **capacity planning** to allocate differentiated computing resources for different types of test tasks (such as ordinary unit testing, integration testing, high-load robustness testing). At the same time, **test stability** monitoring indicators are established to issue alarms for test jobs with frequent OOM.
* **Related indicators (SLI/SLO/SLA)**:
    * **SLI**: The frequency of robustness test jobs in the CI pipeline failing due to OOM (number of times/day).
    * **SLO**: Successful completion rate of robustness test jobs (not failing due to infrastructure issues) &gt; 95%.
    * **Internal SLA**: For robustness test jobs that fail due to OOM, a clear root cause analysis or optimization plan is required within N working days. This ensures that test debt is repaid in a timely manner, maintaining long-term reliable verification capabilities.
