# fix(annotations): ignore duplicate annotation_tag rows on concurrent writes

## Overview

In complex systems such as Grafana, Annotations are a key feature that allow users to add contextual information to monitoring data. Annotation tags (Tags) further provide the ability to classify and retrieve annotations. When multiple users or automated processes create annotations with the same label concurrently, it can cause conflicts in the underlying database operations. This page records in detail a typical concurrent write defect and its repair plan. This repair is crucial to ensuring the **reliability** and **data consistency** of the monitoring system.

## Core concepts

### Non-Atomic Read-Then-Insert Pattern
This is the root cause of this problem. In the code logic before the fix (`ensureTags` function), the system will first query whether the tag already exists before inserting a new tag. This "read first, insert later" sequence of operations is not atomic in a concurrent environment. If two processes read the same tag at the same time, find that it does not exist, and then both try to insert, one of the insert operations will fail.

### Unique Constraint Violation
In order to ensure the uniqueness of tags at the database level, the `annotation_tag` table usually sets a unique index for the combination of `annotation_id` and `tag_id`. When the above non-atomic operation attempts to insert an existing record, the database will violate this unique constraint and throw an error, causing the entire annotation write operation to fail.

### Atomic Insertion
This is the recommended solution. By using a database insert statement that supports ignoring or updating in case of conflicts (such as `INSERT ... ON CONFLICT DO NOTHING`), the two steps of "querying for existence" and "performing the insert" can be combined into a single atomic operation. The database ensures that this operation can be performed safely even under high concurrency, either successfully inserting new records or silently skipping existing records.

## Practice

### Problem phenomenon
In Grafana v13.0.3 and earlier, when annotations with the same label are created in rapid succession or in batches via scripts, errors similar to the following may appear in the system log:
```
pq: duplicate key value violates unique constraint "annotation_tag_annotation_id_tag_id_key"
```
This error will cause some annotations to fail to be created, affecting user experience and data integrity.

### Repair plan
Grafana fixed this issue via commit [PR #126303](https://github.com/grafana/grafana/pull/126303). The core changes are as follows:

1. **Modify SQL statement**: Replace the original `InsertMulti` call (which may execute multiple independent `INSERT` statements internally) with a statement using `INSERT ... ON CONFLICT DO NOTHING` syntax.
2. **Ignore conflicting records**: The new logic clearly specifies that when the inserted `annotation_id`/`tag_id` combination conflicts with an existing record, the database should ignore the insertion request instead of throwing an error.
3. **Backport**: This fix was backported to the stable version branch of 13.0.3 to ensure that old users can also benefit.

**Example logical comparison:**
```sql
-- Pseudo logic before fix (non-atomic)
BEGIN;
SELECT id FROM tag WHERE name = 'new-tag';
-- If not present, insert
INSERT INTO tag (name) VALUES ('new-tag');
COMMIT;

-- Fixed atomic logic
INSERT INTO tag (name) VALUES ('new-tag') ON CONFLICT (name) DO NOTHING;
```
*Note: The above is a schematic, the actual repair is performed at the `annotation_tag` association surface level. *

## SRE Key Points

### Association with reliability
- **Improved system robustness**: This fix eliminates a deterministic failure point caused by concurrency, making Grafana's annotation functionality more stable in high-load, multi-user scenarios.
- **Ensure data consistency**: By avoiding failures caused by unique constraint conflicts, it ensures that all legal annotation requests can be accepted and recorded by the system, maintaining the integrity of the monitoring context data.
- **Impact SLO**: For teams that rely on Grafana annotations for post-mortem analysis or event labeling, such a failure could disrupt critical operational processes, directly impacting internal SLOs (e.g. "Annotation creation success rate &gt; 99.9%"). Remediation helps achieve or maintain that SLO.

### Best practices and common anti-patterns
- **Anti-Pattern: "Read-Modify-Write" under Optimistic Concurrency**: In a distributed or concurrent environment, it is dangerous to simply "query whether it exists first, and then decide to insert or update". Priority should be given to using the atomic operations provided by the database (`UPSERT`, `ON CONFLICT`, `MERGE`).
- **Best practice: Design to be conflict-safe (Conflict-Safe)**: When writing business logic that handles shared resources, it should be assumed that concurrency conflicts may occur, and handled with lock-free or database-guaranteed atomic operations.
- **Best Practice: Refine Error Handling**: For "conflicts" caused by business rules (such as "tag already exists" here), they should be handled as part of the normal process rather than propagated upward as a system exception.

### Related indicators (SLI/SLO)
- **SLI**: `annotation_create_success_rate` (annotation creation success rate), which can monitor the proportion of failed requests caused by unique constraint errors.
- **SLO**: Goals can be set, such as "The annotation creation failure rate due to concurrency conflicts per month is less than 0.01%."
- **Observability**: After the fix, you should observe that the log volume for such unique constraint errors drops significantly to zero via Grafana's logs or metrics panel.
