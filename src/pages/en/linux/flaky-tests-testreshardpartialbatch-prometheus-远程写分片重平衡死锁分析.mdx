# [flaky tests] TestReshardPartialBatch

## Overview

In the continuous integration of Prometheus, `TestReshardPartialBatch` is an integration test used to verify the correct behavior of the Remote Write path when the number of shards is dynamically adjusted (Resharding). The failure of this test (flaky test) exposed a potential flaw of `QueueManager` in high concurrency and fast stop scenarios: **goroutine deadlock**. For SREs, it is critical to understand the root cause of such test failures because it is not purely a testing problem, but reveals the risk of service degradation or data latency that may occur under specific load patterns for remote write components in production environments. Such problems directly affect the data freshness SLA and are reliability risks that require in-depth analysis.

## Core concepts

1. **Prometheus Remote Write**: The mechanism by which Prometheus pushes the collected time series data to remote storage (such as Thanos, Cortex, or other API-compatible systems) through the HTTP protocol. Its core is `QueueManager`, which manages multiple shards (Shards) used to send data asynchronously.
2. **Resharding (shard rebalancing)**: When the throughput demand of the remote write target changes, `QueueManager` will dynamically adjust the number of shards used to send data in parallel (`updateShardsLoop`). This involves stopping the old sharded coroutine and starting a new sharded coroutine, which is a complex concurrent operation.
3. **Deadlock**: In this case, the test log clearly states `Deadlock between sending and stopping detected`. This means that the coroutine responsible for sending data (`runShard`) and the coroutine responsible for responding to stop signals or rebalancing (`reshardLoop`, `updateShardsLoop`) wait for each other to complete, causing the entire remote write path to stall.
4. **Go Goroutine Profile**: A powerful tool for analyzing the status of all active coroutines in a Go program. In the profile of this issue, 72 coroutines are blocked in the queue operation of `(*shards).runShard`, which directly points to the blocking of the sending path as the key to the problem. At the same time, the coroutines of `reshardLoop` and `updateShardsLoop` are also in a blocked state, forming a deadlock evidence chain.
5. **`synctest` package**: Go’s `testing/synctest` package (and the project-encapsulated `testutil/synctest`) is used in the test. This package uses "virtual time" to control the passage of time in concurrent tests. Although it solves the test timing problem, it may also cover up real race conditions in some complex concurrency scenarios, making the problem more difficult to reproduce and debug.

## Practice

To analyze such concurrency deadlock issues, SREs and developers should follow the following debugging practices:

1. **Locate blocking points**: Start with goroutine profile. Identify the stack frame with the largest number of blocked coroutines. In this case, `(*shards).runShard+0x935` is the key. This suggests that the problem occurs in a specific operation of data packaging or sending queue within the shard (such as `(*queue).newBatch`).
2. **Understand the concurrency process**: Trace the relevant code paths.
    * **Normal sending path**: The `runShard` coroutine fetches data from the internal queue, packages it into `WriteRequest`, and then sends it via HTTP. After the sending is completed or when an error occurs and retry occurs, the loop will be re-entered.
    * **Stop/Rebalance Path**: `reshardLoop` listens for the rebalance signal and calls `(*shards).stop` to gracefully terminate all old shard coroutines. It relies on the sharded coroutine to be able to respond to stop signals in a timely manner.
3. **Construct deadlock hypothesis**: A typical deadlock scenario may be:
    * The sharding coroutine (`runShard`) is stuck on the lock of the sending or waiting queue due to network jitter or slowdown of the downstream service.
    * At the same time, `reshardLoop` triggers rebalancing and attempts to `stop` these sharded coroutines.
    * The `stop` method may need to acquire the same lock or wait for the sharded coroutine to complete an operation that cannot be completed (for example, waiting for a queue that will never be consumed), causing `reshardLoop` to also block.
    * Eventually, sending data and stopping/rebalancing operations wait for each other, forming a deadlock.
4. **Reproduction and Simplification**: Data races can be detected by running tests with the `-race` flag (`go test -race`). At the same time, analyze the use of `synctest` to confirm whether it "freezes" some real system calls or network I/O that may expose problems, so that race conditions can only be discovered by manually advancing time in the test.

## SRE Key Points

* **Relationship to Reliability**: Remote writes are a critical link in the Prometheus observability pipeline. Its deadlock will prevent data from being delivered to long-term storage, directly affecting alerts and dashboards based on this data. For SRE, this means **SLO loss**, e.g. the goal of "remote write end-to-end latency < 5s" cannot be achieved. Monitoring metrics such as `prometheus_queue_shards_total` and `prometheus_queue_sent_samples_total` for mutations is critical for early detection of such issues.
* **Best Practices and Anti-Patterns**:
    * **Best Practice**: Perform adequate stress testing and chaos testing of the concurrency logic of core components (such as `QueueManager`). In a production environment, the frequency of `reshard` events should be monitored, as too frequent rebalancing itself may be a sign of instability.
    * **Common anti-pattern**: Assume that all concurrency primitives (such as mutex, channel) are perfect. In complex asynchronous data flows, especially on paths involving stopping and graceful shutdown, special care needs to be taken in the order of lock acquisition and the closing semantics of channels to avoid loop waiting.
* **Related indicators (SLI/SLO)**:
    * **SLI**: Remote write queue depth (`prometheus_queue_length`), number of remote write shards (`prometheus_queue_shards_total`), remote write error rate (`prometheus_remote_storage_samples_total{result="dropped"}`).
    * **SLO**: Example - "99.9% of the time, the latency from when data is ingested by Prometheus to when it is available for remote querying is less than 10 seconds." Deadlocks can directly lead to violations of this SLO.
