### Configuration example: SNI routing using TLSRoute

The following example shows how to configure TLSRoute in `Passthrough` mode to forward encrypted traffic for a specific SNI (`foo.example.com`) directly to a backend service.

```yaml
#Define the Gateway listener that enables Passthrough mode
apiVersion: gateway.networking.k8s.io/v1
Kind: Gateway
metadata:
  name: example-gateway
spec:
  gatewayClassName: example-gateway-class
  listeners:
    - name: tls-passthrough
      protocol: TLS
      port: 8443
      tls:
        mode: Passthrough # Key configuration
---
# Define TLSRoute matching SNI
apiVersion: gateway.networking.k8s.io/v1
kind: TLSRoute
metadata:
  name: foo-route
spec:
  parentRefs:
    - name: example-gateway
      sectionName: tls-passthrough
  hostnames:
    - "foo.example.com"
  rules:
    - backendRefs:
        - name: foo-svc
          port: 8443
```

## SRE Key Points

### The connection between reliability, observability and incident response

- **Reliability**: Standardization of functions means API stability and behavioral consistency, reducing the risk of production failures due to version changes or implementation differences. Adopting the Release Train model makes the release cycle predictable, making it easier for the SRE team to plan upgrade and maintenance windows.
- **Observability**: Standard resources (e.g. ListenerSet, TLSRoute) provide clear, auditable statements about traffic paths. Combined with Kubernetes metrics and logs, SRE teams can more accurately monitor the traffic, connection status, and error conditions of each team or service. For example, each listener introduced by a ListenerSet and its associated backend health can be monitored independently.
- **Incident Response**: When routing or security issues arise, standardized APIs make the diagnostic process more structured. For example, by examining the TLSRoute configuration and listener mode, you can quickly determine whether it is a certificate issue, an SNI mismatch, or a policy denial. Multi-team ListenerSet configuration helps isolate and target changes introduced by specific teams.

### Best practices and common anti-patterns

**Best Practices:**
1. **Gradual Adoption**: Start piloting new features (such as ListenerSet) with non-critical services and then gradually roll them out.
2. **Clear Ownership**: Use ListenerSet and ReferenceGrant to clearly divide listener and resource reference permissions between the infrastructure platform team and the application team.
3. **Security first**: When client certificate verification (mTLS) is enabled, **the `AllowValidOnly` mode is used by default**. Only consider using `AllowInsecureFallback` if you fully understand the risks and cooperate with backend authorization.
4. **Standardized TLS policy**: Based on back-end security requirements, uniformly select `Passthrough` (end-to-end security) or `Terminate` (centralized management) mode, and clarify its applicable scenarios in the policy document.

**Common anti-patterns:**
1. **"Wildcard" CORS configuration**: `allowOrigins: ["*"]` is widely used in production environments, which can bring security risks. Should always be restricted to specific trusted sources.
2. **Ignore version migration**: When upgrading from v1.4 or earlier experimental versions, the change in resource API version (such as migrating from `v1alpha2`/`v1alpha3` to `v1`) is not paid attention to, resulting in existing resources not being recognized by the new controller.
3. **Abuse of `AllowInsecureFallback`**: Using it as the default fallback strategy for client certificate verification failure is equivalent to turning off mTLS protection, completely transferring security responsibilities to the backend, and increasing system vulnerability.

### Related Indicators (SLI/SLO/SLA)

Although the Gateway API itself does not directly define SLOs, its configuration and status are the basis for implementing traffic-related SLOs:

- **SLI (Service Level Indicator)**:
    - `Request Success Rate`: For HTTPRoute, the `2xx` response ratio can be monitored.
    - `TLS handshake success rate`: For the TLSRoute listener, monitor the number of TLS handshake failures.
    - `Number of connections for a specific SNI`: Used to track the traffic of each team in a multi-tenant environment.
- **SLO (Service Level Objective)**:
    - Availability targets (e.g. 99.95% successful request rate) can be defined for critical services exposed through a specific Gateway/Route.
    - Ability to define TLS handshake delay SLOs for critical TLS services such as payment interfaces.
- **Relevance**: Gateway's listener configuration (such as `clientCertificateValidation` mode) directly affects the connection establishment method and failure mode, which in turn affects the calculation of the above SLI. The SRE team needs to correlate Gateway configuration changes with SLO alerts and events.
