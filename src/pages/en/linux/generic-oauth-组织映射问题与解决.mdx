# Grafana Issue

## Overview

This document records and analyzes a serious flaw in the configured Organization Mapping function when using Generic OAuth (such as Auth0) for user authentication in Grafana v11.5.1. This flaw causes users to always be assigned to Grafana's default organization (ID 1) after logging in, regardless of the configured `Organization mapping` rules, and cannot be correctly mapped to the specified target organization. This is a critical issue that affects the reliability of SSO integration and directly breaks the core ability to do multi-tenancy or team isolation based on user identity attributes (such as `org_id` claim).

## Core concepts

- **Generic OAuth and JWT Claims**: Grafana supports access to multiple identity providers (IdP) through Generic OAuth. In the OAuth 2.0 process, IdP usually contains custom user attribute claims (claims) in JWT (JSON Web Token), such as the `org_id` field added by Auth0 in this example. These claims are the data basis for organizational mapping.
- **Organization Mapping**: In Grafana's OAuth authentication configuration, administrators are allowed to set rules to map user attributes returned by the OAuth provider (specified by `Organization attribute path`) to pre-created organizations (specified by organization ID or name) and roles within Grafana. The standard mapping format is: `<incoming_org_value>:<grafana_org_id>:<role>`.
- **Mapping process**: A normal process should be: 1) The user logs in, carrying a token containing the `org_id` claim; 2) Grafana extracts the value (such as `org_k77as8hhsh`) based on the `Organization attribute path` (such as `org_id`); 3) Grafana looks for a rule matching the value in the `Organization mapping` list; 4) Assigns the user to the Grafana specified by the rule Organize and grant appropriate roles.

## Practice

### Problem reproduction and configuration

According to the report, a minimalist configuration to reproduce the error is as follows:

1. **IdP (Auth0) configuration**: Ensure that the logged in user's JWT token contains a simple `org_id` claim, such as `"org_id": "org_k77as8hhsh"`.
2. **Grafana organization preparation**: Pre-create the target organization in Grafana, for example, the organization ID is `2` and the name is `B`.
3. **Generic OAuth authentication configuration**:
    * **Organization attribute path**: `org_id` (used to extract the incoming organization ID).
    * **Organization mapping**: `org_k77as8hhsh:2:Viewer` (expects a user with this org_id to be mapped to organization 2, with role Viewer).
    * **Other fields**: Leave default or blank.

### Problem symptoms and verification

After completing the OAuth login flow using the above configuration, observe:
* The user successfully logs into Grafana.
* **Incorrect Behavior**: The user is assigned to Grafana's **Default Organization (ID=1, Name 'A')** with the role Viewer, completely ignoring the explicitly configured mapping rule `org_k77as8hhsh:2:Viewer`.
* **Verification attempt**: Testing all different combinations of `Role attribute path`, `Organization mapping` and `Organization attribute path` failed to map the user to a non-default organization (such as Organization 2). The only way to make the user appear in org 2 is to use wildcard mapping `*:2:Viewer`, but this will lose the meaning of differential mapping based on different `org_id` and is an ineffective solution.

## SRE Key Points

- **Relationship to Reliability and Observability**:
    * **Reliability Impact**: This flaw directly causes a key feature of the OAuth SSO integration - claims-based organization mapping - to **completely fail**. For Grafana deployments that rely on multiple organizations for environment isolation (such as development/production) or customer isolation, this is a P0 level reliability issue.
    * **Observability Blind Spot**: When a user is incorrectly assigned to an organization after logging in, related audit logs (such as login events, organization assignment events) may not accurately reflect the configuration intent, making security investigation and troubleshooting difficult. Administrators need to additionally check the user's actual organization, not the trust map configuration.
    * **Incident Response**: As an SRE, upon encountering a user reporting "cannot access their intended organization's dashboard", you should first check this OAuth mapping configuration for known bugs and follow official updates from Grafana.

- **Best Practices and Common Anti-Patterns**:
    * **Current best practice (temporary workaround)**: Until an official fix is made, **avoid relying on OAuth `Organization mapping` rules for precise organization assignment**. Alternatives may be considered such as:
        1. Use the `*:2:Viewer` wildcard for rough mapping, and then manually adjust the organization to which the user belongs after first logging in via the Grafana API or user management interface. **This is not suitable for large scale or automated scenarios**.
        2. Temporarily disable organization mapping and instead handle user organization assignments on the IdP side or during the Grafana initialization process.
    * **Anti-Pattern**: Wrongly assuming that this feature works fine in the current version and investing a lot of time trying complex combinations of mapping rules, this is the dilemma experienced by the reporter of this issue.

- **Relevant Indicators (SLI/SLO/SLA)**:
    * **SLI (Service Level Indicator)**: can be defined as "the success rate of users logging in via OAuth whose assigned Grafana organization is consistent with the expected IdP claim mapping rules". This bug causes this SLI to most likely be **0%** in the current version.
    * **SLO (Service Level Objective)**: For systems that rely on this feature, the SLO might be "99.9% of user logins should fall into the correct tenant context".
    * **SLA (Service Level Agreement)**: If Grafana claims to support this OAuth integration mode, this bug may constitute a breach of the SLA.
