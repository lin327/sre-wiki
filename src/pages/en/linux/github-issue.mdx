# GitHub Issue

## Overview

Grafana is an open-source data visualization and monitoring platform, and its Dashboards and Panels are core components for building observability interfaces. Among these, the "Time Shift" feature allows users to specify a time offset in panel queries, used for comparing data between the current time window and a historical time window, which is critical for trend analysis and performance comparison. This page documents a key defect that appeared in certain versions after Grafana 11.2.3: enabling time shift for a panel breaks its association with the Dashboard Time Range, causing the panel's data source query to fall back to a default fixed time window (such as 6 hours). This severely affects monitoring data accuracy and panel usability, and is an issue that SRE teams need to pay close attention to during platform upgrades and routine inspections.

## Core Concepts

- **Dashboard Time Range**: The time window set by the user in the upper right corner of the Grafana dashboard (for example, "past 6 hours"). Under normal circumstances, all panels within the dashboard that do not have individual time overrides will issue data queries based on this unified time window.
- **Panel Time Shift**: A panel-level configuration used to shift the query's time range forward or backward as a whole. For example, setting a time shift of `1h` will shift the queried data relative to the current dashboard time range one hour into the past, used for implementing period-over-period analysis.
- **Panel Time Override**: A more powerful feature than time shift, allowing a panel to completely detach from the dashboard time range and use its own independent time window to query data.
- **Root Cause of the Issue**: In specific Grafana versions (such as 11.2.3-security-01, 11.3.x), there is a software defect. When a user configures any non-zero `timeShift` value on a panel, the panel not only applies the time shift but also **incorrectly disables inheritance of the dashboard time range**, defaulting to a fixed time window (usually 6 hours) for the query. This causes the panel to display data with a time span inconsistent with the time range set by the user on the dashboard, resulting in information confusion.

## Practice

### Problem Reproduction and Confirmation

According to the issue report, the reproduction steps for this problem are very simple:
1.  Open or create a dashboard in an affected Grafana version (11.2.3-security-01, 11.3.0, 11.3.1, etc.).
2.  Select a panel (for example, a `timeseries` panel).
3.  In the panel settings, add any Time Shift value (for example, `1h`) to the query.
4.  Observe the panel data: Although the dashboard time range may be set to "past 24 hours," the panel configured with time shift may only display data from the past 6 hours, while other panels without time shift configured normally display 24 hours of data.

### Impact and Rollback

This defect affects panel visualization using data sources such as Prometheus. According to community feedback, the issue was fixed in Grafana version `11.2.4`, but still persists in multiple versions of the `11.3` branch.

**Recommended SRE Temporary Mitigation Measures**:
1.  **Version Locking**: Before an official stable fix is released, stabilize the production Grafana instance on a known reliable version (such as `11.2.3` or `11.2.4`). See [[version-management]].
2.  **Configuration Review**: Immediately review all monitored dashboards, identify and record all panels configured with panel time shift, and assess their data accuracy, especially for critical business SLO monitoring dashboards.
3.  **Remove Time Shift**: In urgent situations where immediate upgrade or rollback is not possible, consider **temporarily removing** time shift configurations from critical panels, restoring them to use the dashboard time range to ensure data continuity and accuracy, though this will lose period-over-period analysis functionality. See [[time-series-visualization]].
4.  **Upgrade Monitoring**: Closely follow Grafana's official Release Notes and issue tracking, confirming the issue is fully resolved in the target version (such as future 11.3.2 or higher) before upgrading. See [[release-cadence]].

## SRE Key Points

### Connection to Reliability, Observability, and Incident Response

- **Observability Credibility Compromised**: This defect directly undermines dashboard data consistency. When SREs or developers rely on panels for troubleshooting or performance evaluation, incorrect time window data may lead to misjudgments, such as incorrectly concluding that traffic has dropped or error rates have disappeared, when in reality they simply occurred outside the incorrectly displayed time window. This seriously damages the credibility of the monitoring system.
- **Change Risk and Management**: This incident highlights the risks associated with version upgrades to monitoring platforms (such as Grafana). Even minor or patch version upgrades can introduce serious defects affecting core functionality. SRE teams must include monitoring platform changes in formal change management processes, with thorough testing (such as using sandbox environments to test critical dashboards). See [[change-management]].
- **Incident Response Interference**: During production environment troubleshooting, relying on a malfunctioning dashboard will extend MTTR (Mean Time To Repair). SREs need to add checks for the monitoring tool's own health status to incident response runbooks.

### Best Practices and Common Anti-patterns

- **Best Practices**:
    - **Version Compatibility Testing**: Before upgrading Grafana, clone production dashboards in a staging environment and perform regression testing on all panels using advanced time features (such as time shift, time override).
    - **Dashboard Design Standardization**: Establish dashboard design specifications, clearly defining when to use global time range and when to use panel time shift, avoiding abuse that leads to excessive feature coupling.
    - **Monitor the Monitors**: Set up monitoring for the Grafana instance itself, ensuring its availability and response time, and triggering alerts when critical dashboards fail.
- **Common Anti-patterns**:
    - **Blind Upgrades**: Upgrading monitoring tools directly in production without testing environment verification, especially when handling "security patch" versions, assuming small version number changes mean low risk.
    - **Feature Abuse**: Over-relying on complex panel-level time operations to generate fixed views instead of using dashboard template variables or reporting features, increasing fragility during maintenance and upgrades.
    - **Lack of Rollback Plan**: Not preparing a rollback plan before upgrading, resulting in inability to quickly recover service when problems occur.

### Related Metrics (SLI/SLO/SLA)

- This issue does not directly affect system SLIs, but it affects the **accuracy of dashboards** used to measure SLIs. If SLO alerts rely on panel data from affected dashboards, it may lead to **alert silencing or false positives**.
- SREs should define **"Critical Function Availability of Monitoring Platform"** as an internal SLI, for example, "100% of critical SLO dashboards work as designed 99.9% of the time." This incident should be recorded as a violation of this SLI, and the root cause (insufficient platform upgrade testing) should be analyzed to improve processes. See [[error-budget]].
