# GitHub Issue

## Overview

In the operations of observability platforms like Grafana, upgrades are necessary steps to maintain system security and feature freshness, but they also carry the risk of introducing new issues. This document describes a typical post-upgrade configuration drift and environment dependency problem: after upgrading to Grafana 13.0.1, pre-configured Elasticsearch data sources completely fail in air-gapped environments that cannot access the external internet. This issue reveals an important deficiency in Grafana's plugin lifecycle management under specific deployment architectures, directly affecting production environment observability, and is a scenario that SRE teams need to be highly vigilant about when planning upgrades, handling incidents, and ensuring service reliability.

## Core Concepts

- **Air-Gapped Environment**: Refers to an internal network that is completely physically or logically isolated from the external public internet. In industries such as finance, government, and critical infrastructure, this deployment model is a common security requirement. Applications running in such environments cannot access external software repositories or update services.
- **Grafana Plugin Lifecycle**: Many of Grafana's data sources (such as Elasticsearch) are not built-in but managed as plugins. Their lifecycle includes installation, update, verification, and uninstallation. In version 13.0.1, the processing logic for the Elasticsearch plugin changed, causing it to potentially attempt network verification during startup.
- **Data Source Configuration Dependency**: Grafana data source configuration (such as connection addresses, authentication information) is stored in the database or configuration files. However, the availability of a data source depends not only on the configuration itself but also on whether the corresponding backend plugin (such as the `elasticsearch` plugin) is in the correct installed and activated state. The disconnect between plugin state and configuration state is the direct cause of the "Data source not found" error.

## Practice

### Problem Diagnosis Process

When encountering a large number of data source connection failures after a Grafana upgrade, SRE should follow these steps for systematic diagnosis:

1.  **Check UI and API Errors**: Observe the specific error messages in the Grafana interface's data source list. Also check the browser developer tools' network requests, especially calls to the `/api/plugins/<plugin-id>/settings` endpoint and their return values. In this case, `Plugin not found` was returned.
2.  **Verify Local Plugin Installation Status**: Use Grafana CLI to confirm whether the plugin exists on the local file system.
    ```bash
    grafana cli plugins ls
    ```
    The output should show installed plugins, e.g., `elasticsearch @ 12.5.4`. This indicates the plugin files themselves exist.
3.  **Check Grafana Server Logs**: Focus on `level=error` log lines and those containing the `plugin` keyword. Key clues are usually hidden here, such as network request timeouts when attempting to fetch plugin version information from `grafana.com` during startup (`context deadline exceeded`), and logs of data source plugin definition lookup failures.
4.  **Analyze Configuration vs. Runtime State Differences**: Directly query Grafana's data source API (`/api/datasources`) and observe the `type` or `typeName` fields. In this case, the field values were found to change depending on whether external network connectivity exists (`Elasticsearch` vs `elasticsearch`), indicating inconsistent plugin identifier handling at runtime.

### Key Commands and Verification

When troubleshooting in air-gapped environments, network connectivity verification is critical:
- Check whether the Grafana server can resolve and access the `grafana.com` domain.
- Confirm that the Grafana service enters a degraded or failure mode during startup because it cannot complete the plugin version check.
- Use `grafana cli plugins ls` to confirm the plugin installation directory is correct (typically `/var/lib/grafana/plugins/`).

### Mitigation and Solutions

1.  **Temporary Mitigation**: In air-gapped environments, a temporary solution is to "simulate" external access. This can be done by configuring DNS resolution or a proxy on the Grafana server or network layer that points to an internal server, so that requests to `grafana.com` are intercepted and return a valid response (even if the content is not the latest). This is not a long-term solution.
2.  **Fundamental Fix**:
    - **Rollback or Upgrade to Fixed Version**: Closely monitor Grafana's official fix patches for this issue. Before the fix is released, you can temporarily roll back to a known stable version (e.g., 12.4.3).
    - **Improve Offline Plugin Management Process**: Establish a complete offline plugin distribution and installation process for air-gapped environments. Before the upgrade window, manually download all plugins and their required plugin repository metadata for the new Grafana version, and host them in an internal repository to ensure Grafana can complete plugin verification from the internal source after the upgrade.

## SRE Key Points

- **Reliability, Observability, and Incident Response Association**:
    - **Reliability**: This issue causes partial functionality of the core observability platform (Grafana) to completely fail, reducing system reliability. It is a typical regression defect introduced by an upgrade.
    - **Observability**: Elasticsearch data sources are commonly used for log or metric analysis. Their failure directly creates a "blind spot" on the observability platform, potentially masking other system issues.
    - **Incident Response**: Such issues occur after the upgrade window, requiring SRE teams to have rapid rollback capabilities and the ability to effectively distinguish between infrastructure issues and issues caused by application upgrades.

- **Best Practices and Common Anti-Patterns**:
    - **Best Practices**:
        1.  **Environment Consistency Verification**: Before performing Grafana upgrades in restricted environments like air-gapped networks, complete testing must be conducted in a staging environment (simulating the same network policies), including all plugin functionality.
        2.  **Configuration as Code and Version Pinning**: Use Provisioning to manage data sources, and consider explicitly specifying plugin versions in files to reduce runtime uncertainty.
        3.  **Offline Installation Strategy**: Prepare offline solutions for all initialization operations that require external network access (such as plugin version checking, installation) to ensure the environment is fully self-sufficient and controllable.
    - **Common Anti-Patterns**:
        1.  **Ignoring Upgrade Notes**: Not carefully reading the Grafana release notes regarding plugin behavior changes.
        2.  **Assuming "Installed Means Available"**: In offline environments, only focusing on whether plugin files are downloaded while ignoring the online verification or metadata update processes that plugins may depend on.
        3.  **Hidden Network Dependencies**: Not sufficiently auditing all network requests an application makes to internal and external services during startup and runtime.

- **Related Metrics (SLI/SLO/SLA)**:
    - **SLI (Service Level Indicator)**: `grafana_datasource_availability`, i.e., the percentage of Grafana data sources that can be successfully queried.
    - **SLO (Service Level Objective)**: Within 1 hour after upgrade, all historically configured (non-newly created) data sources should achieve 100% availability restoration.
    - **Related Incident Metrics**: `MTTD` (Mean Time to Detect) and `MTTR` (Mean Time to Resolve) are particularly important in this incident, used to measure the effectiveness of upgrade monitoring and rollback mechanisms.

This issue highlights that in complex dependency and restricted environments, **configuration drift** and **implicit dependencies** are key risk points that SRE needs to continuously manage and guard against. See [[upgrade-strategy]] and [[offline-plugin-management]] for more related information.
