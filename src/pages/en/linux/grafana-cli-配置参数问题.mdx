# grafana cli: ignores --config argument

## Overview

When using Grafana for daily operation and maintenance, `grafana-cli` is a core tool for managing plug-ins (such as installation, upgrade, and listing). Its flexibility relies heavily on the ability to specify custom configuration files (such as `grafana.ini`) through the `--config` parameter to override the default path settings (such as the plug-in directory `plugins`). However, this entry describes a flaw discovered in Grafana v9.5.x: the CLI tool silently ignores the `--config` parameter, causing it to always use the default configuration path. This directly undermines the expectations of operation and maintenance personnel to manage the consistency of Grafana server and CLI behavior through a single configuration file. Especially in non-standard installation directories or multi-environment deployment scenarios, it will cause problems such as plug-in management failure. As an SRE, understanding such toolchain flaws can help you quickly diagnose and avoid potential pitfalls in automated operations scripts.

## Core concepts

* **Grafana CLI (`grafana-cli`)**: The command line tool provided by Grafana, mainly used for plug-in life cycle management (`plugins ls`, `plugins install`, etc.), and sometimes used for diagnosis. Its behavior should be driven by the configuration file.
* **`--config` parameter**: A key CLI parameter used to explicitly specify the path to the configuration file that Grafana should load. In theory, after the CLI tool parses this parameter, it should read the configuration file and apply the settings there.
* **Configuration file loading mechanism**: Grafana components (including server and CLI) usually follow a set of configuration loading sequence when starting: default configuration -&gt; custom configuration file (specified through `--config` or `-cfg`) -&gt; command line parameter override. This bug indicates that, in some versions, this loading chain for CLI tools breaks after the first step, failing to handle the `--config` parameter.
* **Plug-in path (`plugins`)**: The `plugins` setting in the `[paths]` section of the configuration file defines the plug-in storage directory. When `--config` is omitted, the CLI will use the built-in default path at compile time (usually `/var/lib/grafana/plugins`) instead of a user-configured custom path (such as `/data/grafana/plugins`).

## Practice

### Diagnosis method

If you suspect you are encountering this issue, you can verify it by following these steps:

1. **Path Check**: Use the `strace` tool to trace the system calls of `grafana-cli` and observe whether it tries to open the configuration file you specify.
    ```bash
    strace -e openat grafana-cli --config /path/to/your/grafana.ini --homepath /usr/share/grafana plugins ls 2>&1 | grep -i grafana.ini
    ```
    If the command output does not point to your `grafana.ini` file path, it confirms that the `--config` parameter is not taking effect.

2. **Behavior comparison**: Run the following commands respectively and compare the output. If both outputs are identical (e.g. both show `no installed plugins found`) and you are sure that the plugin is installed in a custom directory, then there may be a problem.
    ```bash
    #Specify custom configuration file
    grafana-cli --config /data/grafana/grafana.ini plugins ls
    # If not specified, use the default configuration
    grafana-cli plugins ls
    ```

### Temporary solutions and workarounds

Before the official fix is released, you can consider the following methods to ensure the reliability of the operation and maintenance scripts:

1. **Directly specify the plugin path**: Use other parameters such as `--plugins-url` or `--homepath` to explicitly tell the CLI the location of the plugin, thus bypassing dependence on the configuration file.
    ```bash
    grafana-cli --homepath /usr/share/grafana --plugins-url /data/grafana/plugins plugins ls
    # Note: The --plugins-url parameter may not be applicable to all commands. Please refer to the documentation for the specific version.
    ```

2. **Make sure the default path is correct**: If possible, install the plugin to the path that the CLI tool looks for by default (such as `/var/lib/grafana/plugins`), or create a soft link from the default path to the actual plugin directory. This is a compromise but ensures compatibility.

3. **Version downgrade or upgrade**: This problem may exist in a specific version. Evaluate whether you can downgrade to a known available version (such as v9.3.1), or upgrade to a newer version that already contains the fix.

## SRE Key Points

* **Relationship with Reliability**: Hidden flaws in such tool chains will reduce the manageability and maintainability of the system. Deployment pipelines or monitoring scripts that rely on the CLI for automated plug-in upgrades may fail silently, resulting in inconsistent environments or failure to apply security patches in a timely manner, ultimately affecting service reliability.
* **Observability and Incident Response**: In incident response, quickly locating such problems requires clear expectations for tool behavior. When executing a `grafana-cli` command returns unexpected results, the SRE should have the intuition to link it to a "problem with the tool itself" rather than a "user configuration error". Documenting a list of known tool defects (as part of a runbook) can speed up this process.
* **Best Practices and Common Anti-Patterns**:
    * **Best Practice**: In automation scripts, always verify the output and return codes of `grafana-cli` commands. For key operations (such as plug-in upgrade), the plug-in list or version number should be compared before and after execution to confirm that the operation actually takes effect.
    * **Common anti-pattern**: Assume that the CLI tool will faithfully execute all parameters as expected. After upgrading major components (such as Grafana), it should not be assumed that the original automation scripts are still fully valid and necessary regression testing needs to be performed.
* **Related Metrics (SLI/SLO/SLA)**: Although this issue does not directly affect the core service availability SLI, it will affect the **Operation and Maintenance Efficiency SLI** (for example, "automated deployment script first execution success rate"). Ensuring the stability of such infrastructure tools is the cornerstone of achieving higher-level SLOs. Internal SLOs can be set for the health of the operations toolchain, for example, "Critical CLI tools have &gt; 99.9% probability of working as expected in the staging environment."
