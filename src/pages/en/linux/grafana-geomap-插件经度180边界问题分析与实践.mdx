# GitHub Issue

## Overview

When building location-based observability dashboards, Grafana's Geomap plugin is a commonly used tool for visualizing the geographic distribution and status of servers, network nodes, or mobile devices on a map. However, when geographic coordinate data crosses the International Date Line (longitude jumping from 180 degrees back to -180 degrees), a common rendering problem may appear: instead of drawing separate paths on the eastern and western hemispheres of the map, the plugin draws an erroneous connecting line that directly crosses most of the map area (typically through the polar regions or map edges). This problem not only affects accurate data interpretation but also poses a direct availability and reliability challenge for SRE teams that rely on geographic views for rapid fault localization. This page analyzes the technical causes of this problem and discusses response strategies in SRE practice.

## Core Concepts

**Geographic Coordinate System and Longitude Boundaries**: Geographic coordinate systems typically use Longitude and Latitude to define points on the Earth's surface. The longitude range is typically [-180 degrees, 180 degrees]. The 180-degree meridian, also known as the Antimeridian, is the meridian opposite to the 0-degree meridian (Prime Meridian) and serves as the approximate baseline for the International Date Line. When a path's consecutive data points change in longitude from a value less than 180 degrees (e.g., 179 degrees) to a value less than -180 degrees (e.g., -179 degrees), or vice versa, the path has crossed this boundary.

**Map Projections and Connecting Lines**: A map is the result of projecting a three-dimensional sphere onto a two-dimensional plane. When handling continuous paths (such as Route layers), visualization libraries (such as the one underlying Geomap) need to connect two adjacent data points. The standard connection algorithm simply connects the coordinates of two points on the projection plane. When two points are geographically very close (e.g., from 179 degrees E to 179 degrees W), but in a coordinate system that does not correctly handle boundary wrapping, their longitude difference is calculated as 358 degrees, causing the connecting line to be drawn as a straight line spanning almost the entire map.

## Practice

Although this is a reported plugin defect, SRE teams can adopt the following practices when building and maintaining Geomap-based dashboards to work around the problem or perform effective troubleshooting:

1.  **Data Preprocessing and Cleaning**:
    *   **Identification and Segmentation**: Before sending data to Grafana, add logic in the data pipeline (such as InfluxDB queries, Telegraf processors) to detect whether longitude undergoes a jump greater than 180 degrees. Once detected, it means the path has crossed the Antimeridian.
    *   **Coordinate Splitting**: For paths that cross the boundary, split them into two independent path records. For example, one path from the starting point to 180 degrees, and another from -180 degrees to the endpoint. This can be achieved through conditional statements and multiple queries in InfluxQL or Flux queries.
    *   **Coordinate Offset**: Another approach is to uniformly adjust all longitude values to a continuous numerical range, for example converting all to [0 degrees, 360 degrees], before visualization, which can avoid boundary jumps. However, note that this may change the map's default view center.

2.  **Use Alternative or Enhanced Visualization Approaches**:
    *   **Marker Point View**: If precise path connections are not necessary, consider using the "marker" view, which only displays data point positions without drawing connecting lines, completely avoiding this problem.
    *   **Leverage Plugin Configuration**: Follow Grafana Geomap plugin version updates. In certain versions or configurations, options may exist to control path connection behavior (e.g., setting maximum connection distance).
    *   **Custom Visualization**: For mission-critical dashboards, if built-in plugins cannot meet requirements, consider developing a custom Grafana panel plugin using libraries like Leaflet or Mapbox GL JS, explicitly implementing Antimeridian boundary wrapping logic.

3.  **Dashboard and Troubleshooting**:
    *   **Version Control and Reproduction**: Record the specific version of the dashboard and Grafana (such as v11.6.0 in this case). When a problem appears, first try to reproduce it in the latest stable version of Grafana to confirm whether it is a known issue that has been fixed.
    *   **Isolate Data Source**: Verify whether the problem is related to the data format of a specific data source (such as InfluxDB v1). Try exporting data as static GeoJSON and viewing it in external tools to isolate the problem scope.

## SRE Key Points

*   **Reliability, Observability, and Incident Response Association**: This problem directly affects **dashboard availability**, a core SRE concern. A dashboard displaying incorrect map connections can cause SRE personnel to misjudge the geographic distribution and fault scope of services during incident response, thereby extending MTTR (Mean Time to Resolve). It is a negative example of a **data integrity** SLI (Service Level Indicator)—the visualization fails to accurately reflect the true spatial relationships of the underlying data.

*   **Best Practices and Common Anti-Patterns**:
    *   **Best Practices**: Treat geospatial data as "dirty data" requiring special handling. Add data quality checks in the observability pipeline, especially for boundary values. Before creating critical geographic views, first test on small datasets to ensure behavior under boundary conditions meets expectations.
    *   **Common Anti-Patterns**: Assuming the visualization tool can intelligently handle all coordinate boundary cases without any data preprocessing or validation. Ignoring user-reported display anomalies and failing to trace them to underlying data or specific plugin behavior.

*   **Related Metrics (SLI/SLO/SLA)**:
    *   **SLI**: Geospatial data visualization accuracy (e.g., path rendering correctness rate on maps), dashboard load time (time to process complex geographic data queries and rendering).
    *   **SLO**: Ensure critical geographic monitoring dashboards provide accurate, readable views 99% of the time to support fault localization.
    *   **SLA**: Dashboard functionality availability and accuracy guarantees promised to internal users (such as operations teams), which can include descriptions of known display limitations.

Handling such geographic boundary issues reflects the SRE emphasis on **details and boundary conditions**. Through proactive data governance and deep understanding of visualization tool limitations, the reliability and utility of the entire observability system can be effectively improved.
