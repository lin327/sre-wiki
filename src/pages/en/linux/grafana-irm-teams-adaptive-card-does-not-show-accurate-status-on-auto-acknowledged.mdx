# Grafana IRM - Teams adaptive card does not show accurate status on auto-acknowledged

## Overview

Grafana Incident Response Management (IRM) is a core functional module in the Grafana ecosystem for managing, coordinating, and responding to incidents. It achieves efficient incident collaboration through ChatOps integration with multiple notification channels (such as Microsoft Teams). The issue described in this article involves a defect in Grafana IRM under specific scenarios: when an alert group is auto-acknowledged, the Adaptive Card sent to Teams fails to accurately reflect its actual Acknowledged status, instead incorrectly displaying as Unacknowledged. This status display inconsistency seriously disrupts the incident response process, causing confusion among responders and affecting the accuracy and efficiency of incident handling. It is an important issue that SRE teams need to address in their observability toolchain operations.

## Core Concepts

To understand this issue, the following key concepts need to be clarified:

- **Grafana IRM and Alert Group**: IRM is used to aggregate and manage related alerts, forming an "alert group." An alert group represents an independent incident, and its state (such as "Triggered," "Acknowledged," "Resolved") changes as operational actions are performed.
- **Auto-acknowledge**: This is an alert group processing strategy aimed at reducing unnecessary noise. When preset conditions are met (for example, the associated fault automatically recovers or specific rules are satisfied), the alert group's state automatically changes from "Triggered" to "Acknowledged" without manual intervention.
- **Teams Adaptive Card**: This is a rich message format supported by the Microsoft Teams platform. Grafana IRM uses it to push detailed alert information through ChatOps integration. The card's layout and status indicators (such as color, button labels) should stay in sync with the alert group's backend state.
- **State Synchronization Issue**: The core of this case is the synchronization failure between "backend state" and "frontend notification." The alert group is already in the "Acknowledged" state in the Grafana backend, but the Teams Adaptive Card's rendering logic or data transmission fails to fetch or correctly apply this latest state, resulting in an incorrect visual display.

## Practice

### Problem Manifestation and Impact

In this bug, the main manifestations are:
1.  **Trigger Condition**: The alert group is set to "auto-acknowledge," and the triggered alert meets the auto-acknowledge criteria.
2.  **Notification Channel**: ChatOps notifications are configured to be sent through Microsoft Teams.
3.  **Error Symptom**: The received Teams Adaptive Card's status bar or related indicator clearly displays "Unacknowledged," which contradicts the alert group's actual "Acknowledged" status in the Grafana interface.
4.  **User Confusion**: Responders seeing "Unacknowledged" on the card may attempt to acknowledge it again, causing redundant operations; or they may misjudge the incident severity, affecting subsequent handling processes.

### Possible Root Causes

Although the issue report itself does not deeply analyze the cause, based on system interaction principles, possible causes include:
- **State Transmission Delay or Failure**: When the Teams card is generated, it fails to timely fetch the alert group's latest state from the Grafana IRM API.
- **Card Rendering Logic Defect**: The Adaptive Card's template or rendering engine has a logic error. When processing the "auto-acknowledge" special state change path, it hardcodes the initial state or ignores the update.
- **Asynchronous Processing Issue**: The auto-acknowledge operation and card generation/sending are two asynchronous processes. Under specific timing conditions, the state fetched during card generation is still the old state.

### Reproduction Steps (Verification)

Based on the original material, the issue can be reproduced and verified using the following steps:
1.  In Grafana IRM, configure an Alert Group and set an **auto-acknowledge** strategy for it.
2.  Configure ChatOps to send event notifications for this alert group to a specified **Microsoft Teams channel** using Adaptive Card format.
3.  Trigger an alert that meets the above auto-acknowledge strategy, causing it to enter the alert group.
4.  Observe the Adaptive Card received in the Teams channel — **it is expected to display "Acknowledged" status**.
5.  The actual result is typically that the card displays "Unacknowledged" status.
6.  Click the link in the card to view the alert group details in Grafana, confirming that its status in the backend is **indeed already "Acknowledged"**.

## SRE Key Points

### Connection to Reliability and Incident Response
- **Incident Response Process Disruption**: Accurate incident state is the foundation of the Incident Command System. Incorrect status information in notification channels can mislead frontline responders, potentially triggering incorrect escalation procedures or unnecessary on-site interventions, directly reducing incident resolution efficiency (MTTD/MTTR).
- **Observability Integrity Compromised**: The extension of the three pillars of observability (metrics, logs, traces) also includes the observability of **incident lifecycle state**. This bug undermines the reliability of observing incident state through external integrations (Teams), damaging end-to-end system observability.
- **SLI/SLO Potential Risk**: If certain reliability metrics (such as "Incident Acknowledgment Timeliness SLO") are calculated or guaranteed based on IRM status notifications, inaccurate status will lead to incorrect metric calculations, resulting in misjudgment of SLO achievement.

### Best Practices and Anti-patterns
- **Best Practices**:
    - **Maintain Strong Consistency Between Notifications and Actual State**: Any notification sent externally (especially state change notifications) must guarantee consistency with the source system's final state. This is a fundamental requirement for ChatOps integration.
    - **Establish Integration Verification Processes**: For critical monitoring-notification integration chains (such as Grafana -> Teams), establish regular end-to-end verification mechanisms to ensure critical path functionality is working properly.
    - **Set Clear SLIs**: Consider defining "consistency between notification status in critical event channels (such as Teams) and actual system status" as an observability SLI.
- **Common Anti-patterns**:
    - **Ignoring Timing Issues in Asynchronous Communication**: In microservice or integration architectures, assuming synchronous calls or that state is always immediately available is dangerous.
    - **Relying on a Single Notification Channel to Verify State**: SREs should avoid judging incident progress solely through Teams card status; they should trace back to the Grafana IRM main console to confirm the single source of truth.
    - **Lack of Verification for Automation Results**: While automation strategies like auto-acknowledge improve efficiency, their resulting effects (such as notifications) must be included in the verification scope to prevent automation from producing "hidden errors."
