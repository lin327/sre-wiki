# 

## Overview

In Grafana's alert module, [[alert-routing|notification strategy]] defines how alert messages are routed to different recipients or integrations. This is a key operation and maintenance configuration, and its correctness and modifiability directly affect the timely response to alarms. Recently, a flaw related to the [[api-optimistic-locking|Optimistic concurrency control]] mechanism was discovered, causing users to continue to receive `409 Conflict` errors when modifying notification policies deployed through API (Provisioning) through the Web UI, making daily maintenance and adjustment of the policy difficult. Understanding the mechanics of this issue can help SRE teams avoid similar pitfalls and take a more robust approach when configuring alerting systems.

## Core concepts

* **Notification Policy**: A tree structure used to define alarm routing rules in Grafana. It specifies to which [[contact-point|Contact Point]] (receiving endpoint) alerts matching specific labels (Labels) should be sent or further routing decisions should be made.
* **Resource Version & Hash**: To achieve safe concurrent updates, the Grafana API uses a hash value based on the resource content as the version identifier. When reading a policy, the server calculates a hash; when submitting an update, the client needs to include this hash. The server will recalculate the hash and compare it. If it is inconsistent (`Conflict`), it will reject the update to prevent overwriting the modifications of other users or processes.
* **Autogenerated Routes**: Grafana will include some default routes (such as root routes) automatically created by the system in the API response or when exporting. These routes exist when displayed in the UI and exported by the API, but may be excluded during internal hash calculations.

## Practice

### Problem recurrence

1. **Export**: Export a notification policy configuration file through Grafana API or UI. Make sure the exported JSON contains the auto-generated routes in the `routes` array (usually at the root).
2. **Import**: Use the Provisioning API or configuration file to import the policy. At this point, the policy already exists in the Grafana backend.
3. **Edit**: Try modifying any part of the notification policy in Grafana's web UI (for example, modifying route matching conditions or receiving endpoints), and save. At this point you will see a `409 Conflict` error message.

### Root cause analysis

This is a bug caused by **inconsistent API implementation**. The problem chain is as follows:

1. **Import phase**: The Provisioning API receives and persists the complete policy tree, **including automatically generated routes**.
2. **Reading phase**: When the UI requests policy data, the API will remove (or not include) the automatically generated route and calculate the resource version hash based on this **"lite"** policy before returning it to the front end. The front end stores this hash for subsequent update requests.
3. **Update phase**: The user modifies the policy on the UI and submits it. The update request payload sent by the front end contains the modified policy (still does not include automatically generated routes) and the hash value obtained previously.
4. **Conflict Detection**: After the server receives the update request, it will read the **current** policy from the persistent storage. Since the store still contains auto-generated routes, the server recalculates the hashes based on this **"full version"** policy. **This new hash is inconsistent with the hash carried in the request**, so the server returns `409 Conflict`, rejecting the update.

Essentially, the "resource versions" used for concurrency control are computed differently on reads and writes, resulting in a deadlock that cannot be resolved through normal UI operations.

## SRE Key Points

### Reliability and incident response

* **Impact**: This problem directly hinders the ability to dynamically adjust alarm routing. When an alarm storm occurs or alarm recipients need to be temporarily changed, SRE cannot quickly modify the policy through the UI, which may delay incident response.
* **Avoidance**: Before this bug is fixed, all notification policies managed through API/Provisioning should also be modified through the API or re-import to avoid relying on UI operations.

### Best practices and common anti-patterns

* **Best Practice**: For critical infrastructure configuration (such as alarm routing), the principles of **[[infrastructure-as-code|Infrastructure as code]]** should be adhered to. Use versioned configuration files to be managed via API or Provisioning rather than relying on error-prone manual UI clicks.
* **Anti-Pattern**: When mixing UI and API to manage the same resource, pay special attention to their consistency boundaries. This case is a typical anti-pattern example. There are implicit differences in data processing and state representation between API and UI.
* **Monitoring**: You can monitor the frequency of `409 Conflict` responses in the Grafana API to discover such problems or similar concurrency management flaws in a timely manner.

### Related indicators (SLI/SLO/SLA)

* **SLI**: "Notification policy change success rate" (number of successfully submitted modifications / total number of modification attempts) can be used as an SLI. This bug causes a significant degradation of this SLI.
* **SLO**: Set the SLO for the availability of the "alarm routing configuration management function", such as "the configuration change failure time due to platform defects shall not exceed 5 minutes per month". Such bugs are a potential risk for SLO violations.
* **SLA**: In scenarios facing internal users, this issue may affect the "manageability" terms of the Grafana service commitment. For teams providing Grafana hosting services, workarounds for such known flaws need to be considered in the SLA.
