# Suggested Dashboards: dashvalidator scope metrics cache entries by org

## Overview

In a multi-tenant observability platform like Grafana, an efficient caching mechanism is critical for performance and data isolation. `MetricsCache` is a component within Grafana used to cache metadata related to data sources (such as dashboard recommendations). This update aims to optimize its cache key structure to ensure that cached data can be correctly isolated in a multi-org environment, thereby improving the accuracy and reliability of the system.

## Core concepts

**MetricsCache**: This is a cache service within Grafana that stores calculation results or metadata related to data sources, such as metric entries used by the `dashvalidator` function to generate dashboard recommendations. The purpose of introducing cache is to avoid repeated time-consuming queries or calculations and improve user experience and system performance.

**Multi-org Model**: Grafana supports isolating different tenants through Organization (Organization, referred to as org). Each organization has independent configurations of users, dashboards, and data sources. A data source (identified by `datasourceUID`) may belong to a specific organization, but the `UID` is theoretically unique globally. However, from a cache isolation perspective, just using `datasourceUID` as a cache key is not enough, as data sources with the same name or semantically similar may exist in different organizations.

**Cache Key Scoping**: In order to ensure the uniqueness and correctness of cache entries, the cache key must be able to uniquely identify the context served by a cache entry. In a single-tenant model, `(datasourceUID)` may be sufficient. But in Grafana's multi-tenant model, the correct context is jointly defined by `(orgID, datasourceUID)`. This change upgrades the cache key from `datasourceUID` to `(orgID, datasourceUID)`, enabling cache entries to be scoped by organization.

## Practice

This change mainly occurs at the back-end code level of Grafana, which is transparent to end users, but can bring a better experience. Its core implementation follows Grafana's existing best practices.

1. **Align existing schema**: The new cache key structure is consistent with Grafana’s existing data source cache service located in `pkg/services/datasources/service/cache.go`. This pattern has been used successfully in code bases, ensuring design consistency and maintainability.
2. **Implementation logic**: When generating or querying `MetricsCache`, the system will simultaneously obtain the `orgID` and target `datasourceUID` to which the current request belongs, and combine them into a cache key. For example, for a dashboard suggestion calculation in Organization 1, its cache key will be explicitly associated with `orgID=1`, rather than a global `datasourceUID`.
3. **User Benefits**:
    - **Data Accuracy**: Between different organizations sharing Grafana instances, the risk of "data string tenants" caused by cache key conflicts is avoided, ensuring that the dashboard recommendations or related indicators seen by each organization are calculated based on its own data source configuration.
    - **Performance Optimization**: While correcting isolation, the performance advantages brought by caching are still retained, that is, for the same data source within the same organization, repeated requests can obtain results directly from the cache.

## SRE Key Points

- **Association with reliability, observability, incident response**:
    - **Reliability**: This change directly improves the reliability of the Grafana platform in multi-tenant scenarios and prevents potential cross-tenant data leakage or incorrect correlation, which is one of the core requirements of SaaS services.
    - **Observability**: As the observability platform itself, Grafana's internal caching mechanism is part of its "observability". A misconfigured cache may mislead operations personnel. This fix ensures correct and predictable behavior of Grafana's own components.
    - **Incident Response**: If users report dashboard suggestion errors or data inconsistencies in a multi-tenant environment, SREs should take cache isolation of the Grafana backend (such as this change) into consideration when troubleshooting, especially when `dashvalidator` or similar functionality is involved.

- **Best Practices and Common Anti-Patterns**:
    - **Best Practice**: When designing caches for multi-tenant systems, you should always include the tenant ID (such as `orgID`) as part of the cache key. Give priority to referring to and adopting existing and proven caching models in the system (such as Grafana's data source cache) to ensure design consistency.
    - **Common anti-pattern**: Only use globally unique identifiers (such as `UID`) as cache keys, ignoring the tenant context. This becomes a potential vulnerability that is difficult to find and fix when the system evolves to support multi-tenancy.

- **Related indicators (SLI/SLO/SLA)**:
    - **SLI (Service Level Indicator)**: You can monitor the hit rate (Hit Rate) and isolation effectiveness of `MetricsCache`. Isolation effectiveness can be measured by sampling cache keys from different organizations and checking for unusual crossovers.
    - **SLO (Service Level Objective)**: For the `dashvalidator` feature, you can set an SLO such as "Provide 99% of users with accurate dashboard recommendations based on their own organizational data sources." This change is one of the key technical guarantees for achieving this SLO.
    - **SLA (Service Level Agreement)**: In the SLA of a multi-tenant platform, data isolation is a core term. This change provides technical support for the data isolation commitment in the SLA.

This optimization is a microcosm of Grafana's evolution to a more mature and secure multi-tenant architecture, reflecting the emphasis on accuracy and isolation in caching strategies. Related design patterns can be found in [[multi-tenancy]] and [[caching-strategies]].
