# 

## Overview

In Grafana dashboards, the Mixed datasource panel allows combining queries from different data sources in one visualization. This fix (backported from PR #124665) resolves a critical front-end data flow race issue: when the user changes the dashboard time range, Mixed panels using the "--Dashboard--" data source may fail to re-render data in the new time range and instead get stuck on the old data. This problem stems from the premature processing of the "Done" event in the RxJS data flow. It is a typical asynchronous data flow synchronization timing error. Repair is crucial to ensure the real-time and accuracy of monitoring data, which directly affects users' trust in dashboard data.

## Core concepts

To understand this issue, you need to understand the following key concepts:

1. **Mixed Datasource**: A special Grafana data source type that acts as a "router" to distribute multiple user-defined subqueries to different back-end data sources and combine the results in a "chain".
2. **`SceneQueryRunner` and `ReplaySubject(1)`**: `SceneQueryRunner` is the scene object responsible for executing queries. It uses RxJS's `ReplaySubject(1)` to expose query results, which buffers the most recently emitted value (including status). This buffered, possibly stale completion status is received immediately when a new subscriber (such as a dashboard data source adapter) subscribes.
3. **Race Condition**: The core of the problem is that when the user changes the time range, the following sequence crosses incorrectly:
    * The dashboard data source issues a new query to the `SceneQueryRunner`.
    * The dashboard data source also subscribes to its result stream.
    * The subscription action immediately triggers the **completion status (Done)** of the previous query buffered in `ReplaySubject(1)`.
    * The `emitFirstLoadedDataIfMixedDS` operator inside the system matches this "complete" signal and considers that the data has been loaded, thus closing the subscription for this data stream (`complete`).
    * At this time, the new query may still be executing slowly upstream, and its real "completion" event will arrive later, but the data flow has been closed and cannot be processed.
4. **`emitFirstLoadedDataIfMixedDS` operator**: This is a custom RxJS operator designed to terminate (`complete`) the subflow once the first "Success (Done)" or "Error (Error)" event is received in the Mixed data source chain to ensure that the Mixed chain can quickly combine data. A faulty implementation resulted in the race described above.

## Practice

This fix introduces a critical filtering step in the `datasource.ts` file, implemented as follows:

1. **Introduction of range verification auxiliary function**: Added an auxiliary function named `isSameRange` for comparing whether two time range objects are the same.
2. **Add filtering to the Mixed data source path**: A `filter(...)` operator is added **before** the `emitFirstLoadedDataIfMixedDS` operator. This filter will discard (`filter` out) those events with "termination status (Done/Error)", but only if the **upstream request time range** corresponding to these events is inconsistent with the **request time range** issued by the current Mixed chain.
3. **Scope**: This filter only applies to the query path of the Mixed data source. The code implements this qualification by checking whether `requestId` contains `MIXED_REQUEST_PREFIX`. Non-Mixed data source paths are not affected because:
    * Non-Mixed paths naturally rely on the arrival of new data to be re-emitted.
    * Panels with `PanelTimeRange` overrides (e.g. `timeFrom`, `timeShift`) may inherently observe a different time range than upstream, and applying filtering here will cause them to be permanently in the "loading" state.
4. **Verification and Testing**: The fix passed all existing tests and 3 new regression test cases were added to specifically verify this race condition. All lint, type checking and local tests pass.

## SRE Key Points

### Association with reliability
- **Data Accuracy**: This bug directly causes dashboard panels to display **outdated data**, which is a serious reliability flaw in observability systems. SRE may make judgments or alerts based on incorrect data.
- **User Experience**: A panel that is unresponsive or displays stale data will destroy users' trust in the monitoring platform, increase troubleshooting time, and affect incident response efficiency.

### Best Practices and Anti-Patterns
- **Best Practices**:
    - For front-end code involving asynchronous data flows and complex subscriptions, **strict timeframe/state consistency testing** is required.
    - When using buffered data streams (such as `ReplaySubject`), you must consider whether its cached old data will cause interference in the new context.
    - Fixes should isolate the scope of impact as much as possible (like here only Mixed paths) to avoid introducing new side effects.
- **Common anti-patterns**:
    - **Premature termination of data flow**: Closing a data pipeline based on a stale signal is a typical anti-pattern that leads to this type of problem.
    - **Ignore request context**: When processing asynchronous responses, not checking whether the response corresponds to the currently active request is the main cause of race conditions.

### Related indicators (SLI/SLO/SLA)
- **SLI (Service Level Indicator)**: Can be linked to "Dashboard Data Freshness" or "Query Time Range Coverage Accuracy". This bug causes the indicator value to drop instantly.
- **SLO (Service Level Objective)**: For real-time monitoring systems, the SLO may require that "panel data be refreshed within 2 seconds of time range change". This fix is ​​designed to meet such goals.
- **Root Cause**: The root cause of the problem is improper state management in the RxJS data flow, which is a reliability debt at the front-end implementation level.
