# Grafana OSS logfmt - timestamp name and format different that other grafana

## Overview

When building a unified observability platform, log data from different components needs to be parsed, indexed, and queried consistently. Products in the Grafana ecosystem (such as Grafana OSS, Alloy, Loki, Tempo) usually adopt structured log formats (such as logfmt) to facilitate automated processing. However, a known issue is that the logs generated by Grafana OSS itself are different from other products in the name and format of the timestamp field. This inconsistency brings challenges to the centralized collection and query of logs, and increases the complexity of system operation and maintenance. As an SRE, understanding such differences is critical to designing robust logging pipelines and efficient troubleshooting processes.

## Core concepts

### Logfmt structured log

Logfmt is a simple structured log format in the format of `key=value` pairs, which is easy for humans to read and easy for machines to parse. This format is widely adopted by the Grafana ecosystem. In SRE practice, standard structured logs are the basis for achieving log correlation among the three pillars of observability (metrics, logs, and tracking).

### Timestamp field names are inconsistent

There are two main variations of log timestamp field names in the Grafana ecosystem:
1. **`t=`**: used for logs generated by **Grafana OSS** itself. For example: `t=2024-11-23T22:32:00.31308741+01:00`.
2. **`ts=`**: used for **Grafana Alloy** and other inferred components such as Loki, Tempo, Mimir, etc. For example: `ts=2024-11-23T21:05:36.577881094Z`.

This difference in naming requires that log parsing rules (such as the parsing phase of Promtail and Loki) must perform conditional judgment or maintain multiple sets of configurations.

### Time zone indicates difference

Along with the field name, there is also the timestamp format itself:
1. **Grafana OSS** uses local time zone offset, such as `+01:00`.
2. **Other products** use the standard UTC suffix `Z`.

Using timestamps with time zone offsets increases the complexity of log aggregation and time range queries because of the need for time zone conversion at parse time or query time, whereas a unified UTC timestamp (`Z`) is more predictable and reliable.

## Practice

Handling this inconsistency requires specific strategies in the log collection and parsing pipeline. Take using **Promtail** to collect logs and send them to **Loki** as an example.

### Parsing strategy

1. **Identify field name**: First, you need to identify whether the timestamp field in the log line is `t=` or `ts=`. This can usually be distinguished by the field name itself.
2. **Apply different parsing rules**: In Promtail configuration, you can use regular expressions or conditional statements to process different formats.

**Example configuration snippet (Promtail pipeline):**
```yaml
pipeline_stages:
  # Process Grafana OSS logs
  - regex:
      expression: 't=(?P<timestamp>\S+)'
  - timestamp:
      source: timestamp
      format: RFC3339Nano # Used to parse time with time zone offset, such as `+01:00`

  # Process other Grafana product logs (starting with ts=)
  - regex:
      expression: 'ts=(?P<timestamp>\S+)'
  - timestamp:
      source: timestamp
      format: RFC3339Nano # `Z` suffix can also be parsed by this format
```
*Note: The above is just a schematic. In actual configuration, you may need to pass the `match` stage or more detailed regular rules to ensure the correct order of rules. *

3. **Unify to UTC**: During the parsing phase, it is best to normalize all timestamps to UTC storage. Systems such as Loki usually store data internally in UTC, so you don't have to worry about the original time zone when querying.

### Log query and alarm

When querying logs in Grafana Loki, users may need to write queries that are compatible with both formats, or ensure that the formats have been unified through the collection pipeline. For alarm rules (such as based on log frequency or error patterns), timestamp parsing errors may cause the rules to fail or generate false positives.

## SRE Key Points

### Association with reliability

Logs are the core data source for diagnosing system faults and analyzing performance bottlenecks. Inconsistent timestamp parsing directly harms the **reliability** of this capability:
- **Troubleshooting Delay**: When a system failure occurs, SRE needs to quickly correlate the log timelines of different components. Inconsistent formats increase manual processing time and delay MTTR (Mean Time to Recovery).
- **Monitoring failure**: Log-dependent SLO (such as error rate SLI) alarms may be missed due to the inability to correctly parse the log timestamps of some components.

### Best practices and common anti-patterns

- **Best Practices**:
    - **Promote upstream unification**: As shown in this Issue, feedback to open source projects (such as Grafana) and promoting them to unify the log format of internal components is the fundamental solution.
    - **Standardization at the collection layer**: In the log collection agent (such as Fluentd, Filebeat, Promtail), various input formats are converted into a unified internal format (field name, time zone, time format) through the parsing pipeline before sending.
    - **Use UTC**: Forces all services to use UTC timestamps (`Z` suffix) in logs, eliminating time zone ambiguity.

- **Common anti-patterns**:
    - **Conversion at the query layer**: A large number of complex time zone conversions and field renaming are performed in Grafana Loki's query statements (LogQL), which will degrade query performance and make it difficult to maintain.
    - **Ignore small differences**: Ignore field name differences like `t=` vs `ts=` and expect "should work", which can lead to lost log data or incomplete query results.

### Related indicators

- **SLI (Service Level Indicator)**: For log pipelines, SLI can include "log parsing success rate" or "log ingestion delay". Timestamp format issues will directly affect the parsing success rate.
- **SLO (Service Level Objective)**: You can set the SLO that "100% of key service logs can be correctly parsed and indexed by the central log system". Such format inconsistencies are a barrier to meeting this SLO.

This issue highlights the "glue layer" challenge of achieving end-to-end observability in complex microservices or distributed systems. The SRE team needs to consider the standardization of log formats in the early stages of system design and continuously maintain the parsing pipeline to cope with changes brought about by component evolution.
