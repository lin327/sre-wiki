# 

## Overview

In the observability practice of monitoring systems, the clarity and readability of dashboards are key to ensuring that operation and maintenance personnel can quickly and accurately obtain information. This document analyzes a specific Grafana Stat panel font size fallback issue. This problem has appeared since Grafana was updated, causing the font size of text labels (such as MAC address, device ID, etc.) in the Stat panel to be significantly reduced, seriously affecting the rapid reading of information and reducing the operation and maintenance value of the dashboard. Although this type of front-end rendering rollback does not directly affect the accuracy of the background data flow, it directly damages the "last mile" of interaction between the user and the system, which is a **user experience reliability** issue in a broad sense.

## Core concepts

### Stat panel
Stat panel is a common visualization plug-in in Grafana for displaying individual key indicators (such as status, count, value). It presents data through prominent numbers and optional labels (such as units, descriptions), requiring information to remain legible in different sizes and layouts.

###Font Size Regression
Font size rollback refers to an iteration of software (especially UI components) in which the default or calculated font size of text unexpectedly becomes smaller than in previous versions. This is usually caused by changes to the rendering engine, CSS style adjustments, or modifications to dynamic calculation logic. In this case, users reported that the Stat panel label text changed from readable to illegible.

## Practice

### Problem phenomenon and recurrence
According to user reports, the issue manifests as the Stat panel on Grafana Cloud (stable channel) displaying certain strings (such as MAC address `84:96:90:77:63:92`) with a significantly smaller font size than previous versions. This phenomenon can be stably reproduced by adjusting the panel size. The problem is not isolated, but affects panels using the same plugin version (`stat @ 12.4.0-19938312174`).

### Root cause analysis (based on debugging information)
From the user-provided panel debug snapshot JSON, we can extract key information for analysis:
1. **Plug-in version**: `pluginVersion: "12.4.0-19938312174"`. This is a clear version identification and is the key to troubleshooting the introduction point of changes.
2. **Data source and query**: The panel uses a custom data source (`yesoreyeram-infinity-datasource`) and query, but its core problem lies in front-end rendering and low correlation with back-end data.
3. **Panel Options**: In the `options` configuration of the panel, `textMode: "auto"` indicates that the text display mode is automatic, and the font size is likely to be dynamically calculated based on the panel size by the algorithm inside the panel plug-in. The problem most likely lies in changes in the calculation logic.

### Mitigation and Solution Suggestions
For affected SREs and dashboard maintainers, the following interim and long-term measures can be taken:
1. **Temporary Mitigation**: Adjusting the size of the affected Stat panel (increasing the area) can usually force the text rendering engine to use a larger font size, but this is not a fundamental solution and destroys the original layout.
2. **Version rollback/waiting for patch**: Pay close attention to Grafana’s official change log and Issue tracking (such as this issue #115395). Before the official release of a fixed version, if possible, consider rolling back the Grafana version to the last known stable version (but this option is limited when using Grafana Cloud).
3. **Custom style override**: Try to force a minimum font size (`min-font-size` or `font-size`) for a specific Stat panel or globally through Grafana's **Dashboard JSON Model** or **Custom CSS** functionality, but this requires front-end development knowledge and may not be available in future versions.
4. **Reporting and Tracking**: For the operation and maintenance team, this issue should be filed as an event that affects the readability of the dashboard, its resolution status should be tracked, and its impact on monitoring performance should be evaluated.

## SRE Key Points

* **Relationship with reliability and observability**:
    * **User Experience Reliability**: The ultimate goal of an observability system is to assist decision-making. A dashboard with unclear fonts will greatly reduce its "reliability" on the user side, which may delay fault detection or lead to misjudgment.
    * **Change Management**: This type of UI rollback highlights the importance of rigorous change management and monitoring of front-end dependencies (such as Grafana plugin versions). SREs should include the visual integrity of key dashboards in the observability context.

* **Best Practices and Common Anti-Patterns**:
    * **Best Practices**: Establish "golden snapshots" or visual regression tests for core dashboards (for incident response, on-call dashboards); regularly audit dashboards for accessibility (contrast, font size); use Grafana's versioning capabilities to manage dashboard JSON.
    * **Anti-Pattern**: Focusing only on SLO/SLI of backend metrics while ignoring the reliability of frontend rendering; not doing a comprehensive visual inspection of key dashboards after upgrading Grafana or plugins.

* **Related Metrics (SLI/SLO/SLA)**:
    * While this issue does not directly impact the backend error budget, you may consider defining the following SLI for the **Dashboard Service**:
        * **UI rendering success rate**: The percentage of key panels that are correctly rendered (needs to be achieved through front-end monitoring or regular inspections).
        * **Information Clarity Score**: Evaluates the readability of key metric text via subjective or automated tools.
    * The relevant **SLO** can be set to "the visual elements (fonts, charts) of the core monitoring dashboard meet the design specifications 99% of the time", which falls under the broad scope of SLA and ensures the credibility of the monitoring system itself.
