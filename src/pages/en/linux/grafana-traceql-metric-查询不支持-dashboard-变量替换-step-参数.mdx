## Overview

When building a unified observability dashboard, using Dashboard variables (such as `$interval`) to dynamically control the query step (Step) for all panels is a key practice. This ensures that panels from different data sources (such as Prometheus and Tempo) present data at the same time granularity, facilitating correlation analysis. However, the current TraceQL Metric query function of Grafana has a flaw: its Step parameter does not support the use of Dashboard variables. When trying to use variables, the query will fail with an error, which destroys the consistency and flexibility of the dashboard and is a limitation that the SRE team needs to focus on when building the Trace and metric correlation analysis panel.

## Core concepts

To understand this problem, you need to understand the following concepts:

* **TraceQL Metrics**: A query function provided by the Tempo data source, which is based on the TraceQL language and can aggregate and generate time series metrics (for example: `count_over_time`) from trace data. This allows SRE to compare and analyze Trace data with Metrics data (such as Prometheus) on the same timeline.
* **Step parameter**: In time series queries, `Step` defines the time resolution or sampling interval of the query results. For example, "1m" means one data point every minute. Proper Step settings are critical to controlling query performance, data accuracy, and chart rendering.
* **Dashboard variable substitution**: A core feature of Grafana that allows users to use variables (such as `$interval`, `$datasource`) in queries or panel settings, and dynamically replace them at runtime based on the value selected at the top of the dashboard, thereby achieving interactivity and reusability of the dashboard.

## Practice

The following steps describe how to reproduce this issue and find the current workaround:

**Steps to reproduce the problem:**

1. **Create dashboard variable**: In the dashboard settings, create an **Interval** type variable named `interval`. For example, set the custom options to `1m, 5m, 15m`.
2. **Create TraceQL Metric Panel**: Add a time series panel and select **Tempo** as the data source. Switch the query type to **TraceQL Metrics** and enter a base query, such as `{} | count_over_time()`.
3. **Try using variables**: In the `Step` input box of the query editor, enter the variable `$interval`.
4. **Observe Error**: After saving or refreshing the panel, the query fails and Grafana displays an RPC error similar to `cannot parse "$interval" to a valid duration`. This indicates that the variable value is not being parsed correctly into a valid interval string.

**Current workaround:**

Since variable substitution is not available, to ensure dashboard consistency, the SRE team can take the following temporary measures:

1. **Hardcoded value**: Directly enter a fixed value (such as `1m`) that matches other panels in the Step field of the TraceQL Metric panel. The disadvantage is that it cannot respond to changes in dashboard variables.
2. **Create multiple panels**: Create separate panels for each required Step value (1m, 5m, 15m) and control which panel is displayed via panel visibility rules (based on variable values). This can make the dashboard bloated and difficult to maintain.
3. **Prefer using the Prometheus panel**: For core SLO monitoring, give priority to using the Prometheus query panel that supports variable replacement to calculate key indicators, and use TraceQL Metric queries for auxiliary analysis.

## SRE Key Points

* **Correlation with Observability**: This issue directly affects the ability to analyze the correlation between **Metrics and Traces**. SREs want to see the same time-granularity of error rates (from Prometheus) and number of error traces (from TraceQL) in one view, but Step inconsistencies can cause data points to be misaligned, interfering with root cause analysis.
* **Best Practices and Anti-Patterns**:
    * **Best Practice**: Establish monitoring panel design specifications and explicitly require all time series panels to support the use of a unified `$interval` variable as much as possible to ensure the consistency of the data perspective. In cases where the TraceQL Metric panel is not supported, alternatives should be noted and given in the documentation.
    * **Common anti-pattern**: Accepting this inconsistency leads to confusing data time granularity in different panels in the dashboard, increasing cognitive load and error probability when troubleshooting.
* **Related Metrics (SLI/SLO/SLA)**: While this issue itself is a UI/query functionality flaw, it indirectly affects the accuracy of Traces-based SLI**. If the TraceQL Metric query used to calculate SLI cannot use the same `Step` as other metric panels, then the calculated SLI value may not be correctly aligned with the consumption of the Error Budget (Error Budget) on the timeline, affecting the accuracy of the SLO review. When SRE uses Trace data as an SLI source, it needs to specifically verify the correctness and consistency of its query configuration.
