# [release-13.0.2] Fixes issue with interval variable with Auto value

## Overview

In the Grafana monitoring platform, the interval variable (Interval Variable) of the dashboard is a key component of the control panel query time granularity (such as `1m`, `5m`, `1h`). When this variable is set to "Auto", Grafana will automatically calculate an appropriate interval value based on the currently selected time range. This fix targets a flaw that may cause the **"Auto"** calculation logic to fail or return an incorrect value. In SRE practice, such problems directly affect the aggregation granularity and visualization accuracy of monitoring data, may mislead troubleshooting and performance analysis, and are defects that affect the basic capabilities of observability.

## Core concepts

### Interval Variable
Interval variables are a special template variable in Grafana dashboards, mainly used to dynamically specify the `__interval` or `__interval_ms` macro in panel queries (especially time series queries). It allows users to automatically adjust the aggregation interval of data points under different time ranges (such as 1 hour, 7 days) to obtain the best visualization and query performance.

### “Auto” value
When the interval variable selection is set to "Auto", its value is not fixed, but is automatically calculated by the Grafana backend based on the time range (`time range`) and panel width of the current dashboard panel. Ideally, the system should ensure that the returned interval value can generate a reasonable number of data points (such as 150-300), so as to avoid too many points causing front-end rendering lag, and to avoid too few points causing the loss of details.

### Impact of failure
Among the defects fixed this time, the calculation logic of **"Auto"** may be abnormal, causing the calculated interval value to be seriously inconsistent with expectations. This may appear as:
- **Query timeout or performance degradation**: The generated interval value is too small, causing the backend database to perform unnecessary high-frequency queries.
- **Inaccurate chart data**: The generated interval value is too large, causing the data to be over-aggregated and key peak or valley information to be lost.
- **Dashboard display clutter**: The panel may not render properly due to query errors or data formats that are not as expected.

## Practice

### Problem fixes and upgrades
The fix for this issue is included in the Grafana **13.0.2** patch. For teams that are using the 13.0.x series, planning to upgrade to 13.0.2 or higher should be a priority.

**Brief description of upgrade steps:**
1. **Backup**: Before upgrading, back up Grafana's configuration file (`grafana.ini` or environment variables) and database (such as PostgreSQL, MySQL).
2. **Test environment verification**: It is recommended to deploy version 13.0.2 in the test environment first to verify whether the functions of dashboards that rely on interval variables (especially those key operation and maintenance dashboards that use the "Auto" value) return to normal.
3. **Production environment upgrade**: Arrange rolling updates or blue-green deployment of the production environment according to the team's change management process. After the upgrade, the integrity and availability of the service need to be verified.
4. **Monitoring and Rollback**: Closely monitor the query performance of the Grafana service itself and its associated data sources after the upgrade. If an exception occurs, rollback is performed according to the plan.

### Verify the repair effect
After upgrading, you can verify whether the problem has been resolved by:
- Access a dashboard using the "Auto" interval variable.
- Switch to different global time ranges (such as "last 1 hour" to "last 7 days") and observe whether the relevant panels load normally.
- Check the query of the panel (via the Network tab of the browser developer tools or the query log of Grafana) to confirm whether the `interval` parameter value passed to the data source changes reasonably in different time ranges.

## SRE Key Points

### Association with reliability
Monitoring data accuracy is a cornerstone of SRE work. As the core visualization layer of Grafana, the data distortion displayed by its dashboard will directly mislead incident response and capacity assessment. Therefore, such defects affecting data accuracy should be considered a high-priority issue because it indirectly threatens the reliability of the monitoring system.

### Best practices and common anti-patterns
- **Version Management**: The version of Grafana instances should be strictly managed, and officially released security and repair patches should be tracked in a timely manner. It is recommended to include the Grafana version in the unified management of base images or deployment configurations.
- **Key dashboard testing**: For dashboards that carry key tasks such as core SLO monitoring and alarm rule configuration, regular functional regression testing should be established in non-production environments, especially before and after Grafana platform upgrades.
- **Anti-Pattern**: Avoid long-term use of unvalidated preview (Beta) or edge versions of Grafana in critical production dashboards.

### Related indicators and SLO
Although this fix does not directly change SLI/SLO, it maintains the basis for SLI (such as error rate, latency) to be correctly collected and visualized. A common SRE practice is to establish an SLO that "monitors the health of the system itself". Its SLIs can include:
- Grafana API availability (e.g. success rate of `GET /api/health`).
- First screen load time for key dashboards (e.g., P95 < 3 seconds).
- Success rate and latency of dashboard queries (statistics through Grafana’s data source query plug-in).

Ensuring the correctness of Grafana's own functions is a prerequisite for achieving the above SLO. When such a bug affects the usability of a dashboard or the accuracy of data, it actually eats into the Error Budget of the Monitoring System service.
