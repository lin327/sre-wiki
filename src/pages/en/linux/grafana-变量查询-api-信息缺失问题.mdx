## Overview

In the evolution of the monitoring and visualization platform Grafana, its variable function is the core component for realizing dynamic dashboards and interactive queries. Recently, Grafana's variable query system has undergone API reconstruction and upgrade. This page aims to analyze a compatibility issue that arose during this process: the data structure returned by the new version of the variable query API is missing key metadata information (such as the `name` field) compared to the old version of the API. This issue directly affects the compatibility of data source plug-ins, the migration of dashboards, and the precise control of query results by operation and maintenance personnel. It is an important reliability issue that the SRE team needs to pay attention to when upgrading Grafana instances or developing custom data source plug-ins.

## Core concepts

To understand this problem, we need to first clarify the two main API paradigms of variable query in Grafana:

1. **Legacy API**: The data source plug-in responds to variable query requests by implementing the `metricFindQuery` method. The array of objects returned by this method contains rich metadata, where each object contains at least `text` and `value` fields, but importantly, often also contains a `name` field**. The `name` field provides an unambiguous, human-readable identifier for this query result item and plays a key role in variable value selection, link building, and interaction with other dashboard components.

2. **New API**: Updated API based on `VariableQueryRunner` and `queryRunners.ts` architecture. In this design, the data source plugin is expected to return a more simplified data structure, containing mainly only `text` and `value` fields**. It is clear from the submitted code reference that the code only maps these two core fields when processing the new API return results.

**Essence of the problem**: While pursuing interface simplification, the design of the new API inadvertently discarded the `name` field that was the de facto standard in the old API. This backward-incompatible change has caused the following problems: data source plug-ins, custom scripts, or dashboard JSON models that rely on the old version of the API to return the `name` field for logical judgment may have functional abnormalities or data display errors after the upgrade. For SREs, this involves the stability and maintainability of system observability configurations.

## Practice

There is currently no official built-in fix for this issue, but SREs and platform developers can adopt the following practices to deal with it:

1. **Data source plug-in compatibility adaptation**:
    * For teams that maintain custom data source plug-ins, they should ensure that the data returned by the `metricFindQuery` method works correctly on Grafana instances that are compatible with both old and new APIs. The most robust approach is to explicitly include the `name` field in the query results and keep its value consistent with the `text` field. In this way, no matter which API Grafana uses to parse data, it can obtain complete meta-information.

2. **Dashboard Migration and Verification**:
    * When migrating a dashboard from an old version of Grafana to a new version, focus on checking the links, data point annotations (Annotation) or other advanced features that depend on variable query results. If you find that the relevant functionality is not working, you should go into the JSON model of the dashboard and check whether the expressions referencing the variable query result fields (especially `.name`) are still parsed correctly.

3. **Change Management and Testing**:
    * Variable interaction functionality for all key dashboards should be fully tested in a pre-release environment before planning to upgrade to a major version of Grafana. Establishing automated test cases for variable queries can verify whether fields other than `text` and `value` are passed and used correctly.

4. **Monitoring and Alarm**:
    * Basic monitoring can be set up for key endpoints of the Grafana API (such as interfaces related to dashboard saving and variable evaluation) to ensure that the structure of the API response after the upgrade is as expected. For front-end errors caused by missing fields, you can use front-end monitoring tools (such as Sentry) to capture and alert.

## SRE Key Points

Although this problem is small, it profoundly reflects the multiple aspects that SRE needs to pay attention to in ensuring system reliability:

* **Reliability and Backward Compatibility**: Backward-incompatible changes to the API are a typical **reliability risk**. It breaks existing integration contracts and can lead to functional failures after a seemingly "normal" upgrade. SREs should be involved in reviewing API changes to such underlying platforms to assess the impact from both the integrator and operations perspective.
* **Basics of Observability**: Grafana itself is an observability platform, and the correctness of its dashboards and variables is a prerequisite for **observable data to be accurately understood and presented**. The data structure defects of the basic platform will directly affect the operation and maintenance personnel's judgment of the status of the back-end system, constituting a kind of "observability on top of observability" problem.
* **Best Practices and Anti-Patterns**:
    * **Best Practice**: When evolving your API, adopt a progressive strategy (such as introducing `fields` mappings instead of removing fields), provide clear migration guidance and deprecation cycles. Maintain maximum information integrity in returned data.
    * **Anti-Pattern**: Deleting existing but potentially dependent fields for the sake of interface "purity" is an anti-pattern of **destructive changes**, which will unnecessarily increase the upgrade costs and risks for users of the entire ecosystem.
* **Related Metrics**: Although this issue does not directly correspond to an SLI, it affects the **usability** of the dashboard functionality. This can be tracked as technical debt or post-upgrade verification. For example, define an **SLO**: "Variable filtering functionality for all core dashboards remains 100% functional after upgrade", and fixing this issue is one of the prerequisites for achieving this SLO.
