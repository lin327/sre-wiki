## Overview

In the daily work of SREs, using observability platforms such as Grafana to filter and query logs is a core skill for quickly locating faults and analyzing system behavior. This page focuses on a specific tool behavior issue: In the new Grafana Log Grid Panel, the `|=` operator does not behave as expected when using the Log Query Language (LogQL) `|=` filter. This problem may seem minor, but in troubleshooting high-stress events, any behavior that is contrary to the tool's expectations may mislead the direction of analysis and consume valuable response time. Understanding and avoiding tool pitfalls like these is an important part of ensuring reliable engineering practice.

## Core concepts

* **`|=` Operator (LogQL)**: This is a standard filter in the Log Query Language, used to filter whether log lines contain a specific string or pattern. Its standard semantics is "contains". For example, `|="error"` returns all log lines containing the string "error".
* **Problem Behavior**: According to reports, in the Grafana-specific log table panel, using the `|=` operator to filter a value, such as `|="0"`, the behavior changes from "return all rows containing '0'" **exception to **"return only rows that are exactly equal to '0' or only contain '0' as a standalone word" (specific implementation details need to be verified). This seriously violates the general convention that the `|=` operator is based on substring matching.
* **Differences between old and new panels**: The report clearly states that in "old forms" (possibly an older plugin or a different panel type) the filter works fine. This indicates that the issue is related to a specific implementation or update of the Grafana front-end log visualization component.

## Practice

Based on the issue report, the following practical points can be extracted:

**1. Problem recurrence and impact**
* **Scenario**: When you need to **exclude** lines containing a specific string (such as `0` for a normal count or `200` for a status code) from a large number of logs, using `|= 0` should retain all lines that do not contain "0".
* **Actual Behavior**: The new version panel incorrectly interprets this query as "Only show rows containing '0'", which is exactly the opposite of what the user intended. This can cause the SRE to incorrectly filter out critical information, or become confused.
* **Scope of Impact**: All users who use this specific panel and rely on `|=` for string exclusion operations.

**2. Workaround**
Before the official fix is released, SRE can adopt the following temporary solutions:
* **Use regular expressions `!=`**: Try using LogQL's "not equal" regular operator `!=` instead. For example, use `!=~ ".*0.*"` to match any line containing "0" and exclude it. Note the precise semantics of `!=` and `!=~`.
* **Switch panel type**: If conditions permit, temporarily switch the panel type back to the old table plug-in or other log visualization components that support correct filtering logic.
* **Query moving down**: Complete filtering at the data source level (such as Elasticsearch's `must_not` clause or Loki's combined query), and then display the results in the Grafana panel.

**3. Problem reporting and tracking**
For the SRE team, upon discovering such an issue they should:
* Search or create an issue (such as this case #125160) in official channels (such as Grafana GitHub).
* Provide clear reproduction steps, environmental information, and expected behavior comparisons.
* Subscribe to issue notifications to upgrade in time after the fixed version is released.

## SRE Key Points

* **Relationship with reliability**: **The reliability of observability tools directly affects the efficiency and accuracy of system reliability assurance work**. A misbehaving filter may delay fault detection (MTTD) and mean time to recovery (MTTR). SREs should verify and monitor the behavior of critical toolchains just like they do infrastructure.
* **Best Practice**:
    * **Tool version management**: After the core tools such as Grafana are upgraded, regression testing of key dashboards and query logic should be performed.
    * **Query logic documentation**: For complex log queries commonly used within the team, their expected behavior and applicable scenarios should be recorded, especially those queries that rely on specific version features.
    * **Establish a feedback channel**: Establish a process for quickly reporting tool bugs to the official community to contribute to the team and the entire SRE community.
* **Common anti-patterns**:
    * **Blindly trust the tool**: Each operator of the tool is considered to strictly follow its universal document definition without contextual validation.
    * **Ignore tool update log**: Skip the version update notes of tools such as Grafana and miss key breaking changes or known issues.
* **Related indicators (SLI/SLO/SLA)**: Although they do not directly correspond to a certain SLI, such problems affect the availability of log queries and the accuracy of alarms. For example, a dashboard that relies on this filter to generate error log counts as an SLI may report falsely low error rates due to behavioral errors, masking real system issues.
