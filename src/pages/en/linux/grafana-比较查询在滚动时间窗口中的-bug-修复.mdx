## Overview

In SRE practice, performance comparisons through time series data (e.g., comparing latency this week versus last week, today versus yesterday) are core operations for identifying trends, diagnosing anomalies, and assessing the impact of changes. As a mainstream visualization platform, Grafana's "comparison query" function facilitates this operation. However, there was a known flaw in this feature that could cause comparison data to be calculated incorrectly when the dashboard's time range was set to a "relative" or "rolling" window (e.g., "Last 1 hour", "Rolling 24 hours"). The purpose of this page is to explain this issue, describe its potential impact on monitoring reliability, and describe the correct behavior after the fix.

## Core concepts

* **Rolling Time Window**: Refers to the time range of the dashboard dynamically moving backward based on the current moment, such as "the past 1 hour". As time passes, the start and end time points of the window continue to change, but the duration of the window remains the same.
* **Relative Time Range**: It is a common expression for rolling windows, emphasizing the offset of the time range relative to the current moment (`now`).
* **Comparison query (Time Comparison)**: A feature in Grafana that allows users to overlay and compare the data of the current time window with the data of a previous equal-time window in the same panel. For example, compare data for "last hour" with data for "last hour 24 hours ago."
* **Source of the problem**: Before the fix, when the main time range of the dashboard is a rolling window, the comparison query may have a logic error when calculating the start and end timestamps of the "previous time window", and fails to correctly calculate the offset based on the "current time", resulting in inaccurate or misaligned comparison data segments.

## Practice

This entry stems from an official bug fix for the Grafana project. As an SRE engineer, understanding and validating this fix is ​​critical to ensuring the accuracy of your monitoring panel.

**How to verify and apply**:

1. **Confirmed Release**: This fix has been included in specific subsequent releases of Grafana. Please ensure that your Grafana instance is upgraded to a version that contains this fix (for the specific version number, please refer to the associated milestone or change log of GitHub issue #125102).
2. **Reproduction and Testing**:
    * Create a new Grafana dashboard.
    * Add a time series panel.
    * Configure a comparison query for the panel. For example, enable the Compare option in the Query Editor and set the offset to `1d` (vs yesterday).
    * Set the time range in the upper right corner of the dashboard to "Last 1 Hour" or a similar rolling window.
    * **Performance before repair**: The comparison data displayed on the panel may be for a wrong time period, or the data cannot be correctly aligned, causing the comparison conclusion to be invalid.
    * **Performance after repair**: The panel should clearly and correctly display the data of the current time window and the offset time window, and the duration of the two time windows should be strictly equal.
3. **Check in Dashboard JSON**: For complex dashboards, you can export its JSON model and check the query definition of the relevant panels to ensure that the time offset logic is as expected.

## SRE Key Points

* **Link to Reliability**: The accuracy of monitoring panels is the basis for SREs to trust their toolchains. A comparison query with calculation errors may cause the SRE team to make inappropriate operation and maintenance decisions based on incorrect comparison data (for example, mistaking performance deterioration or improvement), directly affecting the reliability of the service. Fixing such bugs directly improves the data fidelity of the surveillance system.
* **Best Practice**:
    * **Version Maintenance**: Pay attention to and apply stable version updates and security patches of monitoring tools (such as Grafana) in a timely manner. Many updates contain such critical functional fixes.
    * **Panel Test**: For key dashboards that rely on complex time calculations (such as comparisons, predictions), basic smoke tests should be established to verify whether their core functions are normal after Grafana upgrade.
    * **Clear Marking**: Clearly mark the offset logic of the comparison query in the dashboard to avoid team members misunderstanding the baseline for data comparison.
* **Common anti-patterns**:
    * **Blindly trusting "yesterday's comparison"**: Without verifying whether the tool correctly implements the rolling time offset calculation, the conclusion of "yesterday's comparison" is directly written into the post-analysis report or used as an alarm basis.
    * **Ignore Time Range Settings**: Not realizing that the setting of the dashboard's main time range (fixed vs. rolling) can affect the internal calculation logic that relies on it, resulting in inconsistent data when viewed by different team members.
* **Related indicators (SLI/SLO/SLA)**: This fix mainly affects the quality of **observability** itself, rather than directly affecting user-oriented service SLI. However, by ensuring the correctness of the data, it indirectly supports the ability to conduct accurate comparisons and trend analysis of core SLIs such as service delays and error rates, which is indispensable for maintaining related SLOs.
