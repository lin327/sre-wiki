# grafana/grafana#123923: Tempo: Streaming headers bug

## Overview

Tempo is a high-performance, distributed tracing backend in the Grafana ecosystem that stores and queries trace data from OpenTelemetry, Jaeger, and other sources. In a multi-tenant environment, it is crucial to isolate data from different tenants (organizations) through the `X-Scope-Orgid` HTTP header. This document describes a technical issue and root cause analysis of a technical issue where when the streaming feature `streamingForwardTeamHeadersTempo` is enabled, Tempo cannot correctly parse the tenant ID due to a conflict between the incoming gRPC metadata and the header configured by the data source, eventually causing a "no org id" error. This issue directly affects Tempo's reliability and data isolation in a multi-tenant environment, and is a typical boundary condition issue that SREs need to pay attention to when monitoring distributed tracing systems.

## Core concepts

To understand this bug, several key concepts need to be clarified:

- **gRPC Metadata**: In gRPC calls, the client can send metadata in the form of key-value pairs (similar to HTTP headers), and the server can obtain these metadata through the API. Metadata key names are **case sensitive**.
- **Case-Insensitive HTTP Headers**: According to the HTTP/2 and gRPC specifications, header key names will be normalized to all lowercase when transmitted to the network layer. For example, `X-Scope-Orgid` and `x-scope-orgid` are treated as the same header on the network wire.
- **Datasource-Configured Headers**: When configuring the Tempo data source in Grafana, you can predefine some fixed HTTP headers, such as `X-Scope-Orgid` for tenant isolation. These headers should have the highest priority in the request.
- **Team Headers**: This is a mechanism used internally by Grafana to pass context (such as organization ID) between plugins or components, forwarded through the `getTeamHeaders` function.

The root of the problem is that the `getTeamHeaders` function blindly forwards all incoming gRPC metadata, without considering the possibility of key name conflicts (case insensitivity) with higher priority data source configuration headers.

## Practice

### Problem recurrence conditions

1. In the Grafana data source configuration, configure the `X-Scope-Orgid` header for Tempo (for example, the value is `"my-org"`).
2. Enable the feature switch `streamingForwardTeamHeadersTempo=true`.
3. The problem is triggered when the gRPC metadata of a request also contains a key named `x-scope-orgid` (lowercase), and its value is an internal numeric organization ID (such as `"123"`).

### Root cause analysis

`getTeamHeaders` converts and adds all gRPC metadata passed in to a Go `map[string]string`. At the same time, the `getClientOptionsHeaders` function will also add the headers of the data source configuration (such as `X-Scope-Orgid`) to the same map. This results in two keys in the same map:
- `"X-Scope-Orgid"` (from data source configuration, value `"my-org"`)
- `"x-scope-orgid"` (from incoming gRPC metadata with value `"123"`)

When this map is serialized over the gRPC wire for transmission, both keys are normalized to `x-scope-orgid`. Since the iteration order of map in Go language is **uncertain and random**, the header value finally sent to the Tempo server may be `"my-org"` or `"123"`, and the order cannot be guaranteed. If the wrong value `"123"` is parsed by Tempo as the first or only `x-scope-orgid` header, and Tempo cannot find the corresponding tenant based on it, a "no org id" error will be thrown.

### Repair plan

The official fix is to add conflict detection logic in the `GetHeadersFromIncomingContext` function (located in `pkg/tsdb/tempo/utils/stream_utils.go`).

**Fix core logic**:
Before forwarding the team header, check whether each header key name to be forwarded conflicts with the header key name configured by the data source (ignoring case). If there is a conflict, the entry in the team header is skipped and forwarded, thereby ensuring that the header configured by the data source has absolute priority.

**Expected behavior after fix**:
Even if the incoming gRPC metadata contains keys with different case forms such as `x-scope-orgid` or `X-Scope-ORGID`, as long as the data source is configured with `X-Scope-Orgid`, the `x-scope-orgid` header value ultimately sent to Tempo will always be the value configured by the data source (such as `"my-org"`), eliminating data inconsistency problems caused by the randomness of the map iteration order.

## SRE Key Points

- **Association with reliability and observability**: This bug is a typical multi-tenant data isolation failure problem, which directly destroys the **reliability** of tracking data (data is sent to the wrong tenant or cannot be accessed). For SREs that rely on Tempo for problem diagnosis, incorrect tracking query results will seriously mislead the direction of troubleshooting and damage the **observability** of the system.
- **Best Practices and Common Anti-Patterns**:
    - **Best Practice**: When designing mechanisms to pass context across components (e.g. via headers), precedence rules must be clear. Generally, the infrastructure layer (such as data source configuration) should have higher policies than the application layer (such as dynamic metadata carried by requests). Implementations should perform explicit conflict detection and resolution.
    - **Common anti-pattern**: Blindly forwarding or merging configuration items (such as headers) from different sources with the same semantics, without considering naming conflicts (especially case-insensitive conflicts) and priorities, is a common cause of such intermittent failures that are difficult to debug (because the map iteration order is random).
- **Related indicators (SLI/SLO/SLA)**:
    - This issue directly affects the **Tracking data query success rate** of this SLI. When an error occurs, user queries to Tempo will fail.
    - Teams should ensure the reliability of such multi-tenant data isolation, with an SLO that can be set to "proportion of queries successfully returning specified tenant data ≥ 99.9%". The occurrence of this bug may cause the SLO to be eroded and the Error Budget to be consumed. After repair, the coverage of such boundary conditions should be strengthened through integration testing to prevent regressions.
