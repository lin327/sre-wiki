# Grafana Issue

## Overview

In the daily work of SREs, dashboard snapshots are a key tool for recording the system status at a specific moment for post-event failure analysis and knowledge archiving. Grafana is a widely used visualization platform, and the accuracy of its snapshot function directly affects the efficiency of event review. This page documents a known flaw in Grafana related to duplicate rows and snapshots: when a dashboard uses template variables to create duplicate rows, the row headers in the generated snapshot do not correctly display the specific variable values ​​for the current iteration, but incorrectly retain the selection value "All". Understanding this issue helps SRE engineers identify potential data distortions when archiving and reviewing historical snapshots, and take appropriate avoidance measures.

## Core concepts

- **Duplicate Rows**: An advanced feature of Grafana dashboards that allows dynamically generating multiple row panel groups with the same content but different data sources or label filters based on each value of a template variable (such as server name, environment name). This greatly improves the reusability and organization of the dashboard.
- **Snapshot**: Save the complete state of the dashboard at a specific point in time (including data, variable selection, time range, etc.) as a static, shareable JSON file or URL. It is an important means for cross-team collaboration, failure reviews, and compliance audits.
- **Template variables**: Interactive elements of the dashboard, allowing users to filter and change the data range of panel queries through drop-down menus and other methods. When the variable selection is All, the query includes data for all possible values ​​of the variable.
- **Essence of the Problem**: When building a dashboard, the headers of duplicate rows can be dynamically bound to the variable values ​​of the current iteration. However, when the snapshot is generated, the variable context information used to render the header appears to be lost or fixed to "All", causing all duplicate rows' headers to appear as "All", losing distinction.

## Practice

**Problem Manifestation**:
This defect occurs when the following conditions are true:
1. The dashboard contains a template variable that allows the selection of "All".
2. Use the repeat row function based on this template variable.
3. Create a dashboard snapshot when the variable value is "All".

The resulting snapshot will show an error state: all duplicate rows will have the title "All" instead of showing specific variable values ​​for each row (e.g. `server-1`, `server-2`, etc.) as in the live dashboard. This greatly reduces the readability and diagnostic value of the snapshot.

**Temporary solution**:
Until Grafana officially fixes this issue, the SRE team can use the following workarounds:
- **Manually create targeted snapshots**: Avoid creating snapshots when the variable selection is "All". Create a separate snapshot for each important variable value (or a representative subset) that needs to be archived, making sure the titles are correct.
- **Indicate in snapshot title/description**: If you must create a snapshot of "all" values, you can clearly mark "This snapshot is the 'all' variable state in the metadata (title or description) of the snapshot, and the row titles are invalid. Please refer to the chart panel below to distinguish".
- **Combined with Snipping Tool**: Use an external snipping tool to capture the real-time dashboard as a supplementary record.

## SRE Key Points

- **Relevance to Observability and Incident Response**: This flaw directly affects the accuracy of the "observability archive" of dashboard snapshots. In postmortem, a snapshot with a confusing title will increase communication costs, mislead the direction of analysis, and delay root cause identification. SREs must be aware of this limitation when referencing historical snapshots for comparison.
- **Best Practices**:
  1. **Snapshot Verification**: After creating a key snapshot, immediately open and check its integrity, especially the parts involving dynamic elements (such as repeated rows, template variables).
  2. **Category Archiving**: Classify and label important dashboard snapshots, explaining their context and known limitations for subsequent reference.
  3. **Track official updates**: Pay attention to Grafana’s [issue #112455](https://github.com/grafana/grafana/issues/112455) and related support upgrades, and apply the fixed version in a timely manner.
- **Relevant Metrics and SLA**: This issue itself does not directly affect the SLI/SLO of the system, but it affects the **fidelity** of the dashboard used to monitor these metrics. If teams rely on snapshots as evidence for SLO reports or audits, this flaw could lead to a loss of credibility in reports, indirectly impacting SLA-related communications.
- **Common anti-patterns**:
  - **Unconditional Trust Snapshot**: Reference the snapshot content as an absolutely accurate document without verifying it.
  - **Over-reliance on a single snapshot**: Only understand the overall system through a snapshot of the "all" state, while ignoring the lack of detailed information.

Documenting the known flaws of such tool chains in the SRE's documentation and knowledge base is itself a practice that improves the overall reliability culture of the system. It reminds us that the tools used to ensure reliability may themselves have imperfections, requiring careful and critical thinking from engineers.
