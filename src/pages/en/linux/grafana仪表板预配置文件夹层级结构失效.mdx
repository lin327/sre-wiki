## Overview

Dashboard Provisioning is a key feature in Grafana that allows operations teams to manage the creation and synchronization of dashboards and folders through declarative YAML files. This is critical for enabling Infrastructure as Code (IaC), automating deployments, and maintaining large-scale, standardized dashboard environments. In SRE practice, it helps ensure consistent and reproducible monitoring views.

However, Grafana introduced a behavior change in v11.6.0 that caused the normal preconfiguration of folder nesting (subfolders) to fail. All configured folders are created in the root directory of Grafana, destroying the preset hierarchical structure, which may have an impact on the existing monitoring organization logic and operation and maintenance processes.

## Core concepts

### Dashboard Preconfiguration
Refers to the process of automatically creating, updating, or deleting dashboards and folders by reading specified YAML/JSON configuration files when the Grafana server starts. Configuration files are usually located in the `etc/grafana/provisioning/dashboards/` directory.

### Folder hierarchy
Dashboards in Grafana are organized through folders. In v11.5.x and earlier, provisioning supports the creation of nested folders (subfolders). This is accomplished by specifying the parent folder name using the `folder` attribute in the folder definition.

### Configuration model changes
After upgrading from v11.5.3 to v11.6.0, the provisioning engine's folder processing logic has changed. The core problem is that even if the subfolder already exists in the system and has been manually moved to the correct location, the provisioning process still incorrectly attempts to recreate the folder at the root directory, indicating that its synchronization logic (Reconciliation Loop) fails to correctly recognize and maintain the existing hierarchical relationship.

## Practice

Based on the scenario described in the issue, the following are examples and performance of the issue configuration:

**Configuration structure valid in Grafana v11.5.3 (simplified example):**
```yaml
# provisioning/dashboards/structure.yaml
apiVersion: 1
providers:
  - name: 'default'
    folder: 'SERVICES AND SYSTEMS'
    folderUid: 'services'
    type: file
    options:
      path: /var/lib/grafana/dashboards

# provisioning/dashboards/folders.yaml
apiVersion: 1
folders:
  - orgId: 1
    title: SERVICES AND SYSTEMS
    uid: services
  - orgId: 1
    title: BEMTEVI
    uid: bemtevi
    # The parent folder is specified here through the folder attribute
    folder: SERVICES AND SYSTEMS
```

In this configuration, Grafana creates two folders: `SERVICES AND SYSTEMS` as the top-level folder and `BEMTEVI` as its subfolder.

**Exceptional behavior in Grafana v11.6.0:**
- The user configures the `BEMTEVI` folder as a subfolder through `folder: SERVICES AND SYSTEMS`.
- After upgrade, when the preconfiguration script is run, it will recreate an **empty folder** (without any dashboard) named `BEMTEVI` in the **Grafana root**, regardless of whether the `BEMTEVI` folder already exists within `SERVICES AND SYSTEMS`.
- Manually moving this newly created root folder back under `SERVICES AND SYSTEMS` does not solve the problem, a new root folder will be created the next time preconfiguration is executed.

**Current temporary solution:**
Pending an official fix, possible workarounds may include:
1. **Downgrade or keep stable version**: Do not upgrade to the affected Grafana version yet.
2. **Adjust preconfiguration strategy**: Temporarily abandon the nested structure, flatten all folders in the root directory, and wait for official patches.
3. **Combined with API or script for post-processing**: After Grafana is started, the Grafana API is called through a script to correct the folder hierarchy, but this increases complexity and maintenance costs.

## SRE Key Points

- **Link to reliability**: Preconfiguration failures directly impact the **manageability** and **reproducibility** of the monitoring system. During disaster recovery or environment reconstruction, the expected dashboard organizational structure may not be automatically restored, resulting in reduced operation and maintenance efficiency. This is a typical **Configuration Drift** problem.

- **Best Practices and Precautions**:
    1. **Full testing before upgrade**: Any upgrade of basic components should be fully regression tested based on the complete configuration set in the pre-release environment, especially to verify the automated configuration management process.
    2. **Versioned configuration management**: Incorporate dashboard preconfiguration files and application code into Git version control, and record the accompanying Grafana version constraints.
    3. **Implement configuration consistency checks**: You can write a script or leverage a CI/CD pipeline to verify after deployment that the folder/dashboard structure in Grafana is consistent with the expected configuration.
    4. **Monitoring and Alarm**: Monitor the success/failure of the preconfiguration process itself. Set alerts for critical organizational changes.

- **Relevant Indicators (SLI/SLO)**:
    - **SLI**: can monitor "the accuracy of key folder hierarchies after preconfiguration", or "the proportion of dashboards successfully deployed through automated processes".
    - **SLO**: You can set "After each Grafana version upgrade, the structural accuracy of all core folders after preconfiguration reaches 100%."

- **Associated Issue**: This issue reflects the importance of **Backwards Compatibility** and **Configuration Interface Stability** in software upgrades. When implementing a change management process, attention needs to be paid to the risks of such behavioral changes.
