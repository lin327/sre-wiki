## 概述

在使用 Grafana 进行可视化监控时，稳定的会话体验对运维人员至关重要。一个典型的用户体验问题是：仪表盘、播放列表或编辑界面每隔约5分钟会突然显示“未授权（Unauthorized）”错误，随后页面自动刷新，但系统并未强制用户重新登录。这种现象不仅打断了监控工作的连续性，也反映了后端会话管理与前端令牌刷新机制之间可能存在不匹配或配置问题。理解并解决此类问题是保障 Grafana 作为核心可观测性工具可靠性的关键环节。

## 核心概念

此问题主要涉及以下几个核心概念：

1.  **会话令牌（Session Token）**：用户登录 Grafana 后，浏览器会获得一个会话令牌（通常是一个 JWT 或 Session Cookie），用于后续请求的身份验证。该令牌具有有效期。
2.  **刷新令牌（Refresh Token）**：为了维持长期登录状态，Grafana 通常在访问令牌（Access Token）过期前，使用一个生命周期更长的刷新令牌来静默地获取新的访问令牌，无需用户再次输入密码。
3.  **会话超时与静默刷新**：Grafana 后端定义了会话超时时间（`token-max-idle-minutes` 等配置项）。前端应用（如 React 构建的 Grafana UI）则负责在令牌即将过期时，利用刷新令牌在后台发起刷新请求，以无缝更新访问令牌。
4.  **“未授权”错误**：当浏览器发起的 API 请求所携带的令牌已失效（过期或被撤销），而前端又未能成功完成静默刷新时，Grafana 后端会返回 `401 Unauthorized` 错误。前端的错误处理机制捕获此错误后，可能触发页面的重新加载逻辑，试图通过刷新页面来恢复状态。

该问题描述的现象——出现错误、刷新页面、但无需重登——表明 **访问令牌已失效，但刷新令牌仍然有效**。页面刷新触发了新的令牌刷新流程，从而恢复了会话，避免了登录页。

## 实践

针对此问题，可遵循以下步骤进行排查与解决：

### 1. 环境与配置检查

首先确认基础环境配置，尤其是 Docker 部署下的网络和时钟问题。

*   **检查系统时间同步**：确保运行 Grafana Docker 容器的主机与浏览器所在机器的系统时间保持同步。时钟漂移会导致令牌的 `nbf`（生效时间）和 `exp`（过期时间）判断失效。
    ```bash
    # 在 Docker 主机上检查时间
    timedatectl
    ```

*   **审查 Grafana 配置**：检查 `grafana.ini` 或环境变量中的会话相关配置。
    ```ini
    [auth]
    # 会话超时时间（分钟），决定了多久后必须重新登录
    login_maximum_inactive_lifetime_duration = 7d
    login_maximum_lifetime_duration = 30d

    [security]
    # 这是导致问题的关键配置之一，定义了访问令牌的最大空闲时间
    # 如果值设置为 5，与问题现象高度吻合。
    token_max_idle_minutes = 5
    ```
    如果 `token_max_idle_minutes` 设置过短（如5分钟），而前端刷新逻辑未能完美同步，就会周期性出现此问题。可尝试适当延长此值。

### 2. 网络与代理排查

部署在反向代理（如 Nginx、Traefik）之后时，需要检查代理配置。

*   **检查 `Secure` Cookie 属性**：如果 Grafana 通过 HTTPS 提供服务，会话 Cookie 可能被标记为 `Secure`。确保反向代理正确传递了 `X-Forwarded-Proto` 头，使 Grafana 知道当前是 HTTPS 连接，从而设置正确的 Cookie 属性。
    ```nginx
    location /grafana/ {
        proxy_pass http://grafana:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 确保此行存在，传递协议信息
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    ```

*   **检查浏览器网络请求**：在浏览器开发者工具（Network 标签页）中，找到返回 `401` 的 API 请求。检查该请求的 `Cookie` 请求头，确认携带的会话 Cookie 是否正确。同时检查响应头中 `Set-Cookie` 是否有意外的属性（如过短的 `Max-Age` 或不合适的 `SameSite`）导致 Cookie 被浏览器丢弃或限制。

### 3. 前端插件与浏览器兼容性

用户报告使用了 Vivaldi 浏览器（基于 Chromium）并禁用了广告拦截器。可以进行以下测试：

*   **在无痕模式下测试**：排除浏览器扩展、缓存或本地存储的干扰。
*   **使用不同浏览器测试**：在 Chrome、Firefox 等标准浏览器上复现，以确定是否是特定浏览器的兼容性问题。
*   **检查浏览器开发者控制台**：查看是否有 JavaScript 错误，这些错误可能阻止了前端的令牌刷新流程正常执行。

## SRE 要点

### 可靠性与用户体验
此问题直接影响用户对监控系统的可用性感知。虽然它不会导致完全不可用（因为页面会自动恢复），但周期性的视觉中断和潜在的仪表盘数据刷新延迟，会降低运维人员对 Grafana 的信任度，并可能掩盖更严重的底层监控目标（Target）故障。一个可靠的可观测性平台，其自身界面的稳定性是基础。

### 最佳实践与常见反模式
*   **最佳实践**：
    *   **合理配置会话超时**：根据内部安全策略和用户使用习惯，平衡 `token_max_idle_minutes` 和 `login_maximum_inactive_lifetime_duration`。对于内部使用的监控仪表盘，可适当放宽以保障体验。
    *   **确保时钟同步**：在所有基础设施（包括运行 Docker 的主机、浏览器所在的电脑）上启用 NTP 服务。
    *   **完善监控**：不仅监控业务服务的 SLI，也监控 Grafana 自身的可用性，例如通过合成监控（Synthetic Monitoring）定时检查登录和仪表盘访问。
*   **常见反模式**：
    *   在反向代理层过度优化或错误配置缓存头（如 `Cache-Control`），干扰了 Grafana 前端静态资源的正常加载。
    *   忽略 Docker 容器与宿主机、或微服务之间的网络策略，导致用于令牌刷新的 API 请求被意外拦截。
    *   升级 Grafana 或浏览器版本后，未对现有的会话和认证流程进行回归测试。

### 相关指标（SLI/SLO/SLA）
- **SLI (Service Level Indicator)**: 可以定义“Grafana 仪表盘无缝访问成功率”。通过自动化脚本或真实用户监控（RUM）记录会话中遇到 `401` 错误并自动恢复的次数。
- **SLO (Service Level Objective)**: 设定一个目标，例如“每月99.5%的 Grafana 会话期间无认证中断”。
- **事件响应**: 当此类事件报告增多时，应检查 Grafana 更新日志、社区讨论或已知问题，以确认是否为版本回归 Bug。在 [[incident-response-runbook]] 中可添加针对此问题的快速排查步骤。
