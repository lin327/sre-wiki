## Overview
In SRE practice, clear, timely, and actionable alarm notifications are the foundation of effective incident response. Grafana Alerting provides a powerful notification policy (Notification Policy) mechanism to control how alarms are grouped, routed, and sent. A common requirement is to split alerts with different labels (such as different `cluster`) into independent notification messages to avoid a single notification containing too many alerts (such as "32 firing alerts"), thereby making it easier to quickly locate the problem. However, according to the case provided, even if the `not_grouping` parameter is configured correctly, alarm notifications may still be accidentally aggregated, which will seriously affect the judgment and processing efficiency of operation and maintenance personnel.

## Core concepts
Before delving into the problem, several key concepts need to be clarified:
1. **Alarm grouping (Grouping)**: Grafana Alerting will group alarms with the same label set together by default to form an "alarm group" and send it through a notification message. This is controlled by the `group_by` field in the notification policy. The default `group_by` is usually `alertname`.
2. **Notification Policy**: This is a tree routing structure that determines which alarms (based on labels) should be sent to which contact point (Contact Point). It contains route matching rules, grouping rules (`group_by`), waiting time, etc.
3. **`not_grouping`**: This is a special `group_by` value. Theoretically, setting it on a certain notification policy node is intended to prevent the alarms under this node from participating in any grouping, that is, each alarm is sent as an independent message. This is exactly the configuration the user in the case was trying to use.
4. **Policy inheritance**: The child notification policy will inherit the configuration of the parent policy unless it is explicitly overridden. In this case, the user created a child policy and attempted to override the `group_by` setting inherited from the parent policy with `not_grouping`.

## Practice
The problem described in the case is rooted in a lack of understanding of the notification grouping mechanism of Grafana Alerting. When `group_by` is set to `not_grouping`, the meaning is "do not apply any grouping label to these alarms". However, that doesn't mean they won't be grouped by other rules.

The key practical experience is: **Grafana Alerting's notification grouping is determined by the most specific matching strategy, but its behavior follows a core logic - if the alarm is grouped at any upper node in the routing tree before being sent, then this grouping will be retained. **

For this case, the correct operation path and checkpoints are as follows:

1. **Check routing tree matching**: Make sure that the alert generated by your alert rule has a label that matches the **specific sub-notification policy** for which you set `not_grouping`. It is not enough to just check that the "Notification Route Preview" of the rule shows that the policy is present. You also need to confirm that the alarm has not been matched to other earlier policy nodes with different `group_by` rules.
2. **Verify policy configuration**: Go to `Alerting -&gt; Contact Points -&gt; Notification Policies` and double check the complete path from the root policy to your sub-policy. Confirm that the `group_by` setting of the parent or root node does not accidentally group these alerts early except for the node you want to configure `not_grouping` on. The root policy's `group_by: ['alertname']` is the default setting.
3. **Use `group_wait` and `group_interval` for debugging**: On the policy node where `not_grouping` is set, you can try to set `group_wait` and `group_interval` to very small values ​​(such as `0s`). This helps to immediately observe whether the alarm is split and sent, eliminating the possibility of misjudgment caused by waiting time.
4. **Understand the "minimum grouping" rules**: Even if `not_grouping` is configured, if an alarm **does not match any policy rule that explicitly specifies the `group_by` field during the route matching process**, it will still be grouped using the `group_by` of the root policy (usually `['alertname']`). Therefore, you must ensure that the grouping policy you want to apply exists on the matching path of the alarm.

In short, to implement "send each alert individually", you need to ensure that the matching path of the alert ends in a policy node with `group_by: []` set (an empty array, not `not_grouping`). The actual behavior of the `not_grouping` keyword is "use default grouping", which can be confusing in many versions.

## SRE Key Points
### Association with reliability
The grouping strategy of alarm notifications directly affects the timeliness and accuracy of event response. Alarm storms or information overload can slow down MTTR (Mean Time To Resolution). Moderate grouping of related alarms is beneficial, but mixing unrelated alarms (such as the same type of alarms from different clusters) together can create noise. A well-designed notification strategy is a key link in ensuring the effectiveness of the monitoring system and team work efficiency.

### Best practices and common anti-patterns
- **Best Practices**:
  - Design notification policy routing following the **"single focus"** principle, so that each policy node is responsible for processing alarms of a specific type or specific business domain.
  - Fully verify the routing and grouping effects of the notification strategy in the test environment, using the "simulated notification" function provided by Grafana.
  - Add comments to the configuration of `group_by` to explain its design intent (for example: `# Group by cluster to facilitate SRE processing by environment`).
- **Common anti-patterns**:
  - **Configured but not verified**: As shown in the case, `not_grouping` is configured but its actual effect in the complete routing chain is not verified in depth.
  - **Ignore inheritance relationship**: It is not realized that the child policy will inherit the `group_by` of the parent policy, resulting in the configuration that needs to be overwritten not taking effect.
  - **Excessive grouping**: Setting `group_by` to a label that is too broad for the sake of safety causes related alarms to be drowned.

### Related indicators
- **SLO vs. Error Budget**: The effectiveness of alert notifications can itself be an **internal Service Level Objective (SLO)**. For example, "All P1 alarm notifications must be delivered to designated persons within X minutes of triggering." Invalid grouping (information overload or lack of information) may result in "notification has been delivered" but "information cannot be effectively utilized", which indirectly affects the achievement of alarm-based SLO.
- **Alarm quality indicators**: You can monitor derived indicators such as "average number of alarms in notifications" or "proportion of silent alarms". Abnormalities in these indicators may indicate problems with the grouping strategy.
