# Grafana alerting retries crash instance with a webhook failure

## Overview

In SRE practice, the alerting system is critical infrastructure for ensuring system reliability, and it must itself possess a high degree of robustness and stability. However, a poorly designed or configured notification channel can itself become a source of instability. Based on a real production case ([[grafana-alerting]]), this article provides an in-depth analysis of how intermittent failures in an external webhook (such as Microsoft Teams) triggered Grafana's alert manager to enter an aggressive retry loop, ultimately exhausting resources and causing the entire Grafana instance to crash. This case vividly illustrates the dangers of cascading failures and emphasizes the necessity of implementing observability and protection strategies for the alerting system itself.

## Core Concepts

### 1. Retry Storm
A retry storm is a common failure pattern where a system, upon encountering intermittent errors or unavailability of dependent services, follows a preset retry strategy to make a large number of repeated attempts. If the retry mechanism lacks effective backoff, rate limiting, or circuit breaking mechanisms, the massive retry requests (and their associated network connections, threads, and memory resource consumption) will quickly exhaust local or remote system resources, leading to service avalanche. In this case, the Grafana Alertmanager component continuously retried after failing to send notifications to the Teams webhook, forming a "storm."

### 2. System Instability via Resource Exhaustion
System availability is often limited by the scarcest resource, such as CPU, memory, or file descriptors. The key log in this case, `dial udp 127.0.0.53:53: socket: too many open files`, clearly indicates that unlimited retry attempts consumed the operating system's file descriptor quota, causing all subsequent new network connection attempts to fail. This rendered the Grafana instance unable to handle any new requests (including API calls, dashboard access), ultimately appearing "inaccessible" to users. This is a typical cascading system-wide failure triggered by a specific feature (alert notification) malfunction.

## Practice

According to the incident description, the root cause lies in Grafana's alert notifier potentially having an overly aggressive retry strategy or insufficient recognition of downstream errors when facing specific errors (such as HTTP 429 rate limiting, network resolution failures). Although the original report did not provide a fix configuration, we can summarize the following protection and diagnosis steps based on SRE best practices:

**1. Configure Robust Retry and Notification Strategies**
   - **Identify Unrecoverable Errors**: Ensure the system can correctly identify errors like `4xx` client errors (especially `429 Too Many Requests`) as errors that do not require immediate retry. Logs show the system has marked them as "unrecoverable," but retry behavior still occurs, suggesting a potential configuration or logic defect.
   - **Implement Exponential Backoff with Jitter**: Configure all notification channels with exponential backoff strategies that have maximum retry counts and initial delays, avoiding high-frequency retries at fixed intervals.
   - **Set Global and Per-Channel Rate Limits**: In Grafana or underlying Alertmanager configuration, set global concurrent notification sending limits and per-channel sending rate limits to prevent a single faulty channel from consuming all resources.

**2. Use Dead Letter Queues and Alert Degradation**
   - **Configure Backup Notification Channels**: Do not rely on a single notification method. When the Teams webhook is unreliable, it should be possible to automatically or manually switch to alternative channels (such as email, other webhooks).
   - **Review Failed Notifications**: Move repeatedly failed alert notifications into a dedicated "failure queue" or dashboard for subsequent analysis, rather than letting them indefinitely occupy active resources.

**3. Strengthen Grafana Instance Self-Monitoring**
   - **Monitor Key Process Resources**: Set up monitoring for the Grafana process itself, focusing on:
     - `fd_used` / `fd_limit` (file descriptor usage)
     - `net_connections` (network connections)
     - `process_resident_memory_bytes`
   - **Alert on Its Own Health**: When the above metrics reach thresholds (e.g., file descriptor usage exceeds 80%), trigger alerts for the Grafana instance itself, achieving monitoring of the monitoring system.

## SRE Key Points

### Reliability, Observability, and Incident Response Association
- **Reliability**: This incident directly violated the Service Level Objective (SLO). As an observability platform, Grafana's own availability is the cornerstone of higher-level service reliability. A failure in an external notification source should not cause the entire monitoring platform to go down, which exposes Grafana's insufficient fault isolation design.
- **Observability**: This case highlights the importance of deep observability for the alerting system. Not only should the number of alert rule triggers be monitored, but also the **delivery success rate**, **delivery latency**, and **retry queue length** of alert notifications—these meta-metrics ([[observability-fundamentals]]).
- **Incident Response**: The response process for such incidents should include: 1) Quickly identify that it is an alerting system issue rather than a monitored target issue; 2) Temporarily disable or rate-limit the faulty notification channel; 3) Assess and restart the exhausted Grafana instance; 4) Conduct post-incident Failure Mode Analysis (FMEA) to optimize retry strategies.

### Best Practices and Common Anti-Patterns
- **Best Practices**:
  - **Configure Circuit Breakers for External Dependencies**: Calls to critical external services (such as Teams API) should implement circuit breaker patterns, failing fast after consecutive failures to avoid retries.
  - **Implement Layered Degradation**: Alert notifications should have multi-level degradation paths.
  - **Regularly Conduct Failure Drills**: Through Chaos Engineering methods, simulate webhook failure scenarios to verify retry strategies and system resilience.
- **Common Anti-Patterns**:
  - **Unlimited Retries**: Using the same aggressive retry strategy for all error types.
  - **Ignoring System Health**: Only focusing on alerting business functionality while ignoring the resource consumption of the alerting system itself.
  - **Single Point of Failure**: The entire organization's alert notifications depend on a single external channel.

### Related Metrics (SLI/SLO/SLA)
- **Service Level Indicator (SLI)**:
  - `alert_notification_success_rate`: The proportion of successfully sent notifications.
  - `alert_notification_delivery_latency`: The latency from alert trigger to successful delivery.
  - `grafana_process_file_descriptors_usage_ratio`: Grafana process file descriptor usage ratio (system health SLI).
- **Service Level Objective (SLO)**:
  - Monitoring platform self-availability SLO (e.g., no more than 99.9% accessible time per month).
  - Critical alert notification delivery success rate SLO (e.g., 99.5% of notifications delivered within 5 minutes).
- **Error Budget**: This incident consumed a significant amount of the monitoring platform's availability error budget, triggering a priority escalation for fixing this issue.
