# Grafana Issue

## Overview

In an SRE's day-to-day work, Grafana is a core tool for building observability and creating monitoring dashboards. Its powerful data transformation (Transformations) function allows us to aggregate, calculate and reshape data after data query to support complex analysis and visualization requirements. This document describes a specific bug found in Grafana v11.6.0 regarding the Add Field from Calculation transformation chain. This bug causes when a template variable is used in a transformation, its output fields are not visible in the input options of subsequent transformations, thereby destroying the ability to build reliable, maintainable multi-step data processing pipelines. Understanding and avoiding this problem is crucial to ensuring the logical correctness and visualization accuracy of dashboard data processing.

## Core concepts

1. **Data Transformation Chain**: In the Data tab of the Grafana panel, you can add multiple transformation steps. The output of the previous step automatically becomes the input of the next step, forming a data processing pipeline.
2. **Add Field from Calculation Transformation**: This is a common transformation type used to create new calculated fields based on existing fields using binary operations (such as `Add, Subtract, Multiply, Divide`) or more complex functions.
3. **Template variables (`${variable}`)**: A powerful feature of the Grafana dashboard, allowing users to dynamically change values ​​in queries or transformations, and achieve interactive filtering and parameterization of data views.
4. **Field Visibility Issue**: When building a transformation chain, the field selectors (drop-down menus) for subsequent transformation steps should list all fields produced by previous transformations. This bug caused the list to not update correctly when variables were used as input to operations.

## Practice

### Steps to reproduce the problem
The following is a reproduction path compiled from the original report, which can be used to verify or understand the problem:
1. In the Transformations tab of the Grafana panel, add the first transformation: **"Add field from calculation - Binary operation"**.
2. In the configuration of the first transformation, replace one of the input fields with a `${variable}` (for example, a variable with a value of the constant 10).
3. Add a second transformation: **"Add field from calculation - Binary operation"**.
4. Try selecting the calculated result of the first transformation as the input field in the Action drop-down menu of the second transformation.
5. **Observation**: The fields generated by the first transformation do not appear in the optional fields list.
6. **Comparison test**: Replace `${variable}` in the first transformation back to a regular data field, and recheck the field list of the second transformation. At this time, the output field of the first transformation will be displayed normally.

### Temporary solutions and workarounds
Given that this is a confirmed software flaw, the following alternatives can be considered to build a reliable data pipeline until it is officially fixed:

- **Option 1: Solidify variable values**: If the business logic allows, the variable values that need to be used for calculation can be directly "solidified" into a calculated constant field. This can be achieved with an up-front "Add Field" transformation that only creates constant columns, thus bypassing the limitations of using variables in core calculation transformations.
- **Option 2: Restructure the transformation chain**: Try to adjust the transformation order, put the calculation that requires the use of variables at the last step of the transformation chain as much as possible, or isolate it in an independent panel query/transformation path to avoid its output as a dependent input for multiple downstream transformations.
- **Option Three: Use the "Prepare fields" transformation**: It is possible to use the **"Organize fields by name"** transformation to rename or arrange fields from upstream, which can sometimes refresh the internal state of the field list, but this is an unreliable workaround and is not recommended as a primary solution.

## SRE Key Points

### Association with reliability
This bug directly affects the reliability and maintainability of observability data pipelines built with Grafana. When data processing logic relies on a transformation output that relies on variable input, it may not be configured correctly because the field is not visible, resulting in:
- **Visualization Data Error**: Downstream transformations may produce unexpected results due to incorrect or default fields being referenced.
- **Configuration fragility**: Relying on a specific "solidify first and then switch" workaround will increase the complexity and maintenance cost of dashboard configuration, making it prone to errors when the dashboard is migrated or upgraded.
- **Team Collaboration Barrier**: Unintuitive behavior can confuse other SRE engineers when debugging or modifying dashboards.

### Best practices and common anti-patterns
- **Best Practices**:
    - **Test Transformation Chain**: After modifying a complex transformation chain involving variables, you should verify in a test environment that all downstream transformations and panels still get the correct fields and data.
    - **Documented Dependencies**: Clearly document the logic and known workarounds for complex transformation chains in a dashboard comment or in a text panel next to it.
    - **Hierarchical design**: Try to place complex variable calculations in separate queries or transformation groups to reduce their intrusive impact on the main data pipeline.
- **Common anti-patterns**:
    - **Deeply dependent variable transformation chain**: Building a long chain where multiple transformations depend on the result of an intermediate calculation using variables can make the data flow very fragile.
    - **Ignore field validation**: Do not check whether the field list in the transformation configuration drop-down list is complete and configure it directly based on assumptions.

### Related indicators (SLI/SLO/SLA)
While this issue itself does not directly correspond to an SLI, it indirectly affects the availability and accuracy of monitoring data.
- **SLI Correlation**: You can define an SLI for "Dashboard Data Correctness", such as "How often custom fields generated by a transformation match expected values". This bug causes the SLI to drop.
- **Monitoring Recommendation**: For business-critical dashboards, periodic dashboard health checks (e.g., testing the execution of queries and transformations via the Grafana API) can be configured to monitor the occurrence of such configuration issues.
