# Grafana Issue

## Overview

This document records a state synchronization issue caused by multi-valued variable switching when using the "Duplicate Rows" feature in the Grafana monitoring panel. This issue directly undermines the accuracy and real-time nature of dashboard data and is a typical anti-pattern that SREs need to be wary of when building and maintaining automated monitoring dashboards. When SREs perform troubleshooting or capacity assessments based on such dashboards, outdated or erroneous data can lead to misjudgments and extended incident response times (MTTR), so it is critical to understand how this problem works and how to circumvent it.

## Core concepts

1. **Multi-value Variable**: A query variable in a Grafana dashboard that allows users to select multiple values (for example, multiple data centers or service instances). The `includeAll: true` option adds an "All" option, which selects all available values.
2. **Row Repeat**: The function of dynamically creating multiple dashboard rows using variable values. When a variable has N selected values, N corresponding rows will be generated, and the panel in each row will filter and display data for the variable value.
3. **Stale State**: In the context of this question, it means that after the variable value driving the repeated row changes (especially switching from "All" to a specific value), the query or rendering of the panel cannot be fully updated, and there are still references to the old variable value or data cache, causing the displayed data to be inconsistent with the current selection.
4. **Variable Reevaluation**: Ideally, any change in a variable's value should trigger a complete query and re-rendering of all panels it depends on (including duplicate rows and their inner panels). This bug describes a failure of this process.

## Practice

This problem can be reproduced in Grafana v11.6.1 (may affect specific versions). The steps to reproduce are as follows:

1. **Create Dashboard**: Create a new dashboard and create a variable that supports multiple selections (such as `site`), whose `multi` attribute is `true` and `includeAll` is `true`.
2. **Configure row repeat**: Add a "Row" panel to the dashboard and configure `"repeat": "site"` in its settings so that it repeats based on the value of the `site` variable.
3. **Set initial state**: Set the variable `site` to "All" through URL parameters or drop-down boxes. At this point, the dashboard should show rows and data for all data centers (e.g. `eqiad`, `codfw`).
4. **Triggering the problem**: Switch the value of the variable `site` from "All" to a single value (e.g. `eqiad`).
5. **Observation phenomenon**: At this time, although the row panel will be updated (only rows related to `eqiad` will be retained), the monitoring panel (Panel) inside the row still displays data from other data center (such as `codfw`) hosts, which is an outdated state.

**Environment and Examples**:
- The issue was discovered in a production dashboard used to monitor the Wikimedia load balancer that contained duplicate rows.
- Verifiable via the following public link: `https://grafana.wikimedia.org/d/000000343/load-balancers-lvs?orgId=1&from=now-12h&to=now&timezone=utc&var-site=eqiad`.

## SRE Key Points

* **Relationship with Reliability**: This problem directly damages the reliability of the monitoring system. SREs rely on dashboards for health checks, anomaly detection, and incident response. Incorrect panel data will mislead analysis and may lead to wrong decisions (such as misjudgment of fault scope and ignoring real alarms). Fixing or avoiding such problems is an important part of ensuring "observability reliability".
* **Best Practices and Anti-Patterns**:
    * **Anti-Pattern**: Blind reliance on automated variable updates without final validation. After performing key variable switching, the correctness of the panel data should be spot-checked manually or through automated testing.
    * **Best Practice**:
        1. **Version Management**: Before upgrading the Grafana version, fully verify in the test environment whether the complex functions of the dashboard (such as duplication, templates) work properly.
        2. **Defensive Design**: For extremely critical dashboards, consider explicitly displaying the currently active filter conditions (such as variable values) in the panel title or query logic to quickly detect inconsistencies.
        3. **Issue reporting and tracking**: Once such a rendering bug is discovered, it should be reported immediately to the upstream community or maintenance team (such as GitHub Issue in this case), and the repair status should be tracked.
* **Related Metrics (SLI/SLO/SLA)**: Although this issue is not directly related to traditional SLI, it affects the **Accuracy** and **Freshness** of the monitoring data, which are important internal indicators for measuring the quality of the observability system. An unreliable dashboard makes any SLO determination based on its data meaningless.
* **Incident Response**: During incident response, the SRE will frequently manipulate dashboard variables to focus on the fault domain. Such bugs may be ignored under the pressure of events, leading to wrong troubleshooting directions. Therefore, when writing a troubleshooting runbook, you should include a step to verify that the panel data matches the filter criteria.
