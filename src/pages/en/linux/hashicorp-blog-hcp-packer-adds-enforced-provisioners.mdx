# HashiCorp Blog - HCP Packer adds enforced provisioners

## Overview

In complex hybrid cloud environments, using unified "golden images" (such as AMIs, VM images, Docker containers) is a key practice for infrastructure standardization. However, as these images are distributed and used across multiple teams and environments, ensuring they consistently meet security, compliance, and operational standards throughout their lifecycle becomes extremely challenging. The introduction of HCP Packer Enforced Provisioners addresses this core governance challenge. It provides platform and security teams with a centralized mechanism to automatically and mandatorily execute necessary configuration steps in all downstream image builds, thereby guarding image trustworthiness and consistency without increasing user complexity.

## Core Concepts

### Image Governance Challenges

In many organizations, image creation and maintenance involves multiple teams. Typically, platform teams are responsible for building and hardening base images, while downstream application teams customize builds on top of them to meet their own needs. While flexible, this model introduces governance risks: security teams struggle to ensure that hardening configurations, compliance controls, and required software components are not accidentally modified or removed during image handoff. Lacking centralized enforcement mechanisms leads to operational inconsistency across environments and increased security risk.

### Enforced Provisioners

Enforced Provisioners is a new capability provided by HCP Packer designed to address the above challenges. Its core idea is to mandatorily bind **must-execute** configuration logic (Provisioners) to the image build process.

1.  **Centralized definition**: Platform and security teams upload and manage provisioner definitions (e.g., scripts for security scanning, applying compliance settings, installing required monitoring agents) through HCP Packer's UI or API.
2.  **Bucket association**: Associate these provisioners with specific HCP Packer buckets (used for organizing and managing image versions).
3.  **Automatic execution**: When any downstream team triggers a new image build based on that bucket, HCP Packer automatically retrieves and executes all associated enforced provisioners.
4.  **Version tracking**: HCP Packer records the enforced provisioner version used in each image build, providing a clear applied control manifest for each image version, greatly simplifying compliance audit processes.

## Practice

The process of implementing enforced provisioners mainly includes the following steps. The platform team can complete them centrally, while downstream users benefit from enhanced governance without awareness.

1.  **Define configuration logic**: Write configuration scripts or modules that need to be enforced using Packer's standard Provisioner syntax (such as Shell, Ansible, Puppet).
2.  **Upload to HCP Packer**: Register these provisioner definitions as "enforced provisioners" through `packer init` or HCP Packer API/CLI tools.
3.  **Configure bucket policy**: In HCP Packer, configure the enforced provisioner list for the target image bucket and specify execution order.
4.  **Trigger build**: Downstream teams continue using their familiar Packer templates to initiate build requests.
5.  **Enforcement and verification**: HCP Packer automatically injects and executes predefined enforced provisioners during the build process. After build completion, the new image version is recorded and stored along with the provisioner version used.

```hcl
# Example: In a Packer template, the build process will implicitly include
# associated enforced provisioners. The builder's (e.g., amazon-ebs) provisioners
# section only contains team-specific custom steps.
source "amazon-ebs" "app" {
  # ... builder configuration ...
}

build {
  sources = ["source.amazon-ebs.app"]

  # Downstream team's custom provisioners
  provisioner "shell" {
    inline = ["echo 'Installing application-specific dependencies'"]
  }
}

# Note: Enforced provisioners (such as base image hardening scripts) are not
# visible in this template, but will be automatically inserted by HCP Packer
# and executed before this template's provisioners during the build process.
```

## SRE Key Points

### Relationship with Reliability, Observability, and Incident Response

*   **Reliability**: Enforced provisioners directly improve **infrastructure reliability**. By ensuring security patches, configuration hardening, and necessary components (such as log collectors, monitoring agents) are consistently applied to all production images, they reduce service failures and attack surface exposure caused by configuration drift or omissions.
*   **Observability**: This feature enhances **image supply chain observability**. Through versioned enforced provisioner tracking, SRE and security teams can clearly audit the exact controls applied to any production image, providing critical clues for incident investigation and security event analysis.
*   **Incident response**: When security vulnerabilities occur, SRE and security teams can **respond quickly and centrally**. Simply updating a remediation script in the enforced provisioner and reapplying it to relevant image buckets ensures all future builds include the fix, without needing to individually notify and coordinate multiple downstream teams.

### Best Practices and Common Anti-Patterns

*   **Best practices**:
    *   **Keep provisioners atomic and idempotent**: Each enforced provisioner should focus on a clear responsibility (such as installing a specific agent) and be safe to execute repeatedly.
    *   **Version management**: Strict version control for enforced provisioners with associated change logs to support auditing and rollback.
    *   **Gradual rollout**: Pilot new provisioners in non-production buckets, validate before promoting to production.
    *   **Transparent communication**: Clearly explain the purpose and content of enforced provisioners to downstream teams, building trust and positioning them as a platform service rather than a restriction.
*   **Common anti-patterns**:
    *   **Over-centralization**: Making all configurations (including application logic) enforced, which stifles downstream team flexibility and makes provisioners bloated. Only **foundational, security, and compliance** related configurations should be enforced.
    *   **Lack of monitoring and testing**: Not monitoring and alerting on enforced provisioner failures themselves, potentially blocking all image builds.
    *   **Ignoring dependencies**: Not considering execution order and dependencies in the provisioner chain, causing execution failures.

### Related Metrics (SLI/SLO/SLA)

Enforced provisioners primarily affect **compliance SLIs** and **image build success rate SLOs**.

*   **SLI (Service Level Indicator)**:
    *   **Compliant image coverage**: The proportion of image versions in production that have had enforced provisioners executed (target: 100%).
    *   **Provisioner execution success rate**: The proportion of enforced provisioners that successfully complete during the build process.
*   **SLO (Service Level Objective)**: Ensure all newly deployed production hosts come from image versions that include required enforced provisioner execution, and the provisioner version is on the approved list.
*   **SLA (Service Level Agreement)**: For downstream teams, the platform service SLA should commit to enforced provisioner infrastructure availability to ensure their build processes are not blocked.
