# HCP Terraform adds project-level run tasks

## Overview

In the scaled practice of cloud-native and Infrastructure as Code (IaC), maintaining consistency of governance policies and reducing operational burden are core challenges for SRE and platform teams. Hashicorp Cloud Platform (HCP) Terraform, as a mainstream managed Terraform platform, offers a **Run Tasks** feature that allows integration of external tools (such as security scanning, compliance checks, cost analysis, etc.) into the infrastructure change lifecycle to enforce necessary controls. However, previously this feature could only be configured at the Organization or individual Workspace level. For platform teams managing hundreds or even thousands of workspaces, this granularity creates significant operational friction at scale.

Recently, HCP Terraform introduced **Project-level Run Tasks**, which extends the boundary of governance controls from the global or individual workspace level to the **Project** logical grouping layer. Projects are an organizational unit in HCP Terraform that sits between organizations and workspaces, used to categorize infrastructure by application, business unit, or environment. This new capability enables platform teams to naturally align security, compliance, and operational workflows (collectively referred to as "policies") with the infrastructure's organizational structure, and ensure consistency through automatic inheritance mechanisms, thereby greatly improving governance scalability.

## Core Concepts

Understanding this feature requires knowledge of the following key concepts:

*   **Terraform Run Tasks**: Run Tasks are integration points in the HCP Terraform run lifecycle. They allow users to trigger predefined HTTP callbacks at specific lifecycle stages (such as `pre-plan`, `post-apply`, etc.) to interact with third-party services (such as Snyk, Trivy, Cost Estimation tools, etc.) or internal custom services. This can be used to enforce mandatory checks — if the external service returns a failure, it will block the Terraform run from continuing.
*   **HCP Terraform Projects**: A Project is an organizational structure in HCP Terraform. It provides a hierarchy for grouping related Workspaces together, typically reflecting team, application, or environment boundaries. Projects themselves also have their own settings and permissions.
*   **Project-level Run Tasks**: This is the core of this update. It allows defining and attaching Run Tasks at the **Project** scope. Any Workspace created under or moved into that Project will automatically inherit the Run Tasks configured at the project level. This achieves **mid-layer governance** between organization-wide global settings and workspace-specific settings.
*   **Inheritance and Overrides**: Project-level configuration creates a policy inheritance model. Workspaces inherit by default the Run Tasks configured on their parent project. This provides "secure by default" assurance. At the same time, to maintain flexibility, specific overrides or exclusions may be allowed at the workspace level to accommodate edge cases.

## Practice

In typical platform engineering practice, the application of project-level Run Tasks generally follows these patterns:

1.  **Define Governance Boundaries**: First, platform administrators plan projects in HCP Terraform based on the organization's compliance requirements and team structure. For example, projects such as `production-apps`, `staging-apps`, and `shared-services` can be created.
2.  **Configure Project-level Run Tasks**: In the `production-apps` project, administrators configure a set of Run Tasks, for example:
    *   **`post-apply` stage**: Connect to the company's internal CMDB system to automatically update asset information.
    *   **`pre-plan` stage**: Call the company's cost estimation service to perform cost analysis on planned changes in the production environment.
    *   **`post-apply` stage**: Trigger the production environment's smoke test pipeline.
3.  **Automatic Application and Consistency**: When developers create a new Workspace under the `production-apps` project to deploy a production application, that Workspace will automatically execute the above three Run Tasks during every `terraform plan` and `terraform apply` run. No manual configuration by developers is required, nor does the platform team need to repeat setup for each new Workspace.
4.  **Managing Workspace Inheritance**: If an existing Workspace is moved from the `staging-apps` project to the `production-apps` project, it will immediately begin inheriting the project-level Run Tasks, thereby automatically upgrading its governance policies to ensure the production environment is always subject to stricter checks.

**Key Benefits:**
*   **Increased Speed and Scalability**: Platform teams are freed from tedious per-workspace configuration. The governance policy application for new workspace creation and environment migrations becomes automated.
*   **Reduced Risk and Improved Consistency**: Automatic policy inheritance minimizes configuration drift. Security, compliance, and operational standards are consistently enforced across all environments within a project.

## SRE Key Points

For SRE teams, project-level Run Tasks bring significant practical improvements:

*   **Connection to Reliability and Observability**: By integrating reliability checks (such as canary deployment verification, health checks) as Run Tasks into deployment pipelines, SREs can ensure that every change automatically meets reliability standards. This enhances deployment controllability and observability. Project-level configuration enables these reliability "guardrails" to be managed and audited at scale on a per-project basis.
*   **Incident Response**: Consistent, project-level governance reduces the likelihood of incidents caused by configuration inconsistencies. When incidents occur, the clarity of policies based on project structure also helps to more quickly identify the scope of affected workspaces and relevant control points.
*   **Best Practices and Anti-patterns**:
    *   **Best Practices**:
        1.  **Incremental Application**: Start applying project-level Run Tasks to non-critical projects (such as development or test environments) first, verify their impact, and then roll out to production environments.
        2.  **Clear Ownership**: Clearly define which team (typically the platform/SRE team) maintains project-level Run Tasks, and the handling process when task execution fails (such as whether to block deployment, who to notify).
        3.  **Monitor Task Status**: Monitor the execution success rate and latency of Run Tasks themselves, treating them as one of the platform's reliability SLIs.
    *   **Common Anti-patterns**:
        1.  **Ignoring Inter-project Differences**: Attempting to enforce the same strict Run Tasks across all projects (including development environments), causing severe degradation of the developer experience. Leverage project isolation to implement tiered governance.
        2.  **Opaque Configuration**: Run Tasks configuration and failure reasons lack clear documentation and logs, leaving developers bewildered when deployments are blocked.
*   **Related Metrics (SLI/SLO/SLA)**:
    *   **SLI**: Run Tasks execution success rate (successful executions / total executions), execution latency (time from trigger to completion).
    *   **SLO**: SLOs can be set for critical production-level Run Tasks (such as security scanning), for example, "monthly execution success rate > 99.5%" or "95% of executions complete within 60 seconds."
    *   **SLA**: This is the platform team's commitment to its internal customers (developer teams), related to the above SLOs. Ensure that the availability and performance of governance checks do not become a bottleneck for infrastructure changes.

By adopting project-level Run Tasks, SRE and platform teams can build a more robust, consistent, and scalable IaC governance framework, thereby empowering development teams to deliver efficiently while ensuring infrastructure reliability.
