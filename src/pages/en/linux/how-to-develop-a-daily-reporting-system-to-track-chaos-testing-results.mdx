# How to Develop a Daily Reporting System to Track Chaos Testing Results

## Overview

Chaos engineering validates system resilience by proactively injecting faults, and is an important practice for improving the reliability of modern distributed systems. However, the raw logs produced by chaos experiments are often voluminous and difficult to directly convert into actionable insights. A structured daily reporting system that automatically collects, analyzes, and visualizes chaos experiment results serves as a critical bridge between experiment execution and reliability improvement. It enables teams to continuously and efficiently track system performance under failures, quantify fault impact, and quickly identify areas that need hardening.

## Core Concepts

Before building a reporting system, several core concepts need to be understood:

1.  **Chaos Engineering**: A practice of discovering potential weaknesses in systems under real failures through controlled fault injection experiments. Its goal is to enhance system resilience in production environments.
2.  **Observability**: The degree to which a system's internal state can be inferred from its exterior, primarily achieved through the three pillars of Metrics, Logs, and Traces. The chaos testing reporting system is an important tool for improving the observability of chaos experiments.
3.  **Chaos Mesh**: An open-source, cloud-native chaos engineering platform capable of orchestrating fault injection experiments running in Kubernetes environments, supporting various fault types such as Pod, network, and file system failures.
4.  **Daily Reporting System**: An automated pipeline for periodically (e.g., daily) collecting data (mainly logs and metrics) from chaos experiments and the applications under test, performing filtering, analysis, visualization, and ultimately generating readable reports (such as PDF or web pages). Its core value lies in transforming scattered, raw event data into centralized, understandable insights.

## Practice

Building a chaos testing daily reporting system typically includes the following key stages, referencing a practical case based on Chaos Mesh and TiDB.

### 1. Deploy the Experiment Environment

First, deploy Chaos Mesh and the target application to be tested (e.g., TiDB distributed database) on a Kubernetes cluster. Helm is recommended for deploying Chaos Mesh, but be aware that network environments may cause slow image pulls. A practical optimization approach is: pre-pull all required images using `docker pull` on a machine with good network connectivity, then use `docker save` to export as `.tar` files, and finally use the `docker load` command on each cluster node to load them. This method can significantly shorten deployment time, especially in network-restricted environments. When deploying the target application, a similar image pre-loading strategy should also be followed.

### 2. Execute Chaos Experiments

Define chaos experiments by creating Kubernetes manifest files (YAML). For example, use the `PodChaos` resource type to simulate an unexpected Pod crash. Use the command `kubectl apply -f <your-chaos-experiment.yaml>` to start the experiment. The experiment will run periodically according to the predefined schedule.

### 3. Build the Automated Reporting Pipeline

This is the core of the reporting system, typically driven by a scheduled task (such as `cron`), automatically executing every morning.

- **Collect Logs**: Use the `kubectl logs` command to collect logs from specified namespaces and Pods within the past 24 hours. For example: `kubectl logs <pod-name> -n tidb-test --since=24h > tidb.log`. Logs from all related components (such as TiDB Server, TiKV, PD) should be collected.
- **Filter and Analyze**: Filter out Error and Warning messages from massive logs. Linux text processing tools such as `awk` and `grep` can be used, or custom scripts can be written for more complex analysis.
- **Data Visualization**: Plot key metrics (such as Queries Per Second - QPS) changes into charts. For example, using tools like `gnuplot` can visually display the QPS drop and recovery process during Pod fault injection. This visualization is critical for quantifying fault impact.
- **Generate Reports**: Integrate the analyzed text summaries and visualization charts into an easy-to-read document, such as PDF format. Libraries like `gopdf` can be used to programmatically generate PDF files, making them easy to view across different devices and browsers. Report filenames can include status information (e.g., `report-2021-07-09-bad.pdf`) to quickly identify which dates' tests exposed issues.

### 4. Improve Report Accessibility

To further improve report readability and team collaboration efficiency, a simple web application can be built to display these daily reports. For example, using the Vue.js framework and Ant Design Vue UI library, a frontend page can be quickly set up. Place automatically generated report files (such as PDF) in a static resource directory, and the frontend application reads and displays them. This way, team members can directly browse reports via web pages and click on potentially problematic reports (such as those marked "bad") for detailed viewing. Libraries like `pdf.js` can be used to render PDF content directly in the web page.

## SRE Key Points

- **Reliability Association**: This reporting system is a practical tool for implementing the "data-driven reliability" concept. It directly serves SLO (Service Level Objective) achievement by continuously tracking system behavior after chaos experiments (metric recovery, error logs). For example, the QPS recovery time observed during experiments can serve as an SLI (Service Level Indicator) for system resilience, compared against the defined SLO.
- **Best Practices**:
    - **Automation is Key**: Manual collection and analysis of results is unsustainable and must rely on automated pipelines.
    - **Focus on Errors and Recovery**: Reports should highlight anomalies (error logs) and system recovery capabilities (metric recovery curves).
    - **Start Small**: There is no need to build a complex system from the start. First implement core log collection, filtering, and basic report generation, then gradually add visualization and web display.
    - **Version Control Experiment Code**: All chaos experiment YAML definitions and report generation scripts should be version-controlled to ensure repeatability.
- **Common Anti-Patterns**:
    - **Record Without Analysis**: Simply collecting logs without filtering and visualization cannot produce effective insights.
    - **Reports Without Feedback Loops**: Generating reports but having no one follow up and address discovered issues makes the experiments meaningless.
    - **Environment and Production Divergence**: Test environment configuration and topology differ significantly from production, causing experiment results and reports to lack guiding significance.
- **Related Metrics (SLI/SLO)**:
    - **SLI**: The drop magnitude and recovery duration of key business metrics (such as QPS, latency, error rate) during chaos experiments; the time required for system self-healing.
    - **SLO**: For example, "after simulating a single point of failure, the system should recover 99% of service capability within X minutes." Daily reports are used to verify whether this goal is continuously met.
    - **Error Budget**: Chaos experiment reports can help calculate the Error Budget consumed by planned fault injection and assess whether the remaining budget is sufficient to support further experiments or new feature releases.

By implementing such a daily reporting system, teams can transform chaos engineering from one-time exercises into a routine, data-driven process for continuously monitoring and improving system resilience, which is highly aligned with the core ideas of [[reliability-engineering]] and [[observability]].
