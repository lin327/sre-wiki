## Overview

In a Kubernetes cluster, admission webhooks are a key mechanism for achieving scalability and policy control. The reliability and balanced load of its requests are the basis for ensuring the stability and fairness of the cluster control plane. This article details the problem of uneven Webhook load caused by the HTTP connection caching mechanism in Kubernetes API Server in `--enable-aggregator-routing=true` mode and its repair plan. It is an important practice that SRE needs to understand when optimizing cluster component communication and improving service reliability.

## Core concepts

### Source of the problem: HTTP/1.1 connection pool and dynamic parsing

The problem arises as a result of a series of technical compromises. Initially, Kubernetes switched the webhook transport protocol from HTTP/2 back to HTTP/1.1 in order to support load balancing webhook requests to multiple backend Pods. The single-connection multiplexing feature of HTTP/2 prevents concurrent requests from being load-balanced across different backend Pods.

However, HTTP/1.1 introduced persistent connections (keep-alive) and connection pooling. The Go standard library's `http.Transport` caches idle connections based on the hostname of the request URL (i.e. the Service name). In the implementation of Kubernetes, in order to dynamically resolve the Service to a specific Pod IP, developers have customized the `DialContext` function. The problem is that when an idle connection matching the hostname exists in the cache pool, `http.Transport` will directly reuse the connection, thus skipping the custom `DialContext` dialing logic**. This causes all concurrent requests to the same Service to be routed to the specific backend Pod where the connection was originally established, defeating the purpose of load balancing.

### Fix: bypass cache and force redialing

The core idea of the fix is to ensure that each request can trigger the load balancing logic based on the current list of healthy endpoints, rather than blindly reusing cached connections. In terms of specific implementation, Kubernetes has modified the behavior of the HTTP transport layer so that when making load balancing decisions, the host name associated with the cache connection is not used, but the specific and active endpoint IP address parsed through service discovery is directly used as the connection key.

Since the latest endpoint list is obtained and a new IP is selected before each dial, this forces each request (or each batch of concurrent requests) to go through a load balancing decision-making process, thereby achieving an even distribution of requests among all ready webhook backend Pods.

## Practice

### Problem identification and impact

* **Symptoms**: Monitoring shows that most (or all) requests sent to a Webhook Service are concentrated on the same group or a single backend Pod, while the number of requests from other Pods is very small.
* **Impact**: This results in serious uneven load on the Webhook backend, which may cause resource exhaustion (CPU, memory) or request timeout of hotspot Pods, thereby affecting the delay and availability of the entire cluster admission control process. This defeats the purpose of using multiple replica deployments to improve reliability.

### Configuration and Control

As can be seen from the release notes of Kubernetes, this fix is enabled by default and provides feature gate for control:

1. **Default behavior**: In a cluster with `--enable-aggregator-routing=true` enabled, `Kube-apiserver` will automatically load balance requests evenly to all resolved Webhook endpoints, avoiding problems caused by connection caching.
2. **Temporary rollback**: If the new behavior introduces unexpected problems, cluster administrators can **temporarily** restore the old, potentially problematic connection caching behavior by setting the feature gate `WebhookRoundTripLoadBalancing=false` (this feature is in Beta and defaults to `true`). This provides a safety net for troubleshooting and incremental releases.

### Verification and Monitoring

The SRE should verify the effectiveness of this fix and continuously monitor the load balancing effect:
* **Check Webhook Endpoint Distribution**: Observe the request counts for all webhook pods and make sure they are roughly equal.
* **Monitor Webhook Latency**: With improved load balancing, tail latencies (such as P99) should be smoother and latency spikes on hotspot pods should be reduced.
* **Check connection pool utilization**: You can observe whether the number of active TCP connections established between the API Server and the Webhook backend is reasonable, rather than all concentrated on a few IPs.

## SRE Key Points

### Relationship with reliability and observability
This fix is directly related to the **reliability** of the Kubernetes control plane. A webhook with load balancing failure will become a single point bottleneck for the entire cluster, reducing the expected effect of its fault domain isolation. SREs need to monitor the request distribution of the webhook backend as a key **observability** metric to detect similar issues early.

### Best practices and common anti-patterns
* **Best Practice**:
    1. **Enable balancing feature**: Make sure to enable `WebhookRoundTripLoadBalancing=true` (enabled by default) in the production environment to enjoy the benefits of the fix.
    2. **Progressive Release**: Use feature gating for canary release or grayscale launch, and monitor key SLO indicators (such as Webhook latency and error rate) before full promotion.
    3. **Endpoint health check**: Ensure that the Kubernetes Endpoints controller can accurately remove unhealthy Pods and ensure that all endpoints in the load balancing pool are available.
* **Common anti-patterns**:
    * **Blindly disabling new features**: Disabling `WebhookRoundTripLoadBalancing` simply because of a suspected problem without fully investigating. This may cause the cluster to revert to a known, worse state.
    * **Ignore monitoring**: The load distribution of the Webhook was not monitored after deployment, and whether the load balancing took effect was not discovered in time.

### Related indicators (SLI/SLO)
* **SLI**:
    * How uniformly webhook requests are distributed across backend Pods (e.g., measured using standard deviation or Gini coefficient).
    * P90/P99 latency for API Server requests to webhooks.
* **SLO**: The SLO can be specified as "the difference in request volume received by all active Webhook backend Pods does not exceed 20%", or "the P99 of Webhook request latency is consistently less than 200ms".
* **Associated concepts**: This issue is closely related to connection management, load balancing algorithms, and traffic management principles in [[service-mesh]]. Understanding it helps SREs better design and debug the network paths for cloud-native applications.
