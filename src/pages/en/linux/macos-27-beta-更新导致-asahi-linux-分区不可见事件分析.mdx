## Overview

Asahi Linux is an open source project dedicated to providing Linux support for Apple Silicon (Arm-based) Mac computers. Its users need to create a separate boot partition outside of macOS to run Linux. The project recently issued an important warning reminding users to **Never** upgrade to the macOS 27 “Golden Gate” beta. Although this incident was targeted at a specific project, it vividly demonstrates the unexpected impact that operating system updates may have on a multi-system environment, and is a typical teaching case for the principles of [Change Management] and [System Reliability] in SRE practice.

## Core concepts

The core issue in this incident is the unexpected loss of **boot partition visibility**.

1. **Boot Selector Detection Logic Change**: macOS 27 modifies the way the Boot Manager (Boot Selector) and Startup Disk applications detect legitimate boot volumes. The new logic failed to correctly recognize boot partitions created by Asahi Linux, causing these partitions to "disappear" in the selection interface.
2. **Data intact, access blocked**: The Asahi Linux project confirmed that the change was a recognition error at the logical level, not physical deletion or damage. The user's Asahi Linux partition and its data are still safely on the disk, it's just that macOS's boot tool cannot "see" and launch it for the time being.
3. **Installer Precautions**: To avoid getting new users into trouble, the Asahi Linux installer has been temporarily patched to disable use in macOS 27 environments as a proactive risk avoidance measure.
4. **Rollback Path**: For users who have upgraded and are affected, the clear recovery path is to use the installation media or recovery function of macOS 26 (the current official version) to restore access to the Asahi Linux partition by resetting the boot loader.

## Practice

### Instructions for Asahi Linux users

1. **Preventive Measures (Preferred)**:
    * **Upgrade Suspended**: Avoid updating macOS systems to the 27 Beta version until the official version of macOS 27 is released and the Asahi Linux project confirms that the issues have been resolved.

2. **Recovery steps for affected users**:
    * **Prepare the media**: Obtain a macOS 26 installation USB drive or ensure you have access to macOS recovery mode (launched via a shortcut such as `Command + R`).
    * **Boot into a macOS environment**: Boot your Mac through macOS Recovery or Setup.
    * **Reset Boot Loader**: In the macOS environment, use built-in tools or specific commands to reset NVRAM/PRAM and boot records. This process will force macOS to rescan all boot partitions. After restoring visibility to the Asahi Linux partition, you can reselect the default startup item through Startup Disk preferences.
    * **Important Tip**: Be sure to back up important data before operation. Although this incident did not involve data deletion, any operation involving the boot area is risky.

### System design inspiration

For systems designed to require multi-OS boot compatibility (for example, managing heterogeneous devices in a hybrid cloud or test environment), this event prompts us to:
* **The boot environment is a fragile critical path**: Any changes to the boot chain can have widespread and unintended side effects.
* **Dependencies need to be managed explicitly**: The implicit dependence of third-party systems (such as Asahi Linux) on the internal implementation details of the main system (macOS) (such as partition detection logic) is dangerous.

## SRE Key Points

* **Association with Reliability and Observability**: This incident directly affects the **Availability** SLI of Macs running Asahi Linux. Users were unable to boot into Linux systems as expected, resulting in service outages. It emphasizes the importance of bootability as a fundamental reliability metric.
* **Best Practices and Common Anti-Patterns**:
    * **Anti-Pattern: Untested breaking changes**. The change by Apple is a breaking update that was not fully tested for backwards compatibility, affecting an unofficial but widely used configuration.
    * **Best Practice: Phased Updates and Change Control**. SRE practices require that any updates that affect the system should follow a strict change management process, including full testing in a pre-production environment, phased grayscale release, and a clear rollback plan. The Asahi Linux project quickly issues warnings and fixes the installer, which is an example of good responsiveness practices.
* **Related indicators (SLI/SLO/SLA)**:
    * **SLI**: System bootability rate (success rate), average boot time to the target system.
    * **SLO**: For a multi-system development environment, an SLO can be agreed that "the secondary operating system can still start normally within X working days after the primary operating system is updated."
    * **SLA**: This incident itself does not directly involve SLAs, but it highlights the challenges of maintaining such SLOs when running critical services on consumer-grade hardware.
