# Malformed transformation data causes crash and invisible rows in panel edit

## 概述

在 Grafana 平台中，数据转换（Transformations）是构建复杂仪表板的核心功能之一。然而，格式不正确的转换数据会导致严重的用户体验问题：面板编辑界面崩溃以及已配置的转换行在编辑器中“隐形”。这个问题突显了在分布式系统（如 Grafana）中，数据格式兼容性、健壮的错误处理以及清晰的用户反馈对于维护系统可靠性和可操作性的重要性。对于 SRE 而言，理解此类问题的根因和模式有助于预防类似的前端与后端数据格式不一致引发的故障，并优化事件响应流程。

## 核心概念

### 数据转换格式兼容性
Grafana 的转换数据在不同 API 版本（如 `v2beta1` 与 `v2`）之间存在细微但关键的格式差异。在 `v2` 稳定版格式中，一个转换条目必须包含 `kind`、`group` 和 `spec` 三个字段。当使用旧版 SDK 或 API 生成仪表板并未经校验地存储时，可能产生只包含 `kind` 字段而缺失 `group` 字段的畸形数据。这种格式的“中间态”是导致后续问题的源头。

### RxJS 同步抛出与错误处理失效
Grafana 的前端大量使用 RxJS 进行响应式编程。问题中的第一个 Bug 揭示了一个关键陷阱：在设置管道（`pipe`）时，操作符工厂函数（如 `getOperator`）会被**同步调用**。如果其中的函数（如 `standardTransformersRegistry.get()`）抛出错误，该错误会同步发生，此时外层为异步 Observable 设计的 `catchError` 操作符**尚未被添加到管道中**，因此无法捕获这个同步错误，导致整个管道初始化失败，最终引发前端应用崩溃。

### 数据格式正常化（Normalization）
为了兼容新旧版本的转换格式，代码中存在一个 `normalizeTransformation` 函数来检测并统一格式。其判断逻辑依赖于 `kind` 和 `group` 字段是否存在。当遇到 `kind: "Transformation"` 但无 `group` 字段的畸形数据时，函数会错误地将其归类为旧版格式，并使用 `kind` 的值（“Transformation”）作为转换标识符（`id`），这导致了后续的转换注册表查找失败。

## 实践

### 问题诊断与确认
当仪表板编辑器出现以下现象时，应怀疑存在格式错误的转换数据：
1.  退出面板编辑时，弹出 `An unexpected error happened` 错误，详情包含 `"Transformation" not found in: reduce,filterFieldsByName,...`。
2.  面板编辑器的“转换”标签页显示为空白，即使该面板已配置转换。

**诊断步骤：**
1.  通过 Grafana API 或直接访问数据库，获取该仪表板的 JSON 模型。
2.  检查 `panels[].transformations[]` 数组中的每个转换对象。
3.  重点检查 `kind` 字段为 `"Transformation"` 的条目，查看是否存在 `group` 字段。

### 数据修复与规避
**正确的 v2 格式示例：**
```json
{
  "kind": "Transformation",
  "group": "merge", // 关键字段：group 必须存在，且值应为特定转换组（如 merge, reduce 等）
  "spec": {
    "options": {} // 转换的具体配置
  }
}
```

**畸形数据示例（会导致崩溃）：**
```json
{
  "kind": "Transformation"
  // 缺失 "group": "merge" 或其他有效组值
}
```

**修复方案：**
1.  **手动 JSON 修正**：定位到畸形转换条目，为其添加正确的 `group` 字段。这需要了解每个转换应归属的 `group` 值（可通过查阅 Grafana 源代码或官方文档获得）。
2.  **代码层面修复（已由 Grafana 团队提出）**：
    - 在 `packages/grafana-data/src/transformations/transformDataFrame.ts` 中，将 `standardTransformersRegistry.get()` 替换为 `standardTransformersRegistry.getIfExists()`。这确保了当转换 ID 无效时，不会抛出同步错误，而是安全地返回空值并跳过该转换。
    - 在 `packages/grafana-data/src/transformations/transformationCompat.ts` 的 `normalizeTransformation` 函数中，完善逻辑：当检测到 `kind === 'Transformation'` 但 `group` 缺失时，应尝试从 `spec.id` 字段中提取转换 ID，而非错误地使用 `kind` 的值。

### 监控与预防
为防止此类问题流入生产环境：
- 在 CI/CD 管道或仪表板导入流程中，添加针对转换数据格式的验证步骤。
- 对用于生成仪表板的 SDK 和 API 进行版本管理，并明确文档化各版本输出的格式差异。
- 在前端代码中，对转换注册表查找等关键操作，增强错误边界处理，确保即使某个转换配置错误，整个转换管道也能降级运行（例如跳过该转换并记录警告），而非崩溃。

## SRE 要点

### 与可靠性、可观测性及事件响应的关联
- **可靠性**：此 Bug 直接导致功能不可用（面板编辑崩溃），属于服务降级。它强调了在复杂系统中，处理来自外部源（如 Provisioning、旧版 SDK）的数据时，进行严格输入验证和防御性编程的必要性。
- **可观测性**：隐形的转换行使得用户无法通过 UI 感知到错误的存在，这降低了系统的可操作性。SRE 需要推动增加前端的错误日志记录或监控指标（如转换加载失败次数），以便在问题影响更广之前主动发现。
- **事件响应**：处理此类问题时，SRE 的事件响应流程应包括：1）快速识别受影响仪表板（通过日志或错误追踪）；2）评估影响范围（该仪表板的用户和依赖它的告警/报告）；3）执行修复（通常是 JSON 编辑或等待代码修复）；4）事后复盘，将此案例加入知识库。

### 最佳实践与常见反模式
- **最佳实践**：
    1.  **数据格式契约**：对系统内部以及外部集成点的数据格式，维护清晰的 Schema 定义和验证器。
    2.  **优雅降级**：在数据处理管道中，设计好错误处理路径，确保单个非关键组件的失败不会导致整个功能崩溃。
    3.  **版本化与兼容层**：在维护多个数据格式版本时，显式实现向后兼容层（如 `normalize` 函数），并充分测试边界条件。
- **常见反模式**：
    1.  **过度依赖理想数据**：代码假设所有输入都严格符合最新规范，缺乏对畸形或旧版数据的处理。
    2.  **异步错误处理的盲区**：在使用 RxJS 等响应式库时，未充分考虑操作符在管道建立阶段的同步执行特性，导致错误逃逸到 `catchError` 作用域之外。
    3.  **无声失败**：在遇到无法识别的数据时，仅返回 `null` 或静默跳过，而不向用户或日志系统提供任何有意义的反馈，导致问题“隐形”。

### 相关指标（SLI/SLO/SLA）
- **SLI**：面板编辑功能成功率（无崩溃、无不可交互的空白标签页）。可追踪 `panel_edit_exit_without_error` 事件与总 `panel_edit_exit` 事件的比例。
- **SLO**：例如，“在 99.9% 的情况下，用户能够成功完成面板编辑操作而不遇到崩溃或功能缺失。”
- **SLA**：面向内部用户的 SLO 即可，重点是保障运维和监控仪表板的构建效率。此问题直接影响仪表板的创建和修改能力，可能导致监控配置变更延迟，从而间接影响更高层级的服务可用性目标。
