# NRI plugin AddEnv/RemoveEnv silently ignored for env vars that already exist

## 概述

在容器运行时管理中，环境变量是配置应用程序行为的关键机制之一。[[containerd-nri-plugin]] (Node Resource Interface) 提供了一个强大的扩展框架，允许外部插件在容器创建或更新时对其规格进行调整，其中就包括注入或修改环境变量。然而，在 containerd v2.3.0 和 NRI v0.12.0 版本中，存在一个已确认的缺陷：NRI 插件尝试使用 `AddEnv` **覆盖**或 `RemoveEnv` **移除**容器中**已存在**的环境变量时，这些操作会被静默忽略。这导致依赖于环境变量注入或覆盖的运维和可靠性策略（如动态配置、密钥轮换）失效，且由于缺乏错误反馈，使得问题难以排查，对系统可观测性构成挑战。

## 核心概念

理解此问题需要熟悉以下核心概念：

1.  **NRI (Node Resource Interface)**：一个插件系统，允许外部程序在容器生命周期的关键节点（如 `CreateContainer`）介入，通过返回 `ContainerAdjustment` 结构体来动态修改容器的 OCI 规格（例如，添加或修改环境变量、挂载点、设备等）。其设计意图是让插件能够基于运行时上下文对容器配置进行细粒度调整。
2.  **环境变量处理顺序**：在标准的 CRI（Container Runtime Interface）工作流中，容器的环境变量会按照特定顺序合并：首先是容器镜像（Image）定义的变量，其次是 Pod 或容器配置（如 Kubernetes 的 `env` 或 `envFrom`）定义的变量。NRI 插件的调整被设计为在此**之后**应用，因此理论上应具备覆盖前述来源变量的能力。
3.  **静默失败 (Silent Failure)**：指操作未按预期执行，但未向调用方（NRI插件）返回任何错误状态，也未在容器运行时（containerd）的日志中生成任何警告或错误信息。这种行为严重损害了系统的可调试性和可靠性保障。

## 实践

以下基于 Issue 中描述的复现步骤和代码分析，阐述此问题的具体表现和影响范围。

**问题复现场景**：开发一个简单的 NRI 插件，旨在为特定 Pod 中的容器添加一个新变量，并移除或覆盖一个已存在的变量。

```go
// 简化的 NRI 插件处理逻辑
func (p) CreateContainer(_ context.Context, pod *api.PodSandbox, c *api.Container) (*api.ContainerAdjustment, []*api.ContainerUpdate, error) {
    a := &api.ContainerAdjustment{}
    a.AddEnv("NEW_VAR", "works")                      // 添加一个全新的变量：**成功**
    a.RemoveEnv("EXISTING_VAR")                       // 移除一个已存在的变量：**静默失败**
    a.AddEnv("EXISTING_VAR", "intended_override")     // 覆盖一个已存在的变量：**静默失败**
    return a, nil, nil
}
```

当容器已通过 Dockerfile `ENV` 或 Kubernetes `envFrom` (如 ConfigMap) 设置了 `EXISTING_VAR` 时，运行此插件并创建容器后，通过 `crictl inspect` 检查容器的 OCI 规格会发现：
- `NEW_VAR=works` 存在（✅ 插件工作正常）。
- `EXISTING_VAR` 仍保持其原始值，`RemoveEnv` 和 `AddEnv`（覆盖）均未生效（❌）。

**受影响的 API 与设计意图背离**：containerd 的 CRI 实现代码 (`internal/cri/server/container_create.go`) 和 NRI 库的适配逻辑 (`pkg/adaptation/result.go`, `pkg/runtime-tools/generate/generate.go`) 明确显示，其设计是**支持**对已存在环境变量进行替换和删除的。例如，NRI 库的 `AdjustEnv` 函数会遍历已合并的变量列表，匹配并执行删除或替换操作。然而，实际运行时结果与此设计背道而驰，表明 containerd 在集成 NRI 调整至最终 OCI 规格的最后阶段，可能存在处理逻辑上的缺陷或覆盖。

## SRE 要点

此缺陷对站点可靠性工程实践产生多方面影响，需要重点关注：

**与可靠性、可观测性、事件响应的关联**
- **可靠性降级**：任何依赖 NRI 插件进行环境变量动态管理（如：注入临时凭证、设置调试开关、实施配置模板化、屏蔽敏感信息）的流程都将**静默失效**。这可能导致应用因使用错误或过时的配置值而启动失败、行为异常，或泄露本应被屏蔽的信息。
- **可观测性缺口**：问题的核心是“静默失败”。插件调用 `AddEnv`/`RemoveEnv` 后收不到错误反馈，containerd 在 `debug` 级别日志下也无相关记录。这使得 SRE 团队难以通过标准监控和日志管道发现问题，必须依赖主动检查最终容器状态，增加了故障排查难度。
- **事件响应复杂化**：当因环境变量问题导致应用故障时，响应团队可能无法快速定位到 NRI 插件操作失效这一根本原因，因为从插件视角看“操作成功”，而容器却运行在错误配置下。

**最佳实践与规避措施**
- **暂不依赖覆盖/删除操作**：在 containerd 2.3.0 和 NRI v0.12.0 版本中，避免使用 NRI 插件对已知会存在的环境变量执行 `AddEnv` (覆盖) 或 `RemoveEnv`。仅用于添加全新变量。
- **采用替代方案**：
    1.  **在源端控制**：尽可能通过应用配置、镜像构建或 Kubernetes 资源定义（YAML）本身来管理环境变量，减少运行时覆盖的需求。
    2.  **使用其他 NRI 调整点**：评估是否可以通过调整容器的其他部分（如挂载配置）来间接实现目标配置，而非直接修改环境变量。
    3.  **应用层适配**：让应用能够从配置中心或卷挂载文件中动态读取配置，而非完全依赖环境变量。
- **升级与监控**：密切关注 containerd 项目的相关 Issue 进展，及时升级到已修复的版本。在升级前，可对关键容器的环境变量进行定时抽检，作为监控项。

**相关指标 (SLI/SLO/SLA)**
- **SLI (Service Level Indicator)**：可考虑监控“由 NRI 插件注入的、期望覆盖已存在变量的配置，在容器启动后的有效性比例”。这需要插件侧记录操作意图，并与容器实际环境进行对比。
- **SLO (Service Level Objective)**：若业务强依赖此类运行时配置注入，可设立 SLO，如“因 NRI 插件配置失效导致的应用启动或功能故障，每小时发生次数小于 1”。
- **事件指标**：在事件响应手册中，将“检查容器环境变量是否与 NRI 插件预期一致”列为排查启动失败问题的标准步骤之一。
