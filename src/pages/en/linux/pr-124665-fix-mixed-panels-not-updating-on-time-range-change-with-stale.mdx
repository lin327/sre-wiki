# 

## Overview

In Grafana's observability dashboards, **Mixed Data Source** is a powerful feature that allows a single panel to query data from multiple different data sources and display them in a blended view. However, under specific conditions, this feature triggers a critical defect: when a user changes the dashboard's time range, the panel may fail to refresh in time and instead continue displaying "stale" data from the previous time range. This directly undermines the **real-time accuracy** and **correctness** of monitoring data, potentially causing SRE to make judgments based on incorrect information and delay incident response. This fix ensures that Mixed data source panels correctly fetch and render the latest data after time range changes by refining the state management of the asynchronous data flow, thereby maintaining the reliability of the monitoring system.

## Core Concepts

- **Mixed Data Source**: A type of data source in Grafana whose core function is to act as a proxy or "orchestrator," forwarding user query requests to multiple downstream data sources defined within a panel, and merging the results before returning. It does not store data itself.
- **`ReplaySubject(1)`**: A type of Observable in RxJS that "replays" its most recently emitted value to new subscribers. In Grafana's `SceneQueryRunner`, it is used to cache and distribute query results. Its characteristic is that even after a query has completed (`Done`), new subscribers will immediately receive that `Done` status rather than re-executing the query from scratch.
- **`first(Done || Error)` Operator**: Used in the Mixed data source processing flow, its purpose is to wait for the first completion (or error) signal of a sub-query, then consider that sub-query's "first batch of data" as loaded and close subsequent monitoring of that sub-query. This design was originally intended to optimize rendering performance.
- **Race Condition**: The root cause of this issue. When the time range changes, the "stale" completion status (`Done`) from the upstream data source competes in time with the "new" query status expected by the downstream panel. The prematurely received old `Done` status incorrectly triggers the `first` operator, causing the entire sub-stream to close prematurely, and subsequent data for the new time range is therefore ignored.

## Fix Solution and Practice

The core idea of this PR fix is to add a filter before triggering the `first(Done || Error)` "terminal" operation, discarding `Done` or `Error` signals where the **time range does not match**. The specific implementation is as follows:

1.  **Locating the Problem Path**: The fix is strictly limited to the Mixed data source sub-query path (determined by `requestId.includes(MIXED_REQUEST_PREFIX)`). This is because in non-Mixed regular Dashboard data source queries, the data stream is open— even if an old `Done` is received, subsequent new data arriving will still trigger an update. But in the Mixed path, the `first` operator "short-circuits" the data stream, causing a permanent issue.

2.  **Implementing the Filter Logic**:
    - A new filtering step is inserted **before** the existing `emitFirstLoadedDataIfMixedDS` operator.
    - This step checks whether the `request.range` of each `Done` or `Error` signal matches the `options.range` of the current chain panel.
    - **If different, discard**. In a time range change scenario, the upstream ReplaySubject brings a `Done` from the old time range, while the panel expects data for the new time range, so this old signal is successfully filtered out.
    - **If the same, pass through**. This ensures that normal completion signals for the current time range are correctly processed.

3.  **Protecting Special Scenarios**: This filter does not affect panels that support `PanelTimeRange` overrides. Because the filter only applies to the Mixed path, and panels with time overrides have queries that do not belong to the Mixed path—they can freely observe time ranges different from the upstream and receive termination signals normally.

**Flow Comparison**:
- **Before Fix**: `Upstream(Old Done)` -> `MixDS Operator(first matches and closes)` -> `forkJoin gets old data` -> `Panel displays old data`. When new data arrives, no subscriber receives it.
- **After Fix**: `Upstream(Old Done)` -> **Filter(range mismatch, discard)** -> `Upstream(Loading)` -> `Upstream(New Done)` -> `Filter(range match, pass through)` -> `MixDS Operator(normal match and close)` -> `forkJoin gets new data` -> `Panel updates with new data`.

## SRE Key Points

### Reliability Association
This defect directly affects the **reliability** of Grafana monitoring dashboards, a core observability tool. When SRE or developers rely on dashboards for troubleshooting, capacity planning, or performance analysis, seeing stale data may lead to misjudgment. For example, when expanding the time range to view long-term trends, the panel may only show old, incomplete information, masking the true problem patterns. Fixing this issue safeguards the credibility of dashboards as a "single source of truth."

### Best Practices and Anti-Patterns
- **Best Practices**:
    1.  **Focus on Asynchronous State Management**: When working with reactive programming frameworks like RxJS, it is essential to clearly understand the behavior of `Subject` (especially `ReplaySubject`), subscription timing, and the terminal effects of various operators (such as `first`, `take`, `switchMap`) on data streams.
    2.  **Add Context to Operators**: The fix scopes the filter to `MIXED_REQUEST_PREFIX`, which is a good practice. It avoids over-fixing and affecting other legitimate scenarios (such as time overrides), demonstrating precise intervention after deep understanding of different system paths.
    3.  **Regression Testing and Scenario Coverage**: The test plan included in the PR is very comprehensive—it not only verifies the fix itself but also locks down the fix's scope of applicability and ensures existing functionality is not affected. SRE should pay attention to whether monitoring tools or plugins have thorough regression tests when introducing them.

- **Common Anti-Patterns**:
    1.  **Ignoring Initial Values**: Using `ReplaySubject` and unconditionally processing its replayed values without verifying whether the value corresponds to the current valid context (such as the correct time range).
    2.  **Overusing Short-Circuit Operators**: Such as `first()` or `take(1)`—in data streams that may continuously update, careless use can permanently close monitoring of subsequent updates, causing data to "freeze."

### Related Metrics (SLI/SLO/SLA)
This fix itself does not directly define SLI/SLO, but it maintains the **data foundation** used to measure these metrics.
- **SLI (Service Level Indicator)**: For example, "panel query data freshness" can serve as an SLI, measuring the latency from when data is produced by the data source to when panel rendering completes.
- **Potential Impact**: This bug causes anomalous measurement values for this SLI (data completely stalled), potentially incorrectly triggering alerts for the monitoring system itself or masking the true SLI degradation of the monitored service.
- **SLO (Service Level Objective)**: For teams providing Grafana services, a reasonable SLO could be "core dashboard data updates within 10 seconds after time range change." This bug directly causes SLO violations.

### Incident Response Association
During Incident Response, SRE heavily relies on dashboards for rapid diagnosis. If dashboards fail due to known bugs, it severely disrupts the "observation" phase. Therefore, SRE needs to:
1.  **Be Aware of Such Known Defects**: Document them in internal knowledge bases (like this page) for quick identification when troubleshooting monitoring system issues.
2.  **Establish Contingency Measures**: For this specific issue, a "hard refresh" of the page can temporarily resolve it, as it re-instantiates the entire scene tree and clears the `ReplaySubject`. SRE can include this as a temporary workaround step in Runbooks.
3.  **Drive Version Upgrades**: Promptly include the Grafana version containing this fix in the upgrade plan to fundamentally eliminate the risk.
