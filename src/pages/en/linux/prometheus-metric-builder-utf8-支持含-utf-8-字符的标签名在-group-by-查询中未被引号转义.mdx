# Grafana Issue

## Overview

In modern observability practices, Prometheus has extensive support for the UTF-8 character set, allowing metric names and label names to contain richer characters (such as periods, Chinese, etc.). As a mainstream visualization tool, Grafana's Metric Builder is designed to simplify the generation of PromQL queries. However, a recently discovered flaw indicates that when an aggregation query (such as `sum by`) requires grouping by tags containing UTF-8 characters, the builder fails to properly quote-escape the tag names, resulting in a syntactically incorrect query. This directly affects the reliability of monitoring dashboards built by teams using new OpenTelemetry metrics or custom metrics, and is a toolchain flaw that SREs need to pay attention to when maintaining the effectiveness of monitoring systems.

## Core concepts

To understand this issue, it is necessary to clarify the following key points:

1. **Prometheus UTF-8 support**: Starting from Prometheus version 2.21, metric names and label names are supported to contain any UTF-8 characters. However, in order to be compatible with older versions of the query language, in PromQL, if the label name contains non-`[a-zA-Z0-9_]` characters (such as `label.1`), it must be enclosed in double quotes to form `"label.1"` in order to be correctly parsed.
2. **Group By syntax in PromQL**: In aggregation operations such as `sum by(label_name)`, the `label_name` part needs to follow the above quotation mark rules. The correct syntax is `sum by("label.1")`.
3. **Grafana Metric Builder**: This is a graphical interface designed to help users generate PromQL query strings through point-and-click selection and configuration. One of its core logic is to convert user configurations (such as selected aggregation functions, grouping labels) into grammatical text queries.

## Practice

According to the issue description provided, the issue can be reproduced and verified through the following steps:

1. **Problem Manifestation**: When the user selects an aggregate function (such as `sum`) in Grafana's Metric Builder and attempts to group (`Group By`) by a label name (such as `label.1`) that contains a period (`.`), the query fragment generated by the builder is:
    `sum by(label.1) (rate({...}[2m]))`
    This is a PromQL statement with invalid syntax, and an error will be reported when executed.

2. **Correct Behavior**: The expected correct query fragment that the builder should generate is:
    `sum by("label.1") (rate({...}[2m]))`
    That is, double quotes are automatically added to tag names with UTF-8 characters.

3. **Reproduction environment and steps**:
    * **Environment**: Grafana 11.6 (any version that supports UTF-8).
    * **Prerequisite**: There is a Prometheus data source that contains a metric with a UTF-8 label name (such as `label.1`).
    * **Operation**:
        a. Create a Panel in Grafana that uses the Prometheus data source.
        b. Use the edit mode with **Query Type** as **Builder**.
        c. Select the target metric (eg `otlpapp.floatcounter.total`).
        d. Add an aggregate function (such as `Sum`) in **Aggregations**.
        e. In the **Group by** option, select the label (`label.1`) that contains UTF-8 characters.
    * **Result**: Observing the generated query (switch to Code mode or preview), you will find that the necessary quotes are missing.

## SRE Key Points

* **Impact on reliability**: This bug directly affects the **build reliability** of the monitoring panel. Engineers or users who rely on Metric Builder will generate invalid queries, causing monitoring panel errors and data loss, which may mask real system failures or performance issues and delay incident response. SREs need to ensure that the monitoring toolchain itself is robust.
* **Observability correlation**: Correct label grouping is the basis for achieving refined observability. Failure to correctly perform aggregation analysis by business tags or technical dimensions will seriously limit the ability to extract insights from indicator data and defeat the original intention of observability engineering.
* **Best Practices and Anti-Patterns**:
    * **Practice**: When encountering issues with UTF-8 label based queries in Grafana, the SRE should be aware of this flaw and adopt **Code** mode to manually write the correct PromQL (`"label.1"`) as a workaround.
    * **Anti-Pattern**: Graphical builders should not be assumed to be correct in all edge cases, especially when dealing with new features such as UTF-8. Key monitoring queries should undergo syntax review and testing.
* **Related Metrics (SLI/SLO)**: This issue itself does not directly impact the application SLI, but does impact the internal SLO of **Monitoring System Availability**. If a monitoring panel is unavailable due to query errors, the monitoring system is not meeting its own reliability goals.
* **Related Knowledge**: This issue is closely related to the [[prometheus-query-language]] syntax, [[grafana-data-source-configuration]], and [[monitoring-toolchain-reliability]]. Upgrading Grafana or waiting for official fixes (expected in subsequent versions) are the fundamental solutions.
