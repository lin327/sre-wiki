## Overview

In SRE practice, ensuring that alarm rule configurations are correctly loaded and effective is the cornerstone of ensuring system observability. The user verified via `kubectl` or an API endpoint (e.g. `/api/v1/rules`) that Prometheus had correctly loaded the alerting rule containing the `keep_firing_for` parameter, but found that the Alerting UI interface of Prometheus displayed a different value (incorrectly displayed as the value of the `for` field). This reveals a potential tooling flaw that affects the user experience and the configuration validation process. It is critical for SREs to understand this type of UI inconsistency with backend data, as it can misdirect debugging and affect judgments about the health of the monitoring system itself.

## Core concepts

- **`keep_firing_for` parameter**: This is an optional field in the Prometheus alert rule. This parameter defines the time window during which the alarm remains in the "continuously firing" status in Alertmanager after the alarm changes from `firing` to `pending` or `inactive`. Its purpose is to prevent alarms from frequently triggering and dismissing notifications during brief "flapping" periods.
- **Configuration verification method**: SRE typically uses two methods to verify Prometheus rule configuration:
  1. **API endpoint** (`/api/v1/rules`): Returns the details of all rules loaded when Prometheus is currently running. This is the most authoritative runtime configuration source.
  2. **Prometheus Web UI**: Provides a graphical display of alarm rules, aiming to simplify viewing and management.
- **Data Inconsistency**: Ideally, the data displayed by the UI should directly reflect the data obtained from the API. This issue states that for the `keep_firing_for` field, there may be a bug in the UI rendering layer that fails to correctly parse or display the value of that specific field.

## Practice

**Reliability process for verifying alarm rule configuration**

1. **Preferred API verification**: Always use the return value of the Prometheus API. Use the following command to directly query the runtime configuration of a specific rule (such as `KubeContainerOOMRestartTest`) and confirm the value of the `keepFiringFor` field.
    ```bash
    kubectl exec -it <prometheus-pod> -- wget -qO- http://localhost:9090/api/v1/rules | jq '.data.groups[].rules[] | select(.name=="<your-rule-name>")'
    ```
    *Expected Output*: Should contain the correct `"keepFiringFor": 300` (seconds).

2. **Record UI display differences**: When you find that the UI display value does not match the API return value (for example, the UI display value is the same as the `duration` field), you should first record this difference and confirm that the value returned by the API is as expected.

3. **Isolate impact**: This UI display bug usually **does not affect the actual alert behavior**. The alert evaluation engine uses the correct parameter values ​​obtained from the configuration file or API. Therefore, there is no immediate need to reboot or modify core rules to address this display issue.

4. **Report and Track**: Confirm this issue (such as reference #18789) to the Prometheus upstream community and pay attention to its repair status. Note the known limitations of this UI presentation in internal documentation or team communications until the issue is resolved.

5. **Configuration as code checking**: Define alert rules in version-controlled files (such as PrometheusRule CRD or YAML files), and use static analysis tools (such as `promtool check rules`) to perform syntax checks before deployment. This is a key practice to ensure your configuration is sourced correctly.

## SRE Key Points

### Association with reliability, observability, incident response
- **Reliability**: The monitoring system itself is the infrastructure of reliability engineering. Data inconsistencies in the UI of a monitoring tool will reduce SRE's confidence in the tool's output and may cause concerns about "whether the monitoring data can be truly trusted," thereby affecting the judgment of the overall system reliability.
- **Observability**: This issue highlights the importance of "meta-monitoring" (monitoring and monitoring systems). SREs need to ensure that the tools used to present observability data are themselves reliable and accurate.
- **Incident Response**: During incident response, the SRE relies on the UI to quickly view rule status. Incorrect `keep_firing_for` display may lead to misjudgment of the alarm duration. Although it does not affect the alarm logic, it may interfere with the timeline during root cause analysis.

### Best practices and common anti-patterns
- **Best Practices**:
  1. **Multi-Source Validation**: For key configuration parameters, cross-validate via both the API and (if possible) direct inspection of the underlying storage or logs.
  2. **Depend on Automation**: Try to reduce dependence on manual modification of the GUI through declarative configuration (configuration file/CRD) and automated pipeline management rules, thereby reducing the risk of exposure to UI display errors.
  3. **Focus on known issues**: Maintain and review the list of known issues for Prometheus and other monitoring components to avoid falling into "phantom problems" caused by tool bugs when troubleshooting problems.
- **Common anti-patterns**:
  1. **Rely on UI only**: Treating UI as the only source of truth for configuration is very dangerous when such bugs exist.
  2. **Ignore API verification**: After the configuration is pushed, the API is not actively called for final verification. It is mistakenly believed that the correctness of the UI means the deployment is successful.

### Related indicators (SLI/SLO/SLA)
Although this issue itself does not directly correspond to SLI, it affects the credibility of the monitoring data. A related indirect SLI could be:
- **Monitoring Data Consistency SLI**: Regularly compare key rule parameters returned by the Prometheus API with predefined baseline values through automated scripts to measure the self-consistency of the monitoring configuration. For example: "99% of the time, the `keep_firing_for` parameter value of all alerting rules exactly matches the API return value."
Anomalies in this SLI may reveal such UI or configuration loading bugs, and its SLO can be set to "no more than 1 detectable parameter display inconsistency event per month."
