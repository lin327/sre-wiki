## Overview

On May 9, 2016, the Prometheus project officially announced that it had joined the newly established Cloud Native Computing Foundation (CNCF) and became the second hosting project after Kubernetes. This event is not only a key milestone in the development of the Prometheus project, but also marks that the core position of open source monitoring tools in the cloud native technology stack has been recognized by mainstream foundations. It is critical for Site Reliability Engineering (SRE) practices to have a governance-independent, community-driven core monitoring system.

## Core concepts

**Cloud Native Computing Foundation (CNCF)** is an open source software foundation dedicated to promoting the development of cloud native technology, initiated by Google, CoreOS, Docker and other companies. It provides a neutral and sustainable governance platform for critical infrastructure projects such as Kubernetes and Prometheus.

**Project Governance Model** refers to the rules and framework that govern open source project decisions, contributor processes, version releases, and trademark use. Before Prometheus joined CNCF, its governance model may have relied on a certain core contributor or company. Joining the CNCF means that the project will adopt a clear, transparent, and sustainable governance structure, overseen by the Foundation’s Technical Oversight Committee (TOC), ensuring that its long-term development is not controlled by any single company.

**CNCF managed projects** refer to core infrastructure projects accepted by the foundation after rigorous evaluation. Becoming a managed project means that the project can obtain the foundation’s resource support, brand endorsement, and cross-vendor collaboration environment, thereby accelerating its technological evolution and ecological construction.

## Practice

Joining CNCF has a direct impact on the practice of the Prometheus project. First, the project’s decision-making process, contributor guidelines, and code code of conduct will be standardized in accordance with CNCF’s standards, which provides a fairer and more predictable participation environment for global developers. Secondly, Prometheus can use the continuous integration/continuous deployment (CI/CD) infrastructure, security audits, legal support and other resources provided by CNCF to focus on the innovation of the technology itself.

For the SRE team, this means greater long-term reliability in choosing Prometheus as the core monitoring solution. When teams deploy and operate Prometheus, they can be confident that their technical roadmap is jointly driven by a broad community, reducing the technical risks caused by the project "changing hands" or stalling.

## SRE Key Points

- **The Cornerstone of Observability**: Prometheus is the core pillar of the "metrics" part of modern observability systems (metrics, logs, link tracing). Its membership in the CNCF further solidifies its position among cloud-native observability standards.
- **Reliability and Independent Governance**: A core principle of SRE is managing risk. A monitoring system hosted by a neutral foundation can minimize operational risks caused by vendor lock-in or sudden changes in project direction, which is consistent with the idea of ​​managing reliability through `[[SLO]]`.
- **Community Collaboration and Incident Response**: A strong community means faster access to fixes and patches when a security vulnerability or critical flaw occurs. This directly increases the resilience of the SRE team in the event of a failure of the monitoring system itself.
- **Best Practices and Anti-Patterns**:
    - **Best Practice**: Treat monitoring as critical infrastructure, prioritize open source tools with strong community and independent governance, and quantify their value through `[[SLI]]`/`[[SLO]]`.
    - **Common anti-pattern**: Choosing an open source project that is only dominated by a single vendor may face the risk of poor maintenance or sudden changes in direction in the future.
- **Related Metrics**: This event itself does not directly define SLI/SLO, but it provides a more sustainable basis for achieving reliable `[[SLI]]` (e.g. service latency, error rate) through Prometheus. The health of a project (e.g. number of contributors, frequency of releases) can be used as an indirect indicator of its reliability.
