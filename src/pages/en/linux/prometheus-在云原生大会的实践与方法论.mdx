## Overview
As the de facto standard in the field of cloud native monitoring, Prometheus’ discussions and practice sharing at large technical conferences provide valuable reference for SRE and DevOps teams. This Prometheus special event at CloudNativeCon 2017 focused on demonstrating the tool's in-depth application in the Kubernetes environment, standardized application monitoring methodologies (such as the RED method), and real implementation cases in enterprise production environments. These contents are critical to understanding how to build a scalable and maintainable cloud-native monitoring system.

## Core concepts
The core of the conference content focused on several key monitoring methodologies, aiming to provide a consistent framework to reduce the cognitive load of the team and improve observability.

* **RED METHOD**: This is a practical pattern focused on monitoring request-oriented services. It proposes three core metrics: **Rate** (request rate, that is, the number of requests per second), **Errors** (error rate, the proportion of failed requests), and **Duration** (request delay, usually focusing on distribution). The RED approach is designed to provide quick insight into the health of a service from a client or load balancer perspective.
* **USE Method**: Although not expanded upon in detail in the session abstract, it is often mentioned in conjunction with the RED method for monitoring infrastructure resources. USE stands for Utilization, Saturation, and Errors and helps evaluate performance bottlenecks from a resource (e.g., CPU, memory, network) perspective.
* **Google's four golden signals**: This is a set of key monitoring indicators for user experience proposed by Google in its SRE practice, including **latency**, **traffic**, **errors** and **saturation**. The RED method is heavily inspired by this idea and can be seen as its simplification and implementation in more general scenarios.

## Practice
The activities of this conference provide multi-level practical guidance from entry to production.

1. **Prometheus and Kubernetes cluster monitoring**: The Prometheus Salon session provides practical exercises for Kubernetes clusters. Participants can access a real-time Prometheus and Kubernetes cluster environment and directly explore cluster workload, node status and other indicators by writing **PromQL** query statements. This demonstrates the powerful integration capabilities and flexibility of Prometheus as a Kubernetes native monitoring tool.

2. **Application layer instrumentation (Instrumentation)**: Multiple presentations discussed how to integrate Prometheus into applications.
    * Tom Wilkie's speech systematically introduced the application instrumentation model (RED/USE) and discussed its applicable scenarios and limitations.
    * Weaveworks' sharing provides a step-by-step "practical guide" based on Node.js applications, showing the specific process of integrating the Prometheus client library into the application and exposing key indicators (such as request counts, latency histograms).

3. **Production environment integration and self-healing practice**: The FedEx case study is a highlight. It describes in detail the experience of deploying Prometheus in a large enterprise production environment, including reasons for selection and integration configuration steps. Furthermore, they showed how to use Prometheus' **AlertManager** with the systemd service to achieve **self-healing** of the infrastructure, and integrate it with collaboration tools such as Slack to build an automated event management process from alert to response.

## SRE Key Points
* **Association with reliability, observability, and event response**: The indicators provided by Prometheus are the core of the "metric" dimension in the three pillars of **observability** (metrics, logs, and tracking). Standardized indicators based on methodologies such as RED/USE are the basis for defining and calculating service SLO** (Service Level Objective) and **SLI** (Service Level Indicator). A clear SLO helps the team measure reliability and manage the Error Budget appropriately. Integrating AlertManager with the incident response process (such as Slack notifications, automatic restarts) as in the FedEx case is a key practice to improve the efficiency of incident response.
* **Best Practices and Common Anti-Patterns**:
    * **Best Practice**: Using a **consistent methodology** like RED/USE to build monitoring can greatly improve team collaboration efficiency and reduce long-term maintenance costs. For application developers, it is crucial to master the basic instrumentation skills of Prometheus as early as possible. In a production environment, the Prometheus ecosystem (such as AlertManager and various Exporters) should be fully utilized to build an end-to-end monitoring and response system.
    * **Anti-Pattern**: Avoid "metric bloat", where collecting a large number of useless metrics leads to reduced storage and query performance. Monitoring silos should also be avoided, ensuring that monitoring data from infrastructure to applications can be correlated to form a complete view.
* **Related indicators (SLI/SLO/SLA)**: **Request error rate**, **Request delay percentile** (such as P99) defined by the RED method are classic examples of defining user-oriented service SLI. For example, an SLO could be set to "P99 latency less than 200 milliseconds 95% of the time."
