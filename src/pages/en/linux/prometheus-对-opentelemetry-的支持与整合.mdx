# Our commitment to OpenTelemetry

## Overview

OpenTelemetry is a framework and toolset designed to unify the three major observability signals: Traces, Metrics, and Logs. As the de facto indicator monitoring standard in the cloud native field, Prometheus's deep integration with OpenTelemetry is a milestone. For SRE, this means that it is easier to build a unified, powerful, and open observability system, shifting from relying on multiple collectors to a more standardized and integrated data pipeline, thereby simplifying the tool chain and reducing maintenance burden.

## Core concepts

**OpenTelemetry (OTel)**: An open source observability framework that provides vendor-neutral APIs, SDKs, and tools for generating, collecting, and describing telemetry data (Traces, Metrics, Logs). Its core values ​​lie in the uniformity of specifications and the avoidance of vendor lock-in.

**OTLP (OpenTelemetry Protocol)**: The telemetry data transmission protocol defined by OpenTelemetry has become a standard protocol for transmitting Traces, Metrics, and Logs between different components. Prometheus is working on native support for OTLP ingest and export.

**Metrics and Resource Attributes**: OpenTelemetry clearly distinguishes between "metric attributes" that identify the metric itself (such as `http.status_code`) and "resource attributes" that identify the source of the metric (such as `k8s.pod.name`). Prometheus's traditional flat label model needs to evolve here to better support this layering, thereby improving the capabilities of multi-dimensional analysis and filtering.

**Delta Temporality**: As opposed to the Cumulative Temporality commonly used by Prometheus, Delta Temporality reports the incremental changes since the last reporting period. Supports Delta temporary performance to be better compatible with traditional indicator systems such as StatsD, and expands the application scenarios of OTel.

## Practice

According to the Prometheus community’s roadmap, the following key integration features are in progress to make Prometheus the default store for OpenTelemetry metrics:

1. **OTLP Ingestion General Release (GA)**: Prometheus v2.47.0 introduces experimental OTLP ingestion functionality. It is planned to make it officially stable in future versions, improve support for data staleness (Staleness) and out-of-order ingestion (Out-of-order ingestion), and natively support exponential histograms (Exponential Histograms).

2. **Support for UTF-8 metrics and tag names**: To be directly compatible with OpenTelemetry semantic specifications (such as `http.server.request.duration`), Prometheus is developing full support for UTF-8 characters to eliminate the inconsistencies caused by current name conversions due to character restrictions.

3. **Native support for resource attributes**: The community is exploring solutions from multiple levels such as query, user experience and storage. The goal is to implement convenient filtering and grouping analysis of OpenTelemetry resource attributes in Prometheus to make it more suitable for OTel's data model.

4. **OTLP Export in Ecosystem**: Plans to add OTLP export support for Prometheus server, SDK and Exporters. This means that services using the Prometheus SDK will be able to directly push OTLP format data, thus opening up the huge Prometheus exporter ecosystem to OTel users. In the meantime, the OpenMetrics format will continue to be the format optimized for Prometheus pull mode.

5. **Support Delta temporality**: To be compatible with more traditional monitoring system (such as StatsD) scenarios, the Prometheus server is developing native support for Delta temporality indicators.

## SRE Key Points

- **Association with reliability/observability**: The deep integration of Prometheus and OpenTelemetry greatly enhances the possibility of building a unified and complete observability platform. SRE can use OTel's rich semantic data to enrich Prometheus indicators, and use Prometheus's powerful query and alarm capabilities for analysis to more comprehensively understand system behavior and quickly locate the root cause of faults. This integration directly serves the goal of improving system reliability.

- **Best Practices and Common Anti-Patterns**:
    - **Best Practice**: Actively plan the evolution from multi-tool hybrid collection to an OTLP-centric data collection architecture. Evaluate existing Prometheus infrastructure to prepare for UTF-8 support and resource attribute analysis. Participate in community discussions and testing to provide feedback on these features.
    - **Common anti-patterns**: Introducing a large number of changes too early in the early stage of integration leads to stability risks; ignoring the value of the existing monitoring stack based on `remote_write` and completely tearing it down and starting from scratch; treating the integration of Prometheus and OTel only as protocol conversion, while ignoring the fundamental challenges brought by differences in data models.

- **Related Metrics (SLI/SLO/SLA)**: This integration brings new ideas to defining and implementing SLI/SLO. SREs can more naturally leverage OTel's resource attributes to define more fine-grained SLOs (for example, by service version or deployment region), making the calculation and management of Error Budgets more precise and consistent with the business perspective. Prometheus' SLI calculations will be able to incorporate richer OTel contextual information.
