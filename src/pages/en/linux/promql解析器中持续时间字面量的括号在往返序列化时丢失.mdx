# PromQL Parser: Parentheses Around Duration Literals Lost on Round-Trip Serialization

## Overview

In Prometheus's PromQL query language parser, the parsing and serialization (`Expr.String()`) of query strings should have "round-trip consistency." This means that after parsing a query string into an Abstract Syntax Tree (AST) and then serializing it back to a string, a semantically equivalent query should be obtained. This page describes a specific parser defect: when a simple numeric literal wrapped in parentheses (such as `(5)`) is used in a duration expression position (such as `offset` or range brackets `[]`), the serialization process incorrectly loses the parentheses. This issue affects the accurate representation and debugging of queries and needs attention for SRE workflows that rely on precise query representation.

## Core Concepts

- **PromQL Parser**: Responsible for converting text-form PromQL queries into internal data structures (AST) that the Prometheus engine can execute.
- **Round-trip serialization (`Expr.String()`)**: The process of converting the AST object generated by the parser back into a PromQL text string. Ideal round-trip serialization should precisely restore the semantics of the original query.
- **`*NumberLiteral`**: AST node representing a simple numeric value (such as `5`). When wrapped in parentheses, such as `(5)`, in a normal expression context, it is wrapped by a `*ParenExpr` node, which is responsible for outputting parentheses during serialization.
- **`*DurationExpr`**: AST node representing a duration expression (such as `5m`, `5m + 1s`). It has a `Wrapped` field used to indicate whether the expression is wrapped in parentheses, enabling correct parenthesis output during serialization.
- **Duration expression context**: Refers to positions that syntactically require a duration value, such as `5m` in the query `foo offset 5m`, or the range parameter in `foo[5m]`.

## Practice

This issue is evident in Prometheus environments with `ExperimentalDurationExpr: true` configuration enabled. The core issue is inconsistency in the parser's parenthesis handling logic within "duration context."

### Problem Manifestation

When the parser encounters a single numeric literal (such as `5`) wrapped in parentheses used in a duration context, it may generate a direct `*NumberLiteral` node instead of the expected `*DurationExpr` node carrying parenthesis information. Since the `*NumberLiteral` node does not store parenthesis information, parentheses are lost during serialization.

The following table shows specific cases of problem reproduction:

| Input Query | `Expr.String()` Output | Parentheses Preserved | Notes |
| :--- | :--- | :--- | :--- |
| `foo offset (5)` | `foo offset 5s` | **No** | Parentheses lost, unit inferred as `s`. |
| `foo offset +(5)` | `foo offset 5s` | **No** | Positive sign and parentheses both lost. |
| `foo offset -(5)` | `foo offset -5s` | **No** | Negative sign preserved, but parentheses lost. |
| `foo offset (5m)` | `foo offset 5m` | **No** | Parentheses lost. |
| `foo[(5s)]` | `foo[5s]` | **No** | Parentheses within range brackets lost. |

**For comparison, the following cases correctly round-trip serialize:**

| Input Query | `Expr.String()` Output | Parentheses Preserved | Notes |
| :--- | :--- | :--- | :--- |
| `(5)` | `(5)` | **Yes** | Non-duration context, handled by `*ParenExpr`. |
| `-(5)` | `-(5)` | **Yes** | Non-duration context. |
| `+(5)` | `+(5)` | **Yes** | Non-duration context. |
| `(5) + 1` | `(5) + 1` | **Yes** | Non-duration context. |
| `foo offset (5m + 1m)` | `foo offset (5m + 1m)` | **Yes** | Multi-segment duration expression, uses `*DurationExpr` node. |
| `foo offset -(5m + 1m)` | `foo offset -(5m + 1m)` | **Yes** | Multi-segment duration expression. |
| `foo[(5s + 1s)]` | `foo[(5s + 1s)]` | **Yes** | Multi-segment duration expression. |

### Root Cause

The key difference lies in AST node types:
1.  **Multi-segment duration expressions** (such as `5m + 1s`) generate `*DurationExpr` nodes in duration context. This node has a `Wrapped` field, enabling the parser to record parenthesis information and ensure correct restoration during serialization.
2.  **Simple numeric literals** (such as `5`) in duration context may directly generate `*NumberLiteral` nodes in the current implementation. This node **does not** have a field like `Wrapped` to store parenthesis information, leading to information loss during serialization.

### Verification and Impact

- **Verification**: SRE engineers can verify this issue by writing unit tests or entering the above queries in Prometheus's debugging tools, comparing the original input with `Expr.String()` output.
- **Impact**: Although from the Prometheus engine execution perspective, `foo offset (5)` and `foo offset 5s` are usually semantically equivalent, the loss of parentheses affects:
    - **Query readability and intent**: The explicit grouping intent (parentheses) in the original query disappears in the output.
    - **Debugging and log analysis**: When queries are logged or output, their form differs from the original input, which may cause confusion.
    - **Configuration management**: If PromQL queries are stored in configuration files and undergo parse-serialize cycles, their text representation may undergo unexpected changes.

## SRE Key Points

### Relationship with Reliability
This issue directly relates to **query reliability**. Although it may not directly cause service interruptions, it violates the fundamental principle of data representation consistency. In automation operations, GitOps configuration management, or complex query template generation scenarios, inconsistent serialization results may lead to configuration drift or difficult-to-track differences.

### Best Practices and Precautions
- **Awareness**: When writing or debugging duration expressions involving parentheses, be aware of this parser behavior. If parentheses are critical to query intent (for example, grouping in complex expressions), verify whether they are preserved after parsing.
- **Testing**: When developing toolchains that depend on precise text representation of PromQL queries, include this edge case in test cases.
- **Monitor updates**: This issue is tracked in GitHub Issue #18770. SRE teams should monitor Prometheus official releases to confirm whether subsequent versions fix this defect. The fix may involve modifying parsing logic to ensure appropriate AST nodes are generated for simple parenthesized numeric literals in duration context.

### Related Metrics and Monitoring
This issue itself does not directly affect SLI/SLO as it does not change query calculation results (in simple cases). However, if audits or compliance checks are based on query text, inconsistent representation may affect the accuracy of related monitoring metrics. Ensuring Prometheus component versions are known and tracking their known issues is standard practice for managing such risks. For custom query processing middleware, special attention is needed to normalize PromQL text.
