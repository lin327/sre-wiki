# Pull doesn

## Overview

In discussions about monitoring system architecture, the debate between Pull (pull-based) and Push (push-based) metric collection modes has been long-standing. A prevalent view is that "Pull mode cannot scale," meaning that as monitoring scale increases, Pull mode becomes a performance bottleneck. This article aims to deeply analyze this common misconception, combining [[prometheus]]'s design philosophy and practical experience to argue that with proper design, Pull mode not only does not hinder scalability but can bring numerous operational and reliability advantages. Understanding the scalability principles of monitoring systems is crucial for building maintainable, scalable SRE observability systems.

## Core Concepts

To understand Pull mode's scalability, several key concepts and common sources of misunderstanding need to be clarified first.

### 1. Pull Mode vs. Traditional Active Checks

Many people confuse Pull mode with traditional monitoring systems like Nagios. Nagios's scalability issues primarily stem from its architecture: the central server needs to **actively execute check scripts** for each host or service. This consumes significant host resources (CPU, memory, I/O), causing the monitoring server to quickly become overloaded.

Prometheus's Pull mode is fundamentally different. It does not execute any check logic; it simply **fetches** pre-computed, aggregated time series data from targets via HTTP protocol. This process is highly parallelized (utilizing Go's goroutines) and has extremely low overhead. The bottleneck typically lies in the resource consumption of monitored targets, not the monitoring server itself.

### 2. Connection Initiator and Scalability

A common technical concern is "Push can use UDP, avoiding TCP connection establishment overhead." The article points out through empirical data that compared to the core work a Prometheus server needs to handle -- **writing large amounts of time series data to memory and persisting to disk/SSD** -- the overhead of TCP/HTTP protocol is almost negligible. For example, a single Prometheus server in SoundCloud's production environment once achieved a record of receiving 800,000 samples per second. With a 10-second scrape interval and 700 metrics per host, a single Prometheus server can monitor over 10,000 machines. Therefore, **the scalability bottleneck is never about who initiates the connection, but about data ingestion and storage efficiency**.

### 3. Time Series vs. Event Streams

Event-based monitoring systems (like StatsD, ELK) receive every raw event (such as an HTTP request). If Pull mode were used on such architecture, the application would need to buffer massive events and scrape at extremely high frequencies, which is indeed not feasible.

However, Prometheus is not an event storage system. It collects **pre-aggregated time series data**. Applications only need to maintain counters, histograms, and other metrics in memory, then periodically (e.g., every 15 seconds) expose current values to Prometheus. Prometheus scrapes this "current state," not the millions of underlying events. This keeps monitoring traffic at a very low level.

### 4. Service Discovery and Configuration

Pull mode requires the monitoring system to know which targets to monitor and their addresses. This is often criticized as complex configuration and difficult to scale. But SRE practice shows that for any serious monitoring, you need a "desired state" manifest to detect instance downtime, network partitions, or instances unexpectedly disappearing. Therefore, Push mode may actually require **more configuration**: not only defining the desired state but also configuring the monitoring server address in each application instance.

The core advantage of Pull mode lies in centralized and flexible configuration. Prometheus automatically obtains target lists through built-in **service discovery** mechanisms (such as [[service-discovery]] supporting Kubernetes, Consul, EC2, etc.), greatly simplifying configuration in large-scale dynamic environments. It also supports easily running a production monitoring replica on a laptop for experimentation, or manually scraping metrics for debugging.

## Practice

Based on the above understanding, we can summarize the practical advantages of Prometheus's Pull mode in terms of scalability:

1.  **Efficient parallel scraping**: Prometheus servers use thousands of goroutines to simultaneously scrape various targets, fully utilizing network bandwidth and CPU resources, avoiding serialization bottlenecks.
2.  **Leveraging service discovery**: By integrating with infrastructure's service discovery mechanisms, monitoring configuration becomes dynamic and decoupled from application deployment, ideal for microservices and cloud-native environments.
3.  **Centralized control**: All scrape targets, intervals, labels, and other configurations are centralized on the Prometheus server side. This not only simplifies management but also enables more fine-grained control over monitoring traffic.
4.  **Architectural flexibility**: Supports using [[pushgateway]] as a Push endpoint for temporary jobs or short-lived tasks, then having Prometheus uniformly scrape, forming a hybrid architecture with pull as primary and push as supplementary.
5.  **High availability deployment**: To achieve monitoring's own high availability, simply run two Prometheus servers with identical configurations in parallel. They independently scrape the same target set without additional configuration.

A common anti-pattern is configuring independent monitoring server addresses for each service instance in a distributed system. This violates Pull mode's centralized management philosophy and causes configuration complexity to grow linearly with instance count. The correct approach is to rely on shared service discovery mechanisms.

## SRE Key Points

### Reliability and Observability

Pull mode inherently improves monitoring data reliability. TCP-based HTTP requests guarantee successful data transmission or fast failure (connection timeout, rejection), unlike UDP-based Push mode which may silently lose data packets without detection. This aligns with [[sre]]'s core requirement that **observability data must be reliable**.

### Configuration Management and Change Risk

Centralized configuration embodies the SRE pursuit of "simple and reliable" principles. It reduces the blast radius of configuration errors. In Push mode, changes to monitoring endpoint addresses require reconfiguring all application instances, which is a high-risk, high-cost operational task in large-scale environments. Pull mode limits this impact to the monitoring server side.

### Defensive Design: Preventing Accidental DDoS

The article mentions a key operational point: whether Pull or Push, sending too much data to the monitoring system will cause it to crash. But Push mode, due to distributed control points, is more prone to avalanche when an experimental or faulty task pushes garbage data to the production monitoring system. Pull mode centralizes control with the monitoring server, and through limiting scrape frequency and configuring whitelists, can more effectively prevent such risks.

### Related Metrics (SLI/SLO/SLA)

The monitoring system's scalability directly affects its own SLI (Service Level Indicator) as a service. For example:
- **Scrape success rate**: The proportion of Prometheus successfully obtaining target metrics.
- **Scrape latency**: Time from initiating HTTP request to receiving complete response.
- **Data freshness**: The difference between the latest data point and current time.

Based on these SLIs, SRE teams can define SLOs for the monitoring system itself (e.g., 99.9% scrape success rate at all times) and use them to drive architectural optimization. Pull mode's centralized nature makes monitoring these self-metrics very easy.

### Applicable Scenarios and Limitations

Pull mode is not a silver bullet. Its main limitation is network reachability: if the monitoring server cannot actively connect to targets (e.g., targets are behind strict firewalls or in different network segments), Pull mode is difficult to implement. In such cases, [[pushgateway]] or more complex proxy architectures are needed, but this typically falls under network operations rather than Pull mode's scalability issue. For globally distributed, network-partitioned large-scale monitoring, tiered or federated architectures may be needed, but this is equally a challenge Push mode must face.
