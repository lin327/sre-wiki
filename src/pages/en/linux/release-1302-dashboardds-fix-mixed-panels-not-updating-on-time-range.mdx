# 

## 概述

在 Grafana 等可观测性平台中，`Mixed datasource` 是一个强大的功能，允许单个面板（Panel）从多个数据源（Data Source）并行查询数据。这为构建统一、复合的仪表板视图提供了灵活性。然而，这种复杂性也带来了状态管理上的挑战。本文档基于一个生产环境回归缺陷（PR #124894），深入解析在时间范围（Time Range）变化时，Mixed datasource 面板数据无法更新的根因、修复方案及其对 SRE 实践的启示。此类问题是影响仪表板实时性和可靠性的关键，属于可观测性基础设施本身可靠性保障的范畴。

## 核心概念

### 1. Mixed Datasource 与 Dashboard Datasource 子查询
在 Grafana 中，`Mixed datasource` 面板允许其子查询（Sub-query）指定为 `-- Dashboard --` 数据源。这意味着子查询会从父面板或仪表板的上下文中继承数据源配置，形成一种“查询链”。这种机制常用于创建动态、可重用的面板。

### 2. 响应式流（Reactive Stream）与 `ReplaySubject(1)`
Grafana 的查询引擎（如 `SceneQueryRunner`）基于响应式编程模型（如 RxJS）。查询结果通过一个 `ReplaySubject(1)` 流暴露。这个“Subject”会缓存最近的**一次**事件。关键在于，它会保留最后一次成功的 `Done` 状态（包含查询结果和时间范围信息）。

### 3. 终态（Terminal State）操作符 `emitFirstLoadedDataIfMixedDS`
这是一个自定义 RxJS 操作符，专门用于处理 Mixed datasource 子查询。它的核心逻辑是使用 `first(Done || Error)` 来“短路”子查询流：一旦收到第一个 `Done` 或 `Error` 事件，就立即结束该子查询的订阅，认为数据已加载完成。

### 4. 问题的核心：陈旧的 `Done` 状态
当用户在仪表板上更改时间范围时：
1.  `SceneQueryRunner` 会为新时间范围启动查询。
2.  子查询的 Dashboard 数据源会订阅上游 `SceneQueryRunner` 的 `ReplaySubject(1)` 流。
3.  由于 `ReplaySubject(1)` 会立即重放缓存的上一次事件，子查询会**立即收到旧时间范围的 `Done` 事件**。
4.  `emitFirstLoadedDataIfMixedDS` 操作符将此 `Done` 视为有效结果，调用 `first()` 完成了子流。
5.  稍后（3-6秒），上游为新时间范围执行的真实查询返回新的 `Loading` -&gt; `Done` 事件流。但此时子流已经关闭，Mixed datasource 的 `forkJoin` 操作符也已用旧的帧数据解析完成。
6.  结果：面板渲染了旧时间范围的数据，并且**再也不会更新**。

## 实践

### 修复方案：基于请求范围的过滤器
修复的核心思想是：在现有的终态处理逻辑（`emitFirstLoadedDataIfMixedDS`）之前，增加一个过滤器，丢弃那些**请求时间范围不匹配**的终态事件。

```javascript
// 概念性修复代码
上游流
  .pipe(
    // 关键修复：在进入Mixed-DS专用操作符前过滤
    filter(event => {
      // 只在Mixed路径下应用此过滤器
      if (!requestId.includes(MIXED_REQUEST_PREFIX)) return true;
      // 如果是终态事件（Done/Error），检查其携带的范围是否与当前查询范围一致
      if (event.type === 'Done' || event.type === 'Error') {
        return event.request.range === chainPanel.options.range;
      }
      // 非终态事件（如Loading）保持通过
      return true;
    }),
    // 原有的操作符
    emitFirstLoadedDataIfMixedDS()
  )
```

**修复逻辑解析：**
*   **过滤条件**：`event.request.range === chainPanel.options.range`。确保只有与当前面板查询时间范围一致的终态事件才会被后续逻辑处理。
*   **作用范围**：过滤器仅对 `MIXED_REQUEST_PREFIX`（Mixed datasource 路径）生效。对于非 Mixed 的 Dashboard 数据源查询，其流通常保持开放，会自然地等待并接收新范围的 `Done` 事件，无需且**不能**添加此过滤器，否则会错误地阻断如 `PanelTimeRange` 覆盖等合法场景下的数据更新。
*   **测试验证**：修复通过了严格的单元测试和手动冒烟测试，覆盖了时间范围变化、刷新按钮、编辑器添加子查询、面板级时间覆盖等多种场景。

## SRE 要点

### 与可靠性、可观测性、事件响应的关联
*   **仪表板作为可靠性契约**：仪表板是 SRE 和开发团队监控系统健康状况（SLO、Error Budget）的核心工具。数据不能正确更新等同于仪表板本身不可靠，会直接影响事件发现和根因分析的效率。
*   **可观测性系统的自监视**：修复此类问题体现了“用监控监控自身”的理念。可观测性平台（如 Grafana）自身的缺陷，需要通过其自身的流程（PR、测试、回滚）和监控（客户问题上报）来发现和解决。
*   **事件响应中的陷阱**：在排查系统告警时，如果仪表板数据陈旧，可能导致误判。SRE 需要意识到工具本身可能成为“盲点”。

### 最佳实践与常见反模式
*   **最佳实践：防御性响应式编程**：在处理类似 `ReplaySubject` 的缓存流时，应谨慎假设缓存数据的新鲜度。在依赖缓存数据触发后续逻辑（尤其是像 `first()` 这样会终止流的逻辑）前，务必进行验证（如校验时间范围、请求ID等）。
*   **最佳实践：精确的修复范围**：修复应最小化影响范围。本次修复仅针对导致问题的 `Mixed datasource` 路径，避免了波及其他合法功能（如面板时间覆盖），体现了“精准外科手术式”的修复原则。
*   **反模式：盲目信任操作符**：`first(Done || Error)` 本身逻辑正确，但缺乏对上游数据时效性的判断，导致在特定时序下产生竞态条件（Race Condition）。不能孤立地理解一个操作符，必须结合其数据源和上下游环境来评估。
*   **反模式：忽略回退/回归风险**：本次 bug 是由 PR #97116 引入的回归。建立完善的集成测试和端到端测试（特别是针对复杂交互流），是防止此类问题反复发生的关键。

### 相关指标（SLI/SLO/SLA）
*   **仪表板刷新成功率**：可以定义一个 SLI，用于监测用户在仪表板上点击“刷新”或更改时间范围后，面板数据是否在预期时间内（如5秒）更新为最新值。失败的案例可能指向此类 bug。
*   **仪表板数据新鲜度**：对于关键监控面板，可以检查其返回数据的最大时间戳与当前时间的差值。持续的差值可能表明数据源查询卡住或缓存未失效。
*   **Error Budget 消耗**：此类影响用户界面数据准确性的 bug，会消耗可观测性平台自身的“可靠性 Error Budget”。需要将其纳入平台的可靠性报告，驱动基础设施的可靠性改进。
