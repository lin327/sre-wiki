# Interview with ShowMax - Prometheus Blog

## Overview

ShowMax is a subscription video-on-demand service founded in South Africa in 2015 to address the challenges of video streaming in regions with spotty internet connections, such as sub-Saharan Africa. As a technology-driven company, ShowMax runs about 50 microservices and is faced with the task of ensuring that its complex technology stack (including video encoding, multi-platform APIs) runs reliably. The evolution of its monitoring system is a typical case in SRE practice, demonstrating how to migrate from a traditional, difficult-to-extend monitoring solution to a modern, Prometheus-based observability platform, and improving system stability and development efficiency in the process.

## Core concepts

Before the introduction of Prometheus, ShowMax’s monitoring needs were mainly divided into four categories:
1. **Active monitoring and detection**: implemented through Icinga.
2. **Indicator collection and alarm**: This is the core use case for migrating to Prometheus.
3. **Backend service log collection**.
4. **Application event and log collection**.

For the latter two items, ShowMax built a log infrastructure based on RabbitMQ and ElasticSearch. The logs are first collected on the Unix Socket of the local container and then pushed to the consumer for processing.

Previously, ShowMax ran two sets of Collectd-based indicator collection pipelines in parallel (using Graphite and OpenTSDB respectively), but both encountered serious stability and maintainability problems, such as Graphite's high I/O consumption and the complexity of OpenTSDB. This prompted them to seek a more unified and reliable indicator platform.

## Practice

**Migration and Deployment**
ShowMax started as a proof-of-concept in an LXC container and quickly moved Prometheus to a dedicated physical server (Intel Xeon E3-1270 v3, 32GB RAM, SSD) in Hetzner. They utilize SSDs to set data retention to 120 days.

**Indicator push architecture: prometheus-pusher**
ShowMax initially wanted to maintain consistency due to the "push" model of the existing logging infrastructure, also using push mode to send metrics to Prometheus. To do this, they developed a Go daemon called `prometheus-pusher`. This daemon is responsible for grabbing indicators from various local Exporters and pushing them to the Prometheus server through [[prometheus-pushgateway]]. This model simplifies some issues in service discovery, but also creates challenges, such as the difficulty in distinguishing between a "network partition" and a "service crash." This tool is open source.

**Programmable Grafana Dashboard**
While approving of Grafana's integration with Prometheus, ShowMax was dissatisfied with its native approach to dashboard configuration management (persistence within containers, lack of change tracking). So they developed another open source tool: a dashboard builder. The tool receives configuration files maintained in YAML format (stored in Git repositories), generates the JSON files required by Grafana, and can automatically deploy to new Grafana containers. This enables automation, repeatability and auditability of dashboard configuration, perfectly fitting the concept of infrastructure as code.

**Technology Stack and Tools**
ShowMax’s backend services are primarily written in Ruby, Go, and Python. Data storage relies on PostgreSQL and ElasticSearch. They use etcd and custom tools to configure Varnish for request routing. In terms of monitoring, they use Prometheus as the core indicator platform and cooperate with Grafana for visualization.

## SRE Key Points

- **Reliability and stability improvements**: The most direct benefit of migrating from Graphite/OpenTSDB to Prometheus is that the stability and accessibility of the monitoring system itself have been greatly improved. Stable monitoring is the cornerstone of SRE practice, which provides a reliable data basis for tracking [[error-budget]] and [[slo]].
- **Empower developers and DevOps culture**: Prometheus's fast query and stability allow developers to easily and instantly obtain application running indicators (such as JVM heap memory usage), which greatly facilitates problem troubleshooting. This convenience lowers the threshold for obtaining monitoring data, promotes collaboration between development and operation and maintenance, and is a powerful tool for the implementation of DevOps culture.
- **Push vs. Pull Model Tradeoffs**: ShowMax originally chose push mode to be consistent with existing infrastructure. However, they recognized that this conflicted with Prometheus' pull paradigm and introduced additional complexity. According to [[prometheus-best-practices]], they plan to move to a pull model in the future to better leverage Prometheus' design strengths and improve the overall robustness and diagnosability of the system.
- **Observability Engineering Practice**: The case of ShowMax shows that observability is not just about deploying a tool, but also about building a whole set of workflows around it. They solved specific problems in their own environment through self-developed tools (prometheus-pusher, dashboard generator) and codified the configuration, which is a typical feature of advanced observability engineering practices.
- **Best Practices and Anti-Patterns**:
    - **Practice**: Make ongoing investments in monitoring infrastructure and develop custom tools to solve "last mile" problems; bring dashboard configuration into version control; start with a single, reliable source of metrics (Prometheus) and gradually replace complex legacy systems.
    - **Anti-Pattern**: Maintain multiple complex and unstable monitoring pipelines in parallel (such as using Graphite and OpenTSDB at the same time); in a containerized environment, persist key configuration and state inside the container.
