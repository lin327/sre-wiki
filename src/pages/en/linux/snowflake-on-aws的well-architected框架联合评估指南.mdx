## Overview

When running Snowflake on AWS, teams often need to reference two separate sets of best practices simultaneously: the AWS Well-Architected Guide for AWS infrastructure, and the Snowflake Well-Architected Framework for Snowflake compute, data organization, and governance. This separation can lead to disjointed security control mappings, extended production readiness timelines, and difficulties in demonstrating compliance. Custom Well-Architected Framework Lens from Snowflake and AWS fills this gap. It provides a unified assessment view that combines the seven pillars of AWS (security, reliability, performance efficiency, cost optimization, operational excellence, sustainability) with Snowflake’s professional practices to help SRE teams efficiently identify and remediate architectural risks across services.

## Core concepts

This United Lens combines the seven pillars of the AWS Well-Architected Framework with Snowflake’s Guiding Principles into a seven-pillar assessment model. Each pillar contains recommendations at the AWS infrastructure level and the Snowflake data platform level, with the core providing **integration recommendations** showing how the two layers can work together to build a robust production architecture.

Here’s a detailed breakdown of the seven pillars:

### 1. Security and Identity
Security needs to be coordinated at the AWS infrastructure layer (e.g. VPC, IAM, KMS) and the Snowflake data platform layer (e.g. network policy, RBAC, OAuth). The joint recommendations emphasize:
* **Network**: Use AWS PrivateLink between Amazon VPC and Snowflake, and layer Snowflake network policies on top of EC2 security groups for defense in depth.
* **Identity & Access**: Federate Snowflake authentication with AWS IAM Identity Center, mapping identity provider groups to Snowflake database roles for consistent RBAC.
* **Authentication**: Use AWS Secrets Manager to store Snowflake RSA private keys and automatically rotate them; provide a unified IdP for both systems through SAML federation.

### 2. Data Governance and Compliance
Securing the data itself requires spanning two complementary layers: AWS infrastructure (e.g. S3 encryption, lifecycle policies) and Snowflake query layer (e.g. dynamic data masking, row access policies, Tri-Secret Secure). Joint recommendations include:
* **Data Protection**: Use AWS KMS with Snowflake Tri-Secret Secure for dual-managed encryption and apply Snowflake masking policies for column-level protection.
* **Audit & Compliance**: Stream Snowflake audit logs to Amazon CloudWatch or OpenSearch Service via Amazon S3 and Amazon EventBridge for unified compliance monitoring.

### 3. Reliability
Reliability depends on the ability of the two systems to coordinate under failure scenarios. Key integration areas include:
* **Disaster Recovery**: Configure Snowflake cross-region replication to a secondary region on AWS and use Snowflake client redirection for automatic failover.
* **Data Durability**: Align Snowflake Time Travel retention periods with Amazon S3 versioning policies; use zero-copy clones for pre-deployment testing to avoid storage overhead.
* **Recovery Objective**: Defines joint RTO and RPO objectives that take into account Snowflake replication latency and AWS infrastructure recovery time.

### 4. Performance optimization
Performance tuning needs to be done at both the infrastructure and application levels.
* **Compute Provisioning**: Right-size Snowflake virtual warehouses based on query analytics, aligning them with multi-cluster warehouses that automatically scale at the application layer.
* **Data Organization**: Optimize Amazon S3 staging file size for Snowpipe ingestion; apply clustering keys on common filter columns, following lowest to highest cardinality order (this is a requirement specific to Snowflake's micro-partitioning architecture).
* **Caching and Latency**: Design query patterns to maximize Snowflake result cache hit rates; use Amazon ElastiCache to cache frequently accessed Snowflake results at the application layer.

### 5. Cost optimization and FinOps
Manage costs across two billing models (AWS infrastructure consumption and reservations vs. Snowflake compute credits and storage).
* **Cost Visibility**: Combine AWS Cost Explorer data and Snowflake credit consumption in an integrated FinOps dashboard to tag resources with matching cost center tags.
* **Compute Efficiency**: Pair Snowflake capacity commitments with AWS Savings Plans for predictable baselines; aggressively use autosuspends for development warehouses.
* **Storage Efficiency**: Align Snowflake Time Travel retention periods (1 day for development environments, 90 days for regulated data) with Amazon S3 lifecycle conversion to Glacier.

### 6. Operational Excellence
Build observability, automation, and incident response workflows across both applications.
* **Monitoring**: Use Amazon S3 integration to export Snowflake metrics to Amazon CloudWatch to build unified operational dashboards.
* **Automation and IaC**: Manage Snowflake objects and AWS infrastructure in the same Terraform state; use CI/CD pipelines for database migration workflows.
* **Incident Response**: Trigger AWS Lambda automated remediation from Snowflake Resource Monitor alerts via notification integration and Amazon SNS.

### 7. Sustainability
This is the first joint ISV-AWS WAF lens to include sustainability as a first-class pillar.
* **Region Selection**: Select AWS regions consistent with sustainability goals for non-latency-sensitive Snowflake workloads; prioritize secondary regions with higher percentages of renewable energy for disaster recovery.
* **Data Lifecycle**: Minimize storage footprint by aligning Time Travel retention periods with actual recovery needs; use zero-copy clones instead of full data copies for development and testing.

## Practice

The lens offers three access methods to suit different workflows and team preferences:

### 1. AWS Well-Architected Tool Console
Suitable for structured formal review. The steps are as follows:
1. Download the [Snowflake AWS Custom Lens JSON file](https://snowflake-corp-se-workshop.s3.us-west-1.amazonaws.com/AWS-Snowflake-Joint-WAF/Snowflake-WAF-Lens.json).
2. Sign in to the [AWS Well-Architected Tool console](https://console.aws.amazon.com/wellarchitected) and select **Custom lenses** in the navigation pane.
3. Select **Create custom lens**, upload the downloaded JSON file, and then select **Submit**.
This tool generates an improvement plan with priority actions and document links, and supports exporting to PDF/JSON for compliance reporting.

### 2. Kiro (AI-assisted IDE)
Ideal for conversational, AI-assisted reviews within the IDE. The steps are as follows:
1. Download [Snowflake WAF Power](https://snowflake-corp-se-workshop.s3.us-west-1.amazonaws.com/AWS-Snowflake-Joint-WAF/snowflake-WAF-powers.zip) and unzip it.
2. In Kiro, select **Open Folder** and select the unzipped folder.
3. Type “Run a Snowflake and AWS WAF review” into the chat to get started.
Its output contains recommendations and automated mapping categorized by time range (Now/Next/Later).

### 3. Snowflake Cortex Code
Allows reviews to be completed within the Snowflake ecosystem, offering both CLI and browser-based Snowsight options.
* **Option A (CLI)**:
    1. Download and unzip the [Cortex Code zip file](https://snowflake-corp-se-workshop.s3.us-west-1.amazonaws.com/AWS-Snowflake-Joint-WAF/joint-waf-aws-lens.zip).
    2. Run `cortex skill add <decompression path>` in the terminal to add skills.
    3. Start the `cortex` CLI and enter `invoke the joint-waf-aws-lens skill` to start.
* **Option B (Snowsight)**:
    1. In Snowsight, navigate to **Projects &gt; Workspaces** and open or create a workspace.
    2. Open the Cortex Code Assistant panel, select **+ Add context** &gt; **Upload Skill Folder(s)** and upload the skill folder.
    3. Enter `run the joint-waf skill` in the message box to start the review.

## SRE Key Points

This combined lens has immediate practical value for SRE teams, optimizing two separate platforms as one unified system.

* **Link to Reliability Design**: Lens’ Reliability pillar directly guides how SREs design disaster recovery, failover, and recovery objectives (RTO/RPO) across Snowflake and AWS. It prompted the SRE team to define a federated SLO, where the SLI needed to take into account both Snowflake's query performance and the availability of the AWS infrastructure.
* **Observability Integration**: Within the Operational Excellence pillar, Lens explicitly recommends integrating Snowflake monitoring data (e.g. query history, resource monitor alerts) into AWS native observability tools (e.g. CloudWatch, OpenSearch). This enables SREs to build a unified observability dashboard that correlates application performance (Snowflake) with infrastructure health (AWS).
* **Incident Response Automation**: SREs can leverage the guidance of Lens to build automated response workflows from Snowflake alerts (e.g., resource exhaustion, query failures) to AWS automated remediation mechanisms (e.g., Lambda functions, SNS notifications), reducing **TOIL**.
* **Automation and IaC Governance**: Lens emphasizes using IaC tools like Terraform to manage both AWS and Snowflake resources. This lays the foundation for SRE to implement **infrastructure as code**, version control and consistent deployment, and is a key step in realizing GitOps.
* **FinOps and Cost Predictability**: Cost pillars help SREs understand and optimize spend across both platforms, enabling more precise capacity planning and cost forecasting through integrated cost views and joint optimization strategies (such as Snowflake Autosuspend combined with AWS Spot Instances), a critical responsibility of the modern SRE.
* **Sustainability (GreenOps)**: As the first lens to include the sustainability pillar, it guides SREs to incorporate carbon footprint optimization into architectural decisions, such as selecting low-carbon regions and optimizing compute and storage efficiency, which expands the boundaries of SRE's traditional responsibilities for ensuring service reliability.

**Best Practices and Common Anti-Patterns**:
* **Best Practices**: Conduct first review using the Security and Reliability pillars as a starting point; leverage improvement plans to prioritize tasks across teams; export review results as evidence of compliance.
* **Common anti-patterns**:
    1. **Island optimization**: Only optimize Snowflake queries and ignore the selection of underlying EC2 instances, or only optimize S3 storage and ignore Snowflake's data life cycle policy.
    2. **Loose Credential Management**: Service account credentials are managed duplicately or inconsistently across Snowflake and AWS instead of using unified identity federation and Secrets Manager.
    3. **Monitoring fragmentation**: Relying on independent monitoring views of Snowflake and AWS, failing to establish a global view of associated faults, making it difficult to analyze the root cause of events.

**Related Indicators (SLI/SLO)**:
The evaluation results of this lens directly impact the SLI and SLO that defines the federated workload. For example, an end-to-end query latency SLO needs to cover the full path from the AWS network to the Snowflake compute. The SRE team should translate recommendations into measurable **reliability metrics** and **error budgeting strategies** based on lens findings.
