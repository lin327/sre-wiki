# Tempo & SQL Expressions: Instant Metrics Queries not Supported

## Overview

In Grafana's observability platform, users often need to combine data from different data sources for in-depth analysis. The SQL expression function allows users to use familiar SQL syntax for secondary processing of query results, which greatly enhances the flexibility of data exploration. However, when combined with metrics generated by the distributed tracing system Tempo (such as RED metrics extracted from traces), SRE engineers discovered a key limitation: **SQL expressions can only process range (Range) query results, but cannot handle instant (Instant) query results**. This directly affects the ability to conduct real-time and efficient analysis of tracking-derived indicators, and is an important technical detail to pay attention to when building a unified analysis pipeline.

## Core concepts

To understand this issue, you need to clarify the following key concepts:

1. **Frame (Frame) and Frame Type (Frame Type)**: In Grafana's data pipeline, data is transmitted in the format of "data frame" between the data source plug-in and the front-end visualization/conversion layer. Each data frame contains a `meta` object, where the `type` field (i.e. the frame type) is crucial metadata. It tells Grafana's downstream processing capabilities (such as the SQL expression engine) how to interpret and process this data, such as whether it is a time series (`timeseries-multi`), a table (`table`), or a numeric array (`numeric-multi`).

2. **SQL Expressions**: This is a data transformation function in Grafana. It allows users to write a SQL query (usually a `SELECT` statement) that calculates, aggregates or renames data frames returned by previous queries (such as Prometheus or Tempo metric queries) to generate new visual data. It relies on the input data frame having explicit `type` information in order to correctly build the context in which the SQL expression is executed.

3. **Instant query vs interval query**:
    * **Instant Query**: Query the value of a point in time (`now`) and return a single, instant data point. Often used in monitoring to obtain the current status.
    * **Range Query**: Query data within a time range and return a series of data points that change over time. Often used to draw charts.

The root cause of this problem is that when the Tempo data source returns the result frame of an instant query, the `meta.type` field of the frame is not set correctly (or is missing). The SQL expression engine therefore cannot recognize the structure of the input data, causing the conversion to fail. The community speculates that the type of the instant query result frame should be `numeric-multi`.

## Practice

In an actual Grafana dashboard or alerting rule, this problem manifests itself as a specific failure scenario:

* **Scenario**: The user creates a metric query based on Tempo tracking data (e.g., counts bad requests per second) and sets it to "Instant" mode (`Instant`).
* **Attempt to apply SQL expression**: The user then attempts to use a SQL expression to perform secondary processing on the results of this instant query, such as renaming fields or performing calculations with other metrics.
* **Result**: The SQL expression query failed, and the error message usually points to an unsupported data format or type. As shown in the screenshot in the issue, the debug information will clearly indicate that `frame.meta.type` is `undefined` or missing.

**Possible solutions**:
The fundamental fix for this problem needs to be done at the Tempo data source plugin or Grafana core framework level. Need to ensure that the instant indicator query result data frame generated by Tempo is correctly marked with its type (such as `numeric-multi`). As a temporary solution, SRE engineers can:
1. Avoid using SQL expressions directly for immediate query results.
2. Change the query to interval query mode, but this will lose the advantage of "immediacy".
3. Explicitly add type information to the data frame through additional transformation steps (such as a "reduce" transformation) before applying the SQL expression, but this may increase the complexity of the query chain.

## SRE Key Points

For SRE teams, understanding this limitation is critical to designing reliable monitoring and analytics pipelines:

* **Impact on Monitoring Strategies**: This issue prevents real-time, complex cross-data source analysis of key performance indicators (especially trace-based). For example, there is no way to conveniently compare an instant error rate metric with a statically configured threshold (perhaps obtained from another data source via a SQL expression) in the same panel. This can lead to alerts or compromises in dashboard design.

* **Observability Correlation**: SQL expressions are a powerful glue when building a unified pipeline from tracing to metrics. This flaw illustrates possible differences in toolchain maturity under different query modes (immediate vs interval). The SRE needs to test the compatibility of all necessary query patterns and transformation functions during the dashboard design phase.

* **Best Practices and Anti-Patterns**:
    * **Best Practice**: In critical dashboard or alert queries that involve SQL expression conversion, prioritize verifying that their query mode (range or immediate) is supported. Create both interval and instant query versions of key indicators for use in different scenarios.
    * **Common anti-pattern**: Assume that all query types pass through all data transformation layers seamlessly. In complex Grafana query chains, you should explicitly test whether the dataframe's metadata is complete.

* **Related Metrics (SLI/SLO)**: While SLI/SLO is not directly defined, this issue affects the **means** to implement and monitor these metrics. If the team's SLO definition needs to rely on real-time error budget calculations based on tracking real-time metrics, then this compatibility issue will become a blocker in implementing the SLO monitoring solution and needs to be considered during technology selection or solution design. It highlights the importance of validating the reliability of the observability toolchain itself.
