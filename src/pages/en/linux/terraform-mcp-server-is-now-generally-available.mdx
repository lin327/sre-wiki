# Terraform MCP server is now generally available

## Overview

Terraform MCP Server is a new feature from HashiCorp that connects AI assistants (such as GitHub Copilot, IBM Bob, Claude Code, etc.) directly to Terraform's Infrastructure as Code (IaC) workflows through the **Model Context Protocol (MCP)**. In SRE practice, this integration is critical because it frees engineers from repetitive operations, allowing them to focus on high-value reliability design and optimization, thereby accelerating infrastructure delivery and iteration while ensuring security. This feature is now generally available and supports both HCP Terraform (managed service) and Terraform Enterprise (self-hosted).

## Core Concepts

Understanding Terraform MCP Server hinges on the following core concepts:

1.  **Model Context Protocol (MCP)**: An open protocol designed to standardize how AI models interact with external tools and data sources. Terraform MCP Server, as a service conforming to this protocol, acts as a secure bridge between AI assistants and the Terraform ecosystem (such as private registries, workspaces, plan files).
2.  **AI-Assisted Workflows**: MCP Server enables AI assistants to understand and execute Terraform-related tasks. For example, AI can generate compliant HCL code based on an organization's module standards, explain complex `terraform plan` output, or query workspace state to answer operational questions, reducing manual operations and context switching.
3.  **Security Boundary**: A core principle of MCP Server design is "security by design." It serves as a controlled interface layer, ensuring AI assistants can only access the metadata and configuration information necessary to complete their tasks, and **never** touches underlying credentials or sensitive data. It inherits and enforces Terraform's own authentication and authorization mechanisms.
4.  **Private Registry Integration**: AI assistants can directly connect to an organization's internal Terraform module and provider private registries. This enables AI to discover and recommend organization-approved modules, ensuring generated code conforms to internal architectural patterns and policies, thereby achieving infrastructure consistency.

## Practice

Terraform MCP Server provides two main deployment modes to accommodate different team needs and security strategies:

1.  **Local Execution Mode**:
    *   **Scenario**: Suitable for individual developers doing rapid prototyping, local testing, or learning.
    *   **Implementation**: Run MCP Server on the developer's machine. All data processing and interaction occurs locally; data never leaves the development environment.
    *   **Advantages**: Fastest setup, highest privacy, suitable for individual development and debugging workflows.

2.  **Shared Service Mode**:
    *   **Scenario**: Suitable for team collaboration requiring centralized management and auditing.
    *   **Implementation**: Deploy MCP Server as a team-shared service (e.g., in a Kubernetes cluster or as a standalone microservice). Team members authenticate remotely via their individual Terraform tokens to access the service.
    *   **Advantages**: Facilitates centralized configuration, monitoring, and security policy management. All access is through individual tokens, maintaining clear individual accountability.

Regardless of which mode is adopted, MCP Server provides the following typical use cases:

*   **Generate Standards-Compliant Code**: Describe requirements to the AI assistant (e.g., "create a secure AWS S3 bucket"), and the AI will search the private registry for recommended modules and generate code conforming to organizational standards.
*   **Query Workspace State**: Query workspace information through natural language, such as: "list workspaces not updated in the past 90 days" or "show workspaces managing more than 1000 resources," without manually switching UI or executing CLI commands.
*   **Understand Plan Changes**: Hand `terraform plan` output to AI for analysis. AI can explain resource dependencies, change impacts, and potential risks in natural language, assisting code review and approval processes.
*   **Enhanced Observability**: MCP Server integrates OpenTelemetry, supporting monitoring and security auditing, and can collect request metrics and logs, facilitating SRE team monitoring and troubleshooting.

## SRE Key Points

Terraform MCP Server enhances and impacts SRE practice in multiple ways:

*   **Reliability, Observability, and Incident Response Association**:
    *   **Reliability**: By ensuring infrastructure code consistency and reducing human configuration errors, it directly improves infrastructure reliability. AI-assisted code generation and plan explanation help identify potential issues earlier before changes are made.
    *   **Observability**: MCP Server itself provides OpenTelemetry integration, making it an observable service. Simultaneously, by enabling AI to quickly obtain workspace state and historical change information, it indirectly enhances the team's awareness and insight into overall infrastructure status.
    *   **Incident Response**: During Incident Response, SRE can quickly query the Terraform configuration and dependencies of affected services through natural language, accelerating Root Cause Analysis (RCA) and recovery plan development.

*   **Best Practices and Common Anti-Patterns**:
    *   **Best Practices**:
        1.  **Follow the Principle of Least Privilege**: Configure MCP Server and AI assistants with the most granular permissions possible, only granting scope-limited tokens needed for specific tasks.
        2.  **Leverage Shared Service Mode**: For teams, prioritize shared service deployment to achieve centralized policy management and auditing.
        3.  **Integrate into CI/CD Pipelines**: Include AI-assisted generated code in existing Pull Request (PR) reviews and CI/CD pipelines ([[ci-cd-pipeline]]) for automated testing and policy checks.
        4.  **Combine with Policy as Code**: Use policy engines like Sentinel or OPA ([[policy-as-code]]) to enforce compliance checks after AI generates code or before applying plans.
    *   **Common Anti-Patterns**:
        1.  **Blindly Trusting AI Output**: Never skip human review and directly apply AI-generated or interpreted changes. AI may produce code that is incorrect or does not conform to the latest security policies.
        2.  **Using Shared High-Privilege Credentials**: Avoid configuring MCP Server with a long-lived credential that has global administrator permissions. Use short-lived, scope-limited tokens integrated with identity providers.
        3.  **Ignoring Monitoring and Logging**: Even when using MCP Server, its own health, request patterns, and potential errors must be monitored, just like any other critical internal service.

*   **Related Metrics (SLI/SLO/SLA)**:
    *   **SLI (Service Level Indicator)**: Monitor MCP Server availability (successful request ratio), latency (response time), and error rate.
    *   **SLO (Service Level Objective)**: Set reliability targets for MCP Server for internal teams, such as "monthly uptime at least 99.5%" or "95% of query response times < 500ms."
    *   **Impact**: While MCP Server itself does not directly produce user-facing SLAs, it indirectly supports business service SLA achievement by improving the quality and speed of infrastructure changes ([[slo-reliability-budget]]).
