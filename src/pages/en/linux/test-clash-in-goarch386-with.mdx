# Test clash in GOARCH=386 with

## Overview

This article analyzes a severe runtime error that appeared in a Go language application's (using Prometheus as an example) continuous integration (CI) testing: "found bad pointer in Go heap (incorrect use of unsafe or cgo?)." This error is specifically triggered under **32-bit architecture (GOARCH=386)**. It is a fatal error thrown by the Go runtime during garbage collection (GC) heap scanning when it discovers an illegal pointer pointing to an unallocated or invalid memory region, directly causing the process to crash. For SREs, such memory safety issues are critical factors affecting service reliability. They can lead to service unavailability, data corruption, or difficult-to-diagnose intermittent failures, especially in specific hardware architectures or mixed-language programming environments.

## Core Concepts

To deeply understand this error, the following core concepts need to be mastered:

1.  **Go heap and garbage collection**: Dynamically allocated memory in Go programs resides on the "heap." Go's garbage collector (GC) is responsible for automatically managing heap memory, reclaiming objects no longer in use. During GC work, it needs to traverse (scan) the entire heap to determine which objects are still referenced.
2.  **Illegal pointers**: During GC scanning, the runtime validates every pointer found in the heap. A valid pointer should point to an allocated, correctly-typed memory object. If a pointer points to an unallocated memory region (`unallocated span`), freed memory, or violates Go's memory type rules, it is considered an "illegal pointer."
3.  **GOARCH=386**: This is Go's compilation target architecture, representing 32-bit x86 architecture. 32-bit architecture has limited memory addressing space (typically max 4GB) and different constraints on pointer size (4 bytes) and integer arithmetic, which may cause code that works normally on 64-bit architecture to experience integer overflow, memory layout differences, and other issues on 32-bit.
4.  **unsafe package and cgo**: The error message explicitly points out possible root causes.
    - `unsafe`: Allows developers to perform unsafe memory operations (such as converting pointers to integers), bypassing Go's type system and memory safety guarantees. Improper use is a common cause of illegal pointers.
    - `cgo`: Allows Go code to call C code and C code to interact with Go's heap. When passing pointers between C and Go, if correct conventions are not followed (such as using `C.CString` or `runtime.Pinner`), it is easy to cause Go's runtime to lose track of or manage these external pointers, triggering crashes during GC.

## Practice

This section analyzes based on the provided Prometheus issue case.

**Problem scenario**:
In a Prometheus project Pull Request (#18598) CI test, when running the test suite with `GOARCH=386` (32-bit mode), the program crashed during the garbage collection phase. Key logs:
```
runtime: pointer 0x127c0781 to unallocated span span.base()=0xdcc4000 span.limit=0xdcc5e80 span.state=0
fatal error: found bad pointer in Go heap (incorrect use of unsafe or cgo?)
```
This clearly indicates that at heap address `0x127c0781`, there exists an illegal pointer whose target memory span has not been allocated to any Go object.

**Root cause analysis directions**:
1.  **Locate suspicious code**: Review recently changed code involving the `unsafe` package or `cgo` calls. Pay special attention to pointer type conversions, slice and array underlying operations, and interactions with C libraries.
2.  **Architecture-specific issues**: Since the error only appears on 32-bit architecture, focus on examining calculations related to pointer size and integer size. For example, using `int` or `uint` types to store pointer values differs in size between 32-bit and 64-bit platforms, potentially causing truncation or misinterpretation. Check if any code assumes pointer size matches machine word size.
3.  **Memory model violations**: In `cgo` scenarios, check if Go pointers are passed to C functions and during C function execution, Go's GC moved the objects pointed to (although Go typically pins pointers, improper use may still have issues). Or C code attempts to use memory already reclaimed by Go's GC after returning.

**Debugging suggestions**:
- **Reproduce**: Try reproducing locally with `GOARCH=386 go test ./...`.
- **Tools**: Use `go build -race` to enable race condition detection (though it may not catch this issue), or use lower-level memory analysis tools.
- **Minimal reproduction**: Associate the crash stack trace with specific test cases or source code lines, and try writing a minimal program using only `unsafe` and `cgo` to trigger the same error.

## SRE Key Points

- **Impact on reliability**: Such memory safety errors are among the highest severity failures. They cause processes to terminate immediately without opportunity for graceful shutdown, potentially interrupting request handling, causing data loss, and triggering automatic service restarts (e.g., by Kubernetes Liveness Probe), affecting **availability SLO**. Due to their relationship with GC and memory layout, they may manifest as difficult-to-reproduce "mysterious" failures, increasing MTTR (Mean Time to Recover).
- **Observability relationship**:
    - **Metrics**: Monitor process crash counts, restart counts. In Go applications, consider monitoring GC-related metrics like `go_memstats_gc_pause_total_ns`; abnormal GC pauses or frequency may be precursors to memory issues.
    - **Logs**: Such `fatal error` messages are printed to standard error. Ensure all Go services' stdout/stderr logs are centrally collected and alerted. The complete stack trace in logs is critical for diagnosis.
    - **Tracing**: Memory errors themselves are outside distributed tracing scope, but tracing can help locate the business logic code path being executed before the crash.
- **Best practices and anti-patterns**:
    - **Prevention**: Strictly review `unsafe` package usage with detailed comments. Prefer standard libraries or verified libraries that use `unsafe`. For `cgo`, use Go's officially recommended `Pinner` API (Go 1.21+) to safely pin pointers for C code use. **Adding `GOARCH=386` to the CI test matrix** is an effective means of discovering such architecture-related issues.
    - **Anti-patterns**: Blindly using `unsafe` for performance; mixing Go and C code without understanding Go's memory model; ignoring 32-bit platform support.
- **Related metrics (SLI/SLO/SLA)**:
    - **SLI**: Can define "process crash count due to memory safety errors" or "test case success rate on 32-bit architecture."
    - **SLO**: Should include such severe crash occurrence rates in the service's overall reliability target (e.g., "monthly crash count < 1").
    - **SLA**: This issue directly affects the availability level committed to customers.

**Next steps**: According to SRE's incident response process, this issue should be immediately associated with relevant code changes, the development lead notified, and after fix verification, ensure `GOARCH=386` tests in the CI pipeline pass stably, thereby closing this incident.
