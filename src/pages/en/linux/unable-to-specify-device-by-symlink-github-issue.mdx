# Unable to specify device by symlink (GitHub Issue)

## Overview
In containerized environments, secure and reliable delivery of host devices to containers is a common but critical need. Typically, we rely on udev-generated stable symbolic links (such as `/dev/serial/by-id/...`) to refer to physical devices to avoid inconsistencies in kernel device names (such as `/dev/ttyUSB0`) after reboots or device changes. This issue report reveals that containerd v2.0.0 has a flaw in handling such symbolic links, which not only prevents intended device mounting, but also introduces security risks that can be exploited maliciously, posing a challenge to SRE practices that rely on device transparent transmission.

## Core concepts
- **Device symbolic link**: A link to the actual device node under `/dev` generated by the udev subsystem based on the device's stable properties (such as serial number, port). Its core value is to provide a stable identity that does not change with the kernel device enumeration order.
- **Device path resolution**: The container runtime must resolve the incoming path to a real character device or block device node before mapping the host device path to the container internal path. This process requires checking the file type of the target path (using the `stat` system call and checking the `S_ISBLK` or `S_ISCHR` macro).
- **Security Impact**: When stable paths (symbolic links) are not available, SREs and developers may fall back to using dynamic kernel names. This can lead to a race condition: an attacker can pre-emptively insert a malicious device at system startup or device connection, thereby intercepting the device pointed to by the expected device symlink, performing a man-in-the-middle attack (MITM) or data tampering.

## Practice
According to the issue report, containerd fails with a "not a device node" error when trying to map a symlink path (such as `/dev/serial/by-id/usb-ITead_Sonoff_Zigbee_3.0_USB_Dongle_Plus_[...]`) to a fixed path within the container (such as `/dev/ttyUSB0`) via the `--device` parameter.

### Speculation on the root cause of the problem
The error message indicates that containerd may not obtain a standard device node after parsing the symbolic link path, or its checking logic may be defective. This may be due to containerd not properly resolving the final target of the symlink when trying the `stat` path, or its criteria for judging device nodes not matching the actual output of udev.

### Current Mitigation Measures (Temporary Solution)
Until an official fix is released, the SRE team can consider the following workarounds:
1. **Use `realpath` to resolve the path**: In the script or configuration that starts the container, first use the `realpath` command to resolve the symbolic link into an actual device path (such as `/dev/ttyUSB0`), and then pass the actual path to the container. But this partially or completely gives up the stability benefits of symbolic links.
2. **Rely on udev rules for fixed device names**: By writing custom udev rules, create a fixed device node name based on the unique attributes of the device (such as `ATTRS{idVendor}`, `ATTRS{idProduct}`) instead of relying on the automatically generated `by-id` link.
3. **Version rollback**: If compatibility allows, temporarily roll back to the old containerd version that does not have this problem.

## SRE Key Points
- **Reliability Correlation**: Device management is fundamental to the reliable operation of many stateful or hardware-dependent applications (such as IoT gateways, industrial controls, database physical backups). The failure of symbolic links breaks the "infrastructure as code" stability assumption that SRE pursues, making device mapping unpredictable and brittle.
- **Security and Observability**: This issue highlights the importance of predictability of container runtime behavior. A runtime that does not correctly handle standard device identification methods can render its device mounting policy opaque, increasing configuration drift and attack surface. SREs need to incorporate the correctness of device mounts into health checks and observability metrics.
- **Best Practices**:
    - **Clarity Principle**: In documentation and automation scripts, clearly state how device paths are resolved (whether using symbolic links or direct node paths).
    - **Defensive configuration**: In the container orchestration layer (such as Kubernetes Device Plugin), implement device detection and verification mechanisms to ensure that the requested device path is valid and unique.
    - **Security hardening**: For security-sensitive devices, when possible, give priority to using a stable path based on the device's unique hardware ID for binding, and strictly control access to the `/dev` directory.
- **Relevant Indicators (SLI/SLO)**:
    - **SLI**: Device mounting success rate (the proportion of successfully mounting requested devices during the container startup phase).
    - **SLO**: Achieve 99.9% first-time device mount success rate. When this SLI drops, it may indicate a problem with the underlying container runtime or device management subsystem.
