# Interview with Compose

## Overview

Compose is a company providing production-grade database cluster services for developers, operating across multiple cloud platforms and regions. As business grew, its monitoring system faced dual challenges of performance and reliability. After trying Graphite and InfluxDB, Compose chose to migrate to Prometheus, ultimately achieving a more reliable, more manageable monitoring system with high scalability potential. This article is based on Prometheus's official blog interview with Compose, detailing the evolution and migration practices of its monitoring system, providing valuable reference for SRE teams when selecting and migrating monitoring infrastructure.

## Core Concepts

In Compose's case, several key concepts are crucial for understanding their migration decisions and architecture:

- **Pull-based metric collection**: One of Prometheus's core paradigms. The monitoring server actively scrapes metric data from target endpoints, rather than applications pushing data. This simplifies application configuration and makes the monitoring infrastructure's topology easier to understand and manage. Compose was initially confused by this but quickly recognized its advantages.
- **Telegraf aggregation**: To optimize monitoring in highly containerized environments, Compose used Telegraf as a metric aggregation agent. Telegraf on each host is responsible for collecting metrics from the host itself and all containers running on it, exposing them uniformly as a single Prometheus scrape target. This greatly reduces the number of scrape targets Prometheus needs to manage.
- **File-based service discovery (file_sd_config)**: Prometheus's dynamic service discovery mechanism. Compose wrote a Ruby script that fetches all host lists through the Chef API and writes them to configuration files. Prometheus then automatically discovers and scrapes these newly added or changed hosts through the `file_sd_config` mechanism, achieving seamless integration with configuration management tools.
- **High Availability (HA) and failover**: To eliminate single points of failure, Compose adopted an active-active redundant architecture. Two identical Prometheus instances scrape the same targets, with simple failover achieved through Keepalived combined with DNS updates. This was more reliable than the InfluxDB cluster they previously used.

## Practice

Compose's migration was carried out step by step with incremental validation, demonstrating how to implement a mature monitoring philosophy in a complex production environment.

### 1. Initial Deployment and Dynamic Discovery
As a Chef-proficient company, they first used the community Chef Cookbook to quickly deploy a Prometheus instance with large-capacity EBS storage. Then, they wrote a small Ruby script that used the Chef API to fetch all host information and dynamically generate Prometheus target configuration files. By configuring `file_sd_config`, Prometheus could automatically discover and start scraping all hosts registered to Chef, without manually maintaining static target lists.

### 2. Using Telegraf to Solve Container Monitoring
Each host runs hundreds of containers, making it impractical to individually configure scrape targets for each container. Compose's strategy was to deploy Telegraf on each host. Telegraf was configured to export the host's overall resource metrics and memory usage metrics for all containers. Ultimately, Prometheus only needed to scrape a single Telegraf endpoint on each host to obtain all necessary data, resulting in a simple and efficient architecture.

### 3. Validating Single-Instance Scalability
Before formal switching, they intentionally let a single Prometheus instance bear the entire infrastructure load for stress testing. Surprisingly, this `m4.xlarge` instance with a 15-second scrape interval stably monitored approximately 450 hosts and 40,000 containers producing over 400,000 distinct metrics, with low resource consumption. Disk I/O (1TB gp2 EBS) was considered the long-term potential bottleneck. This validation gave the team tremendous confidence.

### 4. Implementing High Availability and Switching Traffic
After confirming that Prometheus's stability and performance far exceeded the original InfluxDB cluster, they added a second identical Prometheus instance scraping the same target set. Through Keepalived and DNS updates, they implemented active-standby failover, building a more reliable HA architecture than before. Subsequently, they switched their customer-facing charting system to the Prometheus data source and decommissioned the old monitoring system.

## SRE Key Points

From an SRE perspective examining Compose's case, the following key experiences and practices can be distilled:

- **Reliability improvement**: Migrating from InfluxDB (which had data corruption risks and required regular cleanup) to the more stable Prometheus represented a qualitative leap in the monitoring system's own reliability. The dual-instance HA architecture further ensures monitoring data continuity, which is critical for SRE teams that rely on monitoring for incident judgment and decision-making.
- **Enhanced observability**: The migration not only solved stability issues but also opened the door to enhancing system observability. Compose plans to integrate database internal metrics and Mesos cluster component metrics in the future, aiming to build a centralized panoramic dashboard from load balancers to application metrics. This reflects the monitoring evolution from "can see" to "see the full picture."
- **Incident response and team culture**: A stable and reliable monitoring system can boost team confidence. Compose mentioned that team members went from "cautiously dealing with the old system" to "excitedly exploring new uses." This positive cultural shift directly benefits rapid incident discovery, diagnosis, and post-mortem.
- **Best practices**:
    - **Small-scale validation, gradual expansion**: First validate core functionality and performance with a single instance, then consider HA and sharding after confirming viability.
    - **Use aggregation to reduce complexity**: Aggregating all container metrics on a host through agents like Telegraf is an efficient pattern for large-scale container environments.
    - **Integrate with existing toolchains**: Using Chef and `file_sd_config` for automated discovery reduces configuration drift and operational burden.
- **Common anti-patterns and avoidance**: Compose's experience warns us that when choosing monitoring tools, we cannot focus only on feature promises but must value long-term stability and operational costs. They migrated due to InfluxDB's instability and unfulfilled feature promises, which is a typical anti-pattern case.
- **Related metrics**: The scale and effectiveness of this migration can be demonstrated through specific metrics: monitoring targets went from unstable to stably handled by a single instance carrying **450 hosts**, **40,000 containers**, and **400,000+ distinct metrics**; scrape frequency is **15 seconds**; hardware cost is controlled at **a single m4.xlarge instance plus 1TB EBS**. These quantified data provide important reference for evaluating Prometheus's performance capacity.

Looking ahead, the SRE work Compose needs to plan is Prometheus sharding. They plan to deploy independent Prometheus instances per cluster and may retain a global cluster, using **[[Recording-Rules]]** for downsampled aggregated metrics from each cluster for long-term storage and cross-cluster querying, balancing query flexibility with system scalability.
