## Overview

In containerd, Snapshotters are responsible for creating and managing the file system layer for containers. To optimize performance and cost, production environments often use a mix of local snappers (such as `native`) and remote snappers (such as `overlayfs` or cloud storage-based snappers). This document describes a critical bug fix: when the CRI (Container Runtime Interface) plugin processes images in a mixed snapper environment, it may encounter unpack failures, causing the container to fail to start. This fix significantly improves the reliability of container deployment under hybrid architecture by forcing a re-pull to ensure that the required underlying content blobs are correctly obtained.

## Core concepts

- **Snapshotters**: A plug-in in Containerd used to manage the container file system layer (usually corresponding to each layer of the container image). They determine where and how the file system layer is stored. Mixing snappers means that different layers of the image may be distributed on local disk and remote storage.
- **CRI (Container Runtime Interface)**: The standardized container runtime interface defined by Kubernetes, containerd integrates with this interface through its CRI plug-in.
- **Image Unpacking**: Before the container is started, the pulled image data (usually a compressed package) needs to be decompressed and combined into a file system layer readable by the container. This process relies on snappers.
- **Content Blobs**: The actual data objects that make up the mirroring layer are stored in the content-addressable store.
- **Root Cause**: This issue (issue #12752) is that when the CRI plug-in tries to unpack an image whose layers are partly managed by the local snapper and partly by the remote snapper, it fails to correctly obtain all necessary content blobs for some reason, causing the unpacking process to fail and ultimately the container cannot start.

## Practice

The core logic of this fix (PR #12753) is to adjust the recovery strategy of the CRI plug-in when encountering unpacking failure.

1. **APPLY PATCH**: Make sure your containerd version includes this fix (build based on PR #12637). This usually means updating to a version that contains this commit (for example, a stable or nightly version since 2026-01-07).
2. **Verification Fix**: In an environment configured with mixed snappers (e.g., `io.containerd.snapshotter.v1.overlayfs` for the system layer and `io.containerd.snapshotter.v1.native` for the application layer), simulate pulling an image whose layers are managed by both snappers. Before the repair, this operation may report an error during the unpacking phase; after the repair, containerd will automatically trigger a re-pull to obtain the required blobs from the registry again to complete the unpacking.
3. **Monitoring**: Although this fix handles failures automatically, you should keep an eye on the `containerd` and `CRI` logs to ensure that the "re-pull" and subsequent unpacking completes successfully. Relevant success indicators should return to baseline levels.

## SRE Key Points

- **Reliability and Incident Response**: This fix directly addresses a root cause of container deployment failures and improves the overall reliability of the platform under complex hybrid storage architectures. In incident response, if you observe pod startup failures due to "unpack failure", especially in a mixed snapper environment, you should prioritize upgrading to a containerd version that contains this fix.
- **Observability**: After the repair, although the operation automatically resumes, by increasing the monitoring of the unpacking process duration and the number of retries (such as using the metrics of `containerd`), potential storage or network problems can be discovered earlier to avoid triggering automatic retries.
- **Best Practices and Anti-Patterns**:
    - **Best Practice**: When adopting a hybrid snapper architecture, always ensure that the containerd version supports and has verified such fixes. Regularly updating runtime components is key to preventing such platform-level failures.
    - **Anti-Pattern**: Ignoring containerd's version management and patch application may cause the deployment pipeline to fail intermittently and be difficult to troubleshoot.
- **Related indicators**:
    - **SLI (Service Level Indicator)**: The **success rate** and **latency** of the container image from pulling to unpacking. This fix aims to improve the former.
    - **SLO (Service Level Objective)**: Ensure that the success rate of containers started through CRI is higher than 99.9% when their images are ready.
    - **Error Budget**: The error budget associated with this success rate. Failures due to "unpack failure" consume this budget, and a fix should significantly reduce this consumption.
