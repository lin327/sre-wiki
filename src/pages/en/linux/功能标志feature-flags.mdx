## Overview

Feature Flags are a technology that dynamically enables or disables specific features or code paths without modifying application code or deployment branches. In SRE practice, feature flags are a key tool for achieving **incremental delivery** and **controlled experimentation**. It allows teams to conduct small-scale testing, grayscale release, or A/B testing of new features, performance optimizations, or behavioral changes while maintaining the stability of the core system, thereby effectively managing change risks and collecting feedback from real production environments. Prometheus introduced this mechanism starting from v2.25.0 to manage its "disabled features" list, embodying the SRE principle of striking a balance between reliability and innovation.

## Core concepts

In the context of Prometheus, feature flags are implemented in the following ways:

1. **Disabled Features**: Prometheus maintains a list of features, which are disabled by default. These features are generally considered **experimental**.
2. **`--enable-feature` startup parameter**: Users need to explicitly pass this parameter when starting Prometheus, followed by the feature name, to enable specific experimental features. For example: `--enable-feature=exemplar-storage`.
3. **Experimental Features**: All features enabled through this mechanism come with the following statements and notes:
    * **API Possible Changes**: If this feature involves a Web API or code interface, its specifications may change in future releases.
    * **Behavior may change**: The operating logic and effects of the function may be different from the current version.
    * **May break existing assumptions**: For example, the `@` modifier and the negative offset function break the original assumption that the query will not find samples before the evaluation time point.
    * **Stability Not Guaranteed**: Although every effort will be made to maintain its stability, experimental features themselves may have instability factors.

The core idea of ​​this mechanism is to isolate features from the default stable release until they reach sufficient maturity and widespread use.

## Practice

For Prometheus users or administrators, the practice of using feature flags is as follows:

1. **Follow version updates**: When each new version of Prometheus is released, check the updated "Disabled Features" list in the official documentation to learn about the new experimental features.
2. **Careful evaluation and testing**: In a development or test environment, selectively enable experimental features of interest and evaluate their impact on existing monitoring data, alert rules, and dashboards.
3. **Explicit enablement**: If you decide to use it in a certain environment, you need to add the `--enable-feature=<feature_name>` parameter to the startup command of the Prometheus service (such as systemd unit file or container startup parameters).
4. **Expectation Management**: Fully recognize the experimental nature of the features being enabled, be prepared for potential changes to the API or behavior, and avoid making permanent, critical assumptions about the behavior of these features.
5. **Feedback and Removal**: Participate in community feedback to help evaluate whether the feature deserves to be made a default feature. Experimental features that are no longer needed or prove problematic can be disabled at any time by removing the launch parameters.

## SRE Key Points

### Association with reliability, observability, incident response
* **Support Reliability Objectives (SLO)**: Feature flags are an important means of managing change risks and help avoid availability or performance events that affect SLI caused by hasty rollout of new features. Through small-scale experiments, you can verify the value of the feature without violating the SLO.
* **Enhanced Observability**: You can use feature flags to conduct A/B testing of new monitoring indicators or tracking functions to compare their effects and costs, thereby making a more scientific decision whether to enable them globally.
* **Auxiliary Incident Response**: In a complex failure, if it is suspected to be related to a newly enabled experimental feature, you can quickly disable it by restarting the service (removing the `--enable-feature` parameter) as one of the mitigation measures.

### Best practices and common anti-patterns
* **Best Practice**:
    * **Documentation**: Record the enabled function flags and their expected effects in the operation and maintenance manual or configuration management library.
    * **Monitoring experiment impact**: After enabling new functions, closely monitor the performance indicators and error logs of relevant systems and set up special alarms.
    * **Lifecycle Management**: Regularly review enabled experimental features and decide whether to upgrade them to default features, continue the experiment, or remove them completely.
    * **Progressive rollout**: Follow a progressive enablement path from small scale (such as canary instances) to production environments.
* **Common anti-patterns**:
    * **Blindly enabled in production**: Enable experimental features on critical production instances without testing.
    * **Assume permanent availability**: Build critical automation processes based on experimental feature APIs or behaviors, ignoring the possibility of future changes.
    * **"Enable and forget"**: Lack of follow-up tracking and evaluation after enabling a feature, leading to accumulation of technical debt.

### Related indicators (SLI/SLO/SLA)
Feature flags are not SLI per se, but they are an important process tool for managing changes that impact SLI/SLO. Its use effect can be indirectly evaluated through the following aspects:
* **Change failure rate**: Compare the number of failures or rollbacks caused by changes with and without feature flags.
* **Mean Time to Recovery (MTTR)**: Improve failure recovery time by quickly disabling problematic features.
* **Feature Release Cycle**: Measures how often the team leverages feature flags to safely accelerate the release of new features.
