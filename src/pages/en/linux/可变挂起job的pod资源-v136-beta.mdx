## Overview

In Kubernetes v1.36, an optimization feature for `Job` resources has entered the beta stage, which allows modification of resource requests (requests) and limits (limits) in the Pod template of a Job in a suspended (`suspend: true`) state. This feature greatly enhances the scheduling flexibility of workloads such as batch processing and machine learning (ML) in dynamic cluster environments, allowing queue controllers (such as [Kueue](https://kueue.sigs.k8s.io/)) or administrators to optimize resource allocation based on the current cluster capacity, priority, and hardware (such as GPU) availability before the task is actually run, thereby improving the overall cluster resource utilization and job throughput.

## Core concepts

This feature involves the following key concepts:

- **Suspend status of Job**: When the `spec.suspend` field of a Job is set to `true`, the Job will not create new Pods to perform work, and already running Pods will be terminated. It is in a "waiting" state, usually managed by an external controller such as a queue manager.
- **Pod template resources**: defined in the `resources.requests` and `resources.limits` fields in `spec.template.spec.containers` and `spec.initContainers` of Job. These fields are traditionally immutable after the Job is created.
- **Queue Controller**: In the Kubernetes ecosystem, a controller (such as Kueue) specifically used to manage batch job queues. It is responsible for deciding the scheduling order and resource allocation of jobs based on cluster resources and policies. This feature provides critical flexibility to queue controllers.
- **Feature Gate**: `MutablePodResourcesForSuspendedJobs`. It is enabled by default in v1.36 and needs to be enabled manually in v1.35.

## Practice

### Function usage process

1. **Create a suspended Job**: First create a Job with `spec.suspend: true`, whose initial resource requirements are defined in its Pod template.
2. **Modify Resources**: While a Job is in a pending state and meets the conditions (see below), it is safe to update resource fields in its Pod template. This can be done via `kubectl edit`, `kubectl patch` or via API calls directly from the controller.
3. **Resume Job**: Set the Job's `spec.suspend` to `false`, and Kubernetes will use the updated resource configuration to create and run the Pod.

**Example YAML (Initial Configuration)**:
```yaml
apiVersion: batch/v1
Kind: Job
metadata:
  name: training-job-example-abcd123
  labels:
    app.kubernetes.io/name: trainer
spec:
  suspend: true #Key: Job is in suspended state
  template:
    spec:
      containers:
      - name: trainer
        image: example-registry.example.com/training:2026-04-23T150405.678
        resources:
          requests:
            cpu: "8"
            memory: "32Gi"
            example-hardware-vendor.com/gpu: "4"
          limits:
            cpu: "8"
            memory: "32Gi"
            example-hardware-vendor.com/gpu: "4"
      restartPolicy: Never
```

**After resource modification**: Assuming that the queue controller finds that only 2 GPUs are available in the cluster, it modifies the job's resource request to:
```yaml
        resources:
          requests:
            cpu: "4"
            memory: "16Gi"
            example-hardware-vendor.com/gpu: "2" # Reduce the number of GPUs
          limits:
            cpu: "4"
            memory: "16Gi"
            example-hardware-vendor.com/gpu: "2"
```

**Example of using kubectl operation**:
```bash
#Create pending Job
kubectl apply -f my-job.yaml --server-side

# Edit resource request
kubectl edit job training-job-example-abcd123

#Restore the job and use the modified resources
kubectl patch job training-job-example-abcd123 -p '{"spec":{"suspend":false}}'
```

### Conditions for allowing modification

The API Server only accepts updates to Job Pod template resources when the following conditions are met:
1. Job’s `spec.suspend` value is `true`.
2. If the Job has run before, all currently active Pods must have been completely terminated (`status.active` equals 0). This ensures that no inconsistencies arise between running Pods and templates.

### Modifiable field range

Modifications are limited to resource fields in the following Pod templates:
- `spec.template.spec.containers[*].resources.requests`
- `spec.template.spec.containers[*].resources.limits`
- `spec.template.spec.initContainers[*].resources.requests`
- `spec.template.spec.initContainers[*].resources.limits`

Standard resource validation rules (e.g. `limits` must be greater than or equal to `requests`) still apply.

## SRE Key Points

### Association with reliability and incident response

This feature directly improves the reliability and completion rate (throughput) of batch jobs by avoiding job failures or delays due to insufficient resources. In an incident response scenario, an SRE or platform engineer can quickly intervene to adjust resource quotas for critical jobs that are suspended due to resource contention so that they can run, rather than passively deleting and rebuilding jobs (which results in loss of state and history). This enhances the system's flexibility and operability under pressure.

### Best practices and common anti-patterns

**Best Practice**:
1. **Integration with queue systems**: Use this feature in conjunction with job queue managers such as Kueue to achieve automated, dynamic adjustment of resources based on cluster status.
2. **Set Pod Replacement Policy**: For jobs that may fail, it is recommended to set `podReplacementPolicy: Failed`. This ensures that the replacement Pod is created after the previous Pod has completely terminated, avoiding resource contention due to overlapping runs.
3. **Monitor resource changes**: Record the modification operations on Job resources to facilitate auditing and troubleshooting.

**Common anti-patterns**:
1. **Attempt to modify the resources of a running Job**: Attempting to modify resource fields when `suspend: false` or when there is an active Pod will cause the API Server to reject the request.
2. **Ignore resource validation rules**: Setting unreasonable `limits < requests` or non-integer extended resources will still cause the operation to fail.
3. **Confusing ResourceClaim**: This feature does not apply to dynamic resource allocation (DRA) `resourceClaimTemplates`, which are still immutable.

### Related indicators (SLI/SLO/SLA)

- **SLI (Service Level Indicator)**: You can pay attention to the **completion time** of `Job` from `Created` to `Succeeded`, especially the improvement in the scenario of dynamic resource adjustment. You can also monitor the `Job` **failure rate or retry rate** caused by insufficient resources.
- **SLO (Service Level Objective)**: For the batch processing services provided by the platform, you can set SLO, such as "95% of batch processing jobs obtain resources and start running within 5 minutes after being suspended." This feature helps to achieve this goal.
- **SLA (Service Level Agreement)**: The SLA for upper-level services (such as ML training platform) may include the on-time delivery rate of model training tasks. More flexible resource scheduling is the key technical foundation to support this SLA.
