## Overview
Amazon Cognito provides powerful user authentication and management functions, but when facing a large number of users (such as thousands of accounts), its built-in `ListUsers` API may not be able to meet the needs in advanced search scenarios (such as fuzzy matching, complex filtering across multiple custom attributes, sub-second response). This solution aims to solve this problem by building an independent search layer, which can achieve real-time data synchronization and high-performance query, which is crucial for SRE to quickly locate users, perform troubleshooting, or support the team to respond to work orders.

## Core concepts
The architecture is an event-driven CQRS (Command Query Responsibility Separation) model that decouples data writing and querying through two data streams (ingestion and search).
1. **Data Intake Stream**: Responsible for synchronizing user changes in Cognito to the search index in real time. It is triggered via two mechanisms:
    * **Cognito Lambda trigger**: Capture user data at key nodes in the user authentication process (such as `PostConfirmation` after registration and `PreTokenGeneration` before each login) and write it to DynamoDB.
    * **AWS CloudTrail and EventBridge**: Capture administrator operations (such as creating users, updating properties) performed through the console or CLI that do not trigger Lambda triggers. EventBridge rules listen for these API calls, triggering Lambda functions to read the latest user status and update DynamoDB.
2. **Search flow**: Provides a high-performance query interface. Authenticated users submit query requests through API Gateway, and the requests are forwarded to [[amazon-opensearch-service]] via the Lambda function to perform searches, and finally formatted results are returned to the front end.

DynamoDB serves as the authoritative record store for user data and source of change events (via DynamoDB Streams), while OpenSearch Serverless provides powerful full-text search and filtering capabilities.

## Practice
Here are the detailed steps and key design points for building this search layer:

### 1. Data synchronization and indexing
* **Create DynamoDB user table**: Stores a canonical copy of the user profile, including fields such as `cognitoUserId` (partition key), `email`, `lastName`, `groups`, `lastLoginTime`, etc. Enable DynamoDB Streams to capture all data changes.
* **Deploy Cognito trigger Lambda**:
    * Handle the `PostConfirmation` event: Create an initial record in the DynamoDB table when a user first registers.
    * Handle the `PreTokenGeneration` event: update `lastLoginTime` and the used `appClientId` every time the user logs in.
    * **Important**: This Lambda is deployed within a VPC, and Cognito forces its execution to take no longer than 5 seconds. Make sure its logic is efficient or use provisioned concurrency to avoid cold start delays.
* **Configuring CloudTrail and EventBridge**:
    * Enable CloudTrail to log Cognito's management plane API calls.
    * Create an EventBridge rule to match events with `source: ["aws.cognito-idp"]` and target another Lambda function.
    * After the Lambda function receives the event, it uses the Cognito Admin API to get the latest user attributes and writes them to the DynamoDB table (overwriting or creating a record).
* **Build index pipeline**:
    * Configure an event source mapping for DynamoDB streams to trigger `OSS-ingest-lambda`.
    * `OSS-ingest-lambda` parses streaming events (INSERT/MODIFY), extracts new/old image data from DynamoDB event records, and then updates the data into an OpenSearch Serverless index using the OpenSearch client.

### 2. Build search API
* **Configure OpenSearch Serverless**: Create a collection and index, define appropriate mappings for user data fields (e.g. `email`, `lastName`, `groups`) (e.g. enable tokenizer for `email` to support prefix matching).
* **Deploy Search Lambda**:
    * JWT validation via API Gateway's Cognito authorizer.
    * This Lambda function receives query parameters (such as `q`, `filterGroups`) and builds an OpenSearch DSL query.
    * Use an AWS IAM role (with read-only permissions) to connect to OpenSearch Serverless and execute queries.
    * Handle pagination (`from` and `size`) and format the results back.
* **Create API Gateway**: Configure the REST API to route search requests to the search Lambda function.

## SRE Key Points
* **Relationship with reliability and observability**:
    * **Latency vs. Availability**: The search performance of this architecture (SLO: such as 99% query latency &lt;200ms) directly depends on the performance of OpenSearch Serverless and the cold start status of the search Lambda. **Provisioned Concurrency** should be enabled for Lambda to ensure low latency on the search side. Latency in the data ingestion path (visible from Cognito events to OpenSearch indexes) is another critical SLO.
    * **Data Consistency**: The event-driven nature of the ingestion pipeline means that the data is eventually consistent. The SRE needs to monitor DynamoDB Streams for latency and failure events, as well as Lambda execution failure rates to ensure that the search index remains in sync with the Cognito source data.
* **Best Practices and Common Anti-Patterns**:
    * **Best Practice**: Create separate minimal-privilege IAM roles for the Cognito trigger lambda and the search lambda. Use exponential backoff retries to handle OpenSearch's `429` errors. Enable automatic backups for DynamoDB tables and OpenSearch indexes.
    * **Common anti-pattern**: Do not perform time-consuming operations (such as complex external API calls) in the `PreTokenGeneration` trigger, which will cause authentication timeout. Avoid having index pipelines that depend on DynamoDB Streams for a single region to prevent regional service outages.
* **Related indicators (SLI/SLO/SLA)**:
    * **Ingestion SLI**: End-to-end latency from when a Cognito event occurs until user data is searchable in OpenSearch.
    * **Ingestion reliability**: DynamoDB stream processing failure rate, Lambda function error rate.
    * **Search SLI**: Search API request latency (P90, P99), success rate, query throughput.
    * **Search Accuracy**: The rate at which business-critical queries (such as find by email prefix) return expected results.

By decoupling search capabilities from the core authentication service, this architecture provides SRE and operations teams with a reliable, high-performance tool for quickly retrieving and troubleshooting user account-related issues.
