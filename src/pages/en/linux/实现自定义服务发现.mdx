# Implementing Custom Service Discovery

## Overview

Service discovery is a critical component in the observability stack, dynamically providing monitoring systems (like Prometheus) with lists of targets to scrape. Although Prometheus provides many built-in service discovery (SD) integrations (such as Kubernetes, Consul), maintaining direct integrations for every possible SD system is impractical. **Custom Service Discovery**, through an Adapter pattern, allows SRE teams to create integrations for any internal or external service directory without modifying the Prometheus core binary. This is crucial for monitoring non-standard infrastructure or legacy systems and is an important practice for ensuring monitoring coverage and system reliability.

## Core Concepts

### Adapter Pattern and the Discoverer Interface
The core of custom SD implementation is the `adapter`. It leverages Prometheus's internal `discovery.Manager` to start a custom discovery Provider. All you need to do is implement the `Discoverer` interface defined by Prometheus. This interface is very simple, requiring only a `Run` function that accepts a `context` for cancellation and a channel for sending TargetGroup updates. Your implementation periodically queries the latest target list from the service directory (e.g., a custom HTTP API, database, etc.) and sends the results as `targetgroup.Group` structs to that channel.

### How the Adapter Works
The adapter acts as a bridge between custom discovery logic and Prometheus. It receives updates from the `Discoverer` interface channel, converts Prometheus's internal `targetgroup.Group` structure into JSON files compatible with the `file_sd` format. The key point is: the adapter compares old and new target lists and only writes to the file when changes occur. This design means your custom SD implementation should send updates representing **all targets** it currently knows about, with the adapter responsible for incremental file updates.

### file_sd Configuration
The final integration relies on Prometheus's file-based service discovery (`file_sd_configs`) mechanism. Prometheus is configured to periodically read the JSON files generated by the adapter to obtain targets to scrape. This decoupled approach allows custom discovery logic to be developed, tested, and deployed independently.

## Practice

### Step 1: Implement the Discoverer Interface
You need to write a program implementing the `discovery.Discoverer` interface. The core is implementing the `Run` method. In this method, you can use any means (e.g., HTTP calls, reading configuration files, querying databases) to obtain the target list.

**Key Implementation Logic Example (based on the provided Consul example):**
```go
func (d *consulDiscoverer) Run(ctx context.Context, up chan<- []*targetgroup.Group) {
    ticker := time.NewTicker(d.interval)
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            // 1. Query all services
            services, err := d.client.Services()
            if err != nil { /* Handle error, preferably use complete list */ continue }
            // 2. Query all instances for each service
            var tgs []*targetgroup.Group
            for _, s := range services {
                nodes, err := d.client.Service(s, "")
                if err != nil {
                    // Log error but continue processing other services, avoiding discarding all updates due to a single service failure
                    log.Error("Failed to query service", "service", s, "err", err)
                    continue
                }
                tg := d.parseServiceNodes(s, nodes)
                tgs = append(tgs, tg)
            }
            // 3. Send update if all information (or at least some) was successfully obtained
            up <- tgs
        }
    }
}
```

### Step 2: Start the Service Using the Adapter
In your `main.go`, you need to import Prometheus's adapter package and use it to wrap your `Discoverer` implementation. The adapter is responsible for starting the Manager and your discovery loop, and defining the output JSON file path.

### Step 3: Configure Prometheus
In Prometheus's configuration file, use `file_sd_configs` to read the JSON files generated by the adapter.

```yaml
scrape_configs:
  - job_name: "custom-sd"
    scrape_interval: "15s"
    file_sd_configs:
      - files:
          - /path/to/generated/targets.json
```

### Step 4: Run
Deploy your custom SD executable and Prometheus on the same host or container (e.g., via Docker Compose), ensuring correct file path permissions. Your program is responsible for keeping the `targets.json` file updated.

## SRE Key Points

- **Reliability and Observability**: Custom service discovery directly relates to monitoring **completeness**. If the discovery mechanism fails or is inaccurate, metrics for critical services may be lost, creating blind spots and affecting incident response. Ensure your implementation has robust error handling and retry mechanisms.
- **Error Handling Strategy**: Follow the wisdom in the example -- "better to temporarily use a stale but complete target list than to send an incomplete list". This avoids massive target list flapping caused by transient network issues or individual service query timeouts, maintaining alert stability.
- **Best Practices**:
    - **Independent Deployment and Updates**: Deploy and version-manage the custom SD program separately from Prometheus, facilitating independent iteration and troubleshooting.
    - **Complete Updates**: Each update sent to the channel should contain all known targets, with the adapter handling diff comparison with file contents.
    - **Configuration Management**: Manage your discovery program's own configuration (such as Consul address, polling interval) using configuration files or environment variables.
- **Anti-Pattern**: Do not frequently send incomplete or partial updates to Prometheus, as this causes target list instability. Also avoid coupling the business complexity of custom discovery logic with the Prometheus process.
- **Related Metrics**: Your custom SD program itself should also be monitored. You can expose a simple health check endpoint or metrics (such as last successful discovery time, error count) for Prometheus or other monitoring systems to scrape, forming a monitoring closed loop.
- **Related Pages**: This practice is an advanced application of [[file-based-service-discovery]]. Understanding the target model in [[prometheus-overview]] helps better design your `targetgroup.Group` structure. For service mesh environments, this may be an alternative or complementary approach.
