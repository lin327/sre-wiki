## Overview

In container-as-a-service (CaaS) and Kubernetes environments, reliable pulling of container images is a prerequisite for successful deployment and automatic scaling of workloads. However, the image pulling process may cause temporary byte transmission stagnation due to network fluctuations, image warehouse throttling, or fragmented download mechanisms. This knowledge page documents a key fix for containerd, which resolves an issue where the `transferProgressReporter` in the CRI plugin would incorrectly assume that the transfer was stalled and trigger a timeout when it detected an image download progress report event (but with a byte increment of zero). This problem may cause healthy image pull tasks to be unexpectedly interrupted in a production environment. It is a typical failure that SREs need to understand and prevent.

## Core concepts

1. **`transferProgressReporter`**: This is the core component in the containerd CRI plugin for monitoring and reporting image transfer progress. It is responsible for receiving progress events from the underlying transport layer (such as the `transfer` library) and determining whether the download is still in progress to decide whether to trigger a timeout.
2. **Byte increment timeout detection mechanism**: Before this fix, `transferProgressReporter` mainly relied on the change of sampled `totalBytesRead` (total number of bytes read) within a specific time window (i.e. byte increment) to judge transfer activity. If the byte increment is zero, it may be determined that the transmission is stalled, triggering a timeout.
3. **Transfer progress events**: Modern image transfer protocols (such as OCI Distribution Spec) support fine-grained progress event push. These events not only contain byte growth information, but their existence (event stream) is enough to prove that the connection is active and the transport layer is working. For example, in sharded parallel download, the download of a certain shard may be paused waiting for resources, but other shards are still being transmitted, and overall progress events are still being reported.

## Practice

**Fix Method**:
The core of this fix is to add a key timeout refresh mechanism to the event processing logic of `transferProgressReporter`: **Whenever `transferProgressReporter` receives a valid transfer progress event, the activity timestamp of the timeout detection will be refreshed**. This means that as long as progress events are reported continuously, even if the sampled byte increment is zero for a short period of time (for example, waiting for a network retry, disk IO wait, or shard scheduling), the timeout timer will be reset to avoid false positives. The original detection logic based on byte increments remains unchanged as a safety net.

**Verification and Testing**:
To verify this fix and prevent regressions, a new dedicated regression test case `TestTransferProgressReporterProgressEventRefreshesTimeout` has been added. This test simulates a scenario where the transfer progress event continues to flow but the byte increment is temporarily zero, and the verification timeout is not triggered by the error.

SRE engineers can run tests to ensure the fix works and doesn't break existing functionality with the following command:
```bash
#Run specific timeout refresh tests
go test ./internal/cri/server/images -run 'TestTransferProgressReporterProgressEventRefreshesTimeout'

#Run all tests related to image transfer
go test ./internal/cri/server/images
```
This fix improves the resilience of containerd in pulling images in complex network environments.

## SRE Key Points

* **Relationship with reliability/observability**: This case highlights that in reliability engineering, event-based health detection is often more robust than detection based solely on metrics (Metric-based). The existence of the event stream directly proves the activity of the component and is an important signal for building a highly observable system. SREs should consider combining these two signals when designing monitoring and alerting rules.
* **Best Practices and Common Anti-Patterns**:
    * **Best Practice**: For long-running asynchronous operations (such as image pull, backup, data synchronization), the health detection mechanism should be able to tolerate normal fluctuations during the operation. Prefer using "heartbeats" (such as progress events) to determine activity, and absolute metrics (such as byte growth) as secondary or final timeout conditions.
    * **Anti-Pattern**: Avoid using overly stringent, single performance indicators (such as "at least N bytes must be transmitted within each detection window") as the only activity criterion. This will lead to a large number of false positives in high-latency or intermittent unstable network environments, trigger unnecessary retries or failures, and affect system stability and operation and maintenance efficiency.
* **Related indicators (SLI/SLO/SLA)**: For the image pull service, a key SLI is the **pull success rate** or **the average time taken for the pull task**. Failures like this, caused by false positives over timeouts, directly impact SLI. Teams can set SLOs for "image pull operations" such as "99.9% of image pull tasks completed successfully within 5 minutes." Monitoring the proportion of task failures due to `pull timeout` errors is a direct means to verify the effect of such repairs.
