# How Non-Developers Can Contribute to Prometheus

## Overview

As the de facto standard in cloud-native monitoring, Prometheus's powerful features and thriving community stem not only from core code development but also from non-technical contributions such as documentation, community support, and User Experience (UX) design. For SRE and platform engineers, a healthy, active, and accessible open-source ecosystem is a critical part of ensuring the sustainable development and reliability of monitoring tools. However, contributors from non-technical backgrounds often face unique challenges when participating. This article aims to clarify the value of these challenges and provide practical guidelines.

## Core Concepts

Non-technical contributors play an indispensable role in open-source projects. Their value is not directly reflected in lines of code, but in improving the project's accessibility, organization, and user-friendliness, all of which ultimately point to the same goal: **enhancing system reliability and operational efficiency**.

**The Four Major Challenges Faced by Non-Technical Contributors** are key to understanding participation barriers:
1.  **Intimidation from Technical Barriers**: In a developer-dominated environment, non-technical personnel may feel isolated due to not understanding technical terminology and discussions, making it difficult to speak up confidently.
2.  **Unclear Value Proposition**: Open-source projects' `Contributing Guides` and `Issue Lists` are typically focused on code tasks, rarely explicitly listing needs for documentation, design, or community management, leaving potential contributors unsure how to match their skills with project needs.
3.  **Invisibility of Contributions**: Traditional contribution metrics (such as Git commits, code merges) cannot reflect the value of organizing meetings, user support, or research work, reducing the visibility and recognition of non-technical contributions.
4.  **Lack of Onboarding Guides**: Standard development onboarding guides cannot instruct non-technical contributors on how to participate in documentation improvements, design feedback, or community support, creating a significant gap between "joining" and "making a first contribution."

These challenges arise not from malice but as a natural result of the project's evolution during early development stages. When a project is primarily built by developers for developers, needs such as marketing, community management, and user research may not be immediately recognized.

## Practice

If you wish to contribute non-code value to the Prometheus project, here are specific and active areas of participation:

**1. Join the User Experience (UX) Working Group**
The Prometheus community has established a [UX Working Group](https://cloud-native.slack.com/archives/C09NL3B1EKW) Slack channel focused on improving the user experience of monitoring systems. If you have a background in UX research, design, or usability analysis, this is an excellent entry point. You can participate in discussions in the channel, follow subsequent announcements, and directly contribute to work that affects Prometheus's visualization and interaction experience.

**2. Write for the Prometheus Blog**
The blog is a key platform for sharing knowledge and use cases. You can write tutorials, best practices, use case studies, or community updates. Refer to the [Blog Content Guide](https://github.com/prometheus/docs/blob/main/blog/README.md) for proposal requirements and publishing processes. A blog post about how you used Prometheus to solve a specific problem can greatly help other users.

**3. Improve and Maintain Documentation**
Documentation is the core for lowering the barrier to entry. You can contribute in the following areas:
*   Fix typos and [repair broken links](https://github.com/prometheus/docs/issues/2649).
*   Expand "Getting Started Guides" to be more beginner-friendly.
*   Create new tutorials for common monitoring scenarios (such as Kubernetes service monitoring).
*   Help with documentation [issue triage and prioritization](https://www.youtube.com/watch?v=SzSUa5y7Ji0&t=27105s), helping maintainers focus on priorities. Even if you are not a professional documentation engineer, if you have ever been confused by documentation and eventually figured it out, you can help the next user.

**4. Help Organize PromCon**
[PromCon](https://promcon.io/) is Prometheus's annual event, and its success depends on extensive coordination work. If you have experience in event planning, sponsor outreach, marketing, or communications, you can contact the [organizing team](mailto:promcon-organizers@googlegroups.com) or watch for announcements in community channels.

**5. Advocacy and Promotion**
One of the simplest yet most impactful contributions is spreading the value of Prometheus. You can:
*   Write blog posts about using Prometheus in your actual work.
*   Give talks at local meetups or technical conferences.
*   Share tips and experiences on social media, or create video tutorials.
*   Recommend Prometheus to teams evaluating monitoring solutions.

## SRE Key Points

Non-technical contributions are closely linked to core SRE principles:

*   **Improving Observability Comprehensibility**: High-quality documentation and clear UX design are the last mile for making monitoring data and system state "observable." SRE relies on this information for troubleshooting and capacity planning. Non-technical contributors directly improve the operational efficiency of the entire team by optimizing documentation and interfaces.
*   **Enhancing Community Resilience**: A well-managed, helpful community means that when your team encounters Prometheus-related issues late at night, you are more likely to receive timely responses or find solutions in Slack. This is essentially a distributed support system and part of reliability.
*   **Best Practices and Anti-Patterns**:
    *   **Practice**: Clearly communicate your skills and interests; start small (e.g., fix a documentation link); be patient and observe community rhythms before diving deeper.
    *   **Anti-Patterns**: Trying to solve all documentation issues at once; pushing major changes before sufficiently observing community norms; believing that only code commits are "real" contributions.
*   **Related Metrics (SLI/SLO)**: While non-technical contributions are not easily quantifiable directly, their impact can be measured through indirect metrics, such as:
    *   **Documentation Quality**: Can set a target like "error report rate for critical operation guides below X%."
    *   **Community Support Response Time**: Monitor the average time from user question to first effective response.
    *   **New User Retention Rate**: Track the proportion of users who continue to be active among those who first ask questions or participate.

Ultimately, the prosperity of the Prometheus community and similar open-source projects requires a diverse contributor base. As the original author stated, the question is not whether non-technical contributions matter, but how we create space for them to happen. As SRE or technical leaders, we can shape a healthier, more reliable open-source ecosystem by actively inviting, clearly communicating needs, and recognizing these contributions.
