# Increased memory usage with 3.6 event reuse

## Overview

In SRE practice, it is critical to monitor and optimize resource usage of key components such as the Kubernetes cluster’s key-value store etcd. etcd version 3.6 introduced an "event multiplexing" feature designed to optimize memory usage, but in certain high-density Kubernetes workload scenarios, it unexpectedly led to significant memory usage regression. This case profoundly reveals that in complex distributed systems, optimizations that appear to improve performance may have completely opposite effects under certain conditions, emphasizing the importance of thorough performance testing and capacity planning before release.

## Core concepts

**Event Reuse**
Refers to a memory optimization technology introduced in etcd 3.6 through [PR #17563](https://github.com/etcd-io/etcd/pull/17563). The core idea is to reduce frequent memory allocation and garbage collection (GC) overhead by reusing the memory buffer during Watch event processing, which should theoretically reduce memory usage and CPU consumption.

**Memory Regression**
It refers to the phenomenon that under the same or similar load, the memory usage of a new version of software increases instead of decreasing compared to the old version. In this incident, the average RSS (resident set size) and maximum RSS of etcd 3.6 in high-density Kubernetes clusters were significantly higher than those of version 3.5. Especially when the cluster size and object density increase, the degree of regression worsens sharply.

**Density Workload**
Usually refers to the scenario of running a large number of frequently changing cloud native objects within a unit of resources. In the Kubernetes environment, this manifests itself as the creation, update, and deletion of a large number of Pods, Services, ConfigMap and other resources, resulting in etcd needing to process a massive stream of Watch events.

## Practice

Based on the recurrence path and diagnostic data provided in the report, we can follow the following steps to identify and analyze such memory issues:

1. **Problem Recurrence**:
    * Deploy the target version of etcd (e.g. 3.6.5) in a Kubernetes cluster of sufficient scale (e.g. 120+ nodes).
    * Run specialized high-density workload simulation tools, such as kubeburner's `cluster-density-v2` test suite.
    * At the same time, a controlled experiment was conducted using etcd 3.5 version under the same configuration.

2. **Monitoring and Diagnosis**:
    * **Core Indicators**: Closely monitor the `RSS` (`resident set size`) memory indicator of the etcd process. This is the most direct indicator for observing actual memory usage. Pay attention to averages and peaks.
    * **In-depth analysis**: When abnormal memory growth is observed, use Go's `pprof` tool to capture the heap memory profile (such as the `heap.pb.gz` file), and analyze it through `go tool pprof` or a visualization tool (such as the `web` command to generate SVG). The screenshots in the report clearly show how memory growth correlates with specific code paths.
    * **Configuration check**: Verify etcd's startup parameters and resource limits (such as `--quota-backend-bytes`, container's `limits.memory`) to ensure that the configuration is consistent and reasonable.

3. **Root cause location**:
    * Use bisection testing to pinpoint issues to the specific commit that introduced event reuse (i.e. PR #17563). This indicates that when handling a large number of concurrent Watch connections and event broadcasts, reusing buffers may actually increase memory overhead due to internal lock contention, buffer management strategies, or life cycle issues.

## SRE Key Points

- **Relationship with Reliability**: etcd is the "brain" of Kubernetes, and its out-of-memory (OOM) will directly cause the API Server to be unavailable, thereby affecting the control plane stability of the entire cluster. In this regression, the maximum RSS of the 250-node cluster reached 2.96 GiB, which can easily trigger the memory limit of the container, causing restarts and cluster turbulence. Monitoring etcd memory is a key operation and maintenance action to ensure cluster reliability.
- **Observability and Event Response**: This case highlights the importance of granular observability of etcd internal metrics (such as memory allocation rate, GC pause time) and workload characteristics (number of watches, event rate). When performance abnormalities occur after an upgrade, being able to quickly associate them with specific version features and load patterns is the key to efficient incident response.
- **Best Practices and Common Anti-Patterns**:
    - **Best Practice**: Before upgrading core components such as etcd, it must be verified in a pre-production environment using a stress testing tool that matches the production load, focusing on monitoring SLO-related indicators such as memory, CPU, and latency. Establish resource usage baseline and alarm threshold for etcd.
    - **Anti-Pattern**: Rely only on theoretical optimization or unit test results and ignore integration performance testing in real, complex high-concurrency scenarios. Push code optimized under ideal conditions directly to production without verification.
- **Related indicators (SLI/SLO/SLA)**:
    - **SLI (Service Level Indicator)**: `RSS` memory usage, heap memory object size, `go_memstats_alloc_bytes` of etcd process.
    - **SLO (Service Level Objective)**: Can be set to "Under expected peak load, etcd single instance RSS memory usage does not exceed X GiB" or "etcd memory P99 usage is less than 80% of the container memory limit". This regression directly breaks the original memory usage SLO.
    - **Error Budget**: Memory regression may lead to restarts caused by OOM, consuming the cluster's reliability budget and affecting the overall availability target.
