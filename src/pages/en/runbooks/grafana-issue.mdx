# Grafana Issue

## Overview

When building an observability platform, Grafana dashboards are the core tool for SRE teams to monitor system health in real-time, verify [[slis-slos-slas|SLO]] achievement, and respond quickly to incidents. The accuracy and robustness of dashboards directly affect the team's judgment of system reliability. A known issue (#102039) indicates that when a panel is configured with multiple query data sources and uses the `merge` transformation, if one of the queries returns an empty data frame (e.g., a query with no matching results), the entire panel visualization fails, displaying "No data." This violates the basic requirements of SRE practices for observability data integrity and accurate system state representation, potentially masking changes in critical metrics and misleading incident investigation direction.

## Core Concepts

To understand this issue, the following key technical concepts need to be clarified:

- **Empty Data Frame**: In Grafana's internal data model, a query result may return a data frame that has a structure but contains no data records. This is different from a query failure or data source connection error; it indicates that the query executed successfully but did not hit any data.
- **Data Merge**: This is a commonly used data transformation designed to logically merge fields from multiple queries (or multiple data frames), typically based on common keys (such as timestamps or specific dimensions), to create a unified view for cross-comparison.
- **Merge Transformation Implementation Logic**: According to the issue description, the current `merge` transformation implementation may be similar to JavaScript array's `concat` operation, which directly concatenates data frames. When one of the input data frames is empty (`[]`), this operation may not handle it correctly, causing the final output to also be treated as empty, thereby blocking the visualization of other valid data frames.

## Practice

### Issue Reproduction Steps

Based on the provided minimal reproduction case, the issue can be reproduced with the following steps:

1.  **Create a panel with multiple queries**: Create a new dashboard in Grafana and add a Table type panel.
2.  **Configure multiple data source queries**:
    -   Query A (`refId: "A"`): Use `grafana-testdata-datasource`'s `csv_content` scenario with some sample data.
    -   Query B (`refId: "B"`): Also use `csv_content` with different sample data.
    -   Query C (`refId: "C"`): Use the `raw_frame` scenario, but set `rawFrameContent` to `"[]"` to simulate a query that returns an empty data frame.
3.  **Apply Merge transformation**: In the panel's "Transformations" tab, add a "Merge" transformation.
4.  **Observe results**: After previewing or saving the dashboard, the panel should display "No data," even though queries A and B both have valid data.

### Current Behavior vs Expected Behavior

-   **Current behavior**: When one of the merged data sources contains an empty data frame, the entire visualization output is empty.
-   **Expected behavior**: The visualization should display the merged data of all non-empty queries, ignoring or skipping empty data frames. Empty data frames should not block the entire data flow.

### Possible Temporary Workarounds

Before an official fix for this issue, SRE teams can consider the following temporary solutions to ensure monitoring continuity:

1.  **Data source level filtering**: Ensure all queries sent to Grafana theoretically return at least one row of data, avoiding queries designed to produce empty results. However, this may not be realistic.
2.  **Use other transformations**: Try alternative merge strategies. For example, first use "Add field from calculation" or "Group by" transformations to preprocess each query result to ensure non-empty output, then perform the merge. However, this method is complex and may not fully simulate the desired merge logic.
3.  **Simplify query logic**: Redesign the dashboard to minimize mixing heterogeneous queries that may return empty results within a single panel.

## SRE Key Points

### Relationship with Reliability

This issue directly affects the reliability of the monitoring system. Dashboards serve as the primary information source during [[incident-response|incident response]] and [[on-call|On-Call]] processes. Incomplete or misleading data can:
-   **Mislead incident investigation**: Mask some system metrics, preventing the SRE team from obtaining a comprehensive view of system state, extending [[mttd|MTTD]] (Mean Time to Detect) and [[mttr|MTTR]] (Mean Time to Recover).
-   **Impact SLO calculation and decision-making**: If panels used to calculate critical [[slis-slos-slas|SLIs]] fail due to partial data loss, it may incorrectly trigger Error Budget consumption alerts, or conversely, fail to trigger necessary reliability actions in time.
-   **Reduce observability trust**: Repeated occurrences of "No data" or data loss will reduce the team's trust in the monitoring system, potentially causing important alerts to be ignored.

### Best Practices and Anti-Patterns

-   **Best practices**:
    1.  **Design robust dashboards**: Avoid relying on queries that may produce empty results, or explicitly handle empty frames through data transformations (such as `Filter by name`).
    2.  **Use data validation (Data Alert)**: Configure data condition alerts for critical panels to proactively notify when visualizations unexpectedly become empty or data volume drops sharply.
    3.  **Dashboards as code**: Include dashboard JSON definitions in version control and perform basic syntax and logic checks in CI/CD to detect such configuration issues early.
    4.  **Monitor configuration health**: Regularly review dashboard query success rates, panel error rates, and other metadata to proactively discover similar issues.

-   **Common anti-patterns**:
    1.  **Ignoring partial data failures**: Assuming "as long as the data source is connected, the dashboard should work," ignoring the critical impact of query result content (such as empty frames) on visualization.
    2.  **Overly complex panels**: Stuffing too many, overly complex queries and transformations into a single panel, increasing the risk of unexpected behaviors.
    3.  **Lack of dashboard testing**: Not performing regular "smoke tests" on critical monitoring dashboards (e.g., verifying that critical panels consistently have data), allowing issues to lurk undetected.

### Related Metrics (SLI/SLO/SLA)

While this issue itself does not directly define SLIs, it threatens the accurate observation of SLIs. A robust SRE practice should consider **the monitoring system's own reliability**, and can define the following internal SLIs:
-   **SLI**: Critical monitoring panel data availability rate = (time panels display data normally within time window / total time) * 100%.
-   **SLO**: Critical monitoring panel data availability rate at least 99.9%.
-   **Countermeasures**: When panel data availability falls below the SLO, an incident should be triggered to investigate whether it is a monitoring system issue (such as a Grafana bug, data source issue) or a real issue with the monitored system. This Issue #102039 is a known cause that could lead to SLI violations.
