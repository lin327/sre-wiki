# Kubernetes API Governance

## Overview

In a distributed system as large and rapidly evolving as Kubernetes, APIs are not just REST interfaces exposed to users but encompass all interaction surfaces including command-line flags, configuration file formats, inter-component communication protocols, and data persistence structures. **API Governance** is a sub-project under SIG Architecture whose core mission is to ensure these APIs' **stability, consistency, and backward compatibility** while embracing innovation and evolution. For SREs, understanding and practicing API governance principles is critical because it directly concerns the cornerstone of system reliability — stable commitments to users and predictable control of internal system state.

## Core Concepts

### API Governance Scope and Objectives

API governance extends far beyond REST APIs. It covers all "contractual" surfaces, including:
*   **User-Facing APIs**: REST APIs, `kubectl` command-line parameters, configuration files (such as kubeconfig).
*   **Internal APIs**: Kubelet and Container Runtime Interface (CRI), scheduler and API Server communication, data storage formats, etc.

The fundamental objective is **balancing stability and innovation**. As API Governance lead Jordan Liggitt puts it: "Stability is easy if you never change anything. But that contradicts the goals of evolution and growth." Therefore, governance work is dedicated to establishing clear specifications that allow feature evolution while maintaining compatibility commitments to users.

### Quality Gates and Review Processes

API governance intervenes in the Kubernetes change lifecycle through two main approaches:

1.  **Guidelines and Conventions**: Maintaining detailed API convention documents (such as `api-conventions.md`), which serve as "living documents" for handling various API patterns and are continuously updated as new scenarios emerge.
2.  **API Review**: This is a mandatory review step. Reviews can occur at the **design stage** (through Kubernetes Enhancement Proposals, KEPs) or at the **implementation stage** (when code is submitted). Ideally, large features involving API changes should invite API review involvement early in the design phase to avoid extensive refactoring due to fundamental design issues later. The review process often involves high-bandwidth real-time video discussions to efficiently reach consensus.

### Intervention in the KEP Process

KEPs are the mandatory process for Kubernetes enhancement features. The degree of API governance intervention depends on the KEP's detail level:
*   **Detailed KEPs**: If they include specific API definitions, API review can be completed at the design stage, with implementation mainly verifying design consistency.
*   **Conceptual KEPs**: If they only propose concepts and leave details to implementation, API review will occur at the implementation stage, potentially suggesting structural adjustments.

### Challenges and Evolution Brought by CRDs

The emergence of Custom Resource Definitions (CRDs) was a "watershed" event. It empowered users to define any resource in Kubernetes, greatly expanding the ecosystem but also posing governance challenges.
*   **Initial Phase**: Early CRDs didn't even require schemas, providing flexibility but sacrificing consistency.
*   **Governance Evolution**: As CRDs moved toward GA, schemas became mandatory. A recent major milestone was the introduction of **Built-in Validation Rules**, enabling CRD authors to obtain validation capabilities comparable to built-in resources.
*   **Key Pattern**: Through **Ratcheting Validation** — allowing data to gradually improve without breaking existing objects — governance can guide CRDs toward following conventions while maintaining backward compatibility. The CRD governance journey collectively embodies three themes: **defining schemas, validating data, and handling legacy invalid data**.

## Practices

### Intervention Cadence in the Release Cycle

API governance work is not entirely continuous; its intensity closely correlates with the Kubernetes release cycle:
*   **Before Enhancements Freeze**: Design-stage review demand peaks.
*   **Before Code Freeze**: Implementation-stage review demand increases significantly.
*   **Between Freezes**: The best time for long-term design work and forward-looking thinking.

A common **anti-pattern** is teams hurriedly submitting designs and requesting reviews near the enhancement freeze after months of feature ideation. For major changes affecting APIs, **early involvement** is the golden rule.

### Automation and Continuous Improvement

To ensure consistency and reduce manual burden, API governance relies on automation tools such as linters and validation scripts for verifying common patterns like spec/status semantics. Governance practice itself is also an iterative process: facing new scenarios, teams discuss and feed conclusions back into documentation and tools. Even if the initial approach is wrong, robust solutions can be found through several rounds of iteration. This embodies an engineering culture of **incremental improvement**.

## SRE Key Points

### Connection to Reliability, Observability, and Incident Response

*   **Reliability Cornerstone**: API stability is a direct manifestation of system reliability. Backward compatibility commitments to users ensure stable user integration and operational workflows, avoiding unexpected interruptions from upgrades. This fully aligns with SRE's goal of maintaining reliability through change risk management.
*   **Foundation of Observability**: Consistent APIs (including internal component APIs) make monitoring, logging, and tracing data easier to correlate and understand. If APIs change unpredictably, the maintenance cost of observability pipelines will increase sharply.
*   **Incident Response**: When failures occur, stable API behavior helps quickly locate problems. If API semantics or formats frequently change unexpectedly, it greatly increases troubleshooting complexity.

### Best Practices and Common Anti-Patterns

**Best Practices:**
1.  **Early Participation**: Designs involving API changes should seek API review feedback as early as possible during the KEP stage.
2.  **Follow Conventions**: Strictly adhere to patterns defined in `api-conventions.md` (such as spec/status separation).
3.  **Design for the Future**: Ask: "How can this feature evolve in the future without breaking compatibility?" Leave room for future expansion.
4.  **Embrace Tooling**: Utilize automated linters and validation tools to front-load quality checks in CI/CD.
5.  **Incremental Improvement**: For legacy issues, adopt strategies like ratcheting validation for gradual improvement rather than one-time breaking changes.

**Common Anti-Patterns:**
1.  **Submitting Major Changes Near Freeze**: This creates enormous pressure on both the review team and the submitter, easily leading to rework.
2.  **Ignoring Internal API Governance**: Random changes to internal interfaces also break system stability and team collaboration efficiency.
3.  **Treating Compatibility Requirements as Obstacles**: Recognize that maintaining compatibility is an expression of responsibility to users and building long-term trust, with value far exceeding the convenience of short-term cleanup.

### Related Metrics (SLI/SLO/SLA)

While API governance itself does not directly define SLIs, its work outcomes directly support reliability-related SLI/SLO:
*   **SLO Correlation**: System stability SLOs heavily depend on API stability. Frequent, non-backward-compatible API changes directly increase the risk of SLO violations.
*   **SLI Manifestation**: A well-functioning API governance process can manifest its output as internal metrics such as "**proportion of backward-compatible changes to critical APIs**" or "**number of deployment rollbacks caused by API incompatibility**."
*   **SLA Commitments**: For cloud providers or managed services, published SLAs often include API stability commitments, and API governance is the internal guarantee mechanism for fulfilling these commitments.
