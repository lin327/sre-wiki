# fix: propagate `context deadline exceeded` error properly

## Overview

In the ecosystem of container runtimes (such as containerd), the `shim` process is a key component in managing the container life cycle (starting, stopping, monitoring). When the `shim` process becomes unresponsive due to a failure or being suspended by an external signal (such as `SIGSTOP`), the upper-layer service (such as the containerd daemon) communicating with it through ttrpc (a lightweight RPC protocol based on gRPC) will time out and return the standard error `context deadline exceeded`.

If this error is not properly caught and propagated, it will cause the upstream call chain (such as client tools such as `nerdctl`) to be unable to accurately identify the root cause of the failure, thereby triggering unnecessary retry logic, increasing system load, and significantly reducing the response speed of operations such as container lists. From an SRE perspective, clear error propagation is the basis for achieving **fast fault location**, **graceful degradation** and maintaining **system observability**. This fix aims to ensure that this low-level timeout error is passed up clearly and accurately.

## Core concepts

### Context Deadline Exceeded
This is the standard error defined in the `context` package of the Go language and indicates that the deadline set for the operation (`deadline`) has passed and the operation was forcibly cancelled. In network and RPC calls, this usually means waiting for a timeout from the remote end.

### Shim communicates with ttrpc
In the containerd architecture, **shim** is a lightweight process that interacts directly with the container's runtime (such as runc) and is responsible for process execution and status collection. The containerd daemon communicates efficiently with the shim through the **ttrpc** protocol, such as querying task status (`State()`) and obtaining process information (`State()`).

### Error propagation
It refers to returning errors generated by underlying functions or calls to the upper-level caller without tampering (or appending necessary context information). A good error propagation chain allows each component in the system to obtain enough information to decide how to handle the failure, which is the key to building a **resilient system**.

## Practice

According to the PR information provided, the problem specifically occurs when the shim is unresponsive and the following two API call paths fail to properly handle timeout errors:

1. **Task status check** (`shimTask.State()`)
2. **Process status acquisition** (`getProcessState()`)

When these functions are called via ttrpc to an unresponsive shim, a `context deadline exceeded` error is returned under the hood. However, in the code logic before modification, this error may be swallowed, converted to an irrelevant error type, or directly cause the function to return `nil`, causing upper-level callers (such as `containerd`'s API server) to mistakenly think that the operation is successful or return invalid status.

The fix is ​​to explicitly check and handle the error type returned by the `ttrpc` client in the `shimTask.State()` and `getProcessState()` functions. When a `context deadline exceeded` is identified, propagate it up as an explicit, high-diagnostic error.

**Logic diagram after repair:**
```go
// After calling the ttrpc client inside the function
resp, err := shimClient.State(ctx, req)
if err != nil {
    // Before repair: it may directly return fmt.Errorf("failed to get state: %w", err)
    // After fix: Make sure deadline exceeded errors are retained and propagated
    return nil, err // The upper layer can clearly see that this is a deadline exceeded error
}
```
This modification allows clients (such as `nerdctl`) to recognize that this is a timeout failure and can take targeted action (such as prompting the user that "the shim process may have become unresponsive") rather than getting stuck in a slow retry loop or presenting confusing status information.

## SRE coverage

### Association with reliability
- **Error Budget Consumption**: Redundant retries and slow operations caused by unclear error propagation will directly consume the **Error Budget** of the service and reduce overall availability.
- **Fault Domain Isolation**: Clear error messages help quickly isolate fault domains. Confirming that the shim is unresponsive rather than core data corrupt allows operations and maintenance to prioritize specific processes on specific nodes rather than initiating a full failure recovery process.

### Best Practices and Anti-Patterns
- **Best Practice**: Always check and retain system-level errors such as underlying timeouts and connection rejections at RPC/network call boundaries to provide clear diagnostic information to upper layers.
- **Anti-Pattern**: Encapsulate or convert specific, meaningful errors (such as `context deadline exceeded`) into vague "internal errors" or "operation failures", which will greatly increase the difficulty of troubleshooting.

### Related Indicators (SLI/SLO)
- **Service Latency**: After fix, container list latency (`container_list_latency`) caused by error retry storms should drop significantly.
- **Error rate**: While the `context deadline exceeded` event itself may indicate an underlying infrastructure problem, when properly propagated, the health of the shim can be measured by monitoring such specific errors (`shim_timeout_errors`) and setting the corresponding **SLO** (for example: `shim` health checks should respond within 100ms 99.9% of the time).

### Observability and incident response
- **Observability enhancement**: The fix allows this error to appear correctly in application logs and monitoring indicators, providing accurate trigger conditions for the alarm system.
- **Incident Response**: In incident response, accurate error information is the core of "first step diagnosis". When a "shim timeout" alarm is received, the response manual can be directed to checking the shim process status, system resources, or `SIGSTOP` signal source of the specific node, instead of wasting time troubleshooting the application layer code.
