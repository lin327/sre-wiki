# 修复 containerd 固定镜像标签未应用的问题

## 概述

在容器运行时环境中，管理关键基础镜像的版本稳定性至关重要。`containerd` 提供了“固定镜像”（Pinned Images）机制，通过为特定镜像打上标签（如 `containerd.io/pinned`）来标记和管理那些需要固定版本、避免意外更新的镜像。本文档描述了一个在 `containerd` 版本迭代中引入并被修复的缺陷：当在配置文件中为固定镜像指定地址但未明确指定标签（tag）时，系统未能自动应用固定标签，从而破坏了该核心可靠性机制。此修复确保了固定镜像配置的健壮性和一致性。

## 核心概念

**固定镜像 (Pinned Images)**：在 `containerd` 的配置中，可以通过 `pinned_images` 字段指定一组需要版本锁定的镜像。这些镜像通常被用于核心系统服务（如 Kubernetes 的 pause 容器、CNI 插件、CSI 驱动等），以确保其版本在整个集群生命周期内保持不变，提供可重现的部署和稳定的运行环境。

**固定标签 (Pinned Label)**：`containerd` 会为配置中标记为 `pinned` 的镜像自动添加一个特定的标签（例如 `containerd.io/pinned`）。这个标签的作用包括：
1.  **标识**：清晰区分哪些镜像是被管理、需要固定版本的。
2.  **保护**：防止垃圾回收或垃圾清理机制误删这些重要镜像。
3.  **查询**：允许管理员通过标签快速筛选出所有固定镜像。

**原始缺陷**：在之前一次从 `SandboxImage` 到更通用的 `PinnedImages` 功能重构中，引入了一个逻辑缺陷。当在配置中指定一个镜像引用（如 `registry.k8s.io/pause:3.9`）但其标签部分在某些代码路径下被忽略或未被正确解析时，系统无法完成镜像名称的规范化比较，导致后续的“打标签”操作被跳过。

## 实践

本次修复的核心是在比较镜像引用之前，对引用进行规范化（Normalize）处理。这确保了无论用户提供的镜像字符串格式如何（是否包含标签、是否包含 `docker.io` 等默认前缀），都能转换成一个统一的内部格式进行比对。

**修复逻辑**：
1.  当 `containerd` 处理 `pinned_images` 配置时，对于每一个指定的镜像地址。
2.  系统会先调用规范化函数处理该字符串。规范化过程会补全缺失的默认标签（如将 `nginx` 规范化为 `docker.io/library/nginx:latest`），并确保镜像名称的完整性和一致性。
3.  随后，系统使用规范化后的镜像名，与当前已拉取到本地的镜像列表进行比对，从而准确地为目标镜像打上固定标签。

**配置示例**（`config.toml`）：
```toml
[plugins."io.containerd.grpc.v1.cri"]
  # ... 其他配置 ...

  # 固定镜像配置示例
  [plugins."io.containerd.grpc.v1.cri".containerd]
    # 此处配置的镜像，即使不带标签，也应该被正确地应用固定标签
    pinned_images = [
      "registry.k8s.io/pause:3.9",
      "docker.io/library/alpine", # 即使没有指定:latest，也应被正确处理
      "quay.io/prometheus/prometheus:v2.51.0"
    ]
```

修复后，`containerd` 将确保上述配置中的所有镜像（包括 `alpine`）都会被正确地标记和管理。

## SRE 要点

### 与可靠性、可观测性、事件响应的关联
*   **可靠性**：固定镜像机制是保障服务版本确定性和部署可重现性的基石。此 bug 会导致部分关键镜像（尤其是那些配置时可能省略标签的）未被正确锁定，从而在节点重建、镜像垃圾回收或意外更新时引发故障，直接影响服务的可靠性。修复后，SRE 可以更有信心地依赖此机制。
*   **可观测性**：一个健全的固定镜像系统依赖于标签。通过 `ctr images ls` 或 CRI 接口查询带有 `containerd.io/pinned` 标签的镜像，是运维审计和监控镜像状态的重要手段。此修复确保了可观测性数据的准确性。
*   **事件响应**：在需要快速回滚或排查版本不一致问题时，能够精确控制和识别节点上运行的固定镜像版本至关重要。此 bug 可能在事件调查中造成混淆，使某些镜像的真实版本和预期不符。

### 最佳实践与常见反模式
*   **最佳实践**：
    1.  **明确指定标签**：虽然修复后 `containerd` 能处理无标签情况，但最佳实践仍是在 `pinned_images` 配置中**始终明确指定镜像标签**（如 `image:v1.2.3`），这使配置意图更清晰，避免依赖运行时默认值。
    2.  **版本化配置**：将 `pinned_images` 列表纳入配置管理，并与 Kubernetes 版本或平台版本绑定，实现版本化、可追溯的基础设施管理。
    3.  **监控与审计**：定期（或在 CI/CD 流程中）检查节点上的固定镜像标签状态，确保与配置预期一致。
*   **常见反模式**：
    1.  **依赖隐式标签**：在配置中写 `nginx` 而非 `nginx:1.25.3`，这增加了配置的不确定性。
    2.  **忽视更新流程**：固定镜像不意味着永远不更新。应有专门的流程来评估、测试并更新 `pinned_images` 列表。
    3.  **配置漂移**：各节点上的 `config.toml` 不一致，导致固定镜像集合不同，给运维带来复杂性。

### 相关指标（SLI/SLO/SLA）
*   **SLI (Service Level Indicator)**：可监控“具有 `containerd.io/pinned` 标签的镜像数量”与“`pinned_images` 配置项中定义的镜像数量”的一致率。该指标应接近 100%。
*   **SLO (Service Level Objective)**：对于运行关键服务的节点，应设定 SLO，要求固定镜像标签的应用成功率达到 99.99% 以上。
*   **SLA (Service Level Agreement)**：此问题本身是内部运行时缺陷，通常不直接对外定义 SLA。但平台提供方可以将“固定镜像配置正确性保障”作为内部服务等级协议的一部分，承诺此类机制性问题的修复时效。
