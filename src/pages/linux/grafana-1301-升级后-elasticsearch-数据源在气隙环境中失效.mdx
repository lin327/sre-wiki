## 概述
在 Grafana 等可观测性平台的运维中，升级操作是保持系统安全和功能新颖的必要步骤，但也伴随着引入新风险的可能。本文描述了一个典型的升级后配置漂移与环境依赖问题：在升级到 Grafana 13.0.1 后，预配置的 Elasticsearch 数据源在无法访问外部互联网的气隙环境中完全失效。此问题揭示了 Grafana 插件生命周期管理在特定部署架构下的一个重要缺陷，直接影响生产环境的可观测性，是 SRE 团队在规划升级、处理事件和保障服务可靠性时需要高度警惕的场景。

## 核心概念

- **气隙环境**：指与外部公共互联网完全物理或逻辑隔离的内部网络。在金融、政府、关键基础设施等领域，这种部署模式是常见的安全要求。应用程序在此类环境中运行时，无法访问外部软件源或更新服务。
- **Grafana 插件生命周期**：Grafana 的许多数据源（如 Elasticsearch）并非内置，而是以插件形式管理。其生命周期包括安装、更新、验证和卸载。在 13.0.1 版本中，对 Elasticsearch 插件的处理逻辑发生了变化，导致其在启动时可能尝试进行网络验证。
- **数据源配置依赖**：Grafana 数据源配置（如连接地址、认证信息）存储在数据库或配置文件中。然而，数据源功能的可用性不仅取决于配置本身，还依赖于对应的后端插件（如 `elasticsearch` 插件）是否处于正确安装和激活状态。插件状态与配置状态的脱节是导致“Data source not found”错误的直接原因。

## 实践

### 问题诊断流程
当在 Grafana 升级后遇到大量数据源连接失败时，SRE 应遵循以下步骤进行系统化诊断：

1.  **检查 UI 与 API 错误**：观察 Grafana 界面中数据源列表的具体错误信息。同时，检查浏览器开发者工具的网络请求，特别是对 `/api/plugins/<plugin-id>/settings` 端点的调用及其返回值。本案例中返回了 `Plugin not found`。
2.  **验证本地插件安装状态**：使用 Grafana CLI 确认插件是否存在于本地文件系统。
    ```bash
    grafana cli plugins ls
    ```
    输出应显示已安装的插件，例如 `elasticsearch @ 12.5.4`。这表明插件文件本身存在。
3.  **检查 Grafana 服务器日志**：重点关注 `level=error` 和包含 `plugin` 关键字的日志行。关键线索通常隐藏在这里，例如启动时尝试从 `grafana.com` 获取插件版本信息的网络请求超时（`context deadline exceeded`），以及数据源插件定义查找失败的日志。
4.  **分析配置与运行时状态差异**：直接查询 Grafana 的数据源 API (`/api/datasources`)，观察返回的 `type` 或 `typeName` 字段。本案例中发现字段值在有无外网连接时会变化（`Elasticsearch` vs `elasticsearch`），这表明插件标识在运行时处理不一致。

### 关键命令与验证
在气隙环境中进行故障排查时，网络连通性验证至关重要：
- 检查 Grafana 服务器是否能解析并访问 `grafana.com` 域名。
- 确认 Grafana 服务在启动过程中因无法完成插件版本检查而进入降级或失败模式。
- 使用 `grafana cli plugins ls` 确认插件安装目录正确（通常为 `/var/lib/grafana/plugins/`）。

### 缓解与解决方案
1.  **临时缓解**：在气隙环境中，一个临时的解决方案是“模拟”外部访问。这可以通过在 Grafana 服务器或网络层配置一个指向内部服务器的 DNS 解析或代理，使得对 `grafana.com` 的请求能够被拦截并返回一个合法的响应（即使内容不是最新的）。这并非长久之计。
2.  **根本解决**：
    - **回滚或升级修复版本**：密切关注 Grafana 官方对此问题的修复补丁。在修复发布前，可暂时回滚到已知稳定的版本（如 12.4.3）。
    - **改进离线插件管理流程**：为气隙环境建立完整的离线插件分发与安装流程。在升级窗口前，手动下载新版本 Grafana 所需的所有插件及其依赖的插件仓库元数据，并在内部仓库中托管，确保 Grafana 在升级后能从内部源完成插件验证。

## SRE 要点

- **与可靠性、可观测性、事件响应的关联**：
    - **可靠性**：此问题导致核心可观测性平台（Grafana）的部分功能完全失效，降低了系统的可靠性。它属于典型的升级引入的回归缺陷。
    - **可观测性**：Elasticsearch 数据源常用于日志或指标分析。其失效直接在可观测性平台上制造了一个“盲区”，可能掩盖其他系统问题。
    - **事件响应**：此类问题在升级窗口后发生，要求 SRE 团队具备快速回滚能力，并能够有效区分是基础设施问题还是应用自身升级导致的问题。

- **最佳实践与常见反模式**：
    - **最佳实践**：
        1.  **环境一致性验证**：在气隙等受限环境进行 Grafana 升级前，必须在 staging 环境（模拟相同网络策略）进行完整测试，包括所有插件功能。
        2.  **配置即代码与版本锁定**：使用 Provisioning 管理数据源，并考虑在文件中明确指定插件版本，减少运行时的不确定性。
        3.  **离线安装策略**：为所有需要外部网络才能完成的初始化操作（如插件版本检查、安装）准备离线方案，确保环境完全自主可控。
    - **常见反模式**：
        1.  **忽视升级说明**：未仔细阅读 Grafana 版本发布说明中关于插件行为变更的提示。
        2.  **假设“已安装即可用”**：在离线环境中，仅关注插件文件是否下载到位，而忽略了插件可能依赖的在线验证或元数据更新流程。
        3.  **网络依赖隐性化**：未充分审计应用程序在启动和运行时对内部和外部服务的所有网络请求。

- **相关指标（SLI/SLO/SLA）**：
    - **SLI（服务级别指标）**：`grafana_datasource_availability`，即 Grafana 数据源可成功查询的百分比。
    - **SLO（服务级别目标）**：在升级后 1 小时内，所有历史配置的（非新创）数据源恢复可用性应达到 100%。
    - **相关事件指标**：`MTTD`（平均检测时间）和 `MTTR`（平均修复时间）在此次事件中尤为重要，用以衡量升级监控和回滚机制的有效性。

此问题凸显了在复杂依赖和受限环境中，**配置漂移**和**隐式依赖**是 SRE 需要持续管理和防范的关键风险点。参考 [[upgrade-strategy]] 与 [[offline-plugin-management]] 以获取更多相关信息。
