## 概述

本知识页面记录了在 Grafana 中，通过标准 Dashboard API 更新一个由 Git 仓库管理的仪表板（标记为 `managedBy: repo`）时，遭遇的一个已知缺陷。该问题会导致更新请求失败并返回 HTTP 500 错误，消息为 `"commit changes: empty commit message"`。这直接影响了依赖 GitOps 工作流（如使用 `gcx push`、`kubectl apply` 或直接 API 调用）来管理仪表板配置的自动化流程。对于 SRE 团队而言，理解此问题的根源和解决方案，对于维护配置管理的可靠性、确保监控面板的版本控制与环境一致性至关重要。

## 核心概念

- **Repo-Managed Dashboard（仓库管理仪表板）**：指通过 Grafana 的 Provisioning 功能，其内容源代码托管在 Git 仓库中的仪表板。此类仪表板在资源元数据中包含 `managedBy: repo` 和 `grafana.app/sourcePath` 注解，表明其生命周期由 Git 仓库控制。
- **Dashboard API**：Grafana 提供的、遵循 Kubernetes 风格的 REST API，用于对仪表板资源进行 CRUD 操作。其端点格式为 `/apis/dashboard.grafana.app/v0alpha1/.../dashboards/<uid>`。
- **Commit Message（提交消息）**：在将仪表板变更写回 Git 仓库时必需的 Git 提交说明。Grafana 的内部 Git 集成层依赖此消息来创建有意义的版本历史。
- **错误预算（Error Budget）**：SRE 通过 Service Level Objective（SLO）定义的可接受失败时间或失败请求比例。此类影响自动化部署的缺陷会消耗 SLO 的错误预算，需引起重视。

## 实践

### 问题复现路径

1.  **配置环境**：配置一个由 GitHub 支持的 Provisioning 仓库，并启用 `workflows: ["branch", "write"]` 权限。
2.  **准备资源**：创建或迁移一个仪表板，使其元数据包含 `managedBy: repo` 和 `grafana.app/sourcePath`。
3.  **触发错误**：作为已认证用户（非 Provisioning 系统用户），向 Dashboard API 发送 `PUT` 请求以更新仪表板。
    ```http
    PUT /apis/dashboard.grafana.app/v0alpha1/namespaces/default/dashboards/<uid>
    Content-Type: application/json
    { ... }
    ```
4.  **观察结果**：请求将返回 HTTP 500 状态码及错误消息 `"commit changes: empty commit message"`。

问题的根本原因在于 Grafana 内部的 `handleManagedResourceRouting` 函数。当它识别出目标资源为 repo-managed 时，会将写操作代理到 Provisioning Files 端点。然而，该代码路径在构造转发请求时，**未附带必需的 `message` 查询参数**，导致下游 Git 客户端在执行提交时失败。

### 解决方案与建议修复

目前官方代码库中已提出修复方案。该方案建议在 `handleManagedResourceRouting` 中，优先从仪表板资源的 `grafana.app/message` 注解中提取提交信息；若该注解未设置，则生成一个合理的默认值（例如 `"Update <dashboard-name>"`）。这与现有导出作业中使用该注解的逻辑保持一致。

### 临时解决方案（Workaround）

在官方修复合并前，可直接使用 Provisioning Files 端点进行更新，该端点正确支持 `message` 参数：

```http
PUT /apis/provisioning.grafana.app/v0alpha1/namespaces/default/repositories/<repo>/files/<source-path>?message=<commit-message>
Content-Type: application/yaml

<YAML 格式的仪表板资源定义，需移除服务端管理的字段如 url, status, creationTimestamp, generation, resourceVersion, uid, managedFields 及部分内部注解>
```

## SRE 要点

- **与可靠性的关联**：此缺陷会阻断基于 API 的配置更新流程，影响使用自动化工具（如 CI/CD 流水线）部署仪表板的可靠性。它可能导致配置部署失败，进而影响监控系统的可观察性。
- **最佳实践与反模式**：
    - **最佳实践**：在修复前，对于 repo-managed 仪表板的更新，优先考虑使用 `PUT .../files/<path>?message=...` 端点。在自动化脚本中，应确保能够设置 `grafana.app/message` 注解。
    - **常见反模式**：盲目依赖 Dashboard API 更新所有类型的仪表板，未意识到 repo-managed 资源有特殊的 API 路由规则，可能导致静默失败或难以追踪的错误。
- **相关指标（SLI/SLO/SLA）**：
    - **SLI**：可监控 Grafana Provisioning 事件的失败率，特别是与 Git 提交相关的错误。
    - **SLO**：团队可为仪表板配置变更的自动化部署成功率设置 SLO。此类问题会直接影响该指标。
    - **SLA**：此为内部工具缺陷，不直接影响对外服务的 SLA，但会降低内部团队使用 GitOps 的效率。
- **事件响应**：若收到关于仪表板更新返回 500 错误且包含 `"empty commit message"` 的警报，SRE 应首先检查目标仪表板是否为 repo-managed，并建议用户采用 Provisioning Files API 端点作为临时解决方案。同时，应跟踪 Grafana 官方 issue #124620 的修复进展。
