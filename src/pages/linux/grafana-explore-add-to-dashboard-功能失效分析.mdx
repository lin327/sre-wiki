# Grafana Explore

## 概述

在 Site Reliability Engineering (SRE) 实践中，Grafana 是实现系统可观测性的核心工具之一。其 **Explore** 界面用于快速查询、调试和探索数据，是 SRE 进行根因分析（Root Cause Analysis）和假设验证的关键入口。**“添加至仪表板”（Add to Dashboard）** 功能则允许 SRE 将临时探索的查询逻辑与可视化结果固化为持久化的监控面板（Panel），从而构建和维护关键的运维仪表板（Dashboard）。本文档分析了一个关于此功能失效的缺陷，该缺陷直接中断了从探索到持久化的关键工作流。

## 核心概念

- **Grafana Explore**: Grafana 中的一个交互式查询和探索界面，支持临时执行数据源查询（如 PromQL、SQL）并即时可视化结果。它是 SRE 进行故障排查、指标分析和日志搜索的起点。
- **Dashboard (仪表板)**: 由多个面板（Panel）组成的可视化布局，用于集中展示系统状态、性能指标和业务数据。它是 SRE 日常监控和告警设置的核心载体。
- **Panel (面板)**: 仪表板中的单个可视化组件，包含一个或多个查询、可视化配置和数据转换规则。
- **“添加至仪表板”工作流**: 这是一个功能衔接点，旨在将 Explore 中经过验证的查询和图表配置，一键导出为新仪表板中的一个面板，或追加到现有仪表板中。该功能的可靠性直接影响 SRE 从“临时分析”到“永久监控”的效率。

## 实践

### 故障现象与重现步骤

根据提供的缺陷报告，该问题在 Grafana 的特定版本中可稳定重现。主要表现为两种场景：

1.  **添加至新仪表板**：
    - 用户在 Explore 中执行查询并确认图表显示正确数据。
    - 通过界面上的“Add”下拉菜单选择“Add to Dashboard”，并在弹窗中选择“New Dashboard”。
    - 点击“Open Dashboard”后，系统导航至一个新建的仪表板，但该仪表板是**空**的，未包含从 Explore 带来的任何面板。

2.  **添加至现有仪表板**：
    - 用户首先创建并保存一个包含至少一个面板的仪表板。
    - 随后在 Explore 中执行新查询。
    - 执行“Add to Dashboard”操作并选择上述已有仪表板。
    - 导航至该仪表板后，**仅显示原有面板**，从 Explore 尝试添加的新面板未出现。

### 影响分析

此缺陷导致了“从探索到持久化”的关键路径断裂。SRE 工程师无法将有效的调试查询快速转化为团队共享的监控视图，具体影响包括：
- **工作流中断**：需要手动创建仪表板、复制查询并配置面板，增加了操作步骤和时间成本。
- **知识流失风险**：临时探索的有用查询可能因繁琐的保存过程而被放弃，导致监控覆盖盲区。
- **协作效率降低**：无法快速将分析结果与团队成员分享至统一仪表板。

## SRE 要点

### 与可靠性、可观测性、事件响应的关联
- **可靠性工程**：工具链自身的可靠性是支撑业务系统可靠性的基础。此类基础功能的失效会降低 SRE 团队自身的运维效率，间接影响其维护目标系统的可靠性。
- **可观测性建设**：构建完善的可观测性体系依赖于不断迭代和丰富的仪表板。该缺陷阻碍了从临时探索中快速沉淀有价值的监控面板，延缓了可观测性体系的完善进程。
- **事件响应**：在事件响应（Incident Response）中，SRE 可能需要在 Explore 中快速验证某个告警指标。如果希望将此查询固定为事故期间的核心监控面板，功能的失效会迫使采用更慢的替代方案，影响响应速度。

### 最佳实践与常见反模式
- **最佳实践**：
    1.  **功能验证**：在升级 Grafana 版本后，应将核心工作流（包括此“添加至仪表板”功能）纳入基本的冒烟测试清单。
    2.  **反馈闭环**：鼓励 SRE 和用户及时在官方渠道（如 GitHub Issues）报告此类问题，并追踪修复进度，因为平台工具的可靠性直接影响运维效能。
    3.  **降级方案**：当此功能不可用时，应知晓替代方法，如在 Explore 中手动复制查询 JSON 并在仪表板编辑模式中粘贴。
- **常见反模式**：
    - **忽略工具链故障**：认为此类 UI 缺陷“不严重”而置之不理，导致团队效率长期受损。
    - **绕行而非根治**：完全依赖手动操作，未推动上游修复，使得问题持续存在。

### 相关指标（SLI/SLO/SLA）
虽然此缺陷本身不直接对应传统 SLI，但它关系到内部工具的功能可用性。可考虑定义以下内部指标：
- **SLI (Service Level Indicator)**：`探索到仪表板功能成功率` = `成功通过该功能添加面板的次数` / `尝试使用该功能的总次数`。
- **SLO (Service Level Objective)**：目标为该功能可用性达到 99.5%（每月允许短暂中断或存在未修复版本）。
- **监控建议**：可以通过用户行为日志分析该功能的点击与最终页面跳转结果，监控其成功率下降趋势。
