## 概述

在 Grafana 监控看板中，Geomap 面板常用于可视化地理空间数据，例如站点分布、资产位置或监控区域。当 Geomap 面板配置为从外部 URL（如 Azure Blob 存储的 SAS URL）加载 GeoJSON 文件时，面板会缓存该数据，导致即使源文件已更新，重新加载仪表盘后仍显示旧数据。这一问题直接关系到监控数据的**数据新鲜度**，是影响 SRE 利用可视化看板进行实时决策的关键因素。

## 核心概念

### 缓存行为与数据新鲜度
Grafana Geomap 面板在加载外部 GeoJSON URL 时，可能在其内部组件或浏览器端实施了缓存策略。这种缓存机制虽然提升了加载速度，但牺牲了数据的实时性。在 SRE 实践中，监控数据的时效性至关重要，陈旧的地理数据可能导致对站点状态、容量或事件响应位置的误判。

### 手动刷新的局限性
该问题的典型表现是，即使 SRE 工程师通过浏览器开发者工具清除缓存或使用无痕模式，数据依然无法更新。这表明缓存可能发生在 Grafana 应用层面，而非单纯的浏览器缓存。它暴露了当前 Grafana Geomap 面板在处理外部数据源时，缺乏灵活、可靠的刷新机制来保证数据同步。

## 实践

### 问题复现与确认
1.  **上传初始数据**：将一个 `site.geojson` 文件上传至 Azure Blob 存储，并为其生成一个 SAS URL。
2.  **配置 Geomap 面板**：在 Grafana 仪表盘中添加一个 Geomap 面板，将其 GeoJSON 图层的数据源 `src` 配置为上一步的 SAS URL。
3.  **验证初始数据**：确认地图正确渲染了 GeoJSON 中的地理特征。
4.  **更新源文件**：在 Azure Blob 存储中修改 `site.geojson` 文件的内容（例如，更改某个标记的名称或移动一个区域）。
5.  **尝试刷新**：在 Grafana 中重新加载仪表盘（即使清除了浏览器缓存或使用新的 SAS URL）。
6.  **观察结果**：发现地图仍然显示更新前的旧数据，问题得以确认。

### 可能的规避与排查思路
虽然官方尚未提供修复方案，但在实际 SRE 工作中，可考虑以下临时规避思路：
-   **查询参数缓存失效**：尝试在 GeoJSON URL 末尾动态添加一个随时间变化的查询参数（如 `?t=<timestamp>`），强制绕过缓存。这需要配合数据生成流程，确保每次更新文件时都更新该时间戳。
-   **仪表盘变量与重载**：创建一个仪表盘变量，将其值作为 GeoJSON URL 的一部分，并通过“刷新仪表盘”按钮触发变量更新，间接达到重载数据的目的。
-   **关注官方更新**：持续关注 Grafana 官方对该 issue 的跟进，期待未来版本能增加配置选项，例如在面板选项中提供“重载策略”（如：每次仪表盘加载时重载、基于查询变量重载等）。

## SRE 要点

### 对可靠性与可观测性的影响
-   **监控盲区风险**：依赖该 GeoJSON 层进行监控的 SRE 团队，可能因为数据陈旧而产生“监控盲区”。例如，新增的监控站点或已移除的故障点无法在地图上及时反映，影响态势感知。
-   **事件响应效率**：在事件响应过程中，过时的站点布局或资产位置信息可能误导工程师，延误故障定位和恢复。

### 最佳实践与反模式
-   **反模式**：将频繁变更的实时数据（如动态资产位置）仅通过静态 GeoJSON 文件 URL 提供给 Geomap 面板，因为其更新机制不可靠。
-   **最佳实践**：
    -   **数据源选型**：对于需要实时更新的地理数据，优先考虑使用支持轮询或推送的 Grafana 数据源插件（如 MQTT、HTTP API），将数据作为点位（Markers）动态渲染，而非依赖静态 GeoJSON 文件。
    -   **数据新鲜度 SLO**：如果确实必须使用静态文件，应明确其数据新鲜度的 **SLO（服务级别目标）**，并接受此限制。同时，在文档中注明该地图数据的更新延迟和刷新方法。
    -   **主动刷新机制**：设计包含“手动刷新”按钮的仪表盘，并明确告知用户在数据源可能变更时需要手动操作，以此作为对当前局限性的补偿。

### 相关指标
此问题本身不直接产生 **SLI（服务级别指标）**，但它会影响依赖于此面板的其他监控指标的可信度。SRE 团队可以建立一个**元指标**来监控此类可视化数据的“新鲜度”，例如，通过对比源文件修改时间与 Grafana 面板最后成功加载时间，来度量数据延迟。
