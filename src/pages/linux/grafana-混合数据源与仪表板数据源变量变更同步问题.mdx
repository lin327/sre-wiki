## 概述

在 Grafana 仪表板中，变量是实现动态数据查询和视图交互的核心功能。一个常见的 SRE 实践是使用 `-- Mixed --` 数据源来组合多个查询，并利用 `-- Dashboard --` 数据源引用仪表板上其他面板的查询结果，以构建复杂的派生视图或对比分析。然而，此场景存在一个已知缺陷：当仪表板变量发生变更时，使用 `-- Mixed --` 数据源并包含 `-- Dashboard --` 子数据源的面板**不会自动刷新**，其更新依赖于用户手动点击刷新按钮。此问题破坏了仪表板的预期交互逻辑，可能导致 SRE 人员基于过时数据做出判断，影响故障响应和系统监控的可靠性。

## 核心概念

- **Mixed 数据源 (`-- Mixed --`)**：Grafana 的一个特殊数据源类型，允许在一个面板内配置来自不同后端数据源的多个查询。它本身不查询数据，而是作为查询的路由和聚合层。
- **Dashboard 数据源 (`-- Dashboard --`)**：另一个特殊数据源，允许面板直接引用同一仪表板上其他面板的查询结果。这常用于数据复用，避免重复定义复杂的查询逻辑。
- **变量 (`Variable`) 与刷新机制**：Grafana 变量用于动态参数化查询（例如，`WHERE region = $region`）。当变量值改变时，Grafana 会重新评估所有依赖该变量的查询，并更新相应面板。
- **数据依赖链**：在此问题场景下，存在一个数据依赖链：`变量变更` -&gt; `更新“主面板”` -&gt; `“混合面板”应通过“仪表板数据源”读取“主面板”的最新结果并更新`。当前的缺陷在于该链条的最后一环未能被自动触发。

## 实践

### 问题重现

根据问题报告，可以通过以下最小配置重现该缺陷：

1.  **创建仪表板变量**：创建一个自定义变量（例如名为 `example`），选项为 `1,10,100`。
2.  **创建主面板**：创建一个面板（例如 Stat 类型），数据源为一个常规数据源（如 PostgreSQL）。在其查询中使用上述变量（例如，SQL 中的 `random() * $example`）。
3.  **创建混合面板**：
    *   将面板的数据源设置为 `-- Mixed --`。
    *   在查询配置中，将查询 A 的数据源设置为 `-- Dashboard --`，并指向步骤 2 中创建的“主面板”的 ID。
4.  **验证缺陷**：更改变量 `example` 的值。观察到“主面板”数据已更新，但“混合面板”的数据保持不变，直到手动刷新整个仪表板。

一个可直接导入复现此问题的仪表板 JSON 已包含在 [原始 Issue](https://github.com/grafana/grafana/issues/113579) 中。

### 解决方案与规避方法

在 Grafana 官方修复此缺陷之前，SRE 可采用以下方法规避：

1.  **避免在混合数据源中直接使用 Dashboard 数据源**：这是最直接的规避方式。如果需要关联多个数据源的结果，考虑在后端服务层进行数据聚合，或使用其他可视化手段（如报表导出）。
2.  **使用模板化查询替代引用**：不使用 `-- Dashboard --` 数据源来引用另一个面板，而是将相同的查询逻辑和变量模板直接配置在“混合面板”的各个子查询中。这虽然增加了配置的冗余，但能确保每个查询都响应变量变更。
3.  **添加面板刷新选项**：作为临时措施，可以为“混合面板”启用自动刷新（通过 `面板 -&gt; 选项 -&gt; Refresh` 设置），但这会带来额外的数据源请求开销，且刷新间隔可能不完全匹配变量变更的时机。

## SRE 要点

- **与可靠性的关联**：仪表板的准确性与及时性直接关系到 SRE 对系统状态的判断。变量驱动的动态视图失效，可能导致运维人员遗漏关键变化，延迟事件响应。例如，用于故障排查的仪表板若因变量变更（如切换集群）后数据未更新，将误导问题定位方向。
- **可观测性原则**：此问题违背了可观测性中“数据应及时反映系统真实状态”的原则。监控数据的“新鲜度”（Data Freshness）是一项关键的非功能性指标。SRE 应在构建仪表板时测试变量交互的完整性，避免此类单点失效。
- **最佳实践**：
    *   **测试变量驱动视图**：在关键监控仪表板上线前，系统性地测试所有变量变更是否触发预期的数据更新。
    *   **简化数据流**：优先使用简单、直接的数据源配置。复杂的嵌套引用（如混合数据源引用仪表板数据源）会引入隐蔽的故障点。
    *   **文档化已知限制**：对于无法立即修复的工具缺陷，应在团队内部文档中明确记录其影响范围和规避方法。
- **相关指标（SLI/SLO/SLA）**：
    *   **SLI**：可以定义“仪表板关键变量变更后，所有面板在 X 秒内自动完成数据刷新的比例”。
    *   **SLO**：针对关键监控仪表板，可设立“99.9% 的变量变更能在 10 秒内引发所有相关面板更新”的内部目标。
    *   **SLA**：该缺陷是 Grafana 产品本身的已知问题，其修复优先级将影响基于 Grafana 构建的监控平台的 SLA 条款中关于“仪表板功能完整性”的承诺。SRE 在与内部用户协商 SLA 时需考虑此类工具链限制。

此问题反映了监控工具链中数据流自动化的重要性，SRE 需要深刻理解所用工具的特性与局限，并将其纳入系统可靠性设计考量。相关概念如 [[grafana-variables]] 和 [[dashboard-design-best-practices]] 也值得进一步了解。
