# Grafana 面板尺寸影响转换计算结果

## 概述

在 SRE 实践中，基于 Grafana 的仪表板是监控和呈现系统健康状况、服务 [[service-level-objective|SLO]] 进度及事件趋势的关键界面。仪表板上数据的准确性与一致性是可靠性的基石。本文档记录了 Grafana v13.0.1 中发现的一个特定 Bug：**面板的尺寸（高度/宽度）会影响经过转换（Transformations）计算后的数据值**。这一问题直接威胁到监控数据的可信度，可能导致 SRE 在事件响应或容量规划中做出基于错误数据的决策。

## 核心概念

理解此问题涉及以下几个 Grafana 的核心概念：

1.  **面板尺寸**：在 Grafana 仪表板中，每个面板（Panel）占据一个由行列网格定义的空间。用户可以通过拖拽来调整其大小。
2.  **转换 (Transformations)**：这是 Grafana 提供的一种数据处理能力，允许用户在数据从数据源查询返回后、在面板渲染前，对数据进行过滤、合并、重组或计算。常见的转换包括 `Reduce`（将多行数据聚合为一行）、`Binary Operations`（进行加、减、乘、除等二元运算）以及 `Calculate field`（创建基于现有字段的计算字段）。
3.  **预期行为**：面板的物理显示尺寸应仅影响视觉呈现（如图表密度、标签可读性），而不应影响对底层查询结果的数据处理逻辑。相同的查询、相同的转换，在不同大小的面板上应产生完全一致的输出值。
4.  **实际观察行为 (Bug)**：在特定环境下（Grafana v13.0.1），当面板在仪表板中尺寸较小时，通过转换计算得到的聚合值会显著低于预期值；随着面板尺寸增大，计算结果会成比例增加，但仍然可能不是完全正确的值。关键在于，底层的数据库（如 OpenSearch）查询本身是恒定且正确的。

## 实践

### 问题复现步骤

根据报告，复现此问题需要以下设置：

1.  **数据源**：配置一个 OpenSearch (2.33.1) 数据源。
2.  **面板查询**：创建一个包含至少两个查询的面板。
3.  **转换应用**：在面板的 “Transform” 选项卡中，依次添加转换：
    *   `Reduce`: 对查询结果行进行聚合（例如，求和、计数）。
    *   `Calculate field`: 基于上一步的聚合结果创建新的计算字段。
    *   `Binary Operation`: 使用创建的计算字段进行二元运算（例如，除法以计算比率）。
4.  **触发问题**：
    *   在仪表板中保存该面板。
    *   将面板拖拽到一个较小的尺寸，刷新仪表板，观察计算值（应偏低）。
    *   再将面板拖拽到一个较大的尺寸，刷新仪表板，观察计算值（会变化，可能仍不正确）。

### 排查与缓解思路

对于 SRE 而言，遇到此类问题时的排查和临时缓解思路如下：

1.  **验证查询**：首先，如报告者一样，**独立验证数据源层面的查询结果是否正确**。这可以通过直接访问 OpenSearch 的查询分析工具或运行相同的查询来完成，以排除数据源问题。
2.  **隔离变量**：在 Grafana 内，尝试移除所有转换，仅显示原始查询结果，观察其是否随面板尺寸变化。如果原始数据稳定，则问题锁定在转换处理环节。
3.  **检查版本与更新**：明确记录当前 Grafana 版本（本例为 v13.0.1）。问题报告指出在更新到 v13 后出现，建议关注 Grafana 官方对该 issue 的修复状态，并计划在有修复版本后及时升级。
4.  **临时规避**：在官方修复发布前，可考虑以下临时措施：
    *   避免在关键仪表板的面板中使用涉及多步聚合和二次计算的复杂转换，尤其是这些值是监控 [[service-level-objective|SLO]] 或关键错误预算（Error Budget）的主要依据时。
    *   尝试将复杂的计算逻辑移至数据源查询（如 OpenSearch 的 Painless 脚本）或独立的预处理层中完成，仅让 Grafana 面板负责展示已计算好的最终值。

## SRE 要点

### 与可靠性、可观测性、事件响应的关联

*   **可观测性数据完整性受损**：此 Bug 破坏了“所见即所查”的基本原则。仪表板上展示的衍生指标与真实系统状态出现偏差，严重削弱了系统的可观测性。
*   **事件响应风险**：当 SRE 基于仪表板上的错误指标（如错误率、请求延迟的聚合值）发起或评估一个事件响应时，可能会导致错误的误判（将正常情况误判为故障）或漏判（未能发现真正的故障），延长 MTTR（平均修复时间）。
*   **容量规划误导**：基于此类面板的容量趋势预测也可能失真，导致过度配置或配置不足。

### 最佳实践与常见反模式

*   **最佳实践**：
    *   **数据源侧计算**：尽可能将核心的、用于决策的指标计算逻辑放在数据源查询或数据管道中完成，确保其一致性。Grafana 面板更多用于展示和探索。
    *   **关键面板验证**：对于显示关键 SLO/SLI 或成本相关指标的面板，应定期（或通过自动化测试）验证其计算结果在不同视图（如不同尺寸、不同仪表板）下的一致性。
    *   **版本管理与测试**：在升级 Grafana 等核心可观测性平台前，在非生产环境充分测试，特别是检查现有仪表板的数据呈现是否发生变化。
*   **常见反模式**：
    *   **过度依赖客户端计算**：将复杂、多层的指标计算完全交由 Grafana 前端的转换功能处理，增加了前端表现不确定性带来的风险。
    *   **忽视版本更新影响**：未将 Grafana 纳入关键基础设施的版本管理流程，对版本更新可能引入的回归问题准备不足。

### 相关指标（SLI/SLO/SLA）

此问题直接影响以下可观测性指标：

*   **仪表板数据准确性 (SLI)**：这是一个针对监控系统自身可靠性的 SLI。可以定义 SLO 为“关键仪表板上所有基于转换的聚合指标值，与数据源查询直接返回的聚合值偏差小于 0.1%”。此 Bug 会导致该 SLO 的违规。
*   **SLI 数据可靠性**：对于依赖 Grafana 作为唯一或主要可视化来源的 SLI（如“服务可用性”），此问题可能导致该 SLI 的**数据可靠性下降**。SRE 需在评估 SLI 时考虑此潜在误差源。
*   **错误预算消耗**：如果因使用此错误数据而触发不必要的事件响应或进行了错误的变更，可能会消耗宝贵的 [[error-budget|错误预算]]。
