## 概述
在 SRE 实践中，清晰、及时且可操作的告警通知是有效事件响应的基础。Grafana Alerting 提供了强大的通知策略（Notification Policy）机制，用于控制告警如何被分组、路由和发送。一个常见的需求是将具有不同标签（例如不同 `cluster`）的告警拆分成独立的通知消息，以避免单条通知包含过多告警（如“32 firing alerts”），从而便于快速定位问题。然而，根据提供的案例，即使正确配置了 `not_grouping` 参数，告警通知仍可能被意外地聚合在一起，这会严重影响运维人员的判断和处理效率。

## 核心概念
在深入了解问题前，需要明确几个关键概念：
1.  **告警分组（Grouping）**：Grafana Alerting 默认会将具有相同标签集的告警组合在一起，形成一个“告警组”，并通过一条通知消息发送。这由通知策略中的 `group_by` 字段控制。默认的 `group_by` 通常是 `alertname`。
2.  **通知策略（Notification Policy）**：这是一个树状路由结构，决定了哪些告警（基于标签）应该被发送到哪个联系点（Contact Point）。它包含路由匹配规则、分组规则（`group_by`）、等待时间等。
3.  **`not_grouping`**：这是一个特殊的 `group_by` 值。理论上，将其设置在某个通知策略节点上，意图是让该节点下的告警不参与任何分组，即每个告警都作为独立的消息发送。这正是案例中用户尝试使用的配置。
4.  **策略继承**：子通知策略会继承父策略的配置，除非被显式覆盖。案例中，用户创建了一个子策略，并试图用 `not_grouping` 覆盖继承自父策略的 `group_by` 设置。

## 实践
案例中描述的问题，根源在于对 Grafana Alerting 的**通知分组机制**理解不足。当设置 `group_by` 为 `not_grouping` 时，其含义是“不对这些告警应用任何分组标签”。但是，这并不意味着它们不会被**其他规则**分组。

关键的实践经验是：**Grafana Alerting 的通知分组是由最具体的匹配策略决定的，但其行为遵循一个核心逻辑——如果告警在被发送前，在路由树的任何上级节点被分组了，那么这个分组就会被保留。**

针对此案例，正确的操作路径和检查点如下：

1.  **检查路由树匹配**：确保你的告警规则生成的告警，其标签能够匹配到你设置了 `not_grouping` 的那个**特定的子通知策略**。仅检查规则的“通知路由预览”显示该策略是不够的，还需要确认告警没有先被匹配到其他更早的、且带有不同 `group_by` 规则的策略节点。
2.  **验证策略配置**：进入 `Alerting -&gt; Contact Points -&gt; Notification Policies`，仔细检查从根策略到你子策略的完整路径。确认除了你想要配置 `not_grouping` 的节点外，其父节点或根节点的 `group_by` 设置没有意外地将这些告警提前分组。根策略的 `group_by: ['alertname']` 是默认设置。
3.  **使用 `group_wait` 和 `group_interval` 进行调试**：在设置 `not_grouping` 的策略节点上，可以尝试将 `group_wait` 和 `group_interval` 设置为非常小的值（如 `0s`），这有助于立即观察告警是否被拆分发送，排除等待时间导致误判的可能。
4.  **理解“最简分组”规则**：即使配置了 `not_grouping`，如果一个告警在路由匹配过程中，**没有匹配到任何一条明确指定了 `group_by` 字段的策略规则**，它最终仍会使用根策略的 `group_by` (通常是 `['alertname']`) 进行分组。因此，必须确保告警的匹配路径上存在你希望应用的分组策略。

简而言之，要实现“按每个告警单独发送”，你需要确保告警的匹配路径终止于一个设置了 `group_by: []`（空数组，而非 `not_grouping`）的策略节点。`not_grouping` 关键字的实际行为是“使用默认分组”，这在很多版本中容易造成混淆。

## SRE 要点
### 与可靠性的关联
告警通知的分组策略直接影响**事件响应的时效性和准确性**。告警风暴或信息过载会拖慢 MTTR（Mean Time To Resolution）。将相关的告警适度分组是有益的，但将不相关的告警（如不同集群的同类告警）混在一起则会产生噪音。一个经过精心设计的通知策略，是保障监控系统有效性和团队工作效率的关键环节。

### 最佳实践与常见反模式
- **最佳实践**：
  - 遵循 **“单一关注点”** 原则设计通知策略路由，让每个策略节点负责处理特定类型或特定业务域的告警。
  - 在测试环境充分验证通知策略的路由和分组效果，利用 Grafana 提供的“模拟通知”功能。
  - 对 `group_by` 的配置添加注释，说明其设计意图（例如：`# 按集群分组，便于SRE按环境处理`）。
- **常见反模式**：
  - **配置但未验证**：如案例所示，配置了 `not_grouping` 但未深入验证其在完整路由链中的实际效果。
  - **忽略继承关系**：没有意识到子策略会继承父策略的 `group_by`，导致需要覆盖的配置未生效。
  - **过度分组**：为了清静而将 `group_by` 设置为过于宽泛的标签，导致相关告警被淹没。

### 相关指标
- **SLO 与错误预算**：告警通知的有效性本身可以是一个**内部服务级别目标（SLO）**。例如，“所有 P1 告警通知必须在触发后 X 分钟内送达指定人员”。无效的分组（信息过载或缺失）可能导致“通知已送达”但“信息无法被有效利用”，这间接影响了基于告警的 SLO 达成。
- **告警质量指标**：可以监控“通知中的平均告警数量”或“被静默的告警比例”等衍生指标，这些指标异常可能暗示分组策略存在问题。
