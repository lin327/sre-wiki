# Portal 嵌套渲染顺序修复与 UI 可靠性

## 概述
在 Grafana 等复杂前端应用中，组件库（如 Portal、Combobox、Modal）的可靠渲染是用户体验的基础。`Portal` 组件常用于将子元素渲染到 DOM 树的其他位置（如模态框容器），以解决 CSS 上下文（如 `overflow: hidden`）或层级问题。然而，当多个 `Portal` 组件嵌套并指向同一目标容器时，React 的渲染机制会导致视觉层级错乱，这直接构成了一个 **UI 层面的可靠性问题**。本页面总结了该问题的成因、通用解决方案及其在 SRE 实践中的意义。

## 核心概念
### React Portal 与 DOM 渲染顺序
`Portal` 是 React 提供的将子节点渲染到 DOM 树中不同位置的机制。其核心特点在于：
- **解耦组件树与 DOM 树**：Portal 内的组件仍然保留 React 上下文，但其 DOM 节点位于父组件之外。
- **由 React 提交驱动**：当多个 `Portal` 组件渲染到同一个 DOM 容器时，React 的协调器（Reconciler）是**自底向上**地提交（commit）fiber 节点。这导致内层 `Portal` 的 DOM 节点先于外层 `Portal` 的节点被插入目标容器，从而**颠倒了预期的视觉层级**。

### 层级控制：Z-Index 与嵌套深度
解决视觉层级错乱的关键在于控制 CSS `z-index`。原生的 `z-index` 是静态值，无法感知组件嵌套关系。解决方案引入了**动态上下文追踪**：
1.  **嵌套深度追踪**：通过 React Context 在 `Portal` 组件层级间传递并递增“嵌套深度”值。
2.  **动态 Z-Index 计算**：内层 `Portal` 根据更深的嵌套深度值，自动计算出更高的 `z-index`，确保其始终覆盖在外层 `Portal` 之上，从而纠正了 React 提交顺序带来的视觉倒置。

## 实践
### 问题复现与修复方案
**问题场景**：两个 `Portal` 组件嵌套，外层 `Portal` 是下拉菜单的容器，内层 `Portal` 是菜单中的模态框或另一个弹出层。当它们渲染到同一容器时，模态框可能被菜单背景遮挡。

**修复原理**：
1.  **引入 `PortalContext`**：在 `Portal` 组件内部创建一个 Context，其值为当前嵌套深度。
2.  **深度计算与传递**：每个 `Portal` 在渲染时，读取父 Context 的深度值并加 1，然后将新值传递给其 Context.Provider。
3.  **样式应用**：`Portal` 组件根据计算出的深度值，为渲染目标节点动态设置 `style={{ zIndex: calculatedZIndex }}`。

```javascript
// 简化示例：Portal 组件修复逻辑
const PortalContext = React.createContext(0);

function Portal({ children, container }) {
  const parentDepth = useContext(PortalContext);
  const currentDepth = parentDepth + 1;
  // 基于深度计算z-index，例如：baseZIndex + currentDepth * 100
  const style = useMemo(() => ({ zIndex: baseZIndex + currentDepth * 100 }), [currentDepth]);

  return (
    <PortalContext.Provider value={currentDepth}>
      {ReactDOM.createPortal(
        <div style={style}>{children}</div>,
        container
      )}
    </PortalContext.Provider>
  );
}
```

**附加清理**：此次修复同时移除了 `Combobox`/`MultiCombobox` 组件上用于解决类似问题的 `portalContainer` 属性。这表明通用方案比组件级的特定配置更优，减少了维护负担和 API 复杂度。

## SRE 要点
- **与可靠性及可观测性的关联**：
    - **用户界面可靠性**：此类修复属于**功能可靠性**范畴。视觉层级错乱会导致用户无法正常交互（例如，点击被遮挡的元素），是严重的功能障碍。
    - **可观察性**：修复后的组件行为更可预测。前端监控工具（如 Sentry、Datadog RUM）能更准确地报告用户交互路径，因为界面元素始终按预期可见和可点击。
    - **事件响应**：对于依赖 Grafana UI 进行告警配置或数据可视化的用户，组件的视觉错乱可能间接导致配置错误或数据读取错误，需要被纳入 **用户体验事件** 的范畴。

- **最佳实践与常见反模式**：
    - **反模式**：为解决单一组件的层级问题，而引入组件专属的容器属性（如旧的 `portalContainer`）。这会导致 API 膨胀和逻辑分散。
    - **最佳实践**：**通过通用基础设施（如 Context）解决通用问题**。确保基础组件（如 `Portal`）的健壮性和正确性，能提升整个组件库的可靠性，符合“为失败而设计”的原则。

- **相关指标（SLI/SLO/SLA）**：
    - **SLI (Service Level Indicator)**：可关注 **“关键用户交互成功率”**。例如，“在 Grafana 探索功能中，成功打开并使用嵌套菜单/模态框的会话占比”。
    - **SLO (Service Level Objective)**：为上述 SLI 设定目标，例如“99.5% 的复杂 UI 交互操作在无视觉异常下完成”。
    - 此修复直接贡献于提升该 SLI，从而帮助达成 SLO。在发布此修复后，可通过用户会话录制与重放工具（如 Cypress, Playwright）的回归测试，来验证相关场景的成功率是否提升。

此案例强调，在分布式系统与复杂前端应用中，**组件层的微小缺陷会级联为用户体验的显著退化**。SRE 的关注点应从后端服务延伸到关键前端组件的可靠性，通过通用的、可组合的解决方案构建更稳健的系统。
