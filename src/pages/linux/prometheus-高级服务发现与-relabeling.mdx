## 概述

在云原生和动态基础设施环境中，监控目标（Targets）的地址和元数据会频繁变化。手动维护静态目标列表不可持续。服务发现（Service Discovery）机制允许 Prometheus 自动发现和跟踪这些变化的目标，是构建可扩展、高可靠监控系统的基石。Prometheus v0.14.0 版本显著增强了这方面的能力，引入了对 **Consul** 和基于**文件**的自定义服务发现的原生支持，并强化了 **Relabeling** 机制，为从服务发现源提取和转换元数据提供了强大的灵活性。掌握这些技术是 SRE 实践中确保监控系统自身可靠性和可维护性的关键一环。

## 核心概念

### 服务发现（Service Discovery）
指 Prometheus 与基础设施（如 DNS、Consul、Kubernetes API、云平台 API 或自定义脚本）集成，以动态获取被监控目标列表的过程。它取代了传统的静态配置，使得监控系统能够自适应地反映服务拓扑的变化。

### Relabeling 机制
这是 Prometheus 在标签处理流水线中的最后一步，也是最强大的一步。它允许在目标被抓取前，对与之关联的任意标签进行创建、修改或删除操作。该过程基于正则表达式匹配和标签值重组，可以实现：
1.  从服务发现提供的元数据标签（如 `__meta_consul_tags`）中提取信息，生成新的、结构化的标签（如 `region`, `version`）。
2.  过滤掉不需要抓取的目标（例如，只抓取带有 `production` 标签的实例）。
3.  标准化标签格式，为后续的查询和告警规则提供一致的数据模型。

### 元数据标签（Meta Labels）
以 `__` 开头的标签，由服务发现机制自动附加到目标上（例如 `__meta_dns_name`, `__meta_consul_service`）。这些标签**不会**出现在最终抓取到的时间序列中，它们仅作为 Relabeling 阶段的输入数据源。Relabeling 阶段结束后，这些临时标签将被丢弃。

## 实践

### 1. 利用 DNS-SRV 记录发现与提取区域信息
通过结构化的 SRV 记录名称，我们可以使用 Relabeling 自动提取“区域”（zone）和“作业”（job）标签。

```yaml
scrape_configs:
- job_name: 'myjob'

  dns_sd_configs:
  - names:
    - 'telemetry.eu-west.api.srv.example.org'
    - 'telemetry.us-east.auth.srv.example.org'

  relabel_configs:
  # 从 SRV 记录名中提取区域（如 eu-west）
  - source_labels: ['__meta_dns_name']
    regex:         'telemetry\.(.+?)\..+?\.srv\.example\.org'
    target_label:  'zone'
    replacement:   '$1'
  # 从 SRV 记录名中提取作业名（如 api, auth）
  - source_labels: ['__meta_dns_name']
    regex:         'telemetry\..+?\.(.+?)\.srv\.example\.org'
    target_label:  'job'
    replacement:   '$1'
```

### 2. 基于 Consul 的服务发现与分组
Prometheus 可以从 Consul Agent 获取服务列表及其元数据。利用 Consul 的标签（Tags）来区分不同的部署环境。

```yaml
scrape_configs:
- job_name: 'consul-discovery'

  consul_sd_configs:
  - server:   '127.0.0.1:8500'
    services: ['auth', 'api', 'load-balancer', 'postgres']

  relabel_configs:
  # 将 Consul 服务名映射为 job 标签
  - source_labels: ['__meta_consul_service']
    target_label:  'job'
  # 将 Consul 节点名映射为 instance 标签（覆盖默认的 IP:port）
  - source_labels: ['__meta_consul_node']
    target_label:  'instance'
  # 从 Consul 标签中提取部署组（如 production, canary）
  - source_labels: ['__meta_consul_tags']
    regex:         ',(production|canary),'
    target_label:  'group'
    replacement:   '$1'
```

### 3. 基于文件的自定义服务发现
适用于需要对接非标准服务注册表或自定义逻辑的场景。你需要编写一个桥接程序，定期将服务发现结果写入特定格式的文件。

**目标组文件示例 (`tgroups/db.json`):**
```json
[
  {
    "targets": ["10.11.150.1:7870", "10.11.150.4:7870"],
    "labels": { "job": "mysql", "env": "prod" }
  }
]
```

**Prometheus 配置监控该文件：**
```yaml
scrape_configs:
- job_name: 'file-based'

  file_sd_configs:
  - names: ['tgroups/*.json'] # 监控目录下所有 JSON 文件
```

**桥接程序伪代码逻辑（以 Python 为例）：**
1.  从自定义数据源（如数据库、API）查询服务实例列表。
2.  按逻辑（如服务类型、环境）分组，构造上述 JSON 结构。
3.  **原子性地**将新文件写入临时路径，然后通过重命名覆盖目标文件，确保 Prometheus 读取到完整的、一致的配置。

## SRE 要点

### 与可靠性的关联
- **动态适应性**：自动的服务发现确保监控覆盖能随生产环境变化而调整，避免因遗漏新实例或监控已下线实例而产生告警风暴或盲区，这是 [[monitoring]] 系统自身可靠性的体现。
- **减少配置漂移**：声明式的服务发现配置（特别是 Consul、文件方式）比手动维护静态列表更不容易出错，降低了人为配置错误导致的监控故障风险。
- **故障隔离**：利用 Relabeling 过滤功能，可以轻松实现按环境（`env=prod`）、集群（`cluster=us-east`）分组监控和告警，实现故障域隔离。

### 最佳实践与反模式
- **最佳实践**：
    - **使用元数据标签**：充分利用服务发现提供的 `__meta_*` 标签，这是构建丰富监控维度的基础。
    - **原子化文件更新**：对于基于文件的服务发现，始终通过“写临时文件 -&gt; 重命名”的方式更新，避免 Prometheus 读取到半写状态的文件。
    - **分离逻辑分组**：将大量目标组拆分到不同的文件中，便于管理和调试。
    - **Relabeling 顺序**：注意 Relabeling 规则的执行顺序，后面的规则会覆盖前面设置的同名标签。
- **常见反模式**：
    - **忽视元数据**：直接使用 `__address__` 作为标签，忽略服务发现提供的丰富上下文（如版本、区域），导致告警规则和仪表盘缺乏必要维度。
    - **过度复杂的 Relabeling**：试图在一个 Relabeling 规则中完成过于复杂的转换，导致规则难以阅读和维护。应拆分为多个简单步骤。
    - **硬编码环境信息**：在 Relabeling 规则中硬编码环境标签，而不是从 Consul Tags 或文件标签等动态源提取，削弱了自动化的灵活性。

### 相关指标与考量（SLI/SLO）
- **SLI**: 服务发现系统的**覆盖率**可以作为一个 SLI，即通过自动发现的实例数 / 预期应被监控的实例总数。
- **SLO**: 可以为“服务发现覆盖率”设定 SLO，例如“99.9% 的生产实例在部署后5分钟内被 Prometheus 自动发现”。
- **Error Budget**: 如果覆盖率 SLO 出现亏损，可能意味着需要优化服务发现集成（如调整 Consul Agent 刷新间隔）或检查桥接程序的健壮性，这是消耗 [[error-budget]] 的一个场景。
