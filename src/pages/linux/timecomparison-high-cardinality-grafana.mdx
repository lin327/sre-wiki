# TimeComparison: High Cardinality (Grafana)

## 概述

在 SRE 的日常工作中，基于 Grafana 的时间序列数据对比分析（如对比当前时段与上一时段）是排查性能回退、发现异常流量模式的关键手段。`TimeComparison` 功能正是为此设计。然而，当监控指标具有**高基数**（High Cardinality）特性时（即时间序列拥有大量唯一的标签组合，例如 `user_id`, `request_path`），该功能可能遭遇性能瓶颈或显示错误。本页面聚焦于 Grafana 在此场景下的一个已知问题及其修复，旨在帮助 SRE 理解潜在风险并采取最佳实践。

## 核心概念

- **高基数（High Cardinality）**: 指时间序列数据库（如 Prometheus, Loki）中某个标签（Label）拥有大量唯一值。高基数会导致时间序列数量爆炸式增长，对存储、查询和可视化性能产生巨大压力。这是 SRE 在设计监控体系和 SLI 时必须谨慎控制的反模式之一。
- **TimeComparison 功能**: 在 Grafana 中，这通常指在面板（Panel）设置中启用“比较（Compare）”选项，以便在同一个图表上同时显示当前时间段的数据和过去某个参考时间段的数据，用于直观对比趋势。
- **问题本质**: 原始 Issue 指出，当查询返回大量时间序列（Many Series），**并且**比较窗口（例如，对比过去 1 小时）返回的时间序列标签集与当前窗口不完全一致时，会出现显示错误或崩溃。这本质上是一个数据对齐和渲染层面对高基数场景处理不足的缺陷。

## 实践

当遇到此类问题时，可采取以下措施：

1.  **诊断与规避**:
    - **观察 UI 表现**: 面板可能长时间加载、显示“无数据”或出现 JavaScript 错误。
    - **检查查询结果集**: 在 Grafana 的查询编辑器中，点击“查询历史”或使用“数据检查”视图，确认返回的时间序列数量。如果数量极大（例如数千或更多），则可能触发了此问题。
    - **临时规避**: 考虑在对比查询中主动添加或简化标签，以减少基数。例如，对比时忽略 `user_id` 标签，仅对比 `service` 级别的聚合数据。

2.  **升级与修复**:
    - **升级 Grafana 版本**: 此问题已在后续版本中得到修复。确保你的 Grafana 实例升级到包含了此修复的版本（请参考官方 Release Notes 或 Issue 中的链接）。
    - **验证修复**: 升级后，在相同面板上再次运行高基数对比查询，验证显示是否恢复正常。

## SRE 要点

- **与可靠性的关联**: 监控系统自身的可靠性（Monitoring the Monitor）至关重要。此类 UI/渲染层 bug 会直接导致 SRE 无法有效使用关键分析工具，影响事件响应速度和准确性，属于**可用性降级**。它提醒我们，监控栈组件（如 Grafana）的稳定性也是整体系统可靠性的一部分。
- **最佳实践与反模式**:
    - **控制基数（最佳实践）**: 从源头设计上避免高基数标签，或使用 **Recording Rules** 预聚合高基数数据，生成可供比较的聚合时间序列。
    - **分片与采样（最佳实践）**: 对于必须保留的高基数原始数据，考虑使用支持高效查询的后端（如 Mimir, VictoriaMetrics）或启用采样。
    - **忽视基数（反模式）**: 无限制地使用动态用户 ID、请求 ID 等作为标签，不仅会引发此类显示问题，更会导致 TSDB 压力剧增、查询变慢，严重时可能影响整个监控平台的可用性。
- **相关指标 (SLI/SLO)**:
    - **SLI**: 可定义为 “Grafana 面板在处理对比查询时的成功渲染次数与总尝试次数之比”。
    - **SLO**: 对核心监控面板，可设定如 “99.5% 的时间对比分析功能可正常响应” 的目标。此 bug 的修复直接贡献于该 SLO 的达成。
