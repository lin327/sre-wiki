## 概述

在 Grafana 等复杂系统中，资源的存储版本（`storedVersion`）是客户端识别资源磁盘格式、确保向后兼容性以及进行版本转换的关键元数据。本次修复（源自 PR #124707）解决了仪表板 API 响应中 `status.conversion.storedVersion` 字段未能准确反映资源实际存储版本的问题。在修复前，无论仪表板以何种版本存储，该字段可能始终显示旧版本（如 `v0alpha1`），这严重影响了 API 消费者对数据真实状态的判断，可能导致迁移工具误判或数据转换逻辑失效。从 SRE 视角看，准确的元数据是保障系统可观测性、可诊断性和 API 契约可靠性的基石。

## 核心概念

本修复围绕几个关键概念展开：

*   **GVK (Group-Version-Kind)**：API 对象的标识符，由 API 组（Group）、版本（Version）和类型（Kind）组成。存储层在解码字节流时会确定其 GVK，这是填充 `storedVersion` 的权威来源。
*   **`status.conversion.storedVersion` 字段**：嵌入在仪表板 API 响应状态中的一个字符串字段，用于声明该资源在持久化存储中所使用的 API 版本。客户端依赖此字段来推断磁盘上的编码格式。
*   **存储层修复（主要路径）**：引入了一个名为 `apistore.DecodedVersionAware` 的通用可选接口。当 API 存储层（如 `Storage.convertToObject`）完成对存储字节流的解码后，会检查解码后的对象是否实现了此接口。若是，则调用其 `SetDecodedVersion(version string)` 方法，将解码时确定的真实 GVK 版本写入 `storedVersion` 字段。这确保了通过标准 Get/List/Watch 路径获取的数据具有准确的版本信息，并能覆盖存储字节中可能存在的陈旧值，同时保留其他转换状态字段（如 `failed`、`error`）。
*   **DTO 构建器修复（纵深防御）**：作为补充，在构建 API 响应的数据传输对象（DTO）时，仍会调用现有的 `conversion.EnsureStoredVersion` 辅助函数。此函数遵循“仅在为空时填充”的语义。在正常的存储读取路径下，由于存储层已填充该字段，此操作是空操作（no-op）。它作为一道防线，确保任何绕过标准存储路径的代码（例如在单元测试或特定逻辑中直接构造仪表板对象）也能生成一个合理的、有依据的 `storedVersion` 值。

## 实践

此次修复的实现分为两个协同工作的层面：

1.  **存储层注入解码版本**：
    *   在 API 存储层的通用代码中定义 `apistore.DecodedVersionAware` 接口。
    *   在 `Storage.convertToObject` 方法中，于 `codec.Decode` 调用后，获取解码器报告的 GVK。
    *   检查解码出的对象是否实现 `SetDecodedVersion`，如果是，则调用该方法并传入获取到的版本字符串。
    *   所有五个仪表板版本（v0alpha1, v1, v1beta1, v2alpha1, v2beta1, v2）的 `Dashboard` 类型均实现此接口，将版本字符串写入 `status.conversion.storedVersion`。

2.  **保留既有 DTO 构建逻辑**：
    *   在 `DashboardsAPIBuilder.UpdateAPIGroupInfo` 中注册的六个版本 DTO 构建器闭包，在将 `*dash` 赋值给 `dto.Dashboard` 之后，继续调用 `conversion.EnsureStoredVersion(d, fallback)`。
    *   这一调用在常规读取路径下成为“无操作”，因为存储层已确保 `storedVersion` 有值，从而避免了覆盖。但在其他路径下，它提供了一个兜底逻辑。

**验证步骤（基于测试计划）**：
*   运行特定的单元测试套件以验证存储层和 DTO 构建器的行为：
    ```bash
    go test ./pkg/storage/unified/apistore/... \
            ./pkg/registry/apis/dashboard/... \
            ./apps/dashboard/pkg/migration/conversion/... \
            ./apps/dashboard/pkg/apis/dashboard/...
    ```
*   手动验证：在开发实例中，创建一个 v2beta1 版本的仪表板，分别通过 `dashboard.grafana.app/v2beta1` 和 `dashboard.grafana.app/v1` 端点获取它，并确认两个响应的 `status.conversion.storedVersion` 字段均为 `v2beta1`。

## SRE 要点

*   **与可靠性的关联**：此修复直接提升了 API 响应的准确性，是构建可靠系统契约的关键一步。错误的 `storedVersion` 可能导致基于版本的自动化工具（如迁移脚本、验证器）产生错误决策，进而影响数据一致性或升级流程的可靠性。
*   **最佳实践**：
    *   **权威来源原则**：应从解码流程中获取版本信息，而非依赖存储数据中可能被静态写入或在跨版本读取时已过期的值。
    *   **纵深防御**：在存储层（主要路径）和 DTO 构建层（防御路径）同时实施修正，确保了不同代码路径下的行为一致性。
    *   **变更的最小性**：修复保留了现有的 `conversion.EnsureStoredVersion` 辅助函数及其“空值填充”语义，仅在其上游补充了可靠的赋值源，降低了引入回归风险。
*   **常见反模式**：在存储/解码层不提供版本感知的回调或接口，而是让上层应用代码去猜测或硬编码版本信息，这会导致版本信息在传递链路中失真。
*   **相关指标（SLI/SLO）**：虽然不直接对应一个标准 SLI，但此修复支撑了 **API 元数据正确性**。可以考虑建立一个 SLI，用于监控仪表板 API 响应中 `storedVersion` 字段与预期（基于实际存储版本）的匹配率，以此作为 API 质量的一个衡量指标。
