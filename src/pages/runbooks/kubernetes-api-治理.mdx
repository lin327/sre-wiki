# Kubernetes API 治理

## 概述

在 Kubernetes 这样庞大且演进迅速的分布式系统中，API 不仅仅是暴露给用户的 REST 接口，还涵盖了命令行标志、配置文件格式、组件间通信协议以及数据持久化结构等所有交互表面。**API 治理（API Governance）** 是 SIG Architecture 下的一个子项目，其核心使命是在拥抱创新与演进的同时，确保这些 API 的**稳定性、一致性和向后兼容性**。对于 SRE 而言，理解并实践 API 治理原则至关重要，因为它直接关系到系统可靠性的基石——对用户的稳定承诺，以及对系统内部状态的可预测性控制。

## 核心概念

### API 治理的范围与目标

API 治理的范畴远超 REST API。它涵盖所有“契约”表面，包括：
*   **面向用户的 API**：REST API、`kubectl` 命令行参数、配置文件（如 kubeconfig）。
*   **面向内部的 API**：Kubelet 与容器运行时接口（CRI）、调度器与 API Server 的通信、数据存储格式等。

其根本目标是**平衡稳定与创新**。正如 API Governance 负责人 Jordan Liggitt 所言：“稳定很容易，如果你永不改变任何东西。但这与演进和增长的目标相矛盾。” 因此，治理工作致力于建立清晰的规范，在允许功能进化的同时，维护对用户的兼容性承诺。

### 质量门禁与评审流程

API 治理通过两种主要方式介入 Kubernetes 变更的生命周期：

1.  **指南与规范（Guidelines & Conventions）**：维护详尽的 API 约定文档（如 `api-conventions.md`），这些是处理各类 API 模式的“活文档”，会随着新场景的出现而不断更新。
2.  **API 评审（API Review）**：这是一个强制性的评审环节。评审可以在**设计阶段**（通过 Kubernetes Enhancement Proposal，KEP）进行，也可以在**实现阶段**（代码提交时）进行。理想情况下，涉及 API 变更的大型特性应在设计早期就邀请 API 评审介入，以避免后期因根本性设计问题导致大量重构。评审过程常常涉及高带宽的实时视频讨论，以高效达成共识。

### KEP 过程中的介入

KEP 是 Kubernetes 增强特性的必经流程。API 治理的介入程度取决于 KEP 的详细程度：
*   **详细 KEP**：若包含具体的 API 定义，则可在设计阶段完成 API 评审，实现时主要验证设计的一致性。
*   **概念性 KEP**：若仅提出概念，将细节留给实现，则 API 评审将在实现阶段进行，可能建议结构性的调整。

### CRD 带来的挑战与演进

自定义资源定义（CRD）的出现是一个“分水岭”事件。它赋予了用户在 Kubernetes 中定义任何资源的能力，极大地扩展了生态，但也对治理提出了挑战。
*   **初始阶段**：早期 CRD 甚至不要求 Schema，带来了灵活性，但牺牲了一致性。
*   **治理演进**：随着 CRD 走向 GA，Schema 变为必需。近期的主要里程碑是引入了**内置验证规则（Built-in Validation Rules）**，使得 CRD 作者能够获得与内置资源相当的验证能力。
*   **关键模式**：通过 **棘轮式验证（Ratcheting Validation）**——允许数据在不破坏现有对象的前提下逐步改善——治理得以在引导 CRD 遵循约定的同时，保持向后兼容。CRD 的治理历程集中体现了**定义 Schema、验证数据、处理存量无效数据**三大主题。

## 实践

### 在发布周期中的介入节奏

API 治理工作并非完全连续，其强度与 Kubernetes 发布周期紧密相关：
*   **增强冻结（Enhancements Freeze）前**：设计阶段的评审需求达到高峰。
*   **代码冻结（Code Freeze）前**：实现阶段的评审需求显著增加。
*   **冻结期之间**：是处理长期设计工作和进行前瞻性思考的最佳时机。

一个常见的**反模式**是团队在特性构思数月后，临近增强冻结才匆忙提交设计并请求评审。对于影响 API 的重大变更，**尽早介入**是黄金准则。

### 自动化与持续改进

为确保一致性并降低人工负担，API 治理依赖自动化工具，例如 Linter 和检查脚本，用于验证如 spec/status 语义等常见模式。治理实践本身也是一个迭代过程：面对新场景，团队会进行探讨，将结论反哺到文档和工具中。即使最初的方案有误，经过几轮迭代也能找到稳健的解决方案。这体现了**渐进式改进**的工程文化。

## SRE 要点

### 与可靠性、可观测性、事件响应的关联

*   **可靠性基石**：API 稳定性是系统可靠性的直接体现。对用户承诺的向后兼容性，确保了用户集成和运维工作流的稳定，避免了因升级带来的非预期中断。这与 SRE 通过管理变更风险来维护可靠性的目标完全一致。
*   **可观测性的基础**：一致的 API（包括内部组件间的 API）使得监控、日志和追踪数据更易于关联和理解。若 API 变化无常，可观测性管道的维护成本将急剧上升。
*   **事件响应**：当故障发生时，稳定的 API 行为有助于快速定位问题。如果 API 的语义或格式经常意外变更，会极大地增加故障排查的复杂度。

### 最佳实践与常见反模式

**最佳实践：**
1.  **早期参与**：涉及 API 变更的设计，应在 KEP 阶段尽早寻求 API 评审反馈。
2.  **遵循约定**：严格遵守 `api-conventions.md` 中定义的模式（如 spec/status 分离）。
3.  **为未来设计**：提问：“这个特性现在想做的事，未来如何演进而不破坏兼容性？”为未来的扩展预留空间。
4.  **拥抱工具化**：利用自动化 linter 和验证工具，在 CI/CD 中前置质量检查。
5.  **渐进式改进**：对于存量问题，采用棘轮式验证等策略逐步改善，而非一次性破坏性更改。

**常见反模式：**
1.  **临近冻结提交重大变更**：这给评审团队和自身都带来巨大压力，极易导致返工。
2.  **忽视内部 API 的治理**：内部接口的随意变更同样会破坏系统稳定性和团队协作效率。
3.  **将兼容性要求视为障碍**：应认识到，维护兼容性是对用户负责、建立长期信任的体现，其价值远高于短期清理带来的便利。

### 相关指标（SLI/SLO/SLA）

虽然 API 治理本身不直接定义 SLI，但其工作成果直接支撑着可靠性相关的 SLI/SLO：
*   **SLO 关联**：系统稳定性的 SLO 严重依赖于 API 的稳定性。频繁的、非向后兼容的 API 变更会直接增加违反 SLO 的风险。
*   **SLI 体现**：一个运行良好的 API 治理流程，其产出可以体现为“**关键 API 向后兼容性变更的比例**”或“**因 API 不兼容导致的部署回滚次数**”等内部度量。
*   **SLA 承诺**：对云提供商或托管服务而言，公开的 SLA 往往包含 API 稳定性的承诺，API 治理正是履行这些承诺的内部保障机制。
